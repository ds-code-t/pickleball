# 3.0.0 Architecture Documentation Audit

**Date:** 2026-11-13  
**Branch audited:** `3.0.0` (tip including PR #22 and index refresh)  
**Scope:** All instructional and descriptive text (AGENTS.md, READMEs, docs/, roadmaps, design docs, build comments, error/help messages, Javadoc/headers where architectural).  
**Current architecture (truth):**  
- In-repo Java DOM engine (`dom-engine` module, package `dev.domengine`, CLI `dev.domengine.cli.DomEngineMain`) is the **default** and packaged inside the pickleball jar. Retains query/geometry/observe/actions/desktop/CLI/MCP. Rust binary is **optional explicit override only** (`pkb_composite_bin` / `pkb_composite_engine=rust`).  
- DOM composite engine is the **core** of element finding, actions, state, geometry, observation across browser DOM and native desktops (one query language / verb set).  
- Dalton is **central**: compiles, hydrates, dehydrates project content, logs, and business entities.  
- Cucumber is a **legacy compatibility adapter only**. Dynamic runtime works on any text input.  
- Remaining stale Rust leftover (live Chrome attach in DirectControlProviderTest / Workbench binary lookup) is being fixed separately; not addressed in code here.

**Method:** Full reads of key live instructional files (README, docs/README, getting-started, direct-control-handoff, cucumber-compatibility, dynamic-steps, configuration excerpts, AGENTS.md, feature-map, release-notes 3.0.0 section, design docs, build.gradle comments). Code search for Rust/dom-composite/COMPOSITE_BIN/sibling checkout. Historical changelog/scoreboard/roadmap entries are distinguished from live instructions.

**Coverage note:** Repository is large. Prioritized all consumer-facing and agent-facing docs, agent contract, design docs, and build comments. Module READMEs, CI workflow comments, and every Javadoc header were sampled or covered where they describe architecture. No product code or tests were changed.

## Findings by Area

### Root and top-level docs

**Finding 1**  
- **File:** `README.md`  
- **Lines:** ~3-5, ~11  
- **Quoted:** "Pickleball is a Java 21 testing framework built on Cucumber." / "Java Selenium integration for browser navigation, element selection, actions, and assertions"  
- **Why stale:** Cucumber is now a legacy adapter, not the foundation. Selenium is not the primary element path; the Java DOM engine is core. No mention of Dalton as central or the in-repo engine.  
- **Severity:** misleading-to-AI-agents / misleading-to-humans  
- **Recommended replacement:** "Pickleball is a Java 21 testing framework. Its dynamic runtime (ParsingMap, NodeMap, templating, loops, modular calls) operates on any text input. Cucumber is a legacy compatibility adapter. Element finding, actions, geometry, and observation use the in-repo Java DOM engine (`dev.domengine`, packaged in the jar) as the core path across browser DOM and native desktops; Selenium remains only for browser lifecycle. Dalton is the central Git-files-to-database archive for content, logs, and entities."

**Finding 2**  
- **File:** `docs/README.md`  
- **Lines:** ~3, ~41 (link description)  
- **Quoted:** "Pickleball extends Cucumber with a dynamic feature-file language while preserving normal Cucumber behavior." / "how dom-composite 2.4.0 attaches to a live Workbench browser"  
- **Why stale:** Same as above; link still frames the old external Rust tool as the attach mechanism.  
- **Severity:** misleading-to-AI-agents / misleading-to-humans  
- **Recommended replacement:** Update intro to match Finding 1. Change link text to: "session descriptor, `session list` / `session info`, and how the in-repo Java DOM engine (or optional Rust override) attaches to a live Workbench browser."

**Finding 3**  
- **File:** `docs/getting-started.md`  
- **Lines:** ~11-12 (Requirements)  
- **Quoted:** "optional: the `composite` binary from [dom-composite](https://github.com/ds-code-t/dom-composite) 2.4.0 when element operations should use that entry point. Without it, Pickleball keeps Selenium for that run. Set `COMPOSITE_BIN` or `pkb_composite_bin` to the binary."  
- **Why stale:** Java engine is default and packaged; no sibling checkout or external binary required. Selenium is fallback only when explicitly off. Example version later is 2.1.16.  
- **Severity:** misleading-to-humans / misleading-to-AI-agents  
- **Recommended replacement:** "The in-repo Java DOM engine is the default for element operations (packaged in the jar; no extra binary). Set `pkb_composite=off` to force the Selenium element path, or `pkb_composite_engine=rust` plus an explicit binary path for the optional Rust override." Also update the Maven version example to 3.0.0.

### Direct-control and engine attach

**Finding 4**  
- **File:** `docs/direct-control-handoff.md`  
- **Lines:** ~5, ~55 (section header), many binary/CLI examples, ~130-140  
- **Quoted:** "dom-composite 2.4.0 is the optional tool." / "## Attach with dom-composite 2.4.0" / extensive `composite session attach`, `COMPOSITE_BIN`, sibling `dom-composite` checkout, native classifiers, `dev.domcomposite.Client` 2.4.0. One later paragraph correctly notes the Java engine.

### Dynamic steps and element path
