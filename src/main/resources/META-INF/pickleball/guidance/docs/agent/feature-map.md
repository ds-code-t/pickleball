## Workbench foundation contract during migration

`pickleball-workbench` is a separate executable companion module and depends one-way on the normal Pickleball runtime. The repository build supplies the Workbench through `pickleballPublishedElements`, a dedicated published-equivalent configuration backed by the root shaded/woven `shadowJar` plus the root publication's non-bundled external runtime dependencies. Do not replace that dependency with a naïve root `project(':')` variant and do not expose `pickleball-control-api` as a Workbench publication dependency.

The Workbench POM contract is exactly `tools.dscode:pickleball`; Workbench-only implementation libraries are shaded into the executable companion. Build verification checks both directions: the Workbench resolves the shaded Pickleball artifact without separate unwoven Cucumber modules, and the normal Pickleball JAR contains no Workbench classes/resources.

Phase 2 moves the controller-side HTTP bridge client into `pickleball-workbench`. `ControlBridgeClient` uses the public `tools.dscode.control.bridge.*` records already bundled in `tools.dscode:pickleball`; it does not duplicate parsing, mapping, browser, service-call, breakpoint, Step Override, or detached-execution semantics in the controller. The consumer-hosted `ControlBridgeRuntime` and `ControlBridgeCoordinator` remain in Pickleball.

The canonical worker bootstrap environment is now `PKB_CONTROL_BRIDGE_SESSION_DIR`, `PKB_CONTROL_BRIDGE_SESSION_ID`, `PKB_CONTROL_BRIDGE_TOKEN`, and `PKB_CONTROL_BRIDGE_PAUSE_FIRST_SCENARIO`. During migration, Pickleball also accepts the prior `PKB_STUDIO_BRIDGE_*` names as compatibility aliases so the old Studio can remain operational until its remaining behavior is replaced. New Workbench code must use only the neutral names.

Phase 3 adds build-established synchronization and direct worker lifecycle. `WorkbenchSynchronizer` uses the selected Maven/Gradle wrapper to run the minimum test-compilation/resource lifecycle and capture the effective test runtime dependency classpath; Gradle metadata is obtained with a temporary init script rather than the Gradle Tooling API. It materializes `.pickleball/workbench/base/classes` as immutable synchronization provenance and one merged `.pickleball/workbench/live/classes` runtime root, applying main output first and test output second so test-owned paths win deterministically. `base` is never placed on `classpath.txt` or a worker classpath. The synchronization fingerprint includes dependency artifact contents as well as merged project output, so a same-version locally republished Pickleball JAR produces a new snapshot identity.

`WorkbenchWorkerManager` launches a consumer JVM directly from that live root plus captured dependencies through Pickleball's thin `WorkbenchWorkerMain`, without invoking Maven or Gradle. `DynamicSuiteBootstrap` recognizes the internal `pickleball.workbench.testOutputRoot` property as an exact preferred test root; when present it does not fall back to Maven/Gradle path-suffix heuristics. The interactive worker uses a session-private anchor feature whose body is a guaranteed no-op core step. Its historical pause-first `SCENARIO_START` stop is only a bootstrap rendezvous: Workbench installs a one-shot `BEFORE_STEP` breakpoint filtered to the anchor marker step `---pickleball-workbench-anchor`, resumes, lets the root scenario step establish normal logging/lifecycle/ParsingMap state, and returns the worker only when the marker itself is paused immediately before execution. The controller then renews the finite pause lease while it owns the anchor and resumes before bounded process shutdown so consumer lifecycle hooks can complete. Restart rejects a non-clean prior shutdown, creates a fresh JVM from the same synchronized classpath, and does not rebuild.

Workbench migration Phase 4 adds the persistent live runtime facade. Phase 5 extends that facade with worker-owned Step Override authoring. `WorkbenchLiveSession` binds every operation to the controller-owned paused scenario and verifies after each command that the same worker PID, bridge runtime id, and scenario id remain active and paused. `compileStepOverride(id, regex, source)` sends a Java source template containing `{{CLASS_NAME}}` to the worker; the worker generates a unique class name, compiles against its authoritative runtime classpath, loads the handler through a dedicated classloader, and registers a scenario-scoped REPLACE/REGEX rule. Recompiling the same id replaces the prior implementation; remove/clear restores ordinary Cucumber fallback immediately. Compiler absence is reported as `UNAVAILABLE`. Normal live calls do not invoke Maven/Gradle, resynchronize, or restart the worker. `live-check` proves ordinary Gherkin plus override-only execution and replacement/removal on one persistent worker.

The old Studio module remains present only while runtime behavior is migrated in later implementation phases. Its presence during this migration is not a reversal of the approved replacement architecture.

## Studio collaboration contract after Phase 4

The desktop UI and MCP server now share one Spring context and therefore one set of managed build/process/runtime services. `StudioCollaborationService` provides a bounded Studio-session activity journal, explicit visible agent sessions/notes, and desktop editor-presence metadata without storing unsaved contents or private model reasoning.

Existing-file collaborative edits use `WorkspaceConcurrencyService`: `workspace_read_versioned` returns a SHA-256 token, and `workspace_write_file_checked` refuses the write when a human editor has unsaved changes or the file no longer matches the expected token. Desktop saves use the same token and present overwrite/reload/cancel when the disk changed. The original `workspace_write_file` remains compatible for intentional create/replace operations.

Phase 4 adds ten MCP tools, bringing the surface from 42 to 52. `process_wait` and `runtime_wait_paused` are bounded deterministic conveniences over the existing `ManagedProcessService` and `RuntimeBridgeService`, not new execution engines. The focused consumer compatibility tag is `@phase4`.

## Runtime-control contract after Phase 3H

The consumer control bridge remains protocol version `1` and loopback/authenticated. Existing Phase 3A-3G capabilities remain compatible. Phase 3H adds the additive capabilities `element_inspect`, `service_call`, and `breakpoints` and six Studio MCP tools.

The Workbench Phase 2 client is a transport adapter over that same protocol. It validates the loopback descriptor and protocol version, supplies the bearer token, and maps bridge responses directly into Pickleball's published `ControlBridge*` DTOs. Scenario-thread ownership and retry-friendly `SUCCESS` / `FAILED` / `UNAVAILABLE` semantics remain consumer-side.

Element inspection is defined by Pickleball vocabulary, not Studio selectors: `ElementControl` resolves the active consumer `ExecutionDictionary`, including registered project categories, then inspects matches through the already-owned scenario WebDriver. Service-call control invokes the existing `ServiceCallSteps.inlineCall(...)` / `CALL:` machinery on the selected scenario thread inside a scoped outer-scenario state isolation; it does not create another HTTP client DSL. Semantic breakpoints match stable `ControlHook` events, use the same scenario lane/pause loop as explicit runtime pause, require at least one filter, and always use finite leases.

The focused consumer tag for this cross-cutting runtime-control surface is `@phase3h`. Because `ControlBridgeCoordinator` owns the scenario-thread command queue used by prior Phase 3 capabilities, the same scenario also revalidates events, mappings/snapshots, page/screenshot evidence, detached retry behavior, scenario targeting, and pause/resume.

## Reusable RUN authoring and result contract

The canonical reusable-invocation form is a bare `RUN` with one DataTable row per invocation. Rows may mix `SCENARIO`, `SCENARIOS`, `COMPONENT SCENARIO`, `COMPONENT SCENARIOS`, `SERVICE CALL`, and `SERVICE CALLS`. Multiplicity is part of each resolved `RunType`, so singular/plural validation is per row. A nonblank table `RunType` overrides an inline type for that row.

Inline `RUN ...` type, quoted `RunKey`, and inline selector text are shorthand for values common to all rows or for invocations that need no DataTable. Repository examples and AI-authored scenarios should prefer the table-driven form when composing related invocations and lift common values into the step text only when doing so reduces repetition.

Keyed deferred `RUN` results are finalized after the selected `ScenarioStep` subtree completes. `RETURN` is saved when present; otherwise the completed default scenario root is saved. Storage uses ordinary RunMap/NodeMap collection semantics rather than pre-execution `putReference()` registration. `StepBase.finalizerSteps`, `StepExtension.createFinalizerStep(...)`, and `CurrentScenarioState` own the generic after-subtree execution mechanism.

## Profile and controlled-run contract

Normal project configuration resolves before profile selection. Public normal source precedence remains JVM system properties, `globalTestProperties()`, `pickleball_local.properties`, `pickleball.properties`, then `globalTestDefaults()`. Named profiles compose left-to-right; later profiles win. `pkb_runvars` is the controlled-run input and `pkb_run_profile` is deterministic derived output only. Named/controlled runs inherit only missing project execution-context RunVars documented in `docs/ai-run-configuration.md`; explicit blank values suppress inheritance. Diagnostic lineage remains metadata separate from execution RunVars.
