# Release notes

## 2.1.18

Direct-control handoff for a live Workbench session. A normal `mvn test` or `gradlew test` does not read `pkb_direct_control_provider` and does not write a session descriptor.

- Headless isolate and the GUI share `WorkbenchLiveSession`. That session writes `.pickleball/runs/<runId>/session/descriptor.json` (`session-descriptor.v1`, contract `"1"`). The CDP address is `se:cdp` when Selenium published it, otherwise `goog:chromeOptions` or `ms:edgeOptions` `debuggerAddress`. No address stays null. Chrome and Edge set `browserType`. The file is replaced atomically and refreshed when the page changes.
- `session list` prints one line per session that is not `stopped`, or a JSON array with `--json`. `session info <sessionId>` prints the descriptor file. `--json` prints those same bytes. `<sessionId>` may be the run id.
- `session hold <sessionId>` sets `held`. The next step waits. `session release <sessionId>` restores the state from when the hold began (`running` or `paused`). `pause` and `play` update the same descriptor. A hold is not overwritten by playback.
- Optional `pkb_direct_control_provider=composite`, or a path to the binary, in that run's `runvars.properties` or the system property of the same name (the `pkb_runvars.pkb_direct_control_provider` form too). Blank starts nothing. `composite` resolves `COMPOSITE_BIN`, then `COMPOSITE_HOME` or a sibling `dom-composite` checkout (`target/debug/composite`, then `target/release/composite`). The provider runs `composite session attach --cdp <url> --id <sessionId> --i-accept-local-attach --session-dir .pickleball/runs/<runId>/session/composite` and waits for that command to exit. Attach is not a resident process. A non-zero exit fails the start. The attach JSON is kept. The same directory and the composite session id are `compositeSessionDir` and `compositeSessionId` on the descriptor (`session-descriptor.v1`; older files that omit them still parse). Pickleball does not set `PICKLEBALL_SESSION_DESCRIPTOR`. Stdout and stderr go to the run's `session/provider.log`. Start and detach append a line to `.pickleball/agent-log`. Detach runs `composite session close --id <id> --session-dir <dir>` and does not kill a browser Pickleball owns. An agent joins the live session with `composite --session-dir <compositeSessionDir> query --session <compositeSessionId> --css 'body'`. A missing binary skips; it does not fail the run.
- When `record.json` already exists, a live session adds `sessionDescriptor` with the absolute descriptor path. A normal run does not add it.
- The attach contract is [Direct-control handoff](direct-control-handoff.md). dom-composite stays a general tool. Pickleball still owns the browser.
- A normal launch reads `pickleball.properties`, `pickleball_local.properties`, and `pickleball_local2.properties` from the classpath as ISO-8859-1. Project-root and `src/test/resources` copies are Workbench-only (seed, dry-run, protected references) and are UTF-8. `globalTestProperties()` still outranks those files. The dry-run prints the Workbench default `pkb_reportingmode=diagnostic`. Prepare writes that default once and does not rewrite an unchanged saved copy. `use-version --version` switches `current.json` only when that version was exported. The until-pass Chrome lookup accepts a Windows `chrome.exe`.
- `query runs|get|query|search|props|errors` reads the existing diagnostic JSON (`run-catalog.json`, `run-index.json`, `clusters.json`, `summary.json`, `events.jsonl`) through one `DiagnosticQuery`. MCP tools `wb_runs`, `wb_get`, `wb_query`, `wb_search`, `wb_props`, and `wb_errors` are thin forwarders to that service. Responses are compact JSON with a relative `where`, a default limit of 20, and `…+N more, use cursor` when a page is short. Stack traces are one line. The default page stays within 4096 UTF-8 bytes. A query appends one line to `.pickleball/agent-log`. Normal `mvn test` output is unchanged. See [Diagnostic query](diagnostic-query.md).
- A derived SQLite index, `reports/diagnostic-runs/diagnostics.db`, is rebuilt from those same JSON rows by `DiagnosticIndexRebuilder` (FTS5 on the stored text). Delete the file and the next rebuild creates it again. `query search` uses it when `sqlite-jdbc` is on the classpath and otherwise reads the files. `DiagnosticReporter` is unchanged.
- `help` starts with the decision `discover`, then `plan`, then `run`. `--runId` and `--agentId` are the canonical `--run-id` and `--agent-id`. `--to=all` is `--to=any`. `session info --run-id=<id>` is the positional id. Unknown commands include a `fix:` line. MCP tool descriptions are one line of at most 160 characters. Worker `worker-*.log` tails are queryable as `kind=log` next to `.pickleball/agent-log`.
- `plan`, `discover`, `confirm`, and the feature catalog share `feature-index.v3` (scenarios, outline rows, and tags, keyed by size and mtime). `plan` prints `indexMs`. Discover passes only the matching feature URIs into Cucumber. `CucumberScanUtil` is unchanged. A normal `mvn test` still scans whatever `pkb_features` the project set.
- No Rust feature-index sidecar. On `maven-consumer-project` (56 feature files, 405 scenarios, tag `@all`) a cold `feature-index.v3` build took 139 ms and a warm read took 18 ms. That is not the cost of a Maven run, so the Java index stays the only implementation (`WorkbenchFeatureIndex.IMPLEMENTATION=java`). Nothing is downloaded or extracted for a native parser.
- Workbench launches and normal launches resolve RunVars through one sequence (`PickleballRunner` `resolveShared` then `PKB_props.resolveInto`). `ProjectPropertySources` is the only reader. A bad file throws. Dry-run (`hint`, `resolve-runvars`, `DiagnosticCli resolve-runvars`) constructs the consumer runner when exactly one is visible on the preferred test-output root, so `globalTestDefaults()` and `globalTestProperties()` are in the preview. It does not publish system properties, start Cucumber, or open a browser. No visible runner means empty hooks. A Workbench launch reads the saved copy with `Workspace.loadForLaunch` and does not apply hooks again. An agent edit of that copy is final. A blank `pkb_reportingmode` on that copy is set to `diagnostic` before `--runvar` edits so Discover retains `pkb_run_profile` in `run-index.json`. An explicit mode is left alone. A normal `mvn test` does not receive that default.
- `isolate` and `session-start` honor `--session-file`. That path is what the controller writes and what the launcher waits on. Omitted, the file stays the run's own `cli-session.json`.
- `finish --status` stores `PASSED`, `FAILED`, `EMPTY`, `TIMEOUT`, or `STOPPED` (default `STOPPED`). An unknown status exits 2. `execute-step` with no gherkin exits 2 before it requires a session. A workspace `runvars.properties` that `Properties` rejects is a read failure (`exit 1`, `Could not read <file>: Malformed \uxxxx encoding.`), not a present run.
- A `--tags` expression that the shell already split (`and` / `or` / `not` as later tokens) exits 2 with `Tag quoting error`. One quoted argument, `--tags-file`, or `--tags-b64` keeps `and` / `or` / `not` inside the expression. A Windows-style path and a non-ASCII run var stay one argument on the wrapper command line.
- `maven.test.failure.ignore=true` can make Maven exit 0 after a failed scenario. Discover still exits 1 with `summary status=FAILED` when `run-index.json` says the run failed. A normal `mvn test` exit code is unchanged. The example consumer POM binds Surefire `testFailureIgnore` to `${maven.test.failure.ignore}` (default `false`). A literal `false` in the POM ignores `-D` and `.mvn/maven.config`.
- `workbench_execute_step` describes that a FAILED result does not stop the worker and is not an MCP error. The call still returns that result and leaves the paused worker running.
- Every launcher command and major flag has a `covers_command_*` or `covers_flag_*` test that calls the command and asserts the result. A method that only shares the name does not pass `WorkbenchCliCoverageGateTest`. Findings: [2.1.18 Workbench coverage findings](roadmaps/2.1.18-workbench-coverage-findings.md).
- Agent usability is a bug class. `help` / `--help` lists the launcher commands; `help <command>` prints one usage line. An unknown command exits 2 with the closest command and does not start the controller. `workspace-show`, `resolve-runvars`, `hint`, `plan`, `status`, and `events` accept `--json` (one object, no preamble). `diagnostic-run --run=<id>` is the diagnostic pack; `--run-id` selects the live session and fills that pack only when `--run` is omitted. Usage errors name the flag and an example. MCP rejects a blank argument with the tool name, the field, and its description. Launch timing stays in `launch-timing.txt` unless `PKB_WORKBENCH_TIMING=1`.
- The until-pass browser step looks up Chrome from `PKB_CHROME_BINARY`, `CHROME_BINARY`, `pickleball.chrome.binary`, `webdriver.chrome.binary`, `PATH`, or `/opt/pw-browsers`. When none of those exist it does not call `setBinary`.

## 2.1.17

### Breaking changes

These three statuses apply only to Pickleball Workbench (`discover`, `confirm`, and the live session commands). A normal `mvn test` / `gradlew test`, Cucumber’s own exit code, and `DiagnosticReporter` are unchanged. Diagnostic mode still reports `NO_TESTS`. Nested `SCENARIO` / `COMPONENT` / `CALL` / `RUN` still fail when `CucumberScanUtil.listPickles` finds nothing.

- **EMPTY.** A Workbench `discover` or `confirm` that selects zero scenarios prints `status=EMPTY`, the effective tags, name, example, and browser, and exits non-zero. It does not print `status=PASSED`. The run record status is `EMPTY`. When the caller did not pass `--learned`, the record says `No scenarios matched …`.
- **FAILED when Maven exits 0.** `maven.test.failure.ignore` (and the Gradle equivalent) can make the wrapper exit 0 after a failed scenario. Discover and confirm read the current run's `run-index.json` (`outcome`, `counts.failed`, and `counts.errors`). A Surefire or index outcome of `ERROR` counts as a failure even when `counts.failed` is 0. The index is accepted at `.pickleball/runs/<run-id>/diagnostic/<run-id>/run-index.json`, at `diagnostic/run-index.json`, or under `reports/diagnostic-runs/<run-id>`, including a Windows path. That result sets the Workbench status, `record.json` (`failureCount`, `failedScenario`, `failureSummary`), the `summary status=` line, and the launcher exit. A worker that already wrote `PASSED` is upgraded when the index or a Surefire error says the run failed. `TIMEOUT` and `EMPTY` are not overwritten. A missing index falls back to a Surefire or Gradle XML report written during this run (failures and errors), then to the wrapper exit code. A normal `mvn test` exit code is unchanged.
- **Current run only.** A discover or confirm summary counts scenarios and steps only for that run. The count walks `.pickleball/runs/<run-id>/diagnostic` when that folder has a scenario directory (`events.jsonl`, or `scenarios/<id>/summary.json` after retention pruning removed the events), otherwise only `reports/diagnostic-runs/<run-id>`. It does not walk other runs. `steps=` adds every scenario in that run, for retention `all`, `failed`, and `none`. A scenario with a step list uses that size. A pruned scenario with an empty list uses the core summary `steps.executed`, then `steps.total`, then `passed` + `failed` + `skipped` + `other`. `run-index.json` `steps.executed` is used only when that sum is 0, so a smaller index does not replace it. A full scan that did not write those scenario directories uses `run-index.json` `counts.total` and `steps.executed`, then a console line such as `1 Scenarios` / `2 Steps`. The retained `pkb_run_profile` and `last-discover.json` come from that run's private `run-index.json` when the index has a `runProfile`. A project-wide `run-catalog.json` row is used only when this run did not write one. A later discover does not reprint an earlier run's tags or scenario count.
- **TIMEOUT.** `--run-timeout` on `discover` or `confirm` records `TIMEOUT` and exit non-zero when that budget is exceeded. Those commands reject `--step-timeout` (`use --run-timeout; per-step limits apply to execute-step`). `--step-timeout` on `execute-step` is measured from the call. `--run-timeout` on `execute-step` is measured from the run's `startedAt`. One transient HTTP failure does not record `TIMEOUT`. When the step budget expires, the step is still running; use `stop --force`. These budgets do not use `pkb_stepMaxTime`. When the budget interrupts a `discover` or `confirm` wrapper, Workbench kills that process and its descendants and waits up to 10 seconds for them to exit. A normal `mvn test` does not.
- **STOPPED.** `stop --force` kills the Workbench worker and its browser process tree and records `STOPPED`. A cooperative `stop` without `--force` is unchanged and still waits.

### Date, time, and expressions

Previously passing expressions, steps, and comparisons stay the same text and the same result.

- An invalid `<{...}>` in `TRACE:`, `DEBUG:`, `INFO:`, `WARN:`, `ERROR:`, or `FAIL:` log text stays the literal text. A valid `<{...}>` and a valid `<name>` still resolve. The same invalid expression outside a log step still fails the step. `ERROR:` and `FAIL:` still hard-fail because of the log token, not because the expression was invalid.
- Nested `<...>` references, including a saved value that itself contains `>`, resolve past two levels and do not leave a stray `>`. One- and two-level nesting stay byte-identical. Plain text such as `->`, `a > b`, and `>=` stays literal. The same `>` inside a nested reference, inside `<{...}>`, and inside `~[~...~]~` still resolves, and a whole-object reference stays a non-string.
- `equal to … within a margin of N minutes`, `within a margin of N minutes`, and `within N minutes` compare date-times only when the margin is a duration and both sides parse as date-times. Other strings stay a string compare, and the margin is ignored. Equal text that already compared as date-times still does. `within N second|minute|hour|day|week|month|year(s)` is rewritten to `margin-of N unit`, and `within a margin of` / `within the margin of` is rewritten to `margin-of`, only when that phrase, outside quotes and between commas or semicolons, already has a comparison word (`equal`, `equals`, `greater`, `less`, `before`, `after`, `at least`, or `at most`) and the within follows that word. A wait or click `within N`, a wait or click `within a margin of`, and a quoted `"within 5 minutes"`, stay unchanged. `margin of` is still normalised to `margin-of`.
- A calendar `DefaultOutputPattern` is also accepted as an input pattern, after the existing `DateTimeFormats`, so the calendar can parse its own rendered output. Patterns that already parsed still parse the same way.
- Pipe modifiers `next business day` and `business day on or after` roll to the calendar’s existing business dates. `next open`, `is business day`, and `+ N business days` are unchanged. An unknown modifier still throws `Unknown date/time pipe modifier`.
- Optional calendar setting `UnzonedInputZone: calendar` reads an unzoned input in the calendar zone. The default, and the values `UTC`, `GMT`, and `Z`, stay UTC. A zoned input is unchanged.

### Workbench

Normal scenario execution is unchanged. The feature index, plan, timeouts, and the reports below exist only on the Workbench path.

- An unsupported tag expression such as `xor` still falls back to a full scan. The index parser is unchanged. Cucumber itself rejects `xor` (`TagExpressionException`). The warning now includes the working escaped form, for example `--tags=@smoke\ xor\ @wip`, which is one literal tag. The Maven `pkb_tags` value is rewritten to `(A or B) and not (A and B)` so the run is not rejected. `and`, `or`, `not`, and an already escaped expression are unchanged. A normal `mvn test` tag expression is unchanged.
- Full scan is no longer required for a nested `SCENARIO` / `COMPONENT` / `CALL` / `RUN` in another feature file. It remains the fallback for an unreadable feature and for an unsupported tag expression. That fallback still enumerates the whole suite.
- Profile glue under narrowing was not confirmed as a failure. Top-level narrowing does not replace `pkb_features`, and `pkb_glue` is a separate key, so the configured glue is what the worker receives. No separate change was made.
- Repeatable `--runvar key=value` on `discover`, `confirm`, and `isolate` merges into the planned run vars. A missing `pkb_` prefix is added. A conflicting value warns and the command-line value wins. `record.json` stores `environment` and `browser` from that merged set. The summary line appends `environment=` and `browser=` when they are set. Trust the run record, not the launcher JVM preview. A launcher `-Dpkb_runvars` is still not the controlled run.
- `pkb_example` decodes a classpath feature URI before opening it. `%20` is a space, and a Windows `\` separator is `/`. A feature that still cannot be read logs `WARNING: pkb_example skipped unreadable feature` and is skipped. It does not abort the run. Other features are still filtered.
- `discover` and `confirm` use a hash-checked feature index. When the index can narrow the selection, the Workbench-built Maven command passes only those feature paths to top-level Cucumber discovery as `-Dpickleball.workbench.topFeatures`. That list does not replace `pkb_features`. Nested `SCENARIO` / `COMPONENT` / `CALL` / `RUN` still call `CucumberScanUtil.listPickles` with the configured feature set, including another feature file and a path that contains spaces or a Windows `wd-file:C:/...` path. `--no-narrow` and `--full-scan` skip the top-level list. A normal `mvn test` is unchanged and does not read the property. An unreadable feature or an unsupported tag expression such as `xor` falls back to a full scan. `CucumberScanUtil.listPickles` is not changed. The index treats `Example:` as a scenario keyword and exact `Scenarios:` as an examples table, skips docstring bodies, indexes a `Scenario Tags` examples column, and always includes a file it cannot model (a `# language:` header other than `en`, an unsupported language, or a real Gherkin keyword from another dialect) without phantom hits. A free-text description such as `Note:` is not a keyword and does not force the file into a narrowed selection. Keywords come from the Cucumber dialect table shipped with this version. The cache schema is `feature-index.v3`. A warm select also reads the sidecar `feature-index.v3.stat` (size and last-modified time). When both match, the file bytes are not read again. A size or time change still hashes the bytes, and a different hash still reparses. `--refresh` ignores the sidecar. The schema version stays 3.

- A large feature tree is parsed once per unchanged file. Maven Surefire discovers the suite and then discovers it again before execution. The second pass used to parse every feature and build every scenario again. A feature whose size and last-modified time still match is not parsed again. The second discovery in that same fork reuses the already filtered suite when the selectors and the configuration are the same, then drops the copy when execution starts so the next run sees current files. This does not narrow a normal `mvn test` and does not change which scenarios run. The 1100 ms scenario-start stagger is unchanged. Measured on this host (2 CPUs) with a synthetic project of 1,800 feature files and 36,000 scenarios (7.1 MB), one `@only` scenario, warm `mvnw test`, log level error, headless Chrome requested but not opened, parallel 1. Before: wall clock 17 s; fork clock first discovery done at 3,341 ms, second discovery done at 4,991 ms, first scenario at 7,170 ms; Surefire 36,000 tests, 35,999 skipped, 0 failures. After: warm wall clock 14 s; runner ready 772 ms, first discovery done at 3,638 ms (1,800 files parsed once), second discovery cache hit at 4,144 ms (6 ms after that discovery started), execute at 4,384 ms, first scenario at 6,369 ms; Surefire still 36,000 tests, 35,999 skipped, 0 failures. The same tree's feature index was 710 ms cold (1,800 reparsed) and 329 ms warm (0 reparsed, narrowed to the one `@only` hit). A separate 14 MB / 200-file tree indexed in 456 ms cold and 72 ms warm. The 6.7 s figure further down is the small example project, not this tree. A 97 s consumer launch was not reproduced on these files; the repeated discovery was the duplicate cost this host did measure.
- The Workbench `discover` / `confirm` path was timed separately from a plain `mvnw test`. The synthetic tree was 1,770 feature files (8.5 MB) with backgrounds, 40-row scenario outlines (74,341 pickles), nested `RUN SCENARIO` and `RUN COMPONENT SCENARIO`, 12 tags, deep folders, 250 glue classes, and a `configs/` folder. `discover --tags=@only` (headless Chrome requested, parallel 1, log level error) is the consumer command. Before the index change below, warm discover wall clock was 12.2 s. The launcher index took 2,702 ms while reparsing 0 files. Inside the test JVM the runner was ready at 988 ms, discovery finished at 1,346 ms (one feature parsed), the second discovery was a cache hit at 1,391 ms, execute started at 1,405 ms, and the first scenario started at 1,895 ms. Surefire ran 42 tests from that one file and skipped 41. The same tree with no Workbench path list (`mvnw test` and `@only` only) parsed all 1,770 files and reached the first scenario at 15,607 ms (Surefire 74,340 tests, 74,339 skipped, cold wall 26.9 s). Parsing that tree with Gherkin outside Maven took 2,329 ms, and a second `getPickles()` took 1 ms. Nothing on this host reached 97 s. Discover and confirm now print `workbench launch jvm=launcher|test stage=<name> elapsedMs=<n>` and append the same line to `runs/<id>/launch-timing.txt`. Launcher stages are `command`, `index` (files, reparsed, cache hits, scenarios, narrowed, full scan, list length), `maven-start`, and `maven-done`. Test-JVM stages are `discover-start`, `runner-ready`, `runner-initialized`, `cucumber-discover-done`, `discover-cache-hit`, `execute-start`, and `scenario-start`. Each JVM has its own clock. A normal `mvn test` prints none of these. Per-file parse marks still need `-Dpickleball.phase4.timing=true`.
- A warm feature index was slower than reading the features. On that 1,770-file tree the index file is 12.7 MB because every Examples cell is stored. An unbuffered read, plus rewriting the whole index on every select, took 2,702 ms with nothing to reparse. A cold select that parsed every file took 1,828 ms. The cache is now buffered (64 KB) and a select that changes nothing does not rewrite the index or the sidecar. The same warm select then took 634 ms and 679 ms, and the cold select took 1,009 ms. The next warm `discover --tags=@only` was wall clock 9.6 s, index stage 649 ms (0 reparsed, 1,771 cache hits), first scenario still 1,809 ms inside the fork. A narrowed path list longer than 4,000 characters is written to `top-features.txt` and the Maven command receives `@` plus that file, so Windows can start the process. The test JVM reads the file back into the same comma-separated `wd-file:` list. A shorter list stays on the command line. A normal `mvn test` does not read the file. Nested `listPickles` is unchanged.
- `status` and `events` print `sleep-gap=<milliseconds>ms at <instant>`, or `sleep-gap=none`. The session heartbeat runs every 5 seconds and records a gap when wall time between beats exceeds 30 seconds. That is a machine sleep or stall. It is not a Gherkin sleep step, and a gap between scenario events does not create one.
- `plan`, and `discover --plan` / `confirm --plan`, resolve `--tags`, `--name`, `--example`, and `--select path/file.feature:line` to scenarios and Examples rows, including argument values. They do not build and do not open a browser. An empty plan warns.
- The Workbench-built Maven command adds the Surefire Cucumber engine filter. A consumer POM and a plain `mvn test` do not.
- `--tags` and `--name` are echoed. An unmatched quote or parenthesis is `Tag quoting error`. An invalid name regular expression is `Name quoting error`. `--tags-file` and `--tags-b64` pass an expression the shell would split. A `--tags` value that Maven `exec` or PowerShell already split into later positional tokens (`--tags=@A` plus `and`, `not`, `@B`) exits non-zero before `plan`, `discover`, `confirm`, `isolate`, or any other `--tags` command runs. The error shows the reconstructed expression (`@A and not @B`) and says to quote it (`--tags='@A and not @B'`) or use `--tags-file` / `--tags-b64`. A later option such as `--run-id=x` is not part of that expression. A quoted `--tags` value is unchanged. Shared `pkb_tags` / `pkb_name` parsing is unchanged.
- `--agent` keeps a per-agent `last-discover-agent-<id>.json`, and each run keeps `last-discover-run-<id>.json`. The shared `last-discover.json` is still the latest discover. Confirm without `--agent` still reads that shared file. Discover reports the current run’s profile, not the newest catalog row.
- Session start closes stdin and logs `start` only after the session is healthy. `No healthy Workbench session` names `never-started`, `still-starting`, `crashed`, or `missing-session-file`.
- Worker start and the `isolate` / `session-start` health wait share `pkb_workbench_worker_start_timeout` (system property, `PKB_WORKBENCH_WORKER_START_TIMEOUT`, or a `pkb_runvars` member, including the dotted `pkb_runvars.pkb_workbench_worker_start_timeout` form). The default is 180 seconds. A blank, non-numeric, or non-positive value stays 180. It is read only by Workbench. The forked controller is started with the resolved `-Dpkb_workbench_worker_start_timeout` so the worker wait matches the health wait. `open-window` still waits 60 seconds. While session start waits, stdout prints `session-start progress elapsed=<ms>ms stage=<stage>` about every 12 seconds. The stage is the latest `progress stage=` line in the session log or a worker stderr log. Before any marker the stage is `starting / Maven resolve or feature index`. A session-start timeout names the stage, the elapsed time, per-stage durations, the last 20 log lines, and how to raise the limit. Stage enter times are recorded in `runs/<id>/session/startup-progress.json`. A worker startup timeout still names the elapsed time, the stage (`compile`, `classpath`, `worker-launch`, `anchor-parse`, `paused`), and the last worker output.
- `--stop-after` is the live-session alias of the existing one-shot breakpoint.
- Failure text captured beside the run can include `final XPath`, `raw match count`, `visible count`, `rejection`, and `expected` versus `actual`. Core `events.jsonl` and `trace.jsonl` are not rewritten. A core `summary.json` is not overwritten. Workbench writes `runs/<id>/workbench/summary.json` and `runs/<id>/workbench/trace-index.json`. The same summary is written beside each scenario directory. A pass whose `events.jsonl` was removed by `--retention=failed` still gets that file from the core summary: scenario name, status, and duration. Step text and the assertion result are included when `events.jsonl` is still there. If the core summary is absent, the same body is also `summary.json`. Discover and confirm copy the wrapper's stdout and stderr into `runs/<id>/console/<scenario>.txt`. A Cucumber `Scenario:` or `Scenario Outline:` line matches the scenario name even when `# file:line` follows, including a path with spaces or a Windows separator. Text that matches no scenario stays in `unassigned.txt`. A Workbench discover or confirm (`pkb_run_purpose` starting with `workbench-`) prefixes each console line with `# pkb-console ` and the URL-encoded scenario name. The split uses that exact name, so `Pend` stays separate from `Pend case` when Cucumber prints no `Scenario:` line. The prefix covers `print`, `println`, `printf`, `print(char[])`, and `write(byte[])`, a Logback or Log4j2 console appender that captured the original stream, a print that contains several lines, and a thread started while that scenario is running, including parallel scenarios and a Windows path such as `C:\Users\Dan She'll\page`. The saved console file keeps the text and drops the `# pkb-console` prefix. `unassigned.txt` is omitted when every line matched. A normal `mvn test` does not install the tap, so its output stays the same. One advice, `TestCase_ConsoleTap`, marks the running scenario. A compact line `summary status=… scenarios=… steps=…` is printed.
- `inspect-page` and `find-element` with `--html=<file>` are an offline fallback. The output is labelled `source=offline-html`. The file is read as XML, so `<!DOCTYPE html>` is accepted and external entities are not loaded. Unclosed HTML tags are still rejected; write the snapshot as XHTML. Without `--html`, both commands use the live session and a read-only worker query. That query builds the XPath with the execution dictionary, then counts `findElements` and `isDisplayed`. It does not click and does not wait. If no session is running, the command prints `start a session first` and exits 2. The live query polls for up to 30 seconds. If the command is still `QUEUED`, `RUNNING`, `STILL_WORKING`, or `STOPPING` when that deadline passes, or the session reports `TIMEOUT`, the command prints `status=TIMEOUT` and exits 3. It does not exit 0 with an empty hit list. Exit 1 is a failed query. `inspect-page` takes no category. The live `ElementControl.inspect` signature is unchanged.
- A locked Workbench directory install tries `deleteTree` and the move, then retries each after 100 ms, 300 ms, and 1000 ms. The temp-sibling copy runs only after those retries fail, with no further wait. The staged tree is copied to a sibling `target.tmp-<n>` and renamed into place. A failed copy deletes that temp directory and leaves the original target absent or unchanged, not a partial tree.
- A CLI error that wraps an `IOException` includes that cause. Session-start and sync failures record a plain-language reason on the run.
- The config copy under `.pickleball/runs/<run-id>/config` is no longer written by the test JVM. Workbench keeps `runvars.properties` and a plain configs copy under `.pickleball/runs/<run-id>/workspace/`. The project config is unchanged. Redaction for logs and reports stays a separate path and does not rewrite that copy.
- Workbench resolves run vars once into `.pickleball/runs/<run-id>/workspace/`. Discover, confirm, isolate, live workers, and the GUI pass only `-Dpkb_workspace` plus selection keys. `workspace-show`, `workspace-edit`, and `workspace-seed` (`--from-run`, `--reseed`) edit the same files as the Config tab and the run-var panel. Writes are atomic. A change on disk is a warning and is not overwritten. `pkb_parallel=auto` stays `auto` until launch. Isolate does not force `pkb_parallel=1`. `pkb_overriderunvars` is deprecated. It still works for a plain `mvn test` or `gradlew test` that does not set `pkb_workspace`. Surefire-only POM values are not in a `java -cp` capture. Hook-computed time, env, and random values are frozen at capture. Hook side effects outside `pkb_*` system properties do not rerun at launch. Protected references read project properties at launch. A normal `mvn test` is unchanged.
- Diagnostic events mask secrets before they are written. JSON `"password":"..."` and `"authorization":"..."` values, and a REST Assured `Authorization=Basic` or `Bearer` dump, are `<redacted>` in `events.jsonl`. The token after `Basic` is masked, not only the word `Basic`. Configuration-file redaction is unchanged and still does not rewrite project config files.
- A multi-line value passed as the step argument is fenced as a DocString when Pickleball builds the temporary `memory:/single.feature`. A one-line argument, a data table, and a value that is already a docstring stay as they were. A newline inside the resolved step text itself, such as `INFO: body=<Page.RESPONSE.body>` when the body is multi-line HTML or JSON, is escaped before that temporary feature is parsed and then restored, so the step text keeps the original line breaks and is not re-parsed as Gherkin. `TRACE:`, `DEBUG:`, `INFO:`, `WARN:`, `ERROR:`, `FAIL:`, `ASSERT:`, and `SOFT ASSERT:` accept that restored text. `ASSERT:` and `SOFT ASSERT:` also compare it without turning a line break into a space. `contains`, `equals`, `starts with`, `ends with`, and `matches` see the break, quoted (`"<Probe.ml>" contains "line two"`) or not (`<Q.RESPONSE.error> contains "no_such_table_x"` against `relation "no_such_table_x" does not exist` plus a line break and `Position: 15`, including `\r\n`). The comma step that evaluates the clause still matches when that text contains a line break. A one-line value still collapses whitespace, including a Windows path or a path that contains spaces. A backtick stays raw. In `matches`, `.` does not cross a line break unless the pattern includes `(?s)`. A one-line step is unchanged. Public Gherkin syntax is unchanged.
- A namespace-prefixed XML root such as `<ns1:R ...>` or `<soapenv:Envelope ...>` parses in Java and in Gherkin. Step text keeps the payload instead of treating the tags as mapping references. A prefix with no `xmlns` declaration is accepted, and the parsed fields use the local name. XML that already parsed is unchanged. `DOCTYPE` and `ENTITY` are still rejected. A data-table cell that is XML is stored too. `| plain | <R> <name>Adax</name></R> |` keeps that text, so `plain=<Probe.plain>` prints it and `<Probe.plain~XML;::name>` is `Adax`. The same is true for `<ns1:R xmlns:ns1="urn:pickleball:test"><name>Adax</name></ns1:R>`. A single unresolved reference such as `<no.such.ref>` is still not stored. JSON and XML DocStrings are unchanged.
- `throttle(String key, int seconds)` still waits on one JVM-wide gate per key and still returns immediately on the first call. It now returns the milliseconds this call waited (`0` when it did not wait). Callers that ignore the result are unchanged. An interrupt still throws `IllegalStateException` and does not move the gate. `isBlank(Object)` is true for null and blank text, including a masked blank, and false for a number or any other object. A Cucumber `@Before` or `@After` can call the run-value methods, `throttle`, and `isBlank`. Scenario, step, and root-scenario reads, and `softFail`, still need a running step. `softFail` still fails the scenario at the end. The JUnit failure's cause message is that text, not null.
- A JDBC `SQLException` still does not fail the step. The message is `RESPONSE.error`, with empty `rows` and zero counts. A blank `sql` still fails before a connection is opened. `NULL` stays null, booleans stay booleans, and numbers, including decimals, stay numbers. Dates, timestamps, and strings come back as text. A `BLOB` comes back as `String.valueOf` of the byte array. A `CLOB` comes back as `String.valueOf` of the driver object. [Experimental features](experimental-features.md) is now in the packaged guidance.
- `saveScenarioObject(String name, Object value)` and `getScenarioObject(String name)` keep a Java object for the current Cucumber scenario, including a `@Before` or `@After` hook. The step sees the same instance the hook stored. The next scenario on that thread does not. This is not the mapping store and it is not Gherkin. A nested `RUN SCENARIO` on the same thread shares that store.

## 2.1.16

### Breaking change

Element text matching is a full match. `matching` used to succeed when the pattern was found anywhere in the element text (`Pattern.find`). It now uses `Matcher.matches`, the same full-match rule phrase `matches` already used, and it honors quote types. A single quote on either side is case-insensitive. A backtick on either side is raw text. There is no regex warning.

On a page with buttons Save, Save All, and Autosave:

- `click the Button matching "Save"` clicks only Save
- `click the Button matching "Save.*"` clicks Save or Save All
- `click the Button matching 'save all'` clicks Save All

`containing` is still a literal partial match. For a partial regular expression, wrap the pattern in `.*`, for example `".*Sa.e.*"`. For exact text that contains `(` `)` `.` or `$`, use `equals` or escape the pattern. Quote types change case and whitespace only. There is no new syntax.

### New features

- Java value API on `tools.dscode.Values`: `getValue` / `saveValue` and the run, scenario, root-scenario, step, default, override, and singleton pairs, plus Jackson `Class<T>` overloads. See [Java values](java-values.md).
- `softFail(String message)` records a soft failure. The step continues, the scenario fails at the end, and `RUN IF SCENARIO SOFT FAILED` runs.
- `throttle(String key, int seconds)` waits until `seconds` have passed since the last call with that key in the JVM. There is no Gherkin syntax.
- `~XML-ESCAPE;` escapes `& < > " '`. It works everywhere conversion directives work, and it is rejected on a `MAP "key" TEXT/OBJECT VALUE` destination key.
- Custom reference prefixes. `registerPrefix` adds `<password:testAccount>`. `secret(value)` prints `******`. `~MASK;` stores a masked value that stays masked in logs, reports, the terminal, and Workbench. `<pw~UNMASK;>` returns the plain value.
- Experimental JDBC service calls. A `REQUEST.endpoint` that starts with `jdbc:` runs a JDBC call. HTTP calls are unchanged. Drivers for PostgreSQL, Microsoft SQL Server, Oracle, MariaDB, and H2 are published with Pickleball. See [Experimental features](experimental-features.md).

### Other

- XML readers reject `DOCTYPE` and `ENTITY` declarations. Normal XML is unchanged. `~XML;` uses Jackson's `XmlMapper` conversion, documented with captured output in [Mapping and templating](mapping-and-templating.md).
- A `file:/...` or unprefixed `/...` path that is not on the classpath fails with a hint to use `wd-file:/...` for a filesystem path.
- Literal key escapes and registered-object cleanup are documented. The existing `cleanup` property runs at scenario end after a pass, a soft failure, or a hard-failed step.
- A hard-failed scenario and a deferred `softFail` both fail the Cucumber scenario after cleanup. The workbook status and the JUnit result stay failed together. `CurrentScenarioState.absorbRecordedScenarioFailure` and `discardDeferredSoftFailure` are not a consumer API.
- A static import of `Values` includes the documented methods and `Values.Context`. Framework helpers are not part of that import.
- Sample `pkb_callpath` and `pkb_componentpath` values use the resources-folder names `calls` and `component`. When those properties are unset, the defaults remain `src/test/resources/calls` and `src/test/resources/component`.
