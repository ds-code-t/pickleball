# Dynamic Control API

Pickleball exposes a small core interception contract plus a separately organized `pickleball-control-api` source module for dynamic tooling. The behavioral control API classes are bundled into the main `tools.dscode:pickleball` artifact; consumers do not add a second Maven dependency. Versioned wire records live separately in the JDK-only `pickleball-control-protocol` module so the Workbench controller never depends on behavioral runtime classes.

## Artifact and compatibility

All consumers, including tooling that uses dynamic control, depend only on Pickleball. `pickleball-control-api` is an internal Gradle source module rather than a separately published Maven artifact.

Installing Pickleball with no control handler and never invoking the bundled control API preserves normal execution behavior. Dynamic execution, Mapping interception, bridge startup, browser/service evidence, breakpoints, and Step Overrides are opt-in.

## Browser facade

`tools.dscode.browser.BrowserFacade` is the protocol boundary for a live page. Methods are `send`, `evaluateIsolated`, `addPreload`, `addBinding`, `screenshot`, `frameTree`, `find`, `click`, and `type`. `ProtocolSelector.forDriver` returns `CdpAdapter` (Chromium, own websocket, `Page.createIsolatedWorld`, `Page.addScriptToEvaluateOnNewDocument`, `Runtime.addBinding`, `Page.captureScreenshot`, `Page.getFrameTree`), `BidiAdapter` (Firefox, `script.callFunction` in a sandbox, `script.addPreloadScript`, `script.message` channels, `browsingContext.captureScreenshot`, `browsingContext.getTree`), or `SeleniumAdapter` when that socket is not available. The Selenium choice logs one WARN per run and reason. `SeleniumAdapter.send` is refused with `error:` and `fix:` and does not call `executeCdpCommand`. `evaluateIsolated` on that adapter is `JavascriptExecutor.executeScript` after the same WARN. `PlaywrightAdapter` is the optional library `[1.40.0, 2.0.0)` and is opened with a Playwright `Page`, not by `forDriver`. `ElementOperations` calls `ProtocolSelector.forDriver(driver, LIBRARY)` and does not send. `DriverConstruction.ready` makes that same `LIBRARY` selection and does not open a socket. `PageSurfaces` calls `forDriver(driver, DIRECT)`. A CDP or BiDi session runs the live helper with `evaluateIsolated` in the `pkb-surface` world, preloads `js("html")` with `addPreload`, and pushes input with `addBinding` (`pkbSurface`). Selenium `executeScript` of `live-helper.js` is the last resort and logs one WARN (`page-surface-script`). `pkb_composite` unset, `auto`, and `off` stay on `SeleniumAdapter`. `on` is the Java engine.

## MCP command registry

MCP is the public agent entry. `domengine mcp` and the Workbench MCP server each expose a registry of parameterized commands: `query`, `click`, `type`, `snapshot`, `observe`, `launch`, and `surfaces`. The domengine server also keeps `domengine`, which forwards an argv list to the CLI. `query`, `click`, `type`, and `observe` build that same argv and call `DomEngineMain`. `snapshot` on the engine calls `dev.domengine.snapshot.CompositeSnapshots.offline`, `.browser`, or `.desktop` and returns that JSON unchanged (`schema` `pickleball.composite-snapshot`, `version` 1). `offline` is the producer. `browser` and `desktop` answer with that producer's error (`isError`) until those producers are implemented. The Workbench command calls `dev.domengine.mcp.SnapshotDispatch.render(JsonNode)` by that exact method. When that class is absent it calls `SnapshotProducers.page` only if a static page method can take String, Map, or JsonNode arguments. Otherwise its body is a schema-shaped placeholder whose `warnings` say the producers are absent. `launch` on the engine server does not start a browser; the Workbench `launch` command forwards to `AgentControl`. `surfaces` lists the page-surface operations and, on Workbench, forwards an `op` to `AgentControl`. The Workbench `surfaces` schema describes every flag it forwards: `op`, `text`, `handle`, `id`, `html` (a local page file path, not markup), `x`, `y`, `width`, `height`, `geometry`, `where`, `number`, `zoom`, `dim`, `direction`, `from`, `to`, `color`, `style`, `preset`, `target`, and `pane`. Numeric flags accept a number or a string.

Other entries stay. The CLI, `POST /v1/agent/command`, and `workbench_agent_command` are internal forwarders to the same `AgentControl` path. They are not a second public catalogue. A group adds a command by registering an `McpCommand` (domengine) or an `McpCommandContributor` (Workbench). It does not edit the server classes. `DOMENGINE_LOG=mcp` logs each command at INFO. That log is off unless the entity is named, and the file is date-stamped and size-capped by `EngineLog`.

## Dynamic execution and Mapping

`DynamicControl` executes Cucumber/Pickleball steps against the currently active Pickleball test context. Detached failures are returned as structured `FAILED` results instead of automatically failing the paused scenario, allowing controller tooling to inspect a failed hypothesis and try another action.

`MappingControl` provides retry-friendly access to the live `ParsingMap` / `NodeMap` structures, caller-defined Mapping contexts, scoped overrides, snapshots, and resolution explanation. Live mutations are deliberate and are not automatically rolled back.

The control API returns `SUCCESS`, `FAILED`, or `UNAVAILABLE` for exploratory operations. Calls without a required live Pickleball context return `UNAVAILABLE`. `DynamicControl.executeStep` does not require that context. With no Cucumber scenario on the thread it runs the step on the native engine. Glue is `NativeDynamicSteps.useGlue` or the `pkb_engine_glue` class list. A live or paused scenario keeps the existing detached execution, including the failure restore. The control bridge uses that native call only when no scenario lane is active. A live lane is unchanged. Step creation, mapping interception, browser evidence, and service calls still return `UNAVAILABLE` without a live scenario.

## Semantic hooks

`ControlRuntime` exposes synchronous semantic hooks across scenario, step, phrase, Mapping, DOM, browser, driver, and service-call boundaries. Handlers may observe, pause by blocking, or use supported skip/value interception semantics. With no handler installed, original Pickleball behavior is retained.

`BEFORE_FIXED_WAIT` and `AFTER_FIXED_WAIT` fire only when a framework fixed wait is about to run. A skip decision suppresses that wait. A literal `save` and a nested `RUN_STEP` do not take the 300 ms browser-settle sleep, even when a session is already open, so they do not emit `BEFORE_FIXED_WAIT`. A click, type, or other page action that still waits does.

The bridge coordinator is an additive observer and does not replace the application's normal control handler.

## Consumer-side Control Bridge

Pickleball bundles a loopback-only Control Bridge server/coordinator used by Workbench to operate against a live consumer scenario. The bridge is not enabled during normal consumer execution unless its session environment is present.

Canonical environment variables are:

```text
PKB_CONTROL_BRIDGE_SESSION_DIR
PKB_CONTROL_BRIDGE_SESSION_ID
PKB_CONTROL_BRIDGE_TOKEN
PKB_CONTROL_BRIDGE_PAUSE_FIRST_SCENARIO
```

For backward compatibility, Pickleball may accept the former `PKB_STUDIO_BRIDGE_*` names as deprecated input aliases. They are not canonical configuration and do not require the removed Studio application.

Each participating consumer JVM binds to `127.0.0.1` on an operating-system-assigned port and writes a runtime descriptor into the session directory. Requests require the session bearer token and responses are marked `Cache-Control: no-store`.

The descriptor advertises the current and minimum-compatible protocol versions, capabilities, PID, Pickleball implementation version, and runtime code source. Workbench rejects incompatible capabilities/versions, a same-process worker, a runtime origin outside the synchronized consumer classpath, version drift, or a worker classpath containing the controller. It never falls back to executing a Workbench-bundled runtime.

The bridge keeps live operations on the real scenario thread through `ControlBridgeCoordinator`. This preserves access to thread-local Cucumber/Pickleball state, glue, browser, services, mappings, and other scenario resources.

Bridge capabilities include:

- runtime/status and active-scenario discovery;
- bounded semantic events;
- finite-lease pause/resume;
- retry-friendly detached step execution;
- read-only step resolution (`/v1/steps/resolve`, capability `resolve_step`) to consumer glue, Pickleball dynamic/framework steps, Step Overrides, or unmatched text;
- Mapping get/put/resolve/snapshot/restore;
- browser page/screenshot evidence;
- Pickleball-native element inspection;
- existing Pickleball service-call execution/evidence;
- semantic breakpoint management;
- scenario-scoped Step Override management.

Workbench owns the controller-side protocol client. MCP and Swing access these capabilities through `WorkbenchServices` / `WorkbenchController`; they do not connect to the bridge independently or implement a second runtime. Workbench imports only `tools.dscode.control.protocol.*`; bridge server/coordinator/bootstrap and conversion to runtime objects remain worker-side.

## Scenario targeting and finite pauses

A consumer runtime may observe more than one scenario thread. Controller calls may target a scenario id discovered from the bridge. A wrong or stale id returns `UNAVAILABLE`; the bridge does not guess.

Pauses and breakpoint pauses use finite leases. Expiry resumes execution automatically. Workbench renews the pause it owns while its persistent interactive worker remains active and resumes before clean shutdown.

## Semantic event evidence

The bridge retains bounded immutable semantic hook metadata rather than arbitrary consumer object graphs. Event reads are read-only and do not require the scenario-thread command queue, so reading evidence cannot consume a hook or block a paused scenario.

## Browser and service investigation

`ElementControl.inspect(...)` resolves a Pickleball category through the active `ExecutionDictionary`, or forwards one engine query string when `query` is set. That string is the composite selector: `css=`, `xpath=`, `text=`, `image=`, `near=`, `below=`, `above=`, `left-of=`, `right-of=`, `>>` stages, and AND/OR/NOT. Workbench, MCP, and the control bridge only forward it. There is no second locator language. Gherkin stays phrase sugar via `SelectorTranslator`. Inspection requires an existing scenario-owned browser and returns `UNAVAILABLE` rather than creating one. A controller query with no `exposure` is `human`: displayed, non-zero size, and inside the visual viewport. `lower` is opt-in on that one query, not a session setting, and every returned node carries reason codes plus a sentence. An action with no exposure is `human` and refuses a node a person could not click. `lower` still acts and keeps the sentence, which starts with `acted on node <handle>;`. A binary that does not list `exposure` or `limit` omits that flag and does not invent a result. `left-of`, `right-of`, `above`, `near`, and `below` are visual distance on that same query, using the geometry view. A binary that does not list `geometry` or the engine name logs `rel fallback` and invents no box. Gherkin `after` and `before` stay document order (`following::` / `preceding::`). `--explain` returns rank and score on that same query. `image=` with promote binds a DOM node when the engine can. Otherwise the hit is `visualOnly` and is not a DOM node. A query plus an optional limit returns handles. A later act sends one of those handles as its selector. Offline HTML is a labelled source read and does not run the engine query. Category+text and Gherkin do not send `exposure`.

`look=` is computed style on that same query string: `look=color=red` or `look=opacity>0.5,background-color=#fff`. A comma is AND and a pipe is OR inside the stage. `contrast` is the contrast of `color` against the painted `background-color`. It is not a screenshot match. There is no engine named `attribute`. A step may add `with look color equaling red` or `with look opacity greater than 0.5` after the existing `with id attribute` / `with id noattribute` clause. That clause becomes the `look=` stage and the live find applies it. `with id attribute` and `with id noattribute` still filter. `pkb_composite=off` fails that step instead of ignoring look. The older attribute phrases are unchanged.

`ServiceCallControl.execute(selector)` runs the same reusable service-call component selected by normal `CALL:` semantics. Existing Pickleball discovery, Mapping, request/configuration processing, REST/SOAP execution, response mapping, and failure behavior remain authoritative.

## Semantic breakpoints

Semantic breakpoints are temporary filters over existing `ControlHook` boundaries. They may filter by scenario, hook, hook signature, current step text, and current phrase text. They use the same finite pause lane as ordinary control pauses and disappear with the consumer runtime.

They are semantic Pickleball interception points, not arbitrary Java source breakpoints.

## Step Overrides

The consumer worker also owns scenario-scoped Step Overrides. Workbench can compile/register REGEX/REPLACE rules through the bridge; matching and execution occur before ordinary Cucumber glue fallback. When no override matches, normal Cucumber matching remains authoritative. Removing or clearing an override restores ordinary fallback without restarting the worker.

Worker-side compilation requires `javax.tools.JavaCompiler`. Workbench sends a Java source template containing `{{CLASS_NAME}}`; the worker owns generated naming, compilation, classloading, matching, captures, replacement, and cleanup.

## Architecture boundary

The control API and bridge intentionally remain independent of MCP, Spring, GUI frameworks, generic project IDE behavior, and build orchestration. Pickleball owns live execution semantics. Workbench is the external controller/adaptation layer and its artifact contains no Pickleball core, behavioral control API, Cucumber, Selenium, or service runtime. The only shared code is the dependency-neutral wire protocol.

## Agent browser control

`POST /v1/agent/command` forwards one agent command to `AgentControl`. The CLI calls that same class directly. Workbench, MCP `workbench_agent_command`, and the bridge do not keep a second implementation. The worker capability is `agent_command`. No active scenario is required.

Commands: `observe`, `launch`, `windows`, `tabs`, `chat-send`, `chat-history`, `chat-poll`, `highlight`, `unhighlight`, `overlay`, `overlay-poll`, `overlay-remove`, `label`, `unlabel`, `border`, `unborder`, `arrow`, `unarrow`, `step-badge`, `unstep-badge`, `magnifier`, `unmagnifier`, `spotlight`, `unspotlight`, `html-write`, `html-replace`, `html-insert`, `html-remove`, `html-cleanup`, `popup-open`, `popup-status`, `popup-close`, `panel-open`, `panel-close`, `guide`, `guide-next`, `guide-back`, `guide-done`, `ask`, `ui-apply`, `ui-poll`, `ui-catalog`, `capture-scenario`. `popup-open` starts or reuses the popup host. `popup-status` reads `host.json`. `popup-close` writes one close row and waits up to 10 seconds for the host pid, the browser pid, and the profile directory to leave. In the last two seconds, and again at the deadline, it force-kills a host or browser that is still alive, the child processes of that host and browser, and any process whose command line contains that profile path, then deletes the profile. The result field `exited` is true when the profile is gone and the host and browser pids are gone, and it can also be true once the host logged its exit and the profile is gone. `PopupCli` `popup-close` exits 1 when the host does not exit. `--target=auto|page|popup|native` picks the surface (`auto` is the default). `--pane=instructions|diagram` selects the popup pane for `html-*` and `overlay` (`instructions` is the default).

Chat input. The popup composer is a text area: Enter sends, Shift+Enter adds a line, and Send stays disabled for a blank message. `POST /chat` refuses blank text with 400 `{"error":"empty"}`. A stored human message is also appended to the popup ledger as a `chat` row with `codes=human`, so the pane shows it at once with a pending, sent, or failed state (failed offers Retry). `/events` is a long-poll stream: each response starts with `retry: 250`, ends after a batch or 15 seconds, and the page lets EventSource reconnect with `Last-Event-ID` instead of closing it. Only agent-placed elements (`data-pkb-id`) post `/input`. The Workbench chat field sends on Enter, and a refused send keeps the text and names the reason. `chat-poll --wait=<seconds>` (up to 25) returns as soon as a newer message exists. `overlay-poll --after=<next>` returns only events after that cursor plus `next`; without `--after` the reply is unchanged. On a CDP or BiDi session, overlay clicks and changes are queued in the `pkb-surface` isolated world (the event preload is installed in that world) and drained there. A same-tab navigation no longer leaves a dead isolated-world context: the CDP adapter creates the world again once. On a page that requires Trusted Types, injected HTML goes through a `pkb-surface` policy, or is shown as text if the page forbids new policies.

Agent panel. `panel-open [--target=auto|page|popup] [--x= --y= --width= --height=] [--tab=chat|steps] [--title=] [--theme=auto|light|dark] [--minimized=true|false]` shows the chat in the page itself: a card (default 360×420, bottom-right) in the runtime's shadow-root layer, with Chat and Steps tabs. Its header drags it (pointer capture, clamped to the viewport, snapping to an edge within 16 px), edge and corner grips resize it (at least 260×200, at most 90% of the viewport), the – button folds it into a pill that counts unread agent messages, × closes it, and a double-click on the header puts it back in the corner. Keys, input, clipboard, and pointer events inside the panel stop at the panel, so a page hotkey cannot take the letters typed there. The composer works like the popup's: Enter sends, Shift+Enter adds a line, a blank message is not sent. A typed message is queued in the `pkb-surface` world and stored in the run chat as `source=human` when the agent next reads chat (`chat-poll`, including each `--wait` check, `chat-history`, `panel-open`, `panel-close`); its bubble turns from pending to sent at that moment. An agent `chat-send` on the `run` channel is shown in an open panel as well as the popup. `--target=auto` (the default) uses the page when a browser page is managed and the popup otherwise; `--target=popup` is `popup-open`/`popup-close`. The popup window and the panel load the same stylesheet (`panel.css`, served to the popup as `assets/surface/panel.css`), so both look the same. While a page's modal `<dialog>` is open the panel is drawn above it but the browser keeps it inert.

`observe` reads `Network.*`, `Runtime.consoleAPICalled`, and `Log.entryAdded` from the CDP Session query, resolve, action, and settle already use for that page. It does not open a capture socket beside that Session. Filters are type, URL substring, time window, and limit. `--wait-ms` is forwarded. `0` reads the retained deque only and fails when no Session is retained, instead of pretending a fresh socket had history. A positive wait opens one Session only when none exists, then collects live traffic for that window. `--events` is a recorded snapshot of that same shape. There is no second buffer. Socket closure and other drain failures are failures, logged as `observe failure`, not as empty traffic. An attached Session with no matching rows is empty traffic (`count` 0). `capture-scenario` does not write a feature when that read fails. When the caller omits `--session` and `--cdp`, observe uses the engine session focused for the current browser and tab. Switching tabs on one browser selects the Session for that page target (`/devtools/page/<id>`), not a host:port shared by every tab. A second browser still has its own session.

`launch --template` writes `.pickleball/agent-launch.json` for the requested project. `DriverConstruction` applies that file, not whichever directory the process was started in. `--arg` is repeatable and is forwarded by the CLI, bridge `extraArgs`, MCP, and Workbench. `--start` calls the existing `DriverConstruction` path. It does not invent a second launcher. Without `--start`, launch does not create live window or tab handles. Templates: `chrome-headed-verbose`, `chrome-headed-quiet`, `chrome-headless-verbose`, `chrome-headless-quiet`, `edge-headed-quiet`, `edge-headless-quiet`, `chrome-headed-logs`, and `chromium-headed-quiet` (the existing Chrome launcher; the fallback already searches `chromium` and `chromium-browser`). A live window is one browser instance. A live tab is a Selenium handle inside that instance. An unknown handle fails. Page helpers act on the focused browser and tab. A ranked handle (`frameId:backendNodeId`) keeps the browser and tab captured with the query result; a later focus change does not reassign it, and the handle is not tried against every driver. It is not only a `data-backend-node-id` attribute, and it stores the browser and tab even when the hit has no visual geometry. Entering that frame fails the command when the frame is missing, the owner cannot be named, `switchTo().frame(name)` throws, or restoring the temporary name and `data-pkb-bridge` does not return true. An originally empty `name` or `data-pkb-bridge` is put back as an empty attribute, not removed. A driver without CDP does not report frame entry unless `switchTo().frame` actually runs. Query ownership is this thread's engine Session, not the global join pointer another thread may have moved. All-contexts hits capture the tab before the query is issued. A failed page-session open does not leave that pointer on the target that failed, does not mark the destination tab focused, and does not report the tab activation as successful. A public window or tab switch does not return an open handle when that focus fails, including when the requested tab's page target cannot be confirmed. A null or blank `Target.getTargetInfo` is not treated as a successful browser-level focus for a specific tab when the driver published `se:cdp` or a Chromium `debuggerAddress` (`goog:chromeOptions` or `ms:edgeOptions`); a target already confirmed for that tab may still open its page session. A destination read that switches tabs puts Selenium back on the thread's focused tab when that tab is known, including when the current handle could not be read and the destination target is unknown. A thread with no engine Session yet does not adopt another thread's join pointer for its first query. Closing a tab focuses the surviving tab's engine session when that page session opens. If it does not, the close fails and the engine session is not left on the closed tab. Known geometry without an owner is not resolved against whichever driver is focused now. Removal searches drivers, tabs, and child frames that received the surface, and succeeds only when that surface was actually removed. A helper failure is a failure. `windows --close` fails when quit throws and does not report the window closed. Those commands do not create a page snapshot. No live driver and no resolved target is a failure.

Chat is stored under `.pickleball/runs/<run-id>/agent/chat/<channel>.jsonl` (or `.pickleball/agent` when no run id is set). Sources are `agent`, `human`, and `system`. Message ids continue from the highest id already stored, including rolled files, so a new process does not restart the cursor. The read of that highest id and the append share an exclusive lock file, so two processes cannot take the same id. A second process prints ready before it blocks on that lock. When a channel file passes the size cap it is renamed aside and kept in history and poll. Send and receive are both logged. The Chat tab loads history, polls, and sends on the selected diagnostic run. It does not send with a null run.

`highlight --preset=yellow|outline-red` paints a find-interface handle. A ranked `frameId:backendNodeId` is resolved on the browser and tab that own that frame, including entering the frame, and `Overlay.highlightNode` uses that backend node id. Entering the frame calls `switchTo().frame(name)` after a predefined `Runtime.callFunctionOn` returns the iframe `name` or `id` (setting `name` only when both are empty). It does not call `WebDriver.findElement`. The helper does not require a pickled `data-backend-node-id` attribute. `DOM.resolveNode` plus a predefined `Runtime.callFunctionOn` stamps `data-pkb-bridge` so replace, insert, overlay, and DOM highlight can find the ordinary node. No agent-supplied script is evaluated. The highlight color follows the preset. An explicit style may set the border and the background when the whole value is a named color, `#RGB`, `#RRGGBB`, or `rgb()` / `rgba()` on `background`, `background-color`, `border-color`, or `outline-color`. `border` or `outline` shorthand that is not only a color (for example `border:9px dashed #abc`) and CSS `color` (text) are not reduced to CDP `borderColor`, including when the handle is a ranked `frameId:backendNodeId`. `Overlay.enable` may run; `Overlay.highlightNode` does not. They are applied as reversible DOM styling, the result includes `styleNote`, and `unhighlight` restores the original `style` attribute. A successful CDP highlight does not also change DOM style. `unhighlight` and cleanup, on a CDP session, call `DOM.enable`, `Overlay.enable`, and then `Overlay.hideHighlight` on every tab that had a highlight. A direct facade whose protocol is not CDP skips that hide, and the DOM cleanup still runs. A tab, frame, or driver that is already closed is skipped, including a handle that is no longer listed, a quit session, and a CDP target that reports no such window or target. Cleanup does not fail those as a tab switch or a tab enumeration. A live tab whose switch fails is a failure and does not hide a different tab. The hide call fails the command when `Overlay.hideHighlight` throws on a live tab. DOM style highlighting remains the fallback, and a repeated DOM highlight does not overwrite the remembered CSS. `unhighlight` with no handle and cleanup clear DOM styles in every managed tab and in ranked child frames, not only the current document. Cleanup, remove, and input polling reset to the top document after selecting a tab, then visit ranked child frames and the live child-frame tree, including a surface whose in-process site record is gone. A remembered frame id that is not in that tree is not entered. A helper that does not return `ok: true`, a tab or frame enumeration failure, a failed frame entry, or a failed tab restore fails the command. A missing or non-map frame tree, and a null or empty window-handle list, are enumeration failures. Cleanup does not pretend the current tab was visited when tab enumeration returned nothing. Scenario teardown still quits owned drivers, then propagates that cleanup failure. Native-overlay completion and later configured object cleanups still run when in-page cleanup throws. Geometry for a ranked handle keeps the query's driver and tab; a later focus change does not reassign it. A second managed browser keeps its own engine session. Two tabs on one host:port keep two sessions, selected by the page target. Focusing that driver and tab selects that session. The result is labeled `style_modified` plus a sentence.

Visual components (label, border, arrow, numbered step badge, magnifier, spotlight, and overlay width and height) share this controller. The contract and the baseline gaps are in the in-repo roadmap `3.0.0-visual-components-roadmap.md` (under `docs/roadmaps`, not exported). `highlight` accepts `--x`, `--y`, `--width`, and `--height` and ignores them. `rememberGeometry` stores only a point. Each placement records its kind. An `un*` verb whose kind does not match the placement its `--id` names exits 2 with `id <id> is a <kind>, not a <kind>; use <verb> --id=<id>` and removes nothing. The page path reads the kind from the page's place record or the focused live page's id store, the popup path from the ledger row's `data-pkb-kind`, and the native path from the rectangle that `show` drew in this process. A placement with no recorded kind (an older ledger row, or a native rectangle from another process) is removed as before.

`overlay` places a surface from the remembered Geometry view (`visual_viewport_relative`) for a resolved handle, or from caller-supplied Geometry JSON. Caller `x`/`y` is used only when that geometry is absent and no handle was supplied. An unresolved handle is rejected even if `x`/`y` were provided. There is no default box. The resolved box is used for the first paint and is what the result fields `x`, `y`, `width`, and `height` report; on a live page the runtime then follows the element itself with `getBoundingClientRect` (see Live tracking). `--width` and `--height` are stored. A resolved element box (visual-viewport width and height, or the same width and height from a native `--query`) is the box on the page path and the native path. Stored width and height are used only when that box is absent. An `--html` / `--page` file keeps the fixed overlay style; a live page restyles the callout (see Live tracking). `label` places that text at the resolved box or at `--x`/`--y`. `border` draws a standalone box (default `3px solid #0a7a32`, or `--color` / `--style`; `--width` and `--height` stay geometry). `arrow` draws from `--from` and `--to` remembered points, or from a target plus `--direction` (`up`, `down`, `left`, `right`). `step-badge --number` is a visual badge only and does not edit Gherkin. `magnifier` is a circular frame (`--zoom` from 1 to 8, default 2); a live page clones the resolved node into that frame. `spotlight` dims the page with a cutout (`--dim` from 0 to 1, default 0.55). Each kind is removed by its `un*` verb, by `html-cleanup`, by undo, and at scenario end. Native draws the same rectangle and stores the caption; it does not paint the HTML callout, the arrow shaft, the magnified clone, or the desktop dim. Step badge and magnifier `--text` is escaped, not markup. A live magnifier copy drops `id`, `name`, `for`, `form`, `tabindex`, inline `on*` handlers, and scripts, and is `inert` and `aria-hidden`. A native `un*` with no `--id` or `--handle` hides `native-<kind>`, the id its show used. Scenario end hides every native rectangle (highlight, overlay, and each visual kind). Logging entities are `label`, `border`, `arrow`, `step`, `magnifier`, and `spotlight`, for both placement and the `un*` removal. `highlight` still ignores `--x`, `--y`, `--width`, and `--height`. Clicks and form changes are polled across every managed tab, not only the driver's current document, and written to the `overlay` chat channel. `html-write`, `html-replace`, and `html-insert` accept structural HTML. A small parser strips script elements, iframe `srcdoc`, encoded and slash-separated `on*` handlers, `javascript:` URLs even when whitespace, entities, or leading C0 controls sit inside the scheme, and active nested documents (`data:text/html`, `data:application/xhtml+xml`, `data:image/svg+xml`, `data:text/xml`, `data:application/xml`). Normal structural tags stay, including an unquoted URL that contains `/`. That is not a tag allowlist. Injected surface ids are allocated under the same exclusive file lock as the placement metadata. An explicit `--html` / `--page` file keeps its own counter. A live id is taken from the destination page after that handle's owner and tab are selected, not from the globally focused page. That page shares one counter across run ledgers (debugger address, that tab's own page target, and tab), so two fresh runs do not both receive `pkb-1`, and a write aimed at a page that already has `pkb-1` does not mint another `pkb-1` there. `Target.getTargetInfo` is read while the destination tab is selected. When the current Selenium handle cannot be read, that tab is selected and confirmed before the read, or a target already remembered for that same tab is reused. A blank target does not start a new counter. The active window's target is not paired with a different Selenium handle, and it is never stored under that other tab, including two tabs of one browser. A ledger that already contains `pkb-N` and has no `next` advances past those ids. Two processes writing the same file still cannot take the same id. Every injected element, including descendants, carries `data-pkb-agent=agent_injected` and a sentence. Agents still see those nodes. Replace keeps an undo snapshot beside the file, not inside the document. `html-remove` and `html-cleanup` restore it. Removal logs the snippet sha256 and a short summary from the placement file (`page.html.place.json` for an explicit page, or `.pickleball/runs/<run-id>/agent/placements.json` for a live command), so a later process can still recover them. The Workbench-native overlay shows the guidance text and the provenance sentence from the same command object. It is removed on `overlay-remove`, `html-remove`, `html-cleanup`, `stop`, `worker-stop`, `close-window`, headless play completion (including a failed step), GUI playback pause, stop, and natural completion, scenario cleanup, and live-session close. In-page surfaces are cleaned when the scenario ends.

Live tracking. On a live page each `overlay`, `label`, `border`, `arrow`, `step-badge`, `magnifier`, and `spotlight` placed on a target is handed to the page runtime (`pkb-runtime.js`, `window.__pkbUi`), which runs once per document in the `pkb-surface` isolated world (CDP or BiDi) and, on a Selenium-only session, in the page itself, installed only for a placement that follows a target. The runtime listens for scroll in the capture phase (so every nested scroll container counts), window and `visualViewport` resize and scroll, a `ResizeObserver` on the target and its scrollable ancestors, and a `MutationObserver` on the document; it repositions once per animation frame, reading every rect before writing. It moves a placement with the CSS `translate` property, so the inline `left` and `top` keep the resolved box. A target that is replaced (for example re-rendered by the page) is found again by id, handle mark, name, CSS path, or tag and text; when it cannot be found the placement is hidden and a `lost` event is queued for `overlay-poll`. A target partly scrolled out of its container clips the ring and border with `clip-path: inset()`, and a target fully out hides the placement. The overlay callout now sits beside its target (right, left, below, then above, whichever fits; `--at=top|bottom|left|right` picks the first try) with an outline ring on the target, so the target stays visible and clickable. `--at=over` keeps the old covering placement, translucent and click-through except for its own links, buttons, and fields. A label sits above the target's top edge, a step badge to its left, and a magnifier beside it; the magnified copy is refreshed when the target changes. Rings, borders, spotlights, labels, badges, and arrows never take pointer events, and the spotlight hole passes clicks, unless `block:true` (or `--block=true`) is set, which intercepts pointer events over the target. Rings live in a shadow root on a `<pkb-layer data-pkb-layer>` element shown with `popover="manual"` so they stay above a modal `<dialog>`. Styles come from constructable stylesheets (`adoptedStyleSheets`), so they apply under a strict page CSP, and follow `prefers-color-scheme` (`--theme=light|dark` forces one) and `prefers-reduced-motion`. The layer is not marked `data-pkb-agent` and is removed when the last tracked placement is removed or cleaned up.

Guided steps. `guide --steps=<json array>|@file.json [--id=g1] [--scroll=true]` shows numbered steps on a live page: each step is `{"t":"<target>","say":"<instruction>","do":"click|input|select|check|any"}` (optional `capture`, `sensitive`, `n`), and `t` is an id, `h:<handle>`, a CSS selector, `text:<words>`, `role:<role>[name=<name>]`, or `x:<xpath>`. A step without `t` or `say`, or with another `do`, exits 2. Every step gets a ring on its target and a numbered badge outside it (left of the target, else above, else below; inside the corner only when all three are cut off by the viewport), so a badge never covers a field (current pulses, done is checked, the rest wait) and the current one gets a tip with its instruction; the panel's Steps tab lists them. A step completes when the person does its action on its target: a click, a change, or typing that has paused for 0.7 s (one keystroke does not skip ahead). Each completed step queues `{type:step, g, s, done:true, how, filled}` for `overlay-poll`, and the last step also queues `{type:guide, done:true}`. A typed value is added only when the step has `capture:true` and its field is not sensitive; a password field, an `autocomplete` of a password, card (`cc-`), or one-time code, or `sensitive:true` never reports its value, and an overlay field of those kinds is stored as `filled=true` without its value. `guide-next`, `guide-back`, and `guide-done` move or close a guide by `--id`. `ask --say=<question> [--choices=Yes,No] [--handle=<target>] [--sensitive=true] [--id=q1]` shows a small question card (beside the target when given); the answer is queued as `{type:answer, id, value}` (`filled:true` with no value for a sensitive question). `ask` with choices covers yes/no confirmation; the existing `confirm` verb is unchanged.

Page state. After each `overlay`, visual placement or removal, `panel-open`/`panel-close`, `guide` verb, and each `overlay-poll` or `chat-poll`, the runtime's snapshot of what is shown (placements with their target locators, guides with the current step, the panel's position, size, tab and fold) is saved in the run's `ui-state.json` and registered again as a `pkb-surface` preload (CDP `Page.addScriptToEvaluateOnNewDocument` with `worldName`, which needs the Page domain enabled; BiDi `script.addPreloadScript` with `sandbox`). A reload or back/forward navigation replays it once the document is ready, and the runtime checks the URL twice a second so an SPA `pushState`/`popstate` route change withdraws or restores it. `--scope=page` (default: same origin, path and query), `--scope=origin`, or `--scope=run` sets where it applies; `--ttl=<seconds>` expires it. Leaving the scope shows nothing there and the saved state is kept, so coming back restores it. The snapshot holds no value a person typed. A step completed by the person is saved at the next agent read (`overlay-poll`, `chat-poll`). `html-cleanup` and scenario end remove the state and the preload. One state is kept per run. `pkb_ui_page_state=session` (see configuration) also keeps a copy in the tab's `sessionStorage` for a Selenium-only session.

Page UI batch. `ui-catalog [--component=<name>]` lists the page UI components (`overlay`, `label`, `border`, `arrow`, `step-badge`, `magnifier`, `spotlight`, `panel`, `panel-close`, `guide`, `guide-next`, `guide-back`, `guide-done`, `ask`, `chat`, `remove`, `clear`) with each option's type and default, a one-line example op, and the undo verb; the whole catalog is under 6 KB. `ui-apply --ops=<json array>|@file.json [--verbose=true] [--scope=] [--ttl=]` validates every op against the catalog first (an unknown component or option, or a missing required field, exits 2 and runs nothing), then runs them in order through the same verbs and saves the page state once. An op is `{"c":"<component>","t":"<target>",…options}`; `t` is a remembered handle (or `h:<handle>`), or an id, CSS selector, `text:<words>`, `role:<role>[name=<name>]`, or `x:<xpath>` that the page runtime finds and marks with a handle. The reply is compact: `{"ok":…,"ops":[{"i":1,"c":"label","ok":true,"id":"pkb-2"},{"i":2,"c":"label","miss":"#missing"}]}`; `--verbose=true` adds each verb's full reply. It exits 1 when any op missed or failed. `ui-poll [--after=<n>] [--chat-after=<id>] [--wait=<seconds, up to 25>]` merges overlay events (step, guide, answer, click, input, lost) and human chat into one reply `{"events":[…],"chat":[…],"next":n,"chatNext":id}` without the label fields, returning as soon as either has something. MCP: `ui`, `ui_poll`, `ui_catalog`.

Agent loop for service calls: observe the buffer, filter by URL or time, then `capture-scenario`. The file is existing service-call component syntax (`MAP "REQUEST"`, `EXECUTE SERVICE CALL`, Examples). No new Gherkin phrase.

Logs use `pkb_composite_log` entities `observe`, `launch`, `window`, `chat`, `highlight`, `overlay`, `html`, `label`, `border`, `arrow`, `step`, `magnifier`, `spotlight`, and `capture`. They are off unless named, date-stamped, and size-capped.
