# 2.1.18 Workbench coverage findings

Bugs found by the coverage tests. Each one was fixed at the shared path. Assertions were not weakened.

## finish ignored --status

- Repro: `covers_command_finish`, `covers_flag_status`
- Expected: `finish --status=FAILED` (also `PASSED`, `EMPTY`, `TIMEOUT`, `STOPPED`, case-insensitive) stores that status on `record.json`. An unknown status exits 2. A missing status stays `STOPPED`.
- Actual: the usage text advertised `--status`, and `MAJOR_FLAGS` lists it, but `finish` always wrote `STOPPED`.
- Fix: `9130c96a` `3.1.18-workbench-command-coverage`. `WorkbenchAgentCommands.finish` reads the flag and passes it to `AgentCoordination.finish`.

## execute-step required a session before usage

- Repro: `covers_command_execute_step`
- Expected: `execute-step` with no gherkin exits 2 and prints the usage line, same as `insert-step` and `update-step`. A command that has text and no session exits 1 with `No healthy Workbench session`.
- Actual: `requireSession` ran first, so a missing text argument exited 1.
- Fix: `9130c96a` `3.1.18-workbench-command-coverage`. `executeStep` checks blank text after `refusedDriver` and before `requireSession`.

## A bad `\u` escape in the workspace copy was not a read failure

- Repro: `corruptWorkspaceIsReportedInsteadOfAPassedRun`
- Expected: `workspace-show` on a `runvars.properties` that Java `Properties` rejects (`pkb_glue=\uZZZZ`) exits 1 and reports that the file could not be read. A space-separated line is not corrupt: `Properties` parses `broken line` as `broken=line`.
- Actual: `Workspace.readRunVars` caught only `IOException`. `Properties.load` throws `IllegalArgumentException` for a bad escape, so the failure was not the same "Could not read" path as a real IO error.
- Fix: `e9822d91` `4.1.18-workbench-e2e`. `readRunVars` wraps `IOException | IllegalArgumentException` as `IllegalStateException("Could not read ...")`.

## Dry-run preview omitted hook defaults

- Repro: `RunVarLaunchParityTest`
- Expected: `hint`, `resolve-runvars`, and `DiagnosticCli resolve-runvars` match a fresh normal launch, including `globalTestDefaults()` and `globalTestProperties()`. A launcher JVM `-D` is part of that preview. The saved workspace copy is what Discover launches, and hooks are not applied again.
- Actual: dry-run called `PKB_props.resolveRunVars` on property files with empty defaults. `hint` passed `includeAmbient=false`, so a launcher `-Dpkb_parallel=80` was absent from the preview while a normal launch would keep it.
- Fix: `a4b60d21` `7.1.18-workbench-hook-preview`. `PickleballRunner.previewLaunch` constructs the consumer runner and calls `resolveShared`.

## Synced consumer classes were not a preferred test root

- Repro: `WorkbenchConsumerScenarioEndToEndTest.discoverRunsARealScenarioAndRecordsThePack` (and a manual `discover --tags=@workbench-cli-probe` before the fix)
- Expected: the seed JVM, forked from `classpath.txt`, finds `PickleballTests` under `workbench/live/classes` and captures `pkb_glue=com.example.pickleball`.
- Actual: `isPreferredTestOutputRoot` ignored `/workbench/live/classes/`. Capture used empty hooks, so glue was blank and the probe step was undefined.
- Fix: `a4b60d21` `7.1.18-workbench-hook-preview`. That directory is a preferred root. `DynamicSuiteBootstrapWorkbenchRootTest.syncedLiveClassesAreAPreferredRootWithoutAnExplicitProperty`.

## Seed cache reused an empty-hook capture

- Repro: the same consumer discover, after sync, restored a workspace in about 30ms with empty glue.
- Expected: once `sync` writes `classpath.txt`, the resolve-cache key changes and capture runs on that classpath.
- Actual: `WorkspaceSeed.detect` fingerprinted only the launcher JVM `java.class.path`, so the first empty-hook capture was reused forever by `mvn exec`.
- Fix: `3142a26a` `10.1.18-workbench-consumer-e2e`. `detect` fingerprints `classpath.txt` when it exists. `WorkspaceSeedTest.detectRecordsClasspathAndDashDAndEnvInputs`.

## Discover exited 1 after a passed scenario

- Repro: `WorkbenchConsumerScenarioEndToEndTest.discoverRunsARealScenarioAndRecordsThePack`
- Expected: exit 0, and `run-index.json` retains `pkb_run_profile`.
- Actual: the saved copy left `pkb_reportingmode` blank, so diagnostic mode stayed off and no index was written. The scenario, `record.json`, and `workbench/summary.json` were `PASSED`, Maven exited 0, and `printCatalog` returned 1: `Workbench finished but run-catalog.json has no retained pkb_run_profile.`
- Fix: `3142a26a` `10.1.18-workbench-consumer-e2e`. `WorkspaceLaunch` sets a blank `pkb_reportingmode` to `diagnostic` before `--runvar` edits. An explicit mode, including `normal`, is left alone. A normal `mvn test` does not get that default.

## isolate ignored --session-file

- Repro: `covers_flag_session_file`
- Expected: `isolate --session-file=<path>` writes the controller state file there and the launcher waits on that path.
- Actual: the flag was parsed into the forwarded argument list, then `sessionStart` always used `run.sessionStateFile()`.
- Fix: `6d277e79` `9.1.18-workbench-player-success`. `SessionFlags.sessionFile` is the path `session-start` forwards.

## Not a product bug

`maven.test.failure.ignore` exiting 0 while `run-index.json` says `FAILED` was already handled by `observe()`. Process repro `failureIgnoreWrapperExitZeroStillFailsTheProcess` and in-process repro `failureIgnoreStillFailsWhenMavenExitsZero` both exit 1 with `summary status=FAILED`. `WorkbenchConsumerScenarioEndToEndTest.realMavenFailureIgnoreStillFailsTheWorkbench` repeats that with a real Maven run and an `AssertionError` step (`@workbench-cli-fail`), not an undefined step. Normal `mvn test` is unchanged.

The until-pass Chrome path was a test helper (`UntilPassBrowserSteps`), not driver construction. `8707410a` looks up a binary and does not call `setBinary` when none exists. `clickSettleMillis >= 250` is unchanged.

Quoting, tag `and`/`or`/`not`, Windows-style paths, and non-ASCII values already matched the launcher. `a69f37f7` only adds the process assertions. A corrupt workspace still exits 1 with `Could not read <file>: Malformed \uxxxx encoding.`
