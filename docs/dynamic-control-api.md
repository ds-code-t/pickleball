# Dynamic Control API

Pickleball exposes a small core interception contract plus a separately organized `pickleball-control-api` source module for dynamic tooling. The behavioral control API classes are bundled into the main `tools.dscode:pickleball` artifact; consumers do not add a second Maven dependency. Versioned wire records live separately in the JDK-only `pickleball-control-protocol` module so the Workbench controller never depends on behavioral runtime classes.

## Artifact and compatibility

All consumers, including tooling that uses dynamic control, depend only on Pickleball. `pickleball-control-api` is an internal Gradle source module rather than a separately published Maven artifact.

Installing Pickleball with no control handler and never invoking the bundled control API preserves normal execution behavior. Dynamic execution, Mapping interception, bridge startup, browser/service evidence, breakpoints, and Step Overrides are opt-in.

## Browser facade

`tools.dscode.browser.BrowserFacade` is the protocol boundary for a live page. Methods are `send`, `evaluateIsolated`, `addPreload`, `addBinding`, `screenshot`, `frameTree`, `find`, `click`, and `type`. `ProtocolSelector.forDriver` returns `CdpAdapter` (Chromium, own websocket, `Page.createIsolatedWorld`, `Page.addScriptToEvaluateOnNewDocument`, `Runtime.addBinding`, `Page.captureScreenshot`, `Page.getFrameTree`), `BidiAdapter` (Firefox, `script.callFunction` in a sandbox, `script.addPreloadScript`, `script.message` channels, `browsingContext.captureScreenshot`, `browsingContext.getTree`), or `SeleniumAdapter` when that socket is not available. The Selenium choice logs one WARN per run and reason. `SeleniumAdapter.send` is refused with `error:` and `fix:` and does not call `executeCdpCommand`. `evaluateIsolated` on that adapter is `JavascriptExecutor.executeScript` after the same WARN. `PlaywrightAdapter` is the optional library `[1.40.0, 2.0.0)` and is opened with a Playwright `Page`, not by `forDriver`. `ElementOperations` calls `ProtocolSelector.forDriver(driver, LIBRARY)` and does not send. `DriverConstruction.ready` makes that same `LIBRARY` selection and does not open a socket. `PageSurfaces` calls `forDriver(driver, DIRECT)`. A CDP or BiDi session runs the live helper with `evaluateIsolated` in the `pkb-surface` world, preloads `js("html")` with `addPreload`, and pushes input with `addBinding` (`pkbSurface`). Selenium `executeScript` of `live-helper.js` is the last resort and logs one WARN (`page-surface-script`). `pkb_composite` unset, `auto`, and `off` stay on `SeleniumAdapter`. `on` is the Java engine.

## Target selector

One target string selects the backend. `browser:auto` is the live page (the worker when its pid is alive, otherwise the browser `start` launched). `browser:<session>` is that session, and `/tab:` / `/frame:` select a tab or frame on it. `browser:cdp=<url>` attaches that endpoint. A `/devtools/page/` URL stays that page. A `/devtools/browser/` URL uses `/tab:<id>` when it is present, otherwise the live host page on that same browser, and does not take the last `Target.getTargets` page. `desktop:<pid>` and `desktop:app~<name>` may add `/window:`. They use the desktop engine (UIA, AX, or AT-SPI), or `--fixture=<file>` to replay a recorded tree. `ref:<docVersion:handle>` is a handle from an earlier `find` or `snap`. It splits on the last colon. A browser ref stays valid when another part of the page changes, including a pkb highlight. It is `stale_ref` when that node is detached, replaced, or its role or name no longer matches, or when that document's URL or loader changes. The reply `fix` is `run snap (or find) again for a fresh ref`.

With no live browser the command exits 1 and the body is `ok:false` with `error: no live browser`. A missing desktop bus is `error: no desktop target <pid|app>`. An unknown session, pid, or app is `error: unknown target`. A verb that did not run is never `ok:true`.

A click reply separates a dispatched click from one that could not land. After the one dispatch, the call waits up to 500 ms (the page watcher on the main frame, then the title and mutation count) before it decides. Exit 0 with `ok:true`, `applied:true`, `dispatched:true`, and `visible:true` means the read-back changed. Exit 0 with `ok:true`, `applied:false`, `dispatched:true`, `visible:false`, and `reason:"no visible change"` means the click was sent and neither the title, the mutation count, nor that element's own text, `aria-selected`, `aria-checked`, `aria-current`, class, `checked`, or value changed. A handler that only increments a counter stays quiet. `act --kind=hover` on a visible element dispatches a hover (mouseover, mouseenter, or a CDP mouse move) and returns `applied:true` and `dispatched:true`. A hidden target is `applied:false` and `dispatched:false`. That reply has no `error`, so a later call is not a retry of the same click. When `--condition` is set, that same quiet click waits instead, and `applied` is true only when the condition is met. Exit 1 with `ok:false`, `error:"could not land"`, `dispatched:false`, and `reason` of `disabled`, `inert`, or `detached` means the click was not sent. A covered click is exit 1 with `error:"covered"`, `coveredBy`, and `dispatched:false`, and it is not sent. `type` and `select` that do not stick stay exit 1 with `error:"not applied"`. The JS fallback (`pkb_cdp_input=off`) uses that same click reply. It reads a select or type back after one timer turn, so a microtask or `setTimeout(0)` reset is `applied:false`. Writes on `data-pkb-*` nodes do not count as the page changing.

A browser reply includes `frame` on success and on failure: the main frame id, the hit's frame, `top` when no CDP id is known, or, after `frame --enter`, the entered frame's CDP id. `find`, `explain`, `wait`, `snap`, `inspect-page`, `eval`, `highlight`, and `act` run in that frame, so a miss or a timeout still names it, and a main-world `eval` reads that frame's document. `watch`, `capture`, `attach`, and `form-fill` carry that same id and do not limit the call to the entered document. A pkb-world `eval` uses the entered frame's `pkb-surface` world when that frame has its own session. A nested hit keeps its own frame id. Hit rows carry that same id. An `act` reply includes `shadow_path` for an open or closed shadow control. A `highlight` on `browser:cdp=` reports that browser's main frame, including when the handle is missing. A desktop reply includes `frame` as the window name. `frame --list` keeps `parentId` for an out-of-process frame. Cross-origin iframes stay attached: `Target.setAutoAttach` uses `waitForDebuggerOnStart`, the child session preloads the surface runtime in the `pkb-surface` world, and the frame resumes after that preload. A frame reports `surface` `ready` when `__pkbUi` is an object in that frame's `pkb-surface` world. The check reads the frame's own session and does not read page attributes. A cross-site iframe is matched by `DOM.getFrameOwner` on the session that owns the iframe, including after `location.replace` and when the iframe is nested in another out-of-process frame. Unknown frames share one wait for the tree. A frame that is already attached is not waited on. `find` and `snap` walk the main document, same-origin frames, and open shadow, plus grafted out-of-process frames and closed shadow. `contexts` is `same` when that matches the contexts steps walk, and `diff` with `contextDiff` when the agent also has an out-of-process frame or a closed shadow. A closed shadow click is one `DOM.resolveNode` call in the `pkb-surface` world, and `applied` follows the read-back. `find --scroll-search=true` tries each overflow box, preferring one whose rendered rows change when it scrolls or whose text matches the query, and then the document. It restores every box after a miss. A hit reports `scrollSearch:true`. A box that is scrolled 40 steps without a hit reports `scrollSearch` as `{container, steps, capped:true}`. `snap` sets `virtualized` when that box is present.

A placement on a live handle adds `visible`, `hidden`, and `lost`. Those fields, plus `hiddenReason` and `overlaps`, are on the placement reply without `--verbose=true`. A `ui-apply` row omits `visible`, `hidden`, `hiddenReason`, `overlaps`, and `lost` unless `--verbose=true`. `ui-poll` is lean: it drops bounds, typed values, and the system `overlay input` chat echo, and it omits an empty `chat` or `agentEvents` list. Name, role, and guide fields (`type`, `s`, `g`, `done`, `how`) stay. `state` stays on the envelope. `ui-apply` and `ui-poll` keep `ms` and `next` and omit `elapsedMs`, `timing`, `cursors`, and `seq`. `ui-apply` `clear` removes placements, guides, and the saved state. The chat panel stays open. `display:none`, `visibility:hidden`, and the hidden attribute stay `visible:false`, `hidden:true`, `lost:false`, with no `hiddenReason`. Any other hidden handle names `hiddenReason` `offscreen`, `transparent`, `zero-size`, or `covered`. `offscreen` means the box misses the viewport and cannot be scrolled into view, and `position:fixed` is never scrolled into view. `transparent` means the effective opacity is 0. `zero-size` means the box is under 1px. `covered` means another element sits on the centre and is not an ancestor, a descendant, or a pkb layer. `hiddenReason` is omitted when the handle is visible or lost. Lost means the handle is not in the page. `overlaps` names other placements on the page now whose boxes intersect, including open shadow roots and an open question card. A placement that was removed is absent. Boxes that only touch an edge do not overlap. Explicit overlay coordinates stay where they were set. Auto-placed pin, toast, checklist, and status cards are panel-style cards, not the small black label. A checklist row is a real checkbox. The page parks those cards on the right, clear of a 160×56 top-left logo zone, and a person can drag one (`data-pkb-parked=user` keeps that spot). Question cards shift so they do not cover another card or that logo zone. `status` is `ui-apply` with `{"c":"status","text":"..."}`, not a separate command. `navigate to:` accepts `file:`, a `data:` URL that contains a comma, and `about:blank`. `text=` and `role=` with the composite runtime off read the top document in one script: the box, whether it is displayed, and whether it is enabled. A `text=` hit matches the element's own text, its `aria-label`, or its inner text, including when an icon prefix sits in front of the visible label. A letter or digit glued to that label does not match. A `role=` hit is the `role` attribute or, when that is absent, the tag. That read does not walk shadow roots or iframes. `near=`, `below=`, and `above=` still come from the page source, which has no layout, so displayed and enabled come from attributes and the box is not a layout box. `selftest ui --component=pages` paints pin, toast, checklist, and status and reads those texts back. The cpu bench stays `selftest ui --cpu`.

A chain logs a line only when a step fails and a later step serves the call, once per run, chain, and reason. The line is appended to `.pickleball/logs/fallback-chain.jsonl`: `{"run","chain","from","to","reason","at"}`. Example: `{"chain":"act","from":"cdp","to":"js","reason":"cdp input disabled"}`. The test property `pkb_cdp_input=off` skips CDP input and takes that next step. It is not a CLI flag. The log stays off when `pkb_fallback_log=off`. Each run keeps its own de-dupe set (capped at 64 reasons). The host remembers 64 runs and drops the oldest run first, so that run's reason can log again. A command for another run id does not clear a run that is still remembered. On Chromium, `Runtime.addBinding` may include `executionContextName` `pkb-surface`.

## Prebuilt one-call functions

`act --condition` dispatches the action once. When the condition is set and that click was applied or quiet, the same call waits and then judges the condition. Success is the condition: `applied` is true, and the reply includes the condition and the title, even when the click itself made no visible change. The click is not sent again. A refused click (disabled, inert, detached, or covered) returns before that wait. A timeout is `error: timeout`, and `applied` stays the click's own read-back. For a click that was sent, the timeout reply also sets `dispatched:true`.

`form-fill` resolves every key before it writes. A key is an id, a name, a short id, a label's text, or an accessible name. A missing key is exit 1, `error: not found`, `missing` lists those keys, and `fields` reads back the keys that were found. Nothing is written. A select uses the select path and the row's `kind` is `select`. A checkbox or radio sets `checked` from `true` or `false` and the row's `kind` is `checkbox` or `radio`. Text is typed only after focus is on that node and the row's `kind` is `text`. Each row includes the value read back. `applied` is true only when every row matches. A row that does not stick is `error: not applied` and `applied:false`.

`ask-and-wait` is the agent confirm. It shows one question and returns `value` and `choice` for only the clicked label. A joined list of every choice is not an answer. An answer that is already in the push channel or the overlay log is returned even when the live worker call times out or cannot be reached. The card shows which choice was picked, then closes. Each call gets its own id unless `--id` is set. Timeout exits 1 with `error: timeout`, no `value`, and the question is removed. `confirm` is the scenario command. It runs matching scenarios. It does not show a question.

`pin` places a comment card. `toast` places a message and then removes it. `checklist --items` places one checkbox row per item, each unchecked. `checklist --id` is that placement's id. `checklist --check` is the 1-based row (the same number as `data-pkb-check`) and exits 0 only when that row reads back checked. `status` is not its own verb. It is `ui-apply` with `{"c":"status","text":"..."}`.

A placement on a live handle reports `visible`, `hidden`, and `lost` as described above, including `hiddenReason` when the handle is offscreen, transparent, zero-size, or covered. `overlaps` is taken from the placements on the page at that moment.

A click waits only for a loading mask that covers the target. The mask is in the hit stack above the click point, or it is a shown modal or backdrop ancestor of whatever is at that point and its box contains the point. The click reply includes `waitedMs` and `maskCleared`. `maskCleared` is true when that covering mask left. A mask that does not cover the target leaves `waitedMs` 0 and `maskCleared` false. Other `act` kinds omit those two fields. If the mask is still covering when the wait ends, the click is not sent: `act` exits 1 with `error:covered`, `dispatched:false`, and `reason` `loading mask still covers the click`. A Gherkin click throws that same error. The same covering-mask wait runs before the click. A step that enters an iframe names that frame and puts the driver back to the document it started in. A raw switch that never noted the frame is still named, then returned to the top document when the step started there.

## Agent reply envelope

Every agent call returns one object. Older fields stay (`error`, `lines`, `ref`, `elapsedMs`, `ok`). The envelope fields are always present:

| Field | Meaning |
|------|---------|
| `v` | Envelope version. `1`. |
| `ok` | True when the call exited 0 and the body is not `ok:false`. |
| `op` | The verb (`snap`, `find`, `act`, `chat-poll`, `tabs`, `frame`, and the rest). |
| `ms` | Wall time of this call. Same number as `elapsedMs` when that field was set. |
| `state` | `session` (the run id), `browser` (`up` only when the worker bridge is alive, or the start host and its recorded Chrome pid are both alive; otherwise `down`, including after `browser_lost`), `frame` (`top` or the frame on the body), `lease` (`held` when that worker is alive or `start --hold` has not expired, otherwise `none`). `leaseLeft=0` is not held. Always present, including on failure, so a separate status call is not required. |
| `sum` | One sentence. The body's `sentence` when it has one, otherwise the verb plus `ok` or the error. |
| `items` | The first list among `lines`, `messages`, `events`, `chat`, `hits`, `ops`, and `placements`. That source and any equal list are removed, so `ui-apply` does not also return `ops` and `ui-verify` does not also return `placements` and `lines`. A different list, such as `ui-poll` `chat`, stays. |
| `next` | One opaque per-channel cursor (`c.` plus the chat id, the event index, the overlay index, and the channel: `chat`, `ui`, or `events`). The same token reads that channel again and does not move another channel. A numeric overlay `next` is also kept as `seq`. Pass it back as `--cursor=` (or `--after=` when it already starts with `c.`). `cursors` names `channel`, `chat`, `ui`, `events`, and `token`. |
| `trunc` | `on` is true when the body was `truncated` or `--budget` dropped rows. `full` is the spill file. `lines` is how many items were returned. |
| `err` | Null on success. Otherwise `code`, `msg`, `fix`, and `candidates` when the call was ambiguous. An ambiguous `act` lists those candidates. `stale_ref` says to run `snap` or `find` again. `no live browser` says to run `start --url=` `--browser=`. |

`--format=lines` prints that same envelope as lines (`v=1 ok=...`, one `state` line, then each item, then `next` and `trunc`). The default stays JSON. A lines view is smaller than the JSON object. A token of letters, digits, and `_./:@+-` is bare. Anything else, including a newline or a non-ASCII character, is a JSON string (`\n`, `\uXXXX`).

## Persistent controller

`controller-start` starts one JVM for the project. The handle is `.pickleball/agent-controller.json` (`pid`, `port`, `token`). Later CLI verbs are one JSON line to that process and one JSON line back, so a warm verb does not start a new JVM. `controller-stop` asks that process to exit and deletes the handle. `controller-status` prints `running=true` or `running=false`. `controller-ping` returns the envelope without running a verb. A verb with no controller runs in-process and does not wait. The classpath is `classpath.cache` or the launching program's classes, not a wrapper classpath that lacks `PkbMain`. Alive means `ProcessHandle` plus a loopback connect, including on Windows. `PKB_NO_AGENT_HOP=1` stays in-process. The live worker bridge and MCP still run the same verbs. The controller does not replace them. The log is `.pickleball/agent-controller.log`.

`call <tool>` is the shell path to those same tools when no IDE MCP client is registered. `--args-file`, `--args-b64`, or stdin JSON become the verb flags. `workbench_agent_command` uses `op`. Names such as `click`, `type`, `snapshot`, `ui_poll`, and `ui_catalog` map onto `act`, `snap`, `ui-poll`, and `ui-catalog`. A name with no shell verb is `unavailable`. Compact MCP tools `workbench_snap`, `workbench_find`, `workbench_act`, `workbench_form_fill`, `workbench_watch`, `workbench_chat_turn`, `workbench_execute_steps`, `workbench_ui_verify`, and `workbench_capture_steps` take `fields` and `budget` and return short ids. `workbench_chat_wait` timeout is a number or a string from 0 to 120. `workbench_start` browser defaults to chrome. `workbench_history_query` op defaults to query. `workbench_request_control` agentName defaults to agent.

`start` (alias `live-start`) is one turnkey browser: `--url` or `--url-key`, `--browser`, `--headed`, `--hold`, `--panel`, and `--size`. The reply envelope carries session, browser, and frame. `chat-turn` sends, then waits for human, answer, or click. The person's message is listed once. The client waits past the verb timeout. A worker that is still up reports `timeout`, not `live worker unreachable`. `act --pick` finds and acts in one snapshot and reads back visible, enabled, and covered after a 500 ms settle. `ui-verify` reports visible, rect, and overlaps for every placement. `execute-steps --file` runs each verb on the same path as a direct command. Page verbs post to the live worker when it is up. `doctor` runs in this process and its lines stay on that step. `stopped` is true only with `--stop-on-fail` (sentence `steps stopped`). A failure without that flag finishes the file and says `steps failed`. The envelope `state.frame` is the last step frame. `watch --until` polls a ref until the condition. `mutation` and `change` include same-origin iframe documents and attached child frames. `snap --within` accepts a ref, short id, backend id, or element id. `--depth` is the levels under that node. `--group=type` headers use the tag. `--priority=on` reorders and marks `priority=`. `chat_wait` defaults to human messages and still advances the one cursor past filtered agent lines. `doctor` adds leaseLeft, orphans, frame, and placed. `chrome=present` only while the recorded Chrome pid is alive. `lease=open` when `leaseLeft` is 0. `live-stop` deletes the consumer session, so the next `doctor` does not keep a stale `session=` or `chrome=present`. `ui-poll` reports `browser_lost` once; later envelopes say `browser` `down` while that Chrome pid is gone. `fixture:` pages are data URLs. Chrome lookup checks PATH, then the usual install directories.

## Short ids

A hit keeps its long `ref:` (document version and backend node id). It also gets a short session id such as `s1.h42`. The same backend node keeps that short id when the document version changes. `ref --id=s1.h42` returns the current full `ref:`. Default lines prefer that short id. A compact line publishes `ref:d<hash>:<backend>` when the literal ref would be longer than 40 characters, including a file URL, so `[ref=]` stays and `act` can use it. A `data:` page uses that same short form. Desktop versions stay `ref:desktop:N:backend`. `act`, `find`, `snap`, `form-fill`, `highlight`, `border`, `magnifier`, `spotlight`, `label`, and `ui-apply` accept the short id in the target. `form-fill` also accepts the visible label. The id is stale only under the existing `stale_ref` rules (the node is gone, its role or name no longer matches, or that document's URL or loader changed). Frame ids in replies are the CDP frame id `frame --list` prints for that document, including an out-of-process frame the parent tree omitted. An XPath or a blank frame is `top`.

## Snapshot

`snap` is compact by default. One tree is read. Interactable rows are grouped under `# role` headers in first-seen order. A line is `- role "name" [ref=ref:<docVersion>:<handle>] id=<short-id> visible=<bool> enabled=<bool> interactive=<bool> frame=<id>`. When the row has a frame id, that `frame=` is the frame, including the main frame when the node carries that id. After `frame --enter`, a row that had no frame, or only the main frame, uses the entered frame's CDP id. A nested hit keeps its own frame id. The reply field is `items` (those lines). It does not also send `lines` or `hits` for those rows. `ref` is the first interactable ref. A later `act`, `explain`, `wait`, or `ui` op reuses that ref. `snap --within=<ref>` keeps that node's subtree. `--depth=<n>` stops that many levels under the root (`--depth=1` is the root's children only). A blank depth is the whole subtree. `--format=lines` renders the envelope as lines. `--fields` returns only the named keys. `--where` and `--limit` narrow the rows. `--budget` limits the JSON bytes of the whole envelope. A value that is not a bare token is a JSON string, so a newline or a non-ASCII name round-trips.

The reply stops at 200 lines or 16 KB. `truncated:true` names `full`, a file under `.pickleball/agent-full/` (`snap-<runId>.txt`) that holds every line. `mode=full` always writes that file. A snap that fits does not set `full`. `mode=diff` on `snap` compares the stored picture. On the browser the picture is the title plus each `role name`, and `diff` is `previous -> current`, or one `added` entry when nothing was stored yet. On the desktop the picture is the compact lines with no ref, so a version bump is not a change. An equal desktop picture is an empty `diff`. The first desktop diff, with nothing stored, returns those current lines.

A browser ref stays valid across unrelated DOM changes and pkb attribute writes. `act` and `explain` answer `error: stale_ref` with `fix: run snap (or find) again for a fresh ref` when that node is detached or replaced, when its role or name no longer matches, or when that frame's URL or loader changed. A desktop ref is stale when its `desktop:<sequence>` is not the session's current sequence. `wait` accepts the same ref (`--target=<ref>` or `--ref`) and polls that node for `visible`, `hidden`, `enabled`, `detached`, or `text=`. Those words are not a page-wide text search. A missing node succeeds only for `detached`. Any other condition on a browser ref waits until the timeout, then exits 1 with `error: timeout`.

`act` and `wait` with `--snap=diff` add `snap`. That object has `title` (`before -> after`) when a title was read, `docVersion` (`before -> after`), and `added`, `removed`, and `updated` lines. A line is `- role "text" [ref=...]`, plus `value="..."` on an input, textarea, or select and `checked=true|false` on a checkbox or radio. `changed` is true only when one of those lists is non-empty, or the title changed, or the URL changed. The URL is the `docVersion` text before its last colon, so a mutation-count bump alone is not a change. The counter lives in the `pkb-surface` world. A desktop diff compares the tree: a fixture re-read with no tree change is `changed:false` even when `docVersion` moves from `desktop:0` to `desktop:1`. A compact desktop snap stores that baseline. The diff is included on a timeout, on a quiet click, and on a click that could not land.

`--snap=auto` on `act` or `wait` writes one pre/post compact snapshot and returns its id as `snapshot`. The file is `.pickleball/agent-full/<id>.txt`. It starts with `## before`, the compact lines from before the call, then `## after` and the compact lines from after the call. The reply does not include those lines. The file is written when the call reached the action or the wait, including a timeout, a quiet click, a refusal, and a desktop target. A `not found` reply has no `snapshot`.

## MCP command registry

MCP is the public agent entry. `domengine mcp` and the Workbench MCP server each expose a registry of parameterized commands: `query`, `click`, `type`, `snapshot`, `observe`, `launch`, and `surfaces`. The domengine server also keeps `domengine`, which forwards an argv list to the CLI. `query`, `click`, `type`, and `observe` build that same argv and call `DomEngineMain`. `snapshot` on the engine calls `dev.domengine.snapshot.CompositeSnapshots.offline`, `.browser`, or `.desktop` and returns that JSON unchanged (`schema` `pickleball.composite-snapshot`, `version` 1). `offline` is the producer. `browser` and `desktop` answer with that producer's error (`isError`) until those producers are implemented. The Workbench command calls `dev.domengine.mcp.SnapshotDispatch.render(JsonNode)` by that exact method. When that class is absent it calls `SnapshotProducers.page` only if a static page method can take String, Map, or JsonNode arguments. Otherwise its body is a schema-shaped placeholder whose `warnings` say the producers are absent. `launch` on the engine server does not start a browser; the Workbench `launch` command forwards to `AgentControl`. `surfaces` lists the page-surface operations and, on Workbench, forwards an `op` to `AgentControl`. The Workbench `surfaces` schema describes every flag it forwards: `op`, `text`, `handle`, `id`, `html` (a local page file path, not markup), `x`, `y`, `width`, `height`, `geometry`, `where`, `number`, `zoom`, `dim`, `direction`, `from`, `to`, `color`, `style`, `preset`, `target`, and `pane`. Numeric flags accept a number or a string.

Other entries stay. The CLI, `POST /v1/agent/command`, and `workbench_agent_command` are internal forwarders to the same `AgentControl` path. They are not a second public catalogue. A group adds a command by registering an `McpCommand` (domengine) or an `McpCommandContributor` (Workbench). It does not edit the server classes. `DOMENGINE_LOG=mcp` logs each command at INFO. That log is off unless the entity is named, and the file is date-stamped and size-capped by `EngineLog`.

## Dynamic execution and Mapping

`DynamicControl` executes Cucumber/Pickleball steps against the currently active Pickleball test context. Detached failures are returned as structured `FAILED` results instead of automatically failing the paused scenario, allowing controller tooling to inspect a failed hypothesis and try another action.

`MappingControl` provides retry-friendly access to the live `ParsingMap` / `NodeMap` structures, caller-defined Mapping contexts, scoped overrides, snapshots, and resolution explanation. Live mutations are deliberate and are not automatically rolled back.

The control API returns `SUCCESS`, `FAILED`, or `UNAVAILABLE` for exploratory operations. Calls without a required live Pickleball context return `UNAVAILABLE`. `DynamicControl.executeStep` does not require that context. With no Cucumber scenario on the thread it runs the step on the native engine. Glue is `NativeDynamicSteps.useGlue` or the `pkb_engine_glue` class list. A live or paused scenario keeps the existing detached execution, including the failure restore. The control bridge uses that native call only when no scenario lane is active. A live lane is unchanged. Step creation, mapping interception, browser evidence, and service calls still return `UNAVAILABLE` without a live scenario.

## Semantic hooks

`ControlRuntime` exposes synchronous semantic hooks across scenario, step, phrase, Mapping, DOM, browser, driver, and service-call boundaries. Handlers may observe, pause by blocking, or use supported skip/value interception semantics. With no handler installed, original Pickleball behavior is retained.

`BEFORE_FIXED_WAIT` and `AFTER_FIXED_WAIT` fire only when a framework fixed wait is about to run. A skip decision suppresses that wait. A literal `save` and a nested `RUN_STEP` do not take the 300 ms browser-settle sleep, even when a session is already open, so they do not emit `BEFORE_FIXED_WAIT`. A click, type, or other page action that still waits does.

The bridge coordinator is an additive observer and does not replace the application's normal control handler.

## Consumer-side Control Bridge

Pickleball bundles a loopback-only Control Bridge server/coordinator used by Workbench to operate against a live consumer scenario. The bridge is not enabled during normal consumer execution unless its session environment is present.

Canonical environment variables are:

```text
PKB_CONTROL_BRIDGE_SESSION_DIR
PKB_CONTROL_BRIDGE_SESSION_ID
PKB_CONTROL_BRIDGE_TOKEN
PKB_CONTROL_BRIDGE_PAUSE_FIRST_SCENARIO
```

For backward compatibility, Pickleball may accept the former `PKB_STUDIO_BRIDGE_*` names as deprecated input aliases. They are not canonical configuration and do not require the removed Studio application.

Each participating consumer JVM binds to `127.0.0.1` on an operating-system-assigned port and writes a runtime descriptor into the session directory. Requests require the session bearer token and responses are marked `Cache-Control: no-store`.

The descriptor advertises the current and minimum-compatible protocol versions, capabilities, PID, Pickleball implementation version, and runtime code source. Workbench rejects incompatible capabilities/versions, a same-process worker, a runtime origin outside the synchronized consumer classpath, version drift, or a worker classpath containing the controller. It never falls back to executing a Workbench-bundled runtime.

The bridge keeps live operations on the real scenario thread through `ControlBridgeCoordinator`. This preserves access to thread-local Cucumber/Pickleball state, glue, browser, services, mappings, and other scenario resources.

Bridge capabilities include:

- runtime/status and active-scenario discovery;
- bounded semantic events;
- finite-lease pause/resume;
- retry-friendly detached step execution;
- read-only step resolution (`/v1/steps/resolve`, capability `resolve_step`) to consumer glue, Pickleball dynamic/framework steps, Step Overrides, or unmatched text;
- Mapping get/put/resolve/snapshot/restore;
- browser page/screenshot evidence;
- Pickleball-native element inspection;
- existing Pickleball service-call execution/evidence;
- semantic breakpoint management;
- scenario-scoped Step Override management.

Workbench owns the controller-side protocol client. MCP and Swing access these capabilities through `WorkbenchServices` / `WorkbenchController`; they do not connect to the bridge independently or implement a second runtime. Workbench imports only `tools.dscode.control.protocol.*`; bridge server/coordinator/bootstrap and conversion to runtime objects remain worker-side.

## Scenario targeting and finite pauses

A consumer runtime may observe more than one scenario thread. Controller calls may target a scenario id discovered from the bridge. A wrong or stale id returns `UNAVAILABLE`; the bridge does not guess.

Pauses and breakpoint pauses use finite leases. Expiry resumes execution automatically. Workbench renews the pause it owns while its persistent interactive worker remains active and resumes before clean shutdown.

## Semantic event evidence

The bridge retains bounded immutable semantic hook metadata rather than arbitrary consumer object graphs. Event reads are read-only and do not require the scenario-thread command queue, so reading evidence cannot consume a hook or block a paused scenario.

## Browser and service investigation

`ElementControl.inspect(...)` resolves a Pickleball category through the active `ExecutionDictionary`, or forwards one engine query string when `query` is set. That string is the composite selector: `css=`, `xpath=`, `text=`, `image=`, `near=`, `below=`, `above=`, `left-of=`, `right-of=`, `>>` stages, and AND/OR/NOT. Workbench, MCP, and the control bridge only forward it. There is no second locator language. Gherkin stays phrase sugar via `SelectorTranslator`. Inspection requires an existing scenario-owned browser and returns `UNAVAILABLE` rather than creating one. A controller query with no `exposure` is `human`: displayed, non-zero size, and inside the visual viewport. `lower` is opt-in on that one query, not a session setting, and every returned node carries reason codes plus a sentence. An action with no exposure is `human` and refuses a node a person could not click. `lower` still acts and keeps the sentence, which starts with `acted on node <handle>;`. A binary that does not list `exposure` or `limit` omits that flag and does not invent a result. `left-of`, `right-of`, `above`, `near`, and `below` are visual distance on that same query, using the geometry view. A binary that does not list `geometry` or the engine name logs `rel fallback` and invents no box. Gherkin `after` and `before` stay document order (`following::` / `preceding::`). `--explain` returns rank and score on that same query. `image=` with promote binds a DOM node when the engine can. Otherwise the hit is `visualOnly` and is not a DOM node. A query plus an optional limit returns handles. A later act sends one of those handles as its selector. Offline HTML is a labelled source read and does not run the engine query. Category+text and Gherkin do not send `exposure`.

`look=` is computed style on that same query string: `look=color=red` or `look=opacity>0.5,background-color=#fff`. A comma is AND and a pipe is OR inside the stage. `contrast` is the contrast of `color` against the painted `background-color`. It is not a screenshot match. There is no engine named `attribute`. A step may add `with look color equaling red` or `with look opacity greater than 0.5` after the existing `with id attribute` / `with id noattribute` clause. That clause becomes the `look=` stage and the live find applies it. `with id attribute` and `with id noattribute` still filter. `pkb_composite=off` fails that step instead of ignoring look. The older attribute phrases are unchanged.

`ServiceCallControl.execute(selector)` runs the same reusable service-call component selected by normal `CALL:` semantics. Existing Pickleball discovery, Mapping, request/configuration processing, REST/SOAP execution, response mapping, and failure behavior remain authoritative.

## Semantic breakpoints

Semantic breakpoints are temporary filters over existing `ControlHook` boundaries. They may filter by scenario, hook, hook signature, current step text, and current phrase text. They use the same finite pause lane as ordinary control pauses and disappear with the consumer runtime.

They are semantic Pickleball interception points, not arbitrary Java source breakpoints.

## Step Overrides

The consumer worker also owns scenario-scoped Step Overrides. Workbench can compile/register REGEX/REPLACE rules through the bridge; matching and execution occur before ordinary Cucumber glue fallback. When no override matches, normal Cucumber matching remains authoritative. Removing or clearing an override restores ordinary fallback without restarting the worker.

Worker-side compilation requires `javax.tools.JavaCompiler`. Workbench sends a Java source template containing `{{CLASS_NAME}}`; the worker owns generated naming, compilation, classloading, matching, captures, replacement, and cleanup.

## Architecture boundary

The control API and bridge intentionally remain independent of MCP, Spring, GUI frameworks, generic project IDE behavior, and build orchestration. Pickleball owns live execution semantics. Workbench is the external controller/adaptation layer and its artifact contains no Pickleball core, behavioral control API, Cucumber, Selenium, or service runtime. The only shared code is the dependency-neutral wire protocol.

Two tabs on one host:port keep two sessions, selected by the page target. Focusing that driver and tab selects that session. The result is labeled `style_modified` plus a sentence.

Visual components (label, border, arrow, numbered step badge, magnifier, spotlight, and overlay width and height) share this controller. The contract and the baseline gaps are in the in-repo roadmap `3.0.0-visual-components-roadmap.md` (under `docs/roadmaps`, not exported). `highlight` accepts `--x`, `--y`, `--width`, and `--height` and ignores them. `rememberGeometry` stores only a point. Each placement records its kind. An `un*` verb whose kind does not match the placement its `--id` names exits 2 with `id <id> is a <kind>, not a <kind>; use <verb> --id=<id>` and removes nothing. The page path reads the kind from the page's place record or the focused live page's id store, the popup path from the ledger row's `data-pkb-kind`, and the native path from the rectangle that `show` drew in this process. A placement with no recorded kind (an older ledger row, or a native rectangle from another process) is removed as before.

`overlay` places a surface from the remembered Geometry view (`visual_viewport_relative`) for a resolved handle, or from caller-supplied Geometry JSON. Caller `x`/`y` is used only when that geometry is absent and no handle was supplied. An unresolved handle is rejected even if `x`/`y` were provided. There is no default box. The resolved box is used for the first paint and is what the result fields `x`, `y`, `width`, and `height` report; on a live page the runtime then follows the element itself with `getBoundingClientRect` (see Live tracking). `--width` and `--height` are stored. A resolved element box (visual-viewport width and height, or the same width and height from a native `--query`) is the box on the page path and the native path. Stored width and height are used only when that box is absent. An `--html` / `--page` file keeps the fixed overlay style; a live page restyles the callout (see Live tracking). `label` places that text at the resolved box or at `--x`/`--y`. `border` draws a standalone box (default `3px solid #0a7a32`, or `--color` / `--style`; `--width` and `--height` stay geometry). `arrow` draws from `--from` and `--to` remembered points, or from a target plus `--direction` (`up`, `down`, `left`, `right`). `step-badge --number` is a visual badge only and does not edit Gherkin. `magnifier` is a circular frame (`--zoom` from 1 to 8, default 2); a live page clones the resolved node into that frame and copies its computed color, font, and size. A blank copy, or a native rectangle, says `target not captured`. `spotlight` dims the page with a cutout (`--dim` from 0 to 1, default 0.55). Each kind is removed by its `un*` verb, by `html-cleanup`, by undo, and at scenario end. Native draws the same rectangle and stores the caption; it does not paint the HTML callout, the arrow shaft, the magnified clone, or the desktop dim. Step badge and magnifier `--text` is escaped, not markup. A live magnifier copy drops `id`, `name`, `for`, `form`, `tabindex`, inline `on*` handlers, and scripts, and is `inert` and `aria-hidden`. A native `un*` with no `--id` or `--handle` hides `native-<kind>`, the id its show used. Scenario end hides every native rectangle (highlight, overlay, and each visual kind). Logging entities are `label`, `border`, `arrow`, `step`, `magnifier`, and `spotlight`, for both placement and the `un*` removal. `highlight` still ignores `--x`, `--y`, `--width`, and `--height`. Clicks and form changes are polled across every managed tab, not only the driver's current document, and written to the `overlay` chat channel. `html-write`, `html-replace`, and `html-insert` accept structural HTML. A small parser strips script elements, iframe `srcdoc`, encoded and slash-separated `on*` handlers, `javascript:` URLs even when whitespace, entities, or leading C0 controls sit inside the scheme, and active nested documents (`data:text/html`, `data:application/xhtml+xml`, `data:image/svg+xml`, `data:text/xml`, `data:application/xml`). Normal structural tags stay, including an unquoted URL that contains `/`. That is not a tag allowlist. Injected surface ids are allocated under the same exclusive file lock as the placement metadata. An explicit `--html` / `--page` file keeps its own counter. A live id is taken from the destination page after that handle's owner and tab are selected, not from the globally focused page. That page shares one counter across run ledgers (debugger address, that tab's own page target, and tab), so two fresh runs do not both receive `pkb-1`, and a write aimed at a page that already has `pkb-1` does not mint another `pkb-1` there. `Target.getTargetInfo` is read while the destination tab is selected. When the current Selenium handle cannot be read, that tab is selected and confirmed before the read, or a target already remembered for that same tab is reused. A blank target does not start a new counter. The active window's target is not paired with a different Selenium handle, and it is never stored under that other tab, including two tabs of one browser. A ledger that already contains `pkb-N` and has no `next` advances past those ids. Two processes writing the same file still cannot take the same id. Every injected element, including descendants, carries `data-pkb-agent=agent_injected` and a sentence. Agents still see those nodes. Replace keeps an undo snapshot beside the file, not inside the document. `html-remove` and `html-cleanup` restore it. Removal logs the snippet sha256 and a short summary from the placement file (`page.html.place.json` for an explicit page, or `.pickleball/runs/<run-id>/agent/placements.json` for a live command), so a later process can still recover them. The Workbench-native overlay shows the guidance text and the provenance sentence from the same command object. It is removed on `overlay-remove`, `html-remove`, `html-cleanup`, `stop`, `worker-stop`, `close-window`, headless play completion (including a failed step), GUI playback pause, stop, and natural completion, scenario cleanup, and live-session close. In-page surfaces are cleaned when the scenario ends.

Live tracking. On a live page each `overlay`, `label`, `border`, `arrow`, `step-badge`, `magnifier`, and `spotlight` placed on a target is handed to the page runtime (`pkb-runtime.js`, `window.__pkbUi`), which runs once per document in the `pkb-surface` isolated world (CDP or BiDi) and, on a Selenium-only session, in the page itself, installed only for a placement that follows a target. The runtime listens for scroll in the capture phase (so every nested scroll container counts), window and `visualViewport` resize and scroll, a `ResizeObserver` on the target and its scrollable ancestors, and a `MutationObserver` on the document; it repositions once per animation frame, reading every rect before writing. It moves a placement with the CSS `translate` property, so the inline `left` and `top` keep the resolved box. A target that is replaced (for example re-rendered by the page) is found again by id, handle mark, name, CSS path, or tag and text; when it cannot be found the placement is hidden and a `lost` event is queued for `overlay-poll`. A target partly scrolled out of its container clips the ring and border with `clip-path: inset()`, and a target fully out hides the placement. The overlay callout now sits beside its target (right, left, below, then above, whichever fits; `--at=top|bottom|left|right` picks the first try) with an outline ring on the target, so the target stays visible and clickable. `--at=over` keeps the old covering placement, translucent and click-through except for its own links, buttons, and fields. A label sits above the target's top edge, a step badge to its left, and a magnifier beside it; the magnified copy is refreshed when the target changes. Rings, borders, spotlights, labels, badges, and arrows never take pointer events, and the spotlight hole passes clicks, unless `block:true` (or `--block=true`) is set, which intercepts pointer events over the target. Rings live in a shadow root on a `<pkb-layer data-pkb-layer>` element shown with `popover="manual"` so they stay above a modal `<dialog>`. Styles come from constructable stylesheets (`adoptedStyleSheets`), so they apply under a strict page CSP, and follow `prefers-color-scheme` (`--theme=light|dark` forces one) and `prefers-reduced-motion`. The layer is not marked `data-pkb-agent` and is removed when the last tracked placement is removed or cleaned up.

Guided steps. `guide --steps=<json array>|@file.json [--id=g1] [--scroll=true]` shows numbered steps on a live page: each step is `{"t":"<target>","say":"<instruction>","do":"click|input|select|check|any"}` (optional `capture`, `sensitive`, `n`), and `t` is an id (a digit-leading id is found bare, as `#id`, or as `[id="..."]`), `h:<handle>`, a CSS selector, `text:<words>`, `role:<role>[name=<name>]`, or `x:<xpath>`. A step without `t` or `say`, or with another `do`, exits 2. Every step gets a ring on its target and a numbered badge outside it (left of the target, else above, else below; inside the corner only when all three are cut off by the viewport), so a badge never covers a field (current pulses, done is checked, the rest wait) and the current one gets a tip with its instruction; the panel's Steps tab lists them. A step completes when the person does its action on its target: a click, a change, or typing that has paused for 0.7 s (one keystroke does not skip ahead; Enter or leaving the field also completes an input step once it has text, and the value is the whole entry). The current step is refused (exit 1, the guide closes, no empty card) when its target cannot be found. Later missing steps are flagged and not drawn. While the panel stays on Steps, Chat shows an unread count for a new agent message. Each completed step queues `{type:step, g, s, done:true, how, filled}` for `overlay-poll`, and the last step also queues `{type:guide, done:true}`. A typed value is added only when the step has `capture:true` and its field is not sensitive; a password field, an `autocomplete` of a password, card (`cc-`), or one-time code, or `sensitive:true` never reports its value, and an overlay field of those kinds is stored as `filled=true` without its value. `guide-next`, `guide-back`, and `guide-done` move or close a guide by `--id`. `ask --say=<question> [--choices=Yes,No] [--handle=<target>] [--sensitive=true] [--id=q1]` shows a small question card (beside the target when given); the answer is queued as `{type:answer, id, choice, value}` for only the clicked label (`filled:true` with no value for a sensitive question), and the card shows that choice before it closes. `ask` with choices covers yes/no confirmation; the existing `confirm` verb is unchanged.

Page state. After each `overlay`, visual placement or removal, `panel-open`/`panel-close`, `guide` verb, and each `overlay-poll` or `chat-poll`, the runtime's snapshot of what is shown (placements with their target locators, guides with the current step, the panel's position, size, tab and fold) is saved in the run's `ui-state.json` and registered again as a `pkb-surface` preload (CDP `Page.addScriptToEvaluateOnNewDocument` with `worldName`, which needs the Page domain enabled; BiDi `script.addPreloadScript` with `sandbox`). A reload or back/forward navigation replays it once the document is ready, and the runtime checks the URL twice a second so an SPA `pushState`/`popstate` route change withdraws or restores it. `--scope=page` (default: same origin, path and query), `--scope=origin`, or `--scope=run` sets where it applies; `--ttl=<seconds>` expires it. Leaving the scope shows nothing there and the saved state is kept, so coming back restores it. The snapshot holds no value a person typed. A step completed by the person is saved at the next agent read (`overlay-poll`, `chat-poll`). `html-cleanup` and scenario end remove the state and the preload. One state is kept per run. `pkb_ui_page_state=session` (see configuration) also keeps a copy in the tab's `sessionStorage` for a Selenium-only session.

Page UI batch. `ui-catalog [--component=<name>]` lists the page UI components (`overlay`, `label`, `border`, `arrow`, `step-badge`, `magnifier`, `spotlight`, `panel`, `panel-close`, `guide`, `guide-next`, `guide-back`, `guide-done`, `ask`, `chat`, `remove`, `clear`) with each option's type and default, a one-line example op, and the undo verb; the whole catalog is under 6 KB. `ui-apply --ops=<json array>|@file.json [--verbose=true] [--scope=] [--ttl=]` validates every op against the catalog first (an unknown component or option, or a missing required field, exits 2 and runs nothing), then runs them in order through the same verbs and saves the page state once. An op is `{"c":"<component>","t":"<target>",…options}`; `t` is a remembered handle (or `h:<handle>`), or an id, CSS selector, `text:<words>`, `role:<role>[name=<name>]`, or `x:<xpath>` that the page runtime finds and marks with a handle. The reply is compact: `{"ok":…,"ops":[{"i":1,"c":"label","ok":true,"id":"pkb-2"},{"i":2,"c":"label","miss":"#missing"}]}`; `--verbose=true` adds each verb's full reply. It exits 1 when any op missed or failed. `ui-poll [--after=<n>] [--chat-after=<id>] [--wait=<seconds, up to 25>]` merges overlay events (step, guide, answer, click, input, lost) and human chat into one reply `{"events":[…],"chat":[…],"next":n,"chatNext":id}` without the label fields, returning as soon as either has something. MCP: `ui`, `ui_poll`, `ui_catalog`.

Agent loop for service calls: observe the buffer, filter by URL or time, then `capture-scenario`. `capture-steps` writes the click and answer rows as `{op,args}` for `execute-steps --file`; an empty capture is count 0 and `no steps captured`. The feature file is existing service-call component syntax (`MAP "REQUEST"`, `EXECUTE SERVICE CALL`, Examples). No new Gherkin phrase.

Logs use `pkb_composite_log` entities `observe`, `launch`, `window`, `chat`, `highlight`, `overlay`, `html`, `label`, `border`, `arrow`, `step`, `magnifier`, `spotlight`, and `capture`. They are off unless named, date-stamped, and size-capped.
