## Decisions (rows 6–11 and 13)

### Row 6 — Control Engine naming
- **Decision:** the engine is called the **Control Engine** in docs, CLI help and capability output. It is one engine for browsers and for Windows, macOS and Linux desktops.
- **No renames:** the Java package `dev.domengine`, the module `:dom-engine`, the `domengine` launcher, `EngineInfo.NAME` (`domengine`) and `COMPAT_COMMAND` (`composite`) stay. They are wire and launcher identities that adapters, tests and consumers read. Renaming them breaks callers and changes no behaviour.
- **Capabilities** add `"display_name": "Control Engine"`.
- **Help:** the first `helpText()` line names the Control Engine.
- **Phases:** 5 (capabilities and help), 7 (docs).

### Row 7 — Layered architecture
- **Three layers:**
  1. **Syntax:** `dev.domengine.query` (`Expressions`, `RelationTerm`, `Query`, `Engines`, `Look`, `HtmlTree`) and the Gherkin phrase model (`ElementPhrase`).
  2. **Dictionaries:** `SelectorTranslator`, `CompositeSelector`, `EngineQuery`, `CombinedBy`, `XPathDefinitions` and `ExecutionDictionary` turn categories and phrases into combined selectors.
  3. **Protocol adapters:** G1's `tools.dscode.browser` package, `DomCompositeAdapter`/`ElementOperations`, and the engine's `cdp`/`session`/`action`/desktop backends.
- **Enforcement:** two boundary tests (Phase 5) fail the build if the syntax or dictionary layer imports a protocol type.
- **`LookFind`:** it reads page source through WebDriver, so it is classified as an adapter-side bridge, not dictionary layer. It is documented as such and stays behaviourally unchanged.
- **Package javadoc:** `dom-engine/src/main/java/dev/domengine/query/package-info.java`.
- **Phases:** 5 (tests and javadoc), 7 (docs).

### Row 8 — Unified Boolean query
- **Confirmed implemented** in `Expressions`: NOT > AND > OR, parentheses, `>>` lowest outside parentheses, mixed AND/OR needs parentheses. `dev.domengine.BooleanQueryTest` already covers this.
- **Gap found:** operators are case-insensitive (`isOpAt` 230-231), while `EngineQuery.seleniumFallback` (82-91) only knows capitals.
- **Fix:**
  - Capital `AND` / `OR` / `NOT` are the canonical form in docs, help, `Expressions.render` and the translator's output.
  - Lowercase operator words keep working, so no existing query breaks. Each lowercase operator logs one `WARN expr lowercase operator '<op>' read as <OP>; write capitals` per run and operator.
  - `EngineQuery.seleniumFallback` uses the same operator detection as the engine: case-insensitive, word-bounded, and aware of relation forms.
- **Phase:** 5 (`BooleanConfirmTest`, `EngineQueryFallbackTest`).

### Row 9 — XPath is one clause type; the combined form comes first; XPath is the fallback
**Engine:**
- `xpath=` is already a stage usable inside AND/OR/NOT/`>>`. Phase 2 proves it with tests on top of engine-defects Phase 3 (`document.evaluate`).
- When a query body carries **both** a pipeline and an `xpath`, the engine runs the pipeline (combined form) first. Only when it matches 0 nodes does it run the XPath once from the same root.
- On fallback the result carries `"fallback": "xpath"`, `--explain` adds a fallback stage, and the engine logs one `WARN query xpath fallback <xpath>` per distinct XPath per process.

**Translator:**
- `SelectorTranslator.phrase` emits the combined form first. All target clauses go in **one AND group** (`(role=button AND text="Save")`), which also fixes the verified `role=button >> text="Save"` descendant-only miss. Context clauses go in one AND group.
- When a phrase carries an XPath **and** a category or text: `pipeline` = combined form and `xpath` = the XPath as the fallback.
- When it carries only an XPath (a pure XPath definition): `xpath` only, plus the deprecation WARN.
- CSS joins the target group as a `css=` clause. Pure CSS stays a `css` pass-through and is not deprecated.

**Dictionary:**
- `ExecutionDictionary` categories gain combined clauses: `CategorySpec.combined(String clause)`. Built-ins mirror `SelectorTranslator.ROLES` and are proven by fixture parity.
- `public Optional<String> combinedFor(String category, ValueWrapper value, Op op)`.
- `CategoryResolution` gains a `String combined` component. The 5-argument constructor is kept and delegates with `combined = null`.
- The resolution reaches the engine as a `CombinedBy` (new `By` subclass). It carries the combined form and the XPath, and its Selenium `findElements` delegates to `By.xpath(xpath)`, so `pkb_composite=off` is byte-for-byte unchanged.
- **Deprecation:** a custom category defined only by XPath still works and logs one WARN per run and definition through `CompositeLog.fallbackOnce("xpath-definition:<category>", …)`, wrapped by the new `XPathDefinitions`.

**Phase:** 2.

### Row 10 — Universal syntax
- **Decision:** one syntax for browsers and desktops. Desktop sessions already run `Query.run` through `DesktopTree`; G2 proves it and reports the differences.
- **Capabilities** gain:
  - a `syntax` block: operators, grouping, pipeline, relations, negative relations, weights and clause types;
  - a `platforms` block computed from code (not prose): browser verbs (`PageActions.VERBS`), desktop verbs (`DesktopTree.VERBS`), desktop backends, browser-only flags and stages (`pierce`, `frame=`, `shadow=`, `eval`, `observe`, `submit`), and `unsupported` entries with a reason.
- **Implementable desktop verb gaps** (scroll, key, dblclick, contextclick, drag, hover) live in G3-owned backend files (`WindowsUia`, `MacAccessibility`, `AtSpi`, `DesktopTree`). G2 records each one as a **cross-group request** in the roadmap with the exact API (UIA pattern, AX action, AT-SPI action or interface) and reports it to the coordinator. G2 never edits those files.
- **Phase:** 5 (`CrossPlatformQueryTest`, `ControlEngineCapabilitiesTest`).

### Row 11 — Relative locators
- **Confirmed:** `near`, `below`, `above`, `left-of`, `right-of` (+ aliases `left`, `right`) exist. Their current semantics stay unchanged; `VisualRelativeTest` pins them.
- **Add `inside`** (geometry): the candidate box lies fully inside an anchor box in the active space.
- **Add `after` and `before`** (document order, the same as Gherkin `XPathyAssembly.afterOf`/`beforeOf`):
  - `after` = XPath `following::`: follows an anchor and is not its descendant.
  - `before` = XPath `preceding::`: precedes an anchor and is not its ancestor.
- **New filter form** `<relation>(<anchor sub-query>)` for all eight relations. The anchor is a full sub-query evaluated from the root, and the relation filters the current scope's elements. Example: `(role=button AND text="Save") AND after(role=region AND text~="Billing")`.
- **Translator context words:** `after`/`before`/`above`/`below`/`left of`/`right of`/`near`/`inside` become filter forms. This replaces the verified no-op below stage and the silently dropped contexts. `in`/`from`/`for` stay `<context> >> <target>`.
- **Phase:** 3.

### Row 13 — Negative relations
- **Syntax:** `not-<relation>=<css>` (stage form), `not-<relation>(<anchor>)` (filter form), and `NOT <relation>=…` / `NOT <relation>(…)`.
- **`NOT` rule:** `NOT` wrapping exactly one relation term becomes that negated term. `NOT` over anything else keeps today's complement.
- **In the engine query,** a negated term is a hard filter.
- **For scoring,** every term (positive and negated) is passed as `List<RelationTerm>` to G3's `AffinityScorer` through G2's single hook. G3 subtracts `0.50 × weight` for a satisfied negated term and adds `0.10 × weight` for a satisfied positive one.
- **Weights:** an optional `@<weight>` suffix on the relation name (`near@2(...)`, `not-inside@0.5(...)`), default 1.0.
- **Phases:** 1 (contract and parser scaffolding), 4 (engine behaviour), 6 (hook).

### Contract 4 — G2 creates `dev.domengine.query.RelationTerm` (Phase 1, W1)
File `dom-engine/src/main/java/dev/domengine/query/RelationTerm.java`, public:

```java
package dev.domengine.query;

public record RelationTerm(Relation relation, boolean negated, String anchor, double weight) {
    public static final double DEFAULT_WEIGHT = 1.0;

    public enum Relation {
        NEAR("near"), ABOVE("above"), BELOW("below"), LEFT_OF("left-of"), RIGHT_OF("right-of"),
        INSIDE("inside"), AFTER("after"), BEFORE("before");
        public String engine();                                // "near", "left-of", ...
        public boolean geometric();                            // false only for AFTER and BEFORE (document order)
        public static java.util.Optional<Relation> fromEngine(String name); // case-insensitive; "left" -> LEFT_OF, "right" -> RIGHT_OF; "not-" prefix NOT accepted here
    }

    public RelationTerm { /* relation != null (NPE "relation"); anchor null -> ""; anchor trimmed;
                             weight finite and >= 0, else IllegalArgumentException("invalid relation weight: <w>") */ }
    public RelationTerm(Relation relation, boolean negated, String anchor) { this(relation, negated, anchor, DEFAULT_WEIGHT); }

    public RelationTerm negate();                              // same term, negated flipped
    public String canonical();                                 // filter form: [not-]<engine>[@<weight>](<anchor>); "@w" omitted when weight == 1.0
    public static RelationTerm parse(String term);             // ONE term in filter form, incl. "NOT near(...)"; throws CdpException("invalid relation: <text>")
    public static java.util.List<RelationTerm> parseAll(String query); // every term in a full pipeline/expression, in source order
}
```

- **`relation`:** exactly `NEAR, ABOVE, BELOW, LEFT_OF, RIGHT_OF, INSIDE, AFTER, BEFORE`, in that order.
- **`negated`:** `true` for `not-<relation>…` and for `NOT` wrapping exactly one relation term.
- **`anchor`:** the anchor sub-query as canonical query text (`Expressions.render` output: capital operators, single spaces, ` >> `).
  - Filter form: the text inside the parentheses.
  - Stage form (`A >> near=css`): the rendered pipeline before the stage, including outer `>>` prefixes when the stage sits in a group on the right of a `>>`.
  - `""` means the document root (a stage-form relation that is the first stage).
  - It is a `String`, not an AST, because `Expressions.Expr` is package-private and G3 consumes the term from `dev.domengine.premap` / `dev.domengine.affinity`.
- **`weight`:** `double`, default `1.0`, from the `@<weight>` suffix. The engine filter ignores it; G3 scoring uses it.
- **Round trip:** `parse(t.canonical()).equals(t)` for every term.
- **G3's side:**
  - G3 never creates `RelationTerm`.
  - G3's `AffinityScorer.score(DomNode label, DomNode interactable, List<RelationTerm> relations)` treats the **label as the anchor node** and the **interactable as the candidate**.
  - Until this record is on origin, G3 builds against a `List<?>` overload and records `waiting on G2 Phase 1`.
