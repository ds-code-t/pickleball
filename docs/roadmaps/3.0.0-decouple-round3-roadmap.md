# Pickleball 3.0.0 Round 3 — Engine Decoupling Roadmap

**Branch:** `3.0.0` only. Never commit, push, or merge to `master`, `2.2.0`, or `2.1.19`. No force-push. No release, tag, or publishing.

**Start SHA:** `c6ee31c80386ae9cf62a393fd48f6466bb94bffc` (tip after Dalton round 2)

**Version:** stays `3.0.0`

All phases are mandatory and must be completed in full. Nothing is optional or deferred.

Between phases Build runs **only targeted tests** tied to the changed code.

The full regression runs **once** at the end of all phases:
```
./gradlew :test :pickleball-control-protocol:test :pickleball-control-api:test :pickleball-workbench:test --rerun-tasks
consumer_sim
scripts/verify_agent_contract.py
scripts/sync_consumer_guidance.py
Windows CI green
```

Existing Gherkin/step syntax and behavior must not change. Do not weaken, delete, or skip existing tests. Cucumber step annotations must stay single string literals (no constants or `+` concatenation). With the native engine off (and for all existing Cucumber runs through the adapter), behavior must remain identical to today.

One shared code path. Simplicity over cleverness. Analyze regression risk per phase.

## CLI-first and logging checklist

Every capability reachable from the CLI. Every non-CLI surface (Workbench GUI, MCP, Gradle tasks, any fast-run launcher) only forwards to the CLI.

New code has toggleable, per-entity (or per-capability), date-stamped, size-capped logging.

Checklist items that must be true at the end of every phase that touches a capability:
- [ ] CLI command exists and is documented
- [ ] Workbench action forwards to CLI (or shared CLI service)
- [ ] MCP tool forwards to CLI
- [ ] Gradle task (if any) forwards to CLI
- [ ] Logging is toggleable, per-entity, date-stamped, and size-capped
- [ ] Existing tests still pass; no regressions in adapter / native-off mode

## Phase 1 — Neutral model

**Functionality**
- Introduce Pickleball-owned types in `tools.dscode.engine`: Step (text, keyword, argument, metadata, source location), Scenario (name, tags, ordered steps, examples/maps), Feature/container, Result/Status.
- Bidirectional converters to/from Cucumber types (used only at the adapter edge later).
- No runtime behavior change.

**Docs**
- New `docs/maintainer/3.0.0-engine-design.md` (linked from Dalton design).
- Append pointer in AGENTS.md and release-notes.md.

**Tests**
- Converter round-trip unit tests.
- Existing suite remains green.

**Regression risk:** Low.

## Phase 2 — Step registry and native matching

**Functionality**
- Pickleball step registry discovers glue (built-in coredefinitions + consumer glue) by reading the same annotations (`@Given`/`@When`/`@Then`/etc.). Annotation values remain single string literals, byte-identical.
- Native matching: regex + Cucumber Expression semantics where used today, parameter types, DataTable/DocString types, step overrides, ambiguity rules. Must produce the same match as Cucumber for every existing step.
- Native dispatch stubs for `,` dynamic steps, IF:/ELSE:/ELSE-IF:, RUN/SCENARIO:/COMPONENT:, SERVICE CALL/CALL:.

**Docs**
- Update engine design and consumer docs as needed.

**Tests**
- Match parity tests against Cucumber for all existing steps.
- Targeted unit/integration only.

**Regression risk:** Medium (matching parity is critical).

## Phase 3 — ExecutionContext

**Functionality**
- Explicit ExecutionContext (scenario, step stack/tree, map scopes, phase, failures, timing, browser/service resources) passed to ParsingMap, NodeMap, MappingProcessor, Phrase/PhraseData/ParsedLine/ElementMatch, data and assertion code.
- Replace GlobalState/CurrentScenarioState ThreadLocal reach-ins.
- Thin GlobalState/CurrentScenarioState compatibility shim delegating to the current context so consumer code and existing aspects keep working.

**Docs**
- Update design.

**Tests**
- Context isolation and delegation tests.
- Existing behavior identical.

**Regression risk:** Medium.

## Phase 4 — Neutral Table and DocText

**Functionality**
- Neutral Table and DocText types used by mappings/dataelements/dataoperations/assertions.
- Converters to/from Cucumber DataTable/DocString only at the adapter edge.
- Consumer glue methods that take DataTable/DocString keep working.

**Docs**
- Update.

**Tests**
- Conversion and existing data operation tests.

**Regression risk:** Low to medium.

## Phase 5 — ScenarioSource SPI and native parse

**Functionality**
- ScenarioSource SPI with implementations: feature files on disk, Dalton DB rows, in-memory Gherkin text, and a generated/runtime-written list of step strings (no file, no URI required).
- Pickleball's own Gherkin-to-model parsing: reuse the gherkin parser library as a pure parser, then convert. Replicate aspect-augmented compile behavior (PickleCompilerAugment, ForceNullValuesRowAspect, EncodingParserLineSwap) so existing features are byte-identical (examples, backgrounds, rules, tags, DataTables, DocStrings, encoding).

**Docs**
- Update.

**Tests**
- Parse parity on repo features.
- Sources for memory and DB.

**Regression risk:** Medium.

## Phase 6 — Native modular resolution

**Functionality**
- Native modular resolution: scenario/component/service-call lookup by tags, names, feature name, example rows, step markers, order/limit — same semantics as CucumberScanUtil/ExampleRowFilter — against any ScenarioSource, including in-memory and DB.

**Docs**
- Update.

**Tests**
- Resolution parity tests.
- In-memory and DB cases.

**Regression risk:** Medium.

## Phase 7 — Public entry points (CLI-first)

**Functionality**
- `PickleballEngine.run(ScenarioSource | String text | List<String> steps, options/ctx)` and `runStep(text, arg, ctx)`.
- Reachable from the CLI (CLI-first). Used by `dalton run`, Workbench, MCP, and Gradle tasks (all forwarding to the CLI).
- Dalton runs natively from DB rows without the Cucumber parser.

**Docs**
- CLI help and consumer docs.

**Tests**
- Native tests that run steps from a string, from a Dalton DB row, and from a runtime-generated list, with nothing on disk.

**Regression risk:** Medium.

## Phase 8 — DynamicControl without live Cucumber

**Functionality**
- DynamicControl.executeStep and the control bridge work without a live Cucumber scenario (create an ExecutionContext on demand; keep current behavior when a scenario is live/paused).

**Docs**
- Update dynamic-control-api.md.

**Tests**
- DynamicControl without a live Cucumber scenario.

**Regression risk:** Low.

## Phase 9 — Cucumber/JUnit adapter

**Functionality**
- Existing suites (JUnit Platform, Cucumber CLI, consumer Maven/Gradle projects) keep running with identical results, reports, diagnostics, and events.
- Toggle `pkb_engine` (system property / env / properties, same precedence as `pkb_dalton`). Adapter path always available.

**Docs**
- Update.

**Tests**
- Adapter path green; dual-run setup.

**Regression risk:** Low (adapter preserves current).

## Phase 10 — Runtime-written steps

**Functionality**
- First-class text-from-anywhere: steps can be inserted/written during execution by any step, phrase, mapping, or controller without Gherkin pickles.
- Reporting/diagnostics/lineage record them like file-sourced steps.

**Docs**
- Update.

**Tests**
- Tests for runtime-written steps inserted mid-execution.

**Regression risk:** Medium.

## Phase 11 — Dual-run parity harness

**Functionality**
- Dual-run harness: the same features produce the same results (status per scenario/step, step text after templating, returned values, map contents, diagnostics events) via the Cucumber adapter and via the native engine, over the repo's feature suites and maven-consumer-project.
- Fix any divergences.

**Docs**
- Update.

**Tests**
- Harness itself; full dual-run green.

**Regression risk:** Must be zero after fixes.

## Phase 12 — Switch default and full regression

**Functionality**
- Native Pickleball engine becomes the 3.0.0 default (only after dual-run harness is green).
- Retire cucumber-core aspects only where the native engine replaces them; keep everything still needed by the adapter path.
- Adapter path remains available and supported.
- Complete logging checklist, docs, AGENTS.md pointers, release notes.

**Docs**
- Append to AGENTS.md and release-notes.md (append-only). Run sync scripts. feature-map free of maintainer links.

**Tests**
- **Full regression once** (Gradle multi-module with `--rerun-tasks`, consumer_sim, agent contract scripts, Windows CI).

**Regression risk:** Must be zero. All previous phases green and full suite green.
