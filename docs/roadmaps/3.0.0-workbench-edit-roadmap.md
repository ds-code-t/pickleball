# Pickleball 3.0.0 Workbench Full-Edit + DOM Engine Core Roadmap

**Status:** Mandatory multi-phase plan. All phases required. Implementation on branch `3.0.0` only. Do not push to master, `2.2.0`, `2.1.19`, or `3.0.0-query-visual`.

**Design:** `docs/maintainer/3.0.0-workbench-edit-design.md`

**Start SHA:** `5b69bcb4` ("Update design: add live native desktop…"), or a newer tip of `origin/3.0.0` if it has moved. Version stays `3.0.0`. Breaking-change list is empty.

### Process rules (Dan, 2026-11-12, still in force)
- Between phases, only light, targeted, quick tests tied to the changed code. If those tests fail or stall, leave them failing, note them on the push, and move on. Do not weaken, skip, or delete existing tests.
- Do NOT run the full multi-module regression. Dan forbade it until he explicitly says to. There is no full-regression phase in this roadmap. Targeted tests only, including at the end. Hold `validate --all`.
- Push each green (or noted) phase to branch `3.0.0` only. No force-push, no release, never master / `2.2.0` / `2.1.19` / `3.0.0-query-visual`.
- Do not truncate or rewrite `AGENTS.md`; append only. Fetch before every push. If a push would truncate it, stop and restore with a normal (non-force) push.
- Do not change existing Gherkin syntax. Cucumber step annotations stay single string literals (no constants or `+` concatenation), values identical.
- Do not touch open engine PRs #2 and #3 on `ds-code-t/dom-composite`, and do not push to that repo.
- CLI-first and logging checklist on every phase (see the bottom of this file and of the design). Workbench, MCP, and Gradle only forward. No business logic or SQLite/core calls in Workbench.
- All ten phases are mandatory. Nothing is optional. Finish every phase unless blocked.
- Existing Workbench collaboration features (chat, overlays, highlights, launch templates, HTML-on-the-fly) are already on `3.0.0`. Leave them alone unless a small non-breaking hook is required for the new editors.

## Phase 1 — Shared CLI-first edit model

**Functionality:**
- One CLI family with stable `--json` output, used by every later edit surface. Introduce or extend:
  - `dalton category list|show|put|remove`
  - `dalton feature scenario-add|scenario-modify|scenario-delete|step-add|step-modify|step-delete` (these parse, apply the change, regenerate valid Gherkin, then call the existing `feature put`, or write the file when Dalton is off; do not land the body of those helpers until Phases 3–5 if that is cleaner, but the command names and JSON shape must be stable here)
  - `dalton file put|delete`
  - `dalton glue list|show|put|remove`
- Workbench gets a unified Editor that reuses the DaltonPanel list+text pattern. Every action goes through `DaltonCliForwarder` only. Deletes are confirmed. Validation runs before write. Conflicts use the existing `db_edited` / untracked / extract behavior; do not silently clobber unflagged or file-side changes. Dalton-off remains a pure file path.
- Logging checklist applies to this shared path.

**Docs:** This roadmap. Append a short pointer in `AGENTS.md` if not already present (append only).

**Tests:** Targeted tests for the CLI JSON contract, forwarder-only Workbench path, delete confirmation, validation-before-write, and conflict/`db_edited` behavior. Existing Dalton and Workbench tests stay green.

**CLI-first:** Every new capability is on the CLI. Workbench only forwards.

## Phase 2 — Element categories

**Functionality:**
- Project categories are editable YAML entities under `dalton-entities/ElementCategory/`, loaded after built-ins.
- Built-ins are immutable (overlay only). Reserved names are blocked. `Loading` and `ALL_CONTEXTS` are special-cased as in `docs/custom-element-definitions.md` and `docs/reserved-element-names.md`.
- Add, delete, and modify work from the CLI and from the Workbench Editor. Changes take effect on the next run.
- Dalton-on uses the entity put path; Dalton-off writes the file.

**Docs:** Update this roadmap and, if needed, `docs/custom-element-definitions.md` (additive).

**Tests:** Targeted tests for add/modify/remove, built-in immutability, reserved-name rejection, overlay-after-built-ins, Dalton-on vs Dalton-off, and next-run effect. Do not weaken existing category tests.

**CLI-first:** `dalton category *` is the only write path. Workbench forwards.

## Phase 3 — Scenarios and scenario steps

**Functionality:**
- Structured helpers parse the feature, apply the add/modify/delete of a scenario or a step, regenerate valid Gherkin (normalize indent on edited regions, preserve comments where possible, always valid), then call the existing `feature put` or write the file when Dalton is off.
- No direct structured row updates of scenario/step text in the Dalton DB (Round 2 Gherkin byte-stability still holds: regenerated feature text goes through `feature put`, which sets `db_edited` when Dalton is on).
- Conflicts are preserved. Existing Gherkin syntax is unchanged.
- CLI: `dalton feature scenario-add|scenario-modify|scenario-delete|step-add|step-modify|step-delete`. Workbench Editor forwards those.

**Docs:** This roadmap. Whitespace and comment policy: a scenario or step edit splices only that region. Comments outside the region stay byte-for-byte, including a leading `#` comment. Comments inside the edited scenario or step stay, re-indented with the step indent. The edited region uses the indent of the first existing scenario (steps two spaces deeper), or two and four spaces when the feature has none. A body line that is not already a step, comment, table, docstring, or examples header is prefixed with `Given`, or with `--keyword`. A body that contains `Feature:` is rejected; the whole file stays `dalton feature put`. The regenerated text is parsed before the write. Dalton on stores it with `db_edited` and leaves the file. Dalton off writes the file and does not open the database.

**Tests:** Targeted tests for add/modify/delete of scenarios and steps, valid regenerated Gherkin, `db_edited` when Dalton is on, file write when Dalton is off, conflict behavior, and unchanged existing feature-put semantics. Do not weaken existing feature tests.

**CLI-first:** All scenario/step edits go through the CLI. Workbench forwards.

## Phase 4 — General configuration and data files

**Functionality:**
- Extend `dalton file put|delete` for general configuration and data files: YAML Selenium configs, `dalton.properties`, run vars, JSON/YAML/CSV test data, and the files behind ConfigTabModel / RunVarOverridePanel.
- Secret redaction uses the existing path: do not display or write secrets in the clear if a redaction path exists.
- Dalton-on goes through the DB edit path where applicable; Dalton-off is file-only. Conflicts and `db_edited` are preserved.

**Docs:** This roadmap. Secret fields (`password`, `token`, `api_key`, `secret-fields=` names, and the other Dalton secret names) must be a reference (`<name>` or `~MASK`). Cleartext is rejected before the write. `dalton file show` and `dalton files show` redact a cleartext value that is already on disk. References stay visible. Dalton-on still sets `db_edited` and leaves the file. Dalton-off writes the file and does not open the database.

**Tests:** Targeted tests for put/delete of config and data files, secret redaction, Dalton-on vs Dalton-off, and conflict behavior. Existing config tests stay green.

**CLI-first:** `dalton file *` is the write path. Workbench forwards.

## Phase 5 — Java and JS/TS step-definition functions

**Functionality:**
- Java glue: `dalton glue list|show|put|remove` validates Cucumber annotations as single string literals (values identical; no constants or `+` concatenation), then triggers the existing fingerprint / warm-worker recompile and restart. A compile failure leaves the prior worker running.
- JS/TS: there is no full JS/TS step-definition runtime. Implement a source-only first slice under `glue/js/` and document that native-engine binding is future work. Do not break Java glue.
- Workbench Editor forwards to the same CLI.

**Docs:** This roadmap. Document the JS/TS source-only slice and the future-binding note.

**Tests:** Targeted tests for Java glue put/remove, annotation-literal validation (reject non-literal annotations), worker restart on successful change, prior worker retained on compile failure, and the JS/TS source-only slice (files can be added and listed; no false claim of a runtime). Existing glue and annotation tests stay green.

**CLI-first:** `dalton glue *` is the write path. Workbench forwards.

## Phase 7 — Java DOM engine packaging (classes and sources in the pickleball jar)

**Functionality:**
- The published `pickleball` jar today contains the old Rust Java client (`dev.domcomposite.*`) and zero `dev.domengine` classes, even though `shadowJar` has `from(project(':dom-engine').sourceSets.main.output)` (added in `ed5f7d7c`). The sources jar also lacks `dev.domengine` sources. The published POM does not depend on a `dom-engine` artifact. That `from(...)` did not actually embed the classes.
- Fix the packaging so `dev.domengine` classes are inside the consumer `pickleball` jar, and `dev.domengine` sources are inside the sources jar. If `from(...)` cannot be made to work, replace it (for example with `zipTree` of the module jar, consistent with other embeds).
- Add a verification test that fails if `dev.domengine` classes are missing from the pickleball jar or if `dev.domengine` sources are missing from the sources jar.
- Do not publish a separate `dom-engine` Maven artifact as a substitute. Do not release. Do not merge engine PRs #2/#3 or push to `ds-code-t/dom-composite`.
- Selenium fallback (`pkb_composite=off`) stays working.

**Docs:** This roadmap and an additive note in the design if the chosen packaging method differs from `from(...)`.

**Tests:** The new verification test must fail when classes or sources are missing, and pass on a correctly packaged jar. Targeted packaging tests only. Existing engine unit tests stay green.

**CLI-first:** Packaging is not a new CLI verb. Logging checklist still applies to any new packaging/verify task.

## Phase 8 — Engine as core of Pickleball (default path, CLI-first surfaces)

**Functionality:**
- The Java DOM engine is the default path inside Pickleball, treated as a core part of Pickleball, not an optional side module. The engine API may stay general-purpose (`dev.domengine`) so it is not tangled with Pickleball types, but it is delivered and reached as part of Pickleball.
- Workbench and other surfaces reach it the same way they reach other core capabilities: CLI-first, thin forwarders only. No business logic in Workbench.
- Selenium fallback (`pkb_composite=off`) remains a working alternative.

**Docs:** This roadmap. Additive Workbench / engine docs pointers.

**Tests:** Targeted tests that Workbench (and any other in-scope surface) reaches the engine only through the CLI forwarder, and that the default path is the Java engine. Selenium fallback tests stay green.

**CLI-first:** Mandatory. MCP and Gradle, if they gain a new engine action, only forward.

## Phase 9 — Live native desktop access (Windows UIA, macOS AX, Linux AT-SPI)

**Functionality:**
- `dev.domengine.desktop.DesktopTree` is fixture-only today: `attach` requires a fixture file; `click` and `type` only mutate or report on an in-memory recorded tree; they do not drive real OS windows. The locked Java design called for native AT where feasible; Phase 3 of the Java rewrite scored done with only the fixture backend. That gap is mandatory in this phase.
- Implement live native desktop access on the machine where the engine runs:
  - Windows: UI Automation (UIA)
  - macOS: Accessibility (AX)
  - Linux: AT-SPI
- Keep the fixture backend for tests and offline / headless CI. Live attach must work without a fixture against real desktop windows.
- Live `click`, `type`, and the other existing desktop verbs (`list`, `attach`, `walk`, `query`, `resolve`, `close`, and any already-shipped desktop verb) must actually act on the real UI, not only return ok on a recorded tree.
- CLI-first: every live desktop capability is on the `domengine` CLI; GUI/MCP only forward. Logging checklist applies.
- Package this as part of the pickleball jar, with the rest of the Java engine (same verification as Phase 7).
- Targeted tests for the live path where the OS allows, plus fixture tests so CI on a headless runner still proves the API. Live tests must fail clearly when the OS or permissions cannot support them, never silently no-op. Do not weaken existing fixture tests.
- The old Rust composite shipped native binaries for linux-x64, linux-aarch64, windows-x64, macos-aarch64, and macos-x64. Retain that platform coverage in the Java live path.

**Docs:** This roadmap. Document how live attach is selected versus the fixture backend, and the permission / focus failure behavior.

**Tests:** Fixture tests pass on headless CI. Live tests run where the OS allows and fail clearly otherwise. Existing desktop fixture tests (`ObserveParityTest.desktopFixtureQueryClickAndType` and any peers) stay green.

**CLI-first:** Live verbs are on the existing desktop CLI. No second CLI.

## Phase 10 — Consistent browser/desktop query and verb model

**Functionality:**
- One query language, one verb set, and one walk/attach/resolve model for the browser DOM and for live native desktop UI on Windows (UIA), macOS (AX), and Linux (AT-SPI).
- Functionality, syntax, and logic match as closely as the platforms allow. A step or CLI invocation that finds or acts on a browser element should look and behave the same way when the target is a desktop window or control, except where a real platform difference makes that impossible.
- Do not invent a second parallel API or a different selector dialect for desktop. Live paths and the browser path share the same CLI surface and the same core logic.
- Named platform exceptions must be written down and justified, not left implicit. Start with the exceptions already named in the design, and expand only if implementation discovers more:
  - Accessibility tree shapes differ (role names, hierarchy depth, bounds units). Map to the shared model; document unmappable attributes.
  - Input injection (click/type) may require elevated permissions or focus on some platforms; fail clearly rather than silently no-op.
  - Shadow/pierce and frame contexts are browser-only; desktop has no equivalent and must not invent one.
  - Image/OCR template matching may differ in precision; share the same CLI verb and document the backend difference.
- Final audit: Phases 1–10 complete; fixture path still works; Selenium fallback still works; Gherkin and annotation rules unchanged; engine classes and sources are in the pickleball jars; breaking-change list still empty.
- Update the scoreboard below.

**Docs:** This roadmap and an exceptions section in the design (append or fill the named list; do not rewrite the rest). Append-only for `AGENTS.md`. Refresh the agent index if new files appeared.

**Tests:** Targeted tests that the same query/verb/walk/attach/resolve forms work against a browser fixture or session and against a desktop fixture (and live, where the OS allows), with the named exceptions documented. No full regression.

**CLI-first / Logging:** Final review of the checklist for every phase.
