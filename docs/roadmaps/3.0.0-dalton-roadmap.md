# Pickleball 3.0.0 Dalton Roadmap

**Branch:** `3.0.0` only. Never commit, push, or merge to `master`, `2.2.0`, or `2.1.19`. No force-push. No release or publishing.

**Start SHA:** `de1f76f9`

**Current build.gradle version:** 2.2.0 (bumped to 3.0.0 in Phase 1).

All phases are mandatory and must be completed in full. Nothing is optional or deferred.

Between phases, Build runs **only targeted tests** tied to the changed code.

The full regression runs **once** at the end of all phases:
```
Gradle :test :pickleball-control-protocol:test :pickleball-control-api:test :pickleball-workbench:test --rerun-tasks
consumer_sim
scripts/verify_agent_contract.py
scripts/sync_consumer_guidance.py
Windows CI
```

Existing Gherkin/step syntax and behavior must not change. Do not weaken, delete, or skip existing tests. Cucumber step annotations must stay single string literals (no constants or `+` concatenation).

One shared code path. Simplicity over cleverness. Analyze regression risk per phase.

## CLI-first and Logging Checklist

Every Dalton capability must be reachable from the CLI. Every non-CLI surface (Workbench, MCP, Gradle tasks) only forwards to the CLI.

New code has toggleable, per-entity (or per-capability), date-stamped, size-capped logging.

Checklist items that must be true at the end of every phase that touches a capability:
- [ ] CLI command exists and is documented
- [ ] Workbench action forwards to CLI (or shared CLI service)
- [ ] MCP tool forwards to CLI
- [ ] Gradle task (if any) forwards to CLI
- [ ] Logging is toggleable, per-entity, date-stamped, and size-capped
- [ ] Existing tests still pass; no regressions in file-only mode

## Phase 1 — Foundation (version bump, schema, gitignore, basic CLI)

**Functionality**
- Bump `build.gradle` version to `3.0.0`.
- Introduce Dalton package structure and embedded SQLite connection (WAL, busy_timeout).
- Create schema version table and `files` table (path, content_hash, raw_content, mtime, source_type).
- Explicit `.gitignore` entry for `.pickleball/dalton/` (parent already ignored; make it obvious).
- Basic CLI skeleton: `pickleball dalton status` and `pickleball dalton hydrate --dry-run`.
- Pointers in `AGENTS.md` and a "3.0.0 in progress" entry in release notes.

**Docs**
- This design doc and roadmap already exist.
- Update `AGENTS.md` with Dalton pointers.
- Release-notes entry.

**Tests**
- Schema creation and migration.
- Content-hash computation.
- CLI status returns expected empty/missing DB message.
- Targeted unit tests only.

**Regression risk:** Low. Additive, default off, no change to existing execution path.

## Phase 2 — Hydrate-in

**Functionality**
- Full hydrate-in of feature files, configs, calls, components, resource maps, and templates.
- Incremental by content hash.
- CLI: `pickleball dalton hydrate [--path=...] [--force]`.
- Gradle task `daltonHydrate` that only forwards to the CLI.
- Auto-on-run only when Dalton is explicitly enabled; otherwise pure file path.
- Windows path and encoding correctness.

**Docs**
- Update configuration and resource-mapping docs with Dalton notes.
- CLI help text.

**Tests**
- Hydrate correctness against consumer features.
- Incremental skip of unchanged files.
- Windows path handling.
- Targeted tests only.

**Regression risk:** Low when disabled. Medium when enabled (must not alter file-only behavior).

## Phase 3 — Parsed model and execute-from-DB

**Functionality**
- Parse Gherkin into structured scenarios, steps, tags, data tables, and docstrings stored in the DB.
- Original raw content always retained.
- When Dalton is enabled, feature loading uses the hydrated DB (alternative FeaturePath / resource supplier) instead of direct files.
- Shared code path: existing loaders remain the default; Dalton supplies an alternative only when enabled.

**Docs**
- Document the execute-from-DB path and the opt-in flag.

**Tests**
- Parse round-trip identity for unchanged features.
- Execute a sample set of consumer scenarios from the DB.
- Targeted tests only.

**Regression risk:** Medium. Must prove file-only path is bit-identical when Dalton is off.

## Phase 4 — Entities and additive references

**Functionality**
- Entity store (type, id, version, payload, secret references only).
- Hydrate entities in and out to stable text files (one file per entity or per collection; project chooses commit vs gitignore).
- Additive reference syntax in mappings (exact syntax locked here; must not collide with existing `<config:>`, `<file:>`, etc.).
- Existing Gherkin and step definitions unchanged.

**Docs**
- Entity authoring guide.
- Reference syntax documentation.

**Tests**
- Entity CRUD and file round-trip.
- Secret-reference-only enforcement (no cleartext).
- Reference resolution in a scenario.
- Targeted tests only.

**Regression risk:** Low. Additive syntax only.

## Phase 5 — Hydrate-out and conflict detection

**Functionality**
- CLI `pickleball dalton extract` with conflict detection (both sides changed since last sync).
- Deterministic, byte-stable formatting. Prefer original raw bytes when no semantic edit occurred.
- Preserve comments, tags, docstrings, data tables, and ordering.
- Clear conflict diagnostics; `--force` required to overwrite.

**Docs**
- Conflict resolution guide.
- Formatting guarantees.

**Tests**
- Lossless round-trip for comments, tags, tables, ordering.
- Conflict cases (file-only change, DB-only change, both).
- Targeted tests only.

**Regression risk:** Medium. Formatter bugs could alter committed files; must be proven stable.

## Phase 6 — Run history, logging, and full integration

**Functionality**
- Store run logs and run history in the DB (integrate with or parallel to existing diagnostic reporting).
- Retention policies (date-stamped, size-capped).
- Workbench, MCP, and Gradle all forward exclusively to the CLI for Dalton operations.
- Toggleable, per-entity, date-stamped, size-capped logging for all new Dalton code.

**Docs**
- Logging configuration.
- Integration notes for Workbench and agents.

**Tests**
- Logging toggles and size caps.
- Forwarding from Workbench/MCP/Gradle.
- Run history retention.
- Targeted tests only.

**Regression risk:** Low to medium. Must not disturb existing diagnostic paths.

## Phase 7 — Polish and full regression

**Functionality**
- Final documentation pass.
- CHANGELOG / release-notes entry completed for 3.0.0.
- Any remaining edge cases (Windows, parallel runs, large feature sets).

**Docs**
- Complete all user-facing and maintainer docs.
- Update repository index / feature map if needed.

**Tests**
- **Full regression once** (Gradle multi-module tests with `--rerun-tasks`, consumer_sim, agent contract scripts, Windows CI).
- No targeted-only restriction in this phase.

**Regression risk:** Must be zero. All previous phases green and full suite green.

## Commit and Push Discipline

After each green phase, commit and push to `3.0.0`. Do not stop early. Do not skip phases. Do not mark anything optional or deferred.
