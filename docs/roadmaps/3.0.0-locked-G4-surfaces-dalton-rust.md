## Decisions

### B. Universal agent surface popup (owner addendum B)

**Decision.** The popup is a **runtime** feature in a new root package `tools.dscode.common.agentsurface`, not a Workbench class. Reason: agent ops already run in the Pickleball runtime (`AgentControl`), desktop scenarios run in the test JVM with or without a Workbench, and the Workbench may not contain Pickleball core (`verifyStrictControllerIsolation`). The Workbench reaches the popup only through the same agent ops it already forwards.

- **Window.** A Chromium-family browser started in app mode: `--app=http://127.0.0.1:<port>/?t=<token>`, `--user-data-dir=<run>/agent/popup/profile` (private profile, deleted on close), `--no-first-run --no-default-browser-check --disable-features=Translate --window-size=<w>,<h> --window-position=<x>,<y>`; `--headless=new` only when `pkb_agent_popup_headless=true` (tests and CI). Default size `420x640`, placed at the right edge of the primary screen (`pkb_agent_popup_size`, `pkb_agent_popup_position=right|left|<x>,<y>`).
- **Browser discovery** (`PopupBrowserLocator`, first hit wins, each probe logged under `browser`): property `pkb_agent_popup_browser`, env `PKB_AGENT_POPUP_BROWSER`, env `DOMENGINE_CHROME`; then per OS — **Windows:** `HKLM`/`HKCU` `SOFTWARE\Microsoft\Windows\CurrentVersion\App Paths\msedge.exe` then `chrome.exe` (read with `reg query`, 5 s timeout), then `%ProgramFiles%`, `%ProgramFiles(x86)%`, `%LocalAppData%` `\Microsoft\Edge\Application\msedge.exe`, `\Google\Chrome\Application\chrome.exe`, `\Chromium\Application\chrome.exe`; **macOS:** `/Applications` then `~/Applications` `Google Chrome.app`, `Microsoft Edge.app`, `Chromium.app`, `Brave Browser.app` (`Contents/MacOS/<name>`); **Linux:** PATH `google-chrome`, `google-chrome-stable`, `chromium`, `chromium-browser`, `microsoft-edge`, `microsoft-edge-stable`, `brave-browser`, then `/snap/bin/chromium`, `/var/lib/flatpak/exports/bin/org.chromium.Chromium`. Edge is first on Windows because every supported Windows has it.
- **Always on top where the OS allows** (`PopupOnTop`, `pkb_agent_popup_on_top=true` default): **Windows** — PowerShell `Add-Type` `SetWindowPos(hwnd, HWND_TOPMOST, …, SWP_NOMOVE|SWP_NOSIZE)` on the browser process's main window, found by PID (retry up to 5 s for the window to appear). **Linux X11** — `wmctrl -i -r <wid> -b add,above` with `<wid>` from `wmctrl -lp` by PID (or `xdotool search --pid`). **Linux Wayland without X** and **macOS** — no supported API for another process's window level; status records `alwaysOnTop.applied=false` with the reason, logs one WARN per run (`ontop-unavailable`), and on macOS the host raises the window (`osascript` "set frontmost of process whose unix id is <pid>") on every new agent message instead. This is the proved platform limit, not a deferral.
- **Channel: loopback HTTP + Server-Sent Events, owned by G4** (`PopupBridge`, JDK `com.sun.net.httpserver.HttpServer`, bound to `127.0.0.1`, ephemeral port). Not CDP: the popup is Pickleball's own page, G1's `ProtocolSelector.forDriver(WebDriver)` needs a WebDriver the popup does not have, and a remote-debugging port on the popup would expose a second debuggable browser to every local process. HTTP+SSE works with any Chromium, needs no debugging port, and survives short-lived CLI callers. A 128-bit random token (SecureRandom, hex) is required on every request (`?t=` or `X-Pkb-Popup-Token`), compared in constant time; the `Host` header must be `127.0.0.1:<port>`; anything else is 403. Every response sets `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`. Endpoints: `GET /` (shell), `GET /assets/<name>` (shell assets and G1 `SurfaceAssets`), `GET /events` (SSE, honours `Last-Event-ID`), `GET /poll?after=<seq>` (JSON fallback; first use logs WARN `sse-unavailable` once), `POST /chat` (human message → `ChatLog` channel `run`, source `human`), `POST /input` (click/form event → the same `overlay-events.jsonl` `overlay-poll` reads), `POST /rendered` (client ack: `seq`, `pane`, `handle`, `textSha256`), `GET /health`.
- **Host process and lifecycle** (`PopupHost`, `PopupHostMain`). One host per (project, run id), out of process so CLI one-shots, the bridge, and the run JVM all see the same window: `popup-open` spawns `java -cp <current classpath> tools.dscode.common.agentsurface.PopupHostMain --project=<p> --run-id=<id>` (pkb_agent_popup* properties forwarded, stdin closed, stdout/stderr to `popup/host.out`, size-capped) unless `popup/host.json` names a live PID whose `/health` answers, in which case it is reused (`reused=true`). `host.json` = `{pid, port, token, browser, browserPath, browserPid, ownerPid, ownerKind (run|cli|workbench), startedAt, headless, alwaysOnTop{applied,method,reason}}`, written atomically with a `FileChannel` lock (`host.lock`). The host exits and deletes `profile/` when: a `close` record is written (`popup-close`, or run end); the browser process exits (status `closed-by-user`; the next surface command or `popup-open` reopens it); `ownerKind=run` and the owner PID is gone (checked every 2 s); or `pkb_agent_popup_idle_minutes` (default 30) pass with no new record and no SSE client. Scenario end (`AgentSurfaceEnd.complete()`) writes a `cleanup` record that clears the Instructions, Diagram, and overlay panes (same meaning as in-page `html-cleanup`), keeps the chat pane, and does not close the window. The run JVM registers a shutdown hook that writes `close` for hosts it opened.
- **Ledger** (`PopupLedger`): `.pickleball/runs/<run-id>/agent/popup/surfaces.jsonl` (`seq`, `op`, `pane`, `handle`, `where`, `html` already neutralized and labeled, `codes`, `sentence`, `at`), `rendered.jsonl`, `host.json`, `popup.log`. Writers append through `AgentStore.appendCapped` semantics (via the bridge class below), so any process can write and the host tails the file (WatchService plus 250 ms poll). Chat is not copied: the host tails `ChatLog` for the run channel and pushes `event: chat`.
- **Same HTML surface code.** The popup shell (`agent-surface-popup.html/.css/.js` under `src/main/resources/tools/dscode/common/agentsurface/`) has three panes — Chat, Instructions, Diagram — and renders agent HTML with the **G1 `SurfaceAssets`** CSS/JS for the `overlay` and `html` kinds (contract 3), inside shadow roots. All agent HTML passes `PageSurfaces.neutralize` and `labelElements` with the same sentences before it is written to the ledger (via `PopupSurfaceBridge`, contract 9), so an identical command yields byte-identical labeled HTML in page and popup. Diagrams are neutralized HTML or inline SVG (`<svg>…`) in the Diagram pane; there is no third-party diagram library.
- **Same command set; routing.** No second command vocabulary. Existing ops gain `--target=auto|page|popup|native` (default `auto`) and, for `html-*`/`overlay`, `--pane=instructions|diagram` (default `instructions`). New ops: `popup-open [--on-top=true|false] [--headless=true|false]`, `popup-status`, `popup-close`. `AgentSurfaceRouter.route(project, runId, op, args, agentId)` decides: explicit `--target` wins; `pkb_agent_popup=off` → `page` (today's behaviour exactly); otherwise **desktop session** → `popup` for `chat-send` (mirror; the message is still stored once), `overlay`, `html-*`, `overlay-poll` (reads the same file), and `highlight`/`unhighlight` → `native`. A run is a desktop session when `PopupSurfaceBridge.hasBrowserPage(project, runId)` is false (no `WindowRegistry` handle and no managed driver for the run) or the run var `pkb_agent_session=desktop` is set. `pkb_agent_popup=always` (the "optionally for browsers" case) also opens the popup in browser sessions: chat is mirrored there, and `html-*`/`overlay` **without** a `--handle` go to the popup, while handle-anchored surfaces and `highlight` stay in the page because they point at page elements. `html-replace`/`html-insert`/`html-remove` by handle and `where=before|after|inside` have the same semantics in the popup shell's DOM as in the page.
- **Thin native highlight** (`NativeHighlightBox`, new in `pickleball-control-protocol`, `tools.dscode.control.protocol.surface`, JDK AWT only so both the runtime and the Workbench can use it). Four undecorated, always-on-top, 3 px `JWindow` strips (`#ff2d55`) around the target bounds — no translucency needed, click-through by construction, identical on all three OSes. Bounds come from `--x --y --width --height` (screen pixels) or `--query=<desktop query>` resolved through the existing desktop query path (engine CLI `desktop query --json`, which already reports bounds); HiDPI is corrected with `GraphicsConfiguration.getDefaultTransform()`. Headless → nothing drawn, result `drawn=false reason=headless`. The caption text for a native highlight goes to the popup Instructions pane, not into a native label.
- **Fallback when no Chromium is found or launch fails:** one WARN per run and reason (`no-chromium`, `launch-failed:<exit>`), `popup-status.fallback=workbench-panel`, chat stays in the Workbench Chat tab (`AgentChatPanel`), captions use the existing `WorkbenchNativeOverlay` label window, and in a run without a Workbench the surface op returns `ok=true, target=none, fallback=<reason>` with the stored chat/ledger rows intact so a later popup or the Workbench shows them.
- **`AgentChatPanel` and `WorkbenchNativeOverlay` afterwards.** `AgentChatPanel` stays the Workbench Chat tab and keeps its static forwarders (tests unchanged); it gains an "Open popup" button (`popup-open`) and a one-line status from `popup-status`, and it remains the fallback surface. `WorkbenchNativeOverlay` becomes the thin highlight: `place(command)` draws a `NativeHighlightBox` when the command carries bounds, shows the caption label window only when the result says the popup is not available (`popup=false`), and `caption`, `remove`, `onPlaybackFinished`, `removedForTests`, `resetForTests` keep their current behaviour (`AgentForwardTest` unchanged and green).
- **Logging** (`PopupLog`): off unless `pkb_agent_popup_log` is `true`, `all`, or a list of `lifecycle,browser,ontop,bridge,route,highlight,ledger`; `pkb_agent_popup_log_entity` limits lines to a run id or handle; ISO-8601 timestamp first; `.pickleball/runs/<run-id>/agent/popup/popup.log` capped by `pkb_agent_popup_log_max_bytes` (default 1048576, minimum 64). WARNs (`WARN: agent popup <reason>: <message>`) go to stderr once per run and reason regardless of the log flag, and into `popup-status.warnings`.
- **Registration.** CLI verbs and the bridge reach `AgentSurfaceRouter` through one guarded line at the top of `AgentControl.execute` (contract 8). MCP: G4 adds its own command classes to G1's `McpCommand` registry (contract 2): `agent_popup_open`, `agent_popup_status`, `agent_popup_close`, and the `target`/`pane` parameters on the existing surface commands' schemas through G4's own command class. Until G1's registry is on origin, the popup is reachable by CLI and `workbench_agent_command` (which already forwards any allowed op); the MCP sub-step records `waiting on G1 Phase 2`.

### Row 18. Dalton central by default

**Decision.** Dalton is on unless explicitly turned off. Files stay the Git source of truth; `.pickleball/dalton/dalton.db` stays the gitignored working copy.
- `DaltonConfig.enabled(project)`: explicit flag (`pkb_dalton` property, then `PKB_DALTON` env) wins; else `dalton.properties` `enabled=`/`pkb_dalton=` if present; else **true**. `falsy(raw)` (`false|no|off|0`) is the opt-out; an unrecognised value is an error at first use (`IllegalArgumentException` naming the key and the accepted values), not a silent default. New `DaltonConfig.source(project)` returns `property|env|file|default` for status and logs.
- **Packaging reversal (required by central):** `org.xerial:sqlite-jdbc:3.47.2.0` becomes a published **runtime** dependency of the Pickleball artifact (Gradle `runtimeOnly` in the published component; Maven POM scope `runtime`), still **not** shaded into the consumer shadow JAR. `verifySqliteNotPublished` is replaced by `verifySqlitePackaging`, which asserts the POM has exactly one `org.xerial:sqlite-jdbc` entry with scope `runtime` and version `3.47.2.0`, and that the shadow JAR has no `org/sqlite/` entry; the task keeps its place in the dependency chain (`dependsOn` at line ~634). The `dalton*` Gradle tasks keep their explicit classpath line. The Workbench stays `runtimeOnly` (its existing guard is unchanged).
- Missing driver while enabled (any source, including default): the existing loud failure stays (`MISSING_DRIVER`), and the message gains `Dalton is on by default; add org.xerial:sqlite-jdbc or set pkb_dalton=false to run file-only.` No silent file-only fallback.
- `dalton status` prints `enabled=true source=<source>`; `--json` adds `enabled` and `enabledSource`. The Workbench Dalton panel shows the same.
- Existing tests that pass `-Dpkb_dalton=true|false` or write `dalton.properties` keep their meaning unchanged.

**Row 18 completion (portable artifact).**
- **GitHub info.** Hydrate records Git provenance via the `git` CLI (5 s timeout each, run in the project dir): `git_commit` (`rev-parse HEAD`), `git_branch` (`rev-parse --abbrev-ref HEAD`), `git_remote` (`remote get-url origin`, with any `user:pass@`/token userinfo stripped), `github_repo` (`owner/name` when the remote host is `github.com`), `git_dirty` (`status --porcelain` non-empty). Stored as new `provenance` columns (schema version +1, `ALTER TABLE … ADD COLUMN` migration, old DBs upgrade in place). Each `files` row gains `git_blob` (Git blob SHA-1 computed in Java: `sha1("blob " + len + "\0" + bytes)`), so a row maps to a Git object and `dalton status` reports `git_changed=<n>` (rows whose `git_blob` differs from `git ls-files -s` for that path). No `git` binary or not a repository → fields empty, one WARN per run (`dalton git unavailable: <reason>`), hydrate still succeeds. Shown by `dalton status` and `--json` (`git.commit`, `git.branch`, `git.remote`, `git.githubRepo`, `git.dirty`, `git.changed`).
- **Binary references.** `binary-policy=hash-only` is implemented: a file that discovery classifies as binary (extension list, null byte, control-byte ratio) is stored as a reference row — `raw_content` zero-length, new column `binary_ref=1`, `content_hash` sha256 of the real bytes, `git_blob`, size column `byte_size`, `source_type=binary-ref`. Extract never writes a binary-ref row back; it verifies the file on disk still matches `content_hash` and reports `binary_ref_changed <path>` when it does not. `dalton status` counts `binaryRefs`. The default policy stays `skip` (existing discovery counts unchanged); `hash-only` is selectable in `dalton.properties` and `pkb_dalton_binary_policy`, and the docs stop saying it is unimplemented.
- **Logs / sync guards** already exist (`DaltonLog`, untracked-DB-edit and both-changed refusals) and are re-verified by the row-18 tests; new log capabilities `git` and `binary` are added to `pkb_dalton_log`.

### Row 19. Rust fully replaced by Java, no residuals

**Decision.** Remove every Rust selection path; keep the stdio client and an explicit engine path with a Java meaning.
- **Removed:** `pkb_composite_engine=rust`/`PKB_COMPOSITE_ENGINE` semantics, `JavaEngineLauncher.rustRequested`, `DirectControlProvider.HOME_ENV`/`COMPOSITE_HOME`, `rustHomes`, `resolveRustBinary`, the sibling `dom-composite` checkout lookup, `composite` on `PATH`, the classpath `dev/domcomposite/natives/<os-arch>/composite` lookup, `dev.domcomposite:composite-native:<v>:<classifier>` jar extraction in `CompositeBinaryLocator`, `src/main/resources/dev/domcomposite/natives/README.txt`, Rust text in `CompositeRuntime` (line 29, ~406), `CompositeMode`, `DomCompositeAdapter` (Rust-2.4.x-only capability tables such as `DESKTOP_VERBS_2_4_0` are deleted only where the Java engine probe already reports the same verbs; otherwise they are renamed to the Java engine's capability list), the `build.gradle` comment block, and Rust wording in comments across `dom-engine` and the control protocol.
- **`pkb_composite_engine` after removal:** unset → nothing. `java` → accepted, one WARN `pkb_composite_engine is no longer used; the Java control engine is the only engine`. Any other value (including `rust`) → `IllegalStateException` at engine start: `pkb_composite_engine=<v> is not supported in 3.0.0: the Java control engine is the only engine. Remove the setting; use pkb_composite_bin only to point at a domengine launcher.` Loud, never silently ignored.
- **Kept:** `pkb_composite_bin` / `pkb_runvars.pkb_composite_bin` / env `COMPOSITE_BIN` / env `pkb_composite_bin` (order unchanged from engine-defects Phase 1, including `COMPOSITE_BIN` working-directory-relative) as the explicit **Java engine launcher** path (the `domengine` start script from `:dom-engine:installDist`, or any binary that speaks the same stdio wire). `dev.domcomposite.*` (Client, Session, Argv, Json, exceptions) stays in that package and keeps its name: consumer glue can catch `dev.domcomposite.*Exception`, and renaming would break them for no behavioural gain; its javadoc says it is the stdio client for the Java control engine CLI.
- **Wire comments and fixtures:** comments that say "as in Rust" are rewritten to state the contract itself ("the wire contract is …"). The vendored conformance HTML/JSON under `dom-engine/src/test/resources/conformance` and `fixtures` stay as the engine's own conformance suite (they are executed by `ConformanceSuiteTest`/`LiveConformanceTest`); a `README.md` there says they are the control-engine wire contract. Their import provenance (dom-composite `d63887c`) is one line in `docs/release-notes.md`, nowhere else.
- **Tests:** `NoRustLeftTest` (new) fails on `(?i)\brust\b`, `COMPOSITE_HOME`, `composite-native`, `target/release/composite`, `domcomposite/natives`, `resolveRustBinary`, `rustRequested` in main sources/resources of every module, the build scripts, and the current-behaviour docs (list in Phase 7), with `docs/release-notes.md` and dated records (`docs/maintainer/**`, `docs/roadmaps/**`, `docs/audits/**`, `prompts/**`) excluded. Rust-path test cases are **converted, never deleted**: each keeps its method and gains an assertion of the new behaviour (see Phase 6 table), and the assertion count per class may not go down. `RustCliShapeTest` is renamed `CliWireShapeTest` with identical methods and assertions, and every reference (CI workflow, docs, index) is updated.
