# 2.1.18 Direct-control handoff

**Status:** Approved for implementation on branch `2.1.18`. Do not reopen the design.  
**Version:** stays `2.1.18`. Never commit to `master`. Master is merged at `35f84790`.  
**Philosophy:** Simplicity and elegance. One shared code path for session descriptors, CLI, pause/hold, and the optional provider. No duplicated config or run-var logic. No per-bug tweaks. Normal non-Workbench runs remain byte-for-byte unchanged because every new branch is gated on an explicit opt-in (absent config = zero behavior change). Pickleball stays the sole owner of browser lifecycle.

dom-composite 2.4.0 (main of https://github.com/ds-code-t/dom-composite at commit `d63887c`, private, not yet on any registry) is the optional direct-control provider for this version. All pickleball-specific glue stays inside pickleball. dom-composite remains a standalone, universal tool.

## Design

### Per-live-session descriptor

Every live Workbench session (headless isolate or GUI-driven) publishes a machine-readable **session descriptor**.

Fields (JSON, stable schema versioned as `session-descriptor.v1`):

- `sessionId`
- `runId`
- `workspacePath` (absolute)
- `browserType` (e.g. chrome, edge)
- `cdpDebuggerAddress` (the value of `goog:chromeOptions` `debuggerAddress` or the `se:cdp` capability when present; null if unavailable)
- `currentUrl` (or null)
- `windowHandles` (array)
- `state` (one of: `idle`, `running`, `paused`, `held`, `stopping`, `stopped`)
- `startedAt` / `updatedAt` (ISO-8601)
- `contractVersion` (`"1"`)

The descriptor is:

1. Written atomically to `.pickleball/runs/<runId>/session/descriptor.json` (and refreshed on meaningful state changes).
2. Reachable through the existing agent CLI surface (Workbench launcher / `WorkbenchSessionCommands` / `WorkbenchAgentCommands`):
   - `session list` — prints one line per live session (or `--json` for an array).
   - `session info <sessionId>` — prints the full descriptor; `--json` emits the raw object.
3. The GUI only displays what the CLI already prints. No second source of truth.

One shared writer in the live-session path (`WorkbenchLiveSession` / worker manager / control bridge) produces the file and the CLI response. No separate GUI-only path.

### Versioned handoff contract

Documented in:

- `docs/direct-control-handoff.md` (canonical)
- Packaged guidance copy under `META-INF/pickleball/guidance/` so `export-guidance` materializes it for consumers.

The contract states:

- How an external tool (specifically dom-composite 2.4.0) attaches: read the descriptor (file or CLI), open a composite session with the published `cdpDebuggerAddress` and join by the published `sessionId` (using the Java `Client.openSession` config fields `cdp` and `id`, or the equivalent CLI flags), and operate only while the session state allows it.
- Pickleball remains the owner of the browser process and WebDriver lifecycle. The external tool must **detach cleanly** (close its composite session / CDP connection, release any holds) before the session is stopped or the browser is closed. Detach must never close a pickleball-owned browser.
- Safety rule: no concurrent conflicting actions while a Gherkin step is running. An agent (or the external tool via a documented request) can request a **pause/hold** state. While `held` or `paused`, Workbench will not advance steps; the external tool may act. On release, normal step execution resumes. The hold is cooperative and visible in the descriptor.
- Versioning: the descriptor carries `contractVersion`. Future versions are additive or explicitly negotiated. 2.1.18 ships only version 1.
- Absent or blank direct-control configuration produces **zero** extra behavior.

### Optional pluggable direct-control provider (dom-composite 2.4.0)

An optional config key (workspace `runvars.properties` or a documented system property, default unset):

```text
pkb_direct_control_provider=composite
```

(or the full path to the `composite` binary). When set, Workbench may launch or connect to that provider, passing the path to the current `descriptor.json` (and the session id / CDP address), and logs the provider's stdout/stderr into the run's short log / session log. The provider is responsible for attaching, acting, and detaching according to the contract.

Agents obtain the most direct control possible by driving the live Workbench browser (and later desktop) through dom-composite's own CLI or MCP (`composite` commands, `serve --stdio`, HTTP `/v1`, or the Java/Python/JS bindings that forward to the CLI). This is in addition to, not instead of, existing Gherkin / Workbench session commands. The session descriptor and `session list` / `session info` are the join point.

- Off by default.
- Absent or blank key = no launch, no extra process, no log noise, no behavior change for any run.
- Because dom-composite 2.4.0 is not yet on a registry, the dependency is optional and detected at runtime. Builds and ordinary tests pass without it present. Tests that exercise the provider obtain it via a local install path:
  - Prefer `COMPOSITE_BIN` environment variable (path to the built `composite` binary).
  - Else look for `target/debug/composite` or `target/release/composite` relative to a documented checkout of the dom-composite repo.
  - The Java binding (`dev.domcomposite:client:2.4.0`) is not published; when a test needs the binding it is installed locally (`mvn install` from the binding tree) or the test uses the CLI path only.
  - If the binary or binding is absent, provider tests are skipped with a clear message; they never fail the suite.
- One shared launch / attach path used by both headless and GUI sessions. Normal non-Workbench `mvn test` / `gradlew test` never reads the key.
- All pickleball-specific glue (descriptor writing, CLI, pause/hold, config key, logging) lives in pickleball. dom-composite stays universal.

### Features needed from dom-composite (general, not pickleball-specific)

None required for the 2.1.18 contract. The existing `openSession` config already accepts `cdp` and `id`. Clean detach that does not close an externally owned browser is already the expected behavior of a CDP attach (the tool only disconnects). If a future need arises it will be requested separately; do not invent pickleball-only flags inside dom-composite.

### CLI-first and logging checklist

Every new surface follows the existing Workbench rules:

- Agents drive via the launcher CLI (`-Dexec.args=...`). The GUI is a view only.
- New verbs (`session list`, `session info`, optional provider launch / attach) are added to the same command parser and session command table.
- Short log (`.pickleball/agent-log`) receives start/stop and provider launch lines. Dense diagnostic logs stay unchanged.
- `record.json` gains an optional `sessionDescriptor` fingerprint or path only when a live session exists; normal runs are unaffected.
- Parallel 80 (drop to 12 on memory pressure). No failing tests. Never weaken assertions.

## Phases

Every phase is mandatory. Push after each phase. The phase number is in the commit message. Stay on branch `2.1.18` only.

### Phase 0 — Roadmap

This document. Push.

### Phase 1 — Session descriptor model and writer

Shared JDK-friendly descriptor record (protocol or launcher package) + atomic writer that lives next to the live session. Unit tests for field population, atomic replace, missing CDP (null), state transitions, and that a non-live run produces no file.

### Phase 2 — CLI surface

`session list` and `session info <id> [--json]` on the existing Workbench command line. Output matches the file byte-for-byte when both exist. Tests cover empty list, single session, `--json`, and unknown id.

### Phase 3 — Handoff contract docs and packaged guidance

Write `docs/direct-control-handoff.md` (including the exact attach sequence for dom-composite 2.4.0: read descriptor, `Client.openSession` or CLI with `cdp` + `id`, clean detach). Update `docs/pickleball-workbench.md`, `docs/consumer-agent-guide.md`, and the packaged guidance copies. `export-guidance` materializes the new doc. No code behavior change yet.

### Phase 4 — Optional provider (dom-composite)

Config key reader (one place, workspace-aware). Launch / attach helper that runs or connects to `composite` (via `COMPOSITE_BIN` or the documented local path) with the descriptor path / CDP address / session id, captures logs, and never starts if the key is absent. Tests: absent = no process; present (when binary available) = command invoked with correct args and clean detach that leaves the browser running; provider exit does not kill the browser; normal runs ignore the key. When the binary is missing the provider tests skip with a clear message.

### Phase 5 — Pause/hold safety

Cooperative `held` state requestable via existing session commands (or a new thin `session hold` / `session release`). Descriptor reflects it. Step execution is blocked while held. Tests prove a running step cannot advance under hold and that release resumes cleanly. External tools (including composite sessions) are documented to request the hold before acting.

### Phase 6 — End-to-end and release notes

Real isolate + GUI sessions publish a usable descriptor with a real CDP address when Chrome is used. Provider attach is exercised with a no-op or minimal composite query when the binary is available. Agents can drive the live browser through the composite CLI/MCP using the published descriptor. Release notes for 2.1.18. Feature-map and repository-index updated if new files appear.

### Phase 7 — Final verification

After the last code change: `./gradlew test` (and workbench/protocol checks) plus the consumer `@all` suite at parallel 80 (12 on memory trouble). Report real pass/fail counts. Push.
