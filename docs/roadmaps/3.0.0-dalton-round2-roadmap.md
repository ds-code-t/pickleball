All phases are mandatory and must be completed in full. Nothing is optional or deferred.

Between phases Build runs **only targeted tests** tied to the changed code.

The full regression runs **once** at the end of all phases:

Existing Gherkin/step syntax and behavior must not change. Do not weaken, delete, or skip existing tests. Cucumber step annotations must stay single string literals (no constants or `+` concatenation). Dalton-off behavior must remain byte-for-byte the current behavior.

One shared code path. Simplicity over cleverness. Analyze regression risk per phase.

## CLI-first and logging checklist

Every capability reachable from the CLI. Every non-CLI surface (Workbench GUI, MCP, Gradle tasks, any fast-run launcher) only forwards to the CLI.

New code has toggleable, per-entity (or per-capability), date-stamped, size-capped logging.

Checklist items that must be true at the end of every phase that touches a capability:
- [ ] CLI command exists and is documented
- [ ] Workbench action forwards to CLI (or shared CLI service)
- [ ] MCP tool forwards to CLI
- [ ] Gradle task (if any) forwards to CLI
- [ ] Logging is toggleable, per-entity, date-stamped, and size-capped
- [ ] Existing tests still pass; no regressions in file-only / Dalton-off mode

## Phase 1 — Core DB edit path

**Functionality**
- Shared core operation (on `DaltonFiles` or a thin `DaltonContent` helper): write `raw_content` + `content_hash`, set `db_edited=1`, leave `last_synced_hash` untouched, re-project the parsed Gherkin tables (scenarios, steps, tags, docstrings, data tables) in the same transaction, and validate Gherkin before committing.
- CLI: `dalton feature put <relative-path> [--text=...] [--file=...]`
- Fix `dalton entity put` to use the same core so flags and any related projection stay consistent.
- Structured edits (direct scenario or step row updates) are explicitly rejected with a clear error. There is no regenerate-raw path in this round (byte-stability with comments/whitespace cannot be guaranteed without risk).
- Unflagged / raw-SQL edit detection: hydrate notices `content_hash != last_synced_hash && db_edited=0`, reports "untracked DB edit on <path>", and treats it as a conflict (does not silently clobber unless `--force`).

**Docs**
- Update `docs/maintainer/3.0.0-dalton-design.md` with a Round 2 section.
- CLI help text and configuration notes.

**Tests**
- Feature put validates Gherkin, sets flags correctly, re-projects tables, rolls back on bad Gherkin.
- Entity put consistency with the core.
- Unflagged detection in hydrate (report, no silent overwrite).
- Targeted unit / integration tests only.

**Regression risk:** Medium. Must not change Dalton-off behavior or unedited extract paths.

## Phase 2 — CLI query surface

**Functionality**

- Stable, documented JSON for GUI and MCP consumers. Human-viewable labels in text mode.

**Docs**
- CLI help updates.

**Tests**
- List/show correctness, empty cases, JSON parseable and stable.
- Targeted only.

**Regression risk:** Low.

## Phase 3 — Discovery config

**Functionality**
- `dalton.properties` (and/or system properties): `include=` (globs, default current fixed directories), `exclude=` (default includes `**/.git/**`, `**/target/**`, `**/build/**`, `**/.pickleball/**`, common binaries), `max-file-size=` (default 1 MiB), `binary-policy=skip` (default; log reason). Optional later `hash-only`.
- Binary detection: extension list + simple content sniff (null bytes or high non-printable ratio).
- `dalton status` reports skipped count and sample reasons.
- Default behavior for existing users stays compatible. `--path` respects size/binary limits unless `--force`.

**Docs**
- `docs/configuration.md` and Dalton docs.

**Tests**
- Glob include/exclude, size and binary skip with logged reason, status output.
- Targeted.

**Regression risk:** Low if defaults preserve current discovery.

## Phase 4 — Packaging and loud fail

**Functionality**
- `sqlite-jdbc` remains not a published or shaded dependency.
- When Dalton is enabled and the driver is missing: auto-hydrate hook and relevant CLI commands fail loudly with an actionable message ("Dalton is enabled but org.xerial:sqlite-jdbc is not on the classpath. Add it as testRuntimeOnly / test scope or use the Gradle dalton* tasks.").
- Document the requirement clearly.

**Docs**
- Update configuration.md, release notes, and consumer guidance.

**Tests**
- Enabled + missing driver produces the clear error (not a silent fallback).
- Targeted.

**Regression risk:** Low. Default-off path unchanged.

## Phase 6 — Fast Dalton-first run path

**Functionality**
- CLI `dalton run` (and supporting warm worker) that reuses or extends the existing Workbench worker model (`WorkbenchWorkerMain` style) with a cached, prebuilt classpath.
- Executes scenarios from the DB.
- Fingerprints Java glue (mtime/class identity); on change triggers one Gradle/Maven compile then restarts the worker. Otherwise stays warm.
- Timing comparison script or tool that measures cold `./gradlew test` (or Maven) versus warm `dalton run`.
- Add Maven wrapper (`mvnw` / `mvnw.cmd`) to `maven-consumer-project` for consistency if useful.
- Keep full Gradle/Maven as the CI and source-of-truth build. The fast path must run the same engine and produce the same results.

**Docs**
- Usage notes for the fast edit-run cycle.

**Tests**
- Timing script runs and shows expected improvement; results match a normal engine run.
- Targeted.

**Regression risk:** Medium. Must prove identical results to the normal path.
