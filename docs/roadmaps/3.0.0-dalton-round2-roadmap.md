## CLI-first and logging checklist

Every Dalton capability must be reachable from the CLI. Every non-CLI surface (Workbench GUI, MCP, Gradle tasks, any fast-run launcher) only forwards to the CLI.

New code has toggleable, per-entity (or per-capability), date-stamped, size-capped logging.

Checklist items that must be true at the end of every phase that touches a capability:
- [ ] CLI command exists and is documented
- [ ] Workbench action / MCP / Gradle / fast-run only forwards to CLI
- [ ] Logging is toggleable, per-entity, date-stamped, and size-capped
- [ ] Existing tests still pass; Dalton-off unchanged

## Phase 1 — Core DB edit path

**Functionality**
- Shared core operation (in DaltonFiles or DaltonContent.putRaw): writes raw_content + content_hash, sets db_edited=1, leaves last_synced_hash untouched, re-projects parsed Gherkin tables (scenarios, steps, tags, docstrings, data tables) in the same transaction, validates Gherkin before commit.
- CLI: `dalton feature put <path> [--text=...] [--file=...]`.
- Fix `dalton entity put` to use the shared core (consistent flags; entities have no Gherkin projection but re-write raw consistently).
- Structured edits (editing a scenario or step row) are explicitly rejected with a clear error. No regenerate-raw path is provided (would not be byte-stable with comments and whitespace).
- Unflagged/raw-SQL edit detection: on hydrate, if a row has content_hash != last_synced_hash and db_edited=0, report "untracked DB edit on <path>" and treat as a conflict (do not silently clobber unless --force).

**Docs**
- Round-2 section in design.md.
- CLI help.

**Tests**
- Feature put validates Gherkin, sets flags correctly, re-projects, rolls back on parse failure.
- Entity put uses core.
- Unflagged detection treated as conflict.
- Targeted unit/integration tests only.

**Regression risk:** Medium. Must preserve Dalton-off and unedited extract behavior.

**Docs**

## Phase 3 — Discovery config

**Functionality**
- dalton.properties supports include= (comma-separated globs; default matches current fixed folders), exclude= (defaults include **/.git/**, **/target/**, **/build/**, **/.pickleball/**, binary extensions), max-file-size= (default 1MB), binary-policy=skip (default; logs reason; hash-only optional later).
- Binary detection via extension + null-byte / high non-text sniff.
- `dalton status` reports skipped count and sample reasons.
- Defaults preserve existing discovery for users with no config. `--path` respects limits unless `--force`.

**Docs**
- configuration.md and Dalton docs.

**Tests**
- Glob include/exclude, size and binary skips, status reporting.
- Targeted only.

**Regression risk:** Low if defaults are compatible.

## Phase 4 — Packaging and loud fail

**Functionality**
- sqlite-jdbc remains not a published or shaded dependency.
- When Dalton is enabled and the driver is missing: auto-hydrate and CLI commands that require the DB fail loudly with an actionable message ("Dalton is enabled but org.xerial:sqlite-jdbc is not on the classpath. Add it as testRuntimeOnly or run via the Gradle dalton* tasks.").
- Document clearly for consumers.

**Docs**
- configuration.md, getting-started notes, release notes.

**Tests**
- Enabled + missing driver produces clear error (not silent fallback).
- Targeted only.

**Regression risk:** Low. Default-off path unchanged.

## Phase 6 — Fast Dalton-first run path

**Functionality**
- `dalton run` CLI that starts or reuses a warm worker holding a cached prebuilt classpath (reuse/extend the existing WorkbenchWorkerMain / worker process model).
- Executes scenarios from the DB.
- Fingerprints Java glue changes (class files / mtime); triggers a Gradle or Maven compile only when needed, then restarts the worker.
- Timing comparison script (cold full build vs warm dalton run) in scripts/ or tools/.
- Add Maven wrapper (mvnw) to maven-consumer-project for consumer consistency.
- Full Gradle/Maven remain the CI source of truth. The fast path must use the same engine and produce identical results.

**Docs**
- Fast-path usage.

**Tests**
- Timing script executes; warm path is faster; results match a normal run.
- Targeted only.

**Regression risk:** Medium. Must prove identical results to the normal engine.
