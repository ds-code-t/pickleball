**Status:** Critical review of the analysis proposal (branch tip b6296b10 or newer). All phases are mandatory; nothing is optional or deferred. Stay on branch `2.1.18` only. Never commit, push, or merge to `master`. Version stays `2.1.18`.

Simplicity, with one shared code path. MCP, GUI and other surfaces are thin forwarders to the CLI, or a long-lived CLI mode on the same path. Include a CLI-first and logging checklist.

## Critical Review of the Proposal

The proposal is sound analysis from read-only inspection. We agree with the core recommendations and improve them as follows.

### Diagnostics / queryable store
Agree: typed record schema (needed regardless) + derived SQLite index as an *additive* sink/adapter. JSON files remain the source of truth. The index is disposable (delete → rebuild). Hang the adapter off `DiagnosticIndexRebuilder` / the existing aspect write points so `DiagnosticReporter` internals are untouched. Data model as proposed (run / scenario / step / event / property / artifact / error / log with FTS).

Improvement: expose a single canonical path or `where` field in every JSON response so agents stop guessing among the five candidate run-index locations in `AgentCoordination`. Truncation must always say `...+N more, use cursor`.

### General retrieval MCP layer
Agree: build on the existing MCP server. Add the six broad read tools (`wb_runs`, `wb_get`, `wb_query`, `wb_search`, `wb_props`, `wb_errors`) backed by a new `DiagnosticQuery` Java service. Later fold the three narrow `workbench_diagnostic_*` tools into them. Compact JSON defaults, explicit `fields`, small limits + cursor, truncation markers, ids rather than paths, stack heads only.

Improvement: one shared code path. CLI `query` (and re-pointed diagnostic verbs), MCP tools, and any UI explorer all call the same `DiagnosticQuery`. Free-text stays for humans; agents get the store. Token-budget assertions on default outputs.

### Rust for diagnostics
Agree: no for now. SQLite is already a native C engine. Reconsider only if profiling shows ingest (not queries) is the bottleneck.

### Feature / scenario retrieval
Agree with the three-parser problem (`WorkbenchFeatureIndex` text+mtime, `ConsumerFeatureCatalog` walk+tag scan, `CucumberScanUtil` full FeatureParser+pickle). First (no Rust): unify into one persistent mtime-keyed index (extend `WorkbenchFeatureIndex` to hold scenarios, outline rows, and tags) that discover/catalog and plan read. Pre-filter by tag *before* invoking `CucumberScanUtil` by passing only matching feature URIs (additive call; leave `CucumberScanUtil` untouched). Warm worker keeps the cache alive.

Rust sidecar later, only if still slow after the Java unification + timing. Preferred integration: sidecar binary speaking JSON over stdio (crash-isolated, no JNI, can also be MCP backend). Parallel index + strict parity tests against `CucumberScanUtil` pickles and tag results. Distribution via Maven classifiers or fat-jar extract. Phases R0–R4 as proposed, but only after Java wins are measured.

### Lifecycle costs
Agree with the estimates. Bigger wins are JVM/daemon warmth, incremental compile, and skipping redundant scans. Rust is plausible only for parsing/indexing/filtering.

### Agent-usability
Agree with the list. Many items already addressed by the in-flight commits around b6296b10; verify. New work:
1. Single help source (`WorkbenchCliHelp`) that errors render from (kill the ~25 duplicated usage strings).
2. Flag normalization with deprecated aliases (positional `session info` → `--run-id` style; consistent subverbs vs mode-flags; `all` vs `any`).
3. `{error, fix}` structured errors instead of mixed usage strings.
4. One canonical command name.
5. `where`/path field.
6. Decision tree in help: discover → plan → run.
7. Trim MCP tool descriptions to one line; move detail to help.
8. Truncation markers.
9. Worker logs feed the store.
10. Parity tests so the three (then one) parsers cannot disagree.

- Fix the stale line at `docs/ai-run-configuration.md:422`.

**Functionality / docs / tests / commit:** Code + parity/unit/e2e tests for each bullet. Docs note the restored normal-launch encoding and Workbench-only extra locations. Commit: "0.1.18-agent-retrieval-phase0".

### Phase 1 — Typed schema + DiagnosticQuery over existing JSON files (no DB)
Define the typed record schema. Implement `DiagnosticQuery` that reads the existing JSON/JSONL files (catalog → run-index → clusters → summary → events). Add CLI `query` command. Add the six MCP tools as thin forwarders. Defaults: compact JSON, explicit fields, limit=10/20 + cursor, truncation `…+N`.

**Functionality / docs / tests / commit:** Schema docs, `DiagnosticQuery` service, CLI `query`, six MCP tools, token-budget assertions (default output ≤ N bytes), fixture-run tests for every tool. Packaged guidance + release notes. Commit: "1.1.18-agent-retrieval-query".

### Phase 2 — Additive SQLite index sink + FTS
SQLite (xerial) `diagnostics.db` per runsRoot. Additive sink/adapter that subscribes or replays what is already written, plus rebuild-from-files. FTS5 on log/event/error text. Index is disposable.

**Functionality / docs / tests / commit:** Sink + rebuild, Win/Mac/Linux CI parity tests (rebuild matches files), FTS search tests. Docs on the derived index. Commit: "2.1.18-agent-retrieval-sqlite".

### Phase 3 — Usability fixes
Single help source (`WorkbenchCliHelp`) that all errors render from. Flag normalization with deprecated aliases. Structured `{error, fix}` errors. Trim MCP descriptions to one line. Add truncation markers, `where` field, decision tree in help. Worker logs feed the store.

**Functionality / docs / tests / commit:** Help/usage golden files, every error has a fix, flag-alias tests, MCP description length assertions. Docs and packaged guidance. Commit: "3.1.18-agent-retrieval-usability".

### Phase 4 — Unified Java feature index + tag pre-filter + timings
Extend `WorkbenchFeatureIndex` (or a shared sibling) to a persistent mtime-keyed index holding scenarios, outline rows, and tags. Discover/catalog and plan read it. Pre-filter by tag before calling `CucumberScanUtil` (pass only matching URIs). Timing instrumentation on discover/plan/scan. Strict parity tests vs `CucumberScanUtil` pickles and tags on fixtures and the consumer project.

**Functionality / docs / tests / commit:** Unified index, pre-filter, parity tests, timings. Docs on the single index. Commit: "4.1.18-agent-retrieval-feature-index".

### Phase 5 — Conditional Rust sidecar (only if Phase 4 timings still show residual cost)
If and only if profiling after Phase 4 shows parse/index/filter is still the dominant cost on large consumers: implement `pkb-core` Rust sidecar (gherkin crate, persistent index, tag evaluator, file watch) speaking JSON over stdio. Java `FeatureIndex` interface with Java and Rust impls selected by property, auto-fallback. Parallel index + CI parity tests on 3 OSes. Do not make Rust the default until parity is green.

**Functionality / docs / tests / commit:** Sidecar, integration, parity, docs, distribution notes. If timings do not justify it, the phase still lands a documented "measured, not needed" note and the Java path remains the only implementation. Commit: "5.1.18-agent-retrieval-rust-or-not".
