**Pickleball 3.0.0 Engine Design (Round 3)**

**Subsystem:** Native Execution Engine  
**Status:** Design locked 2026-11-11; implementation on branch `3.0.0`.

### Purpose
Fully decouple Pickleball's execution engine from Cucumber. Scenarios and steps become any text consumable from anywhere (file, Dalton DB row, in-memory string, API/MCP/CLI input) or written dynamically while executing. Cucumber/JUnit becomes an optional adapter.

### Architecture Decisions
- **Native engine:** Pickleball-owned model in `tools.dscode.engine` (Step, Scenario, Feature/container, Result/Status, ExecutionContext, ScenarioSource SPI). Cucumber types appear only in the adapter.
- **Parser:** Reuse the official `io.cucumber.gherkin` library as a pure parser. Convert AST/messages to the neutral model. Replicate current aspect behaviors (PickleCompilerAugment, ForceNullValuesRowAspect, EncodingParserLineSwap) as post-process rules so existing features are byte-identical.
- **Step registry:** Discovers glue (built-in + consumer) by reading the same `@Given`/`@When`/`@Then` annotations (values remain single string literals). Native matching produces the same result as Cucumber (regex + Cucumber Expression semantics, parameter types, DataTable/DocString, overrides, ambiguity).
- **ExecutionContext:** Explicit context (scenario, step stack/tree, map scopes, phase, failures, timing, resources) passed everywhere. Thin GlobalState/CurrentScenarioState shims for compatibility.
- **Neutral data:** Table and DocText types; converters to/from Cucumber DataTable/DocString only at the adapter edge.
- **ScenarioSource SPI:** Implementations for feature files on disk, Dalton DB rows, in-memory Gherkin text, and runtime-generated step lists (no file/URI required).
- **Entry points:** `PickleballEngine.run(...)` and `runStep(...)`. CLI-first; Workbench, MCP, Gradle, and `dalton run` only forward to the CLI. Dalton runs natively from DB rows.
- **DynamicControl:** Works without a live Cucumber scenario (creates ExecutionContext on demand).
- **Adapter:** Existing Cucumber/JUnit suites remain identical. Default engine stays the Cucumber adapter until the dual-run parity harness is green; then native becomes the default. Toggle via `pkb_engine=native|cucumber` (same precedence pattern as `pkb_dalton`). Adapter path always remains supported.
- **Runtime-written steps:** First-class; inserted/written mid-execution without Gherkin pickles; recorded in reporting/diagnostics/lineage like file-sourced steps.
- **Aspects:** Retire only cucumber-core aspects replaced by the native engine. Keep everything still required by the adapter path.

### Migration (strangler-fig)
Every phase leaves the full existing suite green via the adapter path. Targeted tests between phases; full regression once at the end.

### Non-goals for Round 3
No changes to existing Gherkin/step syntax or behavior. No weakening of existing tests. Version stays 3.0.0. No publishing, tags, or releases. Never touch master/2.2.0/2.1.19.

See `docs/roadmaps/3.0.0-decouple-round3-roadmap.md` for the phased implementation plan.

## Implementation

Phase 1 (model only, no runtime change): `tools.dscode.engine.model` holds `EngineFeature`, `EngineScenario`, `EngineStep`, `ExampleTable`, `Table`, `DocText`, `StepArgument`, `SourceLocation`, `Status`, `StepResult`, `ScenarioResult`, and `RunResult`. `tools.dscode.engine.convert.CucumberModelConverter` converts those to and from Cucumber message `GherkinDocument` / `Feature` / `Pickle`, `DataTable`, `DocString`, and `Status`. Cucumber types stay at that edge.

Phase 2: `tools.dscode.engine.match.StepRegistry` discovers glue from the same step annotations and matches with `ExpressionFactory`. `StepKind` records dynamic, block-conditional, RUN, service-call, override, and glue. `dispatchStub` names the executor and does not call it. Logging is `EngineLog` (`pkb_engine_log`).

Phase 3: `ExecutionContext` holds the scenario, step stack, map scopes, phase, failures, timing, and resources. `GlobalState.getCurrentScenarioState` prefers the Cucumber thread local and otherwise returns the context legacy scenario. `ParsingMap.getRunningParsingMap` returns the context map only when no scenario state is current.

Phase 4: `NeutralRows` and `NeutralAssertions` operate on `Table` and `DocText`. `TabularDataAdapter` and `ParsingMap` accept those types directly. `DataTable` / `DocString` conversion remains `CucumberModelConverter`.
