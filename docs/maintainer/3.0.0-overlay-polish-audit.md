# 3.0.0 Overlay Polish Audit

**Status:** Audit only. Nothing here is implemented yet. It was written on 2026-11-16 from `origin/3.0.0` at `cb494456`, the branch that holds the visual-components merge (`4ce983af`) and the popup fix-back merge (`7666bae6`). The fix plan is `docs/roadmaps/3.0.0-overlay-polish-roadmap.md`. All line numbers below are for `cb494456`.

**Scope:** These are the injectable collaboration elements that AI agents put on live pages or in the agent popup: the chat panel (popup and Workbench tab), overlay callout, highlight, label, border, arrow, step badge, magnifier and spotlight. The audit also covers the listeners, state, input path and agent (CLI/MCP) surface behind them.

Evidence comes from reading the code. Every root cause marked **(code)** can be seen directly in the cited lines. A cause marked **(likely)** follows from the code, but no test covers it yet; roadmap phase P0 adds a failing live test for it first.

## 2. Root causes by Dan's items

### Item 2: Enter or Send does not "take" the message (top root cause)

The form wiring itself is fine. `agent-surface-popup.js:133-142` handles `submit`, so pressing Enter in the `<input>` and clicking Send both POST `/chat`, and `PopupBridge.java:121-126` stores the text. The message fails to show up for three reasons:

1. **The human's own message is never echoed (code).** `/chat` writes only to `ChatLog` (`PopupBridge.java:123` → `PopupSurfaceBridge.sendChat`). The popup draws only `PopupLedger` rows with `op=chat` (`agent-surface-popup.js:77-82`). Only the agent path appends that ledger row (`AgentSurfaceRouter.java:118-121`). So the input clears (`agent-surface-popup.js:141`) and the text disappears. To the person typing, it looks as if nothing was accepted.
2. **The popup goes deaf after the first batch, or after 15 s (code).** `PopupBridge.events` (`PopupBridge.java:153-175`) ends the SSE response after the first rows it writes (`if (wrote && after > 0) return;` at line 169), or after a 15 s deadline (line 159). The browser treats the end of the stream as an error. The client's `onerror` (`agent-surface-popup.js:116-119`) then calls `source.close()`, which cancels EventSource's built-in reconnect, and calls `poll()` once. `poll()` (`agent-surface-popup.js:122-131`) never schedules itself again. From then on, no agent reply, instruction or overlay reaches the popup until it is reopened. The live test (`AgentSurfacePopupLiveTest.java:40-45`) appends every row before the page loads, so the first batch covers everything and this bug never shows.
3. **No feedback and silent failures (code).** A blank message throws `missing text` (`ChatLog.java:95`), which comes back as HTTP 500 (`PopupBridge.java:144-146`). The client `fetch` has no `.then`/`.catch`, so there is no pending, sent or failed state. The agent is never notified either: it sees the message only if it happens to call `chat-poll` on channel `run`.
4. **The Workbench chat tab ignores Enter (code).** `AgentChatPanel.java:20` creates the `JTextField` with no `ActionListener`. Only the Send button is wired (`AgentChatPanel.java:33-37`).
5. **Noise (code).** `agent-surface-popup.js:144-151` posts every click anywhere in the popup, including Send, to `/input` with an empty id. Each one becomes an `overlay input click` chat line (`PageSurfaces.java:574`).

### Item 1: Not draggable or resizable

- **Never specified (code/docs).** No roadmap or design mentions drag or resize (`rg -i "draggab|resiz" docs` finds nothing). There is no in-page panel at all. The popup is an OS app window. The OS can move and resize the window, but its content is a fixed grid (`agent-surface-popup.css:2`, `grid-template-rows: 1fr 1fr auto` with four children, so the composer falls into an implicit row) with no dock, minimize or remembered size. The overlay callout and other kinds are fixed boxes with no handles.

### Item 3: Non-responsive, ugly, clumsy

- Hard-coded colors and fonts: `#fffef2` callout, `2px solid #222` border, `12px sans-serif` labels (`PageSurfaces.java:695-696`, `VisualKinds.java:80-87`, `step.css`, `label.css`). There is no light/dark awareness (`prefers-color-scheme`), no `prefers-reduced-motion`, no transitions and no radius or shadow system.
- **No style isolation (code).** In-page nodes are plain light-DOM `div`s with inline styles (`PageSurfaces.java:408-411`, `live-helper.js:98-149`). Page CSS bleeds in (for example `div { … }` and resets) and our nodes are visible to page scripts and selectors. The popup uses shadow roots per row (`agent-surface-popup.js:51-66`), but the page path does not.
- Every element gets `z-index` 2147483644-6, so page modals in the top layer (`<dialog>`, popover) still cover them.
- Positions are pixel `left/top` written once. Any later move would be a layout write. Nothing uses `transform` or batches reads and writes.
- `ensureSurface` loads `assets/surface/overlay.js` (`agent-surface-popup.js:43-49`). That file is the generic `surface-events.js`, which adds a second set of global listeners in the popup. It is harmless, but it is wasted work.

### Item 4: No MutationObserver or default listeners

- **None exist (code).** Searching `src/main/resources/tools/dscode` and `agentcontrol` finds no `MutationObserver`, `ResizeObserver`, `IntersectionObserver`, `scroll`, `resize`, `popstate`, `hashchange` or `visibilitychange` listener. The only listeners are document `click` and `change` (`live-helper.js:150-163`, `surface-events.js`).
- If the target re-renders (for example after a framework re-mount), the overlay stays at the old pixels. If the target is removed, the overlay stays behind.

### Item 10: No anchoring inside scroll containers, or on resize, zoom or layout shift

- **Static geometry (code).** The box is computed in Java before injection (`PageSurfaces.chooseBox` `PageSurfaces.java:671-691`) from a remembered `visual_viewport_relative` snapshot. It is then written as `position:fixed;left:Npx;top:Npx` (`PageSurfaces.java:695`, `VisualKinds.java:78,81,221`). `docs/dynamic-control-api.md:124` states it: "There is no `getBoundingClientRect` fallback". So scrolling the window or any `overflow:auto|scroll` ancestor, nested or not, leaves the overlay where it was. Browser resize, zoom, font load and any layout shift do the same.
- Nothing clips the overlay. A target that has scrolled out of its container's visible area still has its overlay painted over unrelated content.

### Item 5: Overlays are opaque in the center and block the target

- **Callout covers the element (code).** With a resolved box, `overlayCss` gives the callout the element's own x, y, width and height and an opaque `background:#fffef2` (`PageSurfaces.java:695-698`; the same path is in `live-helper.js:108-117`). It has no `pointer-events:none`, so the callout sits exactly on top of the element it describes and takes its clicks.
- The magnifier is an opaque white circle (`VisualKinds.java:85`) drawn at the target box, so it hides the target too, and it is clickable.
- The label (`VisualKinds.java:80`) is drawn at the target's top-left, over the target, and it is clickable.
- Border, arrow, step and spotlight already use `pointer-events:none` (`VisualKinds.java:82-84,222`). Spotlight's `box-shadow` cutout passes clicks through. That part is correct.

### Item 6: No stored state, so nothing survives refresh or navigation

- **No re-injection (code).** The page path keeps placements only in `.pickleball/runs/<run>/agent/placements.json` for removal bookkeeping (`PageSurfaces.java:448-452`). After a reload the nodes are gone and nothing puts them back. `installSurface` (`PageSurfaces.java:1127-1131`) registers only the event script as a new-document preload, never the placements. No `sessionStorage` or `localStorage` is used.
- **Stale isolated world after navigation (likely).** `CdpAdapter.evaluateIsolated` caches the isolated-world context id per world name (`CdpAdapter.java:113`). The cache is cleared only when a different target is attached (`CdpAdapter.java:86`). A same-tab navigation destroys that context, so the next `pkb-surface` evaluate uses a dead id and the placement fails after any navigation.

### Item 7: Numbered overlays are not linked to instructions

- `step-badge` draws a number and optional text (`VisualKinds.java:92-111`). It is not tied to the Instructions pane, it has no current-step emphasis and nothing marks it done. The Instructions pane is free-form `html-write --pane=instructions` HTML. Nothing watches the user's interaction with the target.

### Input capture bug that affects items 2 and 7

- **Events from CDP-placed overlays are dropped (likely, high confidence).** On Chrome the helper runs in the isolated world `pkb-surface` (`PageSurfaces.java:1116`). Its listeners push to that world's own `window.__pkbEvents` (`live-helper.js:150-163`). `drainTab` reads `window.__pkbEvents` in the main world with Selenium `executeScript` (`PageSurfaces.java:738-742`). The two worlds have separate globals, so clicks and inputs on overlays on the current document are never drained. The main-world preload listeners exist only after the next navigation. The `pkbSurface` CDP binding is registered (`PageSurfaces.java:1130`), but no script ever calls it.
- **No cursor (code).** `overlay-poll` returns the whole event file every time (`PageSurfaces.java:577-586`). That costs tokens and cannot tell an agent what is new.
- **Values are recorded raw (code).** `change` stores `ev.target.value` (`live-helper.js:158-161`). Today that applies only to agent-injected inputs. Once step tracking watches page fields, it must never record values from password or sensitive fields.

### Item 8: Agent surface is costly in tokens

- MCP exposes one generic `workbench_agent_command` (`WorkbenchMcpTools.java:365-386`). Its description lists only 7 op families, while there are 34 verbs, and `args` is an untyped map, so an agent has to guess flag names. There is no batch, so one guided flow takes N calls. There are no short target forms (CSS, text or role); a target must first be resolved to a handle. Every result echoes the sentence, codes, sha256, summary and guidance (`PageSurfaces.java:460-480`).

### Item 9: No toolbox or catalog

- Discovery is only the usage strings in `WorkbenchCliHelp.java` and the long prose in `docs/dynamic-control-api.md:112-128`. Nothing machine-readable lists the components, options, defaults and an example. The inventory (`docs/roadmaps/workbench-cli-inventory.json`) is maintainer-only.

## 3. What works and must be kept

- One spine: `AgentControl.execute` → `AgentSurfaceRouter.route` → page / popup / native. CLI-first, so MCP, Workbench, HTTP and Gradle only forward.
- Provenance: every injected node carries `data-pkb-agent=agent_injected` plus a sentence. The `neutralize` HTML sanitizer, id allocation under a file lock, the undo snapshot, `un*` kind checks, scenario-end cleanup, and native rectangles for desktop sessions.
- Popup security: a 128-bit token compared in constant time, a Host check, a strict CSP (`PopupBridge.java:24`), loopback only.
- Magnifier clone hygiene (`live-helper.js:122-142`). Spotlight cutout pass-through. Escaped badge and magnifier text.
- Toggleable, per-entity, date-stamped, size-capped `pkb_composite_log` logging.

## 4. Security, distribution and licensing notes

- **Strict page CSP.** Scripts evaluated through CDP (`Runtime.evaluate`, `addScriptToEvaluateOnNewDocument`) are not blocked by page CSP. A `<style>` element inside a shadow root **is** blocked by `style-src` without `'unsafe-inline'`. Constructable stylesheets (`adoptedStyleSheets`) and CSSOM writes are not blocked. The runtime must use those.
- **Trusted Types.** Pages with `require-trusted-types-for 'script'` throw on `innerHTML` (`live-helper.js:99,84`). The runtime must build nodes with DOM APIs and use a named Trusted Types policy only where the page allows one. Otherwise it renders agent HTML as text.
- **Page storage.** `sessionStorage` and `localStorage` belong to the page origin and are readable by page scripts. Overlay state must not contain secrets or user-typed values. The roadmap stores state agent-side by default and makes page storage opt-in.
- **Value capture.** Step completion only needs "the user interacted, and the field is non-empty". It must not record values from `type=password`, `autocomplete` `cc-*`, `one-time-code` or `current-password`, or from fields an agent marks `sensitive`.
- **Distribution.** The runtime is one first-party JS asset in the jar. It needs no new runtime dependency and no third-party JS. Box-only live-check scripts use Python Playwright (Apache-2.0) and are not committed or shipped.
