## Root causes in testing
- **CI is ubuntu-only**. The real consumer is Windows + PowerShell + mvnw.cmd + CHROME_HEADLESS. No Windows runner exists. Every Windows-only item is structurally invisible.
- **The consumer job runs only `mvnw test`**, not the Workbench CLI/agent workflow (discover -> isolate -> execute-step -> query -> rerun -> confirm). The workflow that consumers report on is tested via in-process unit tests and stubs (e.g. B9/before-all test calls the hook directly; failure fields asserted on stubbed results).
- **Tests are written by the same Build session that wrote the fix**, against its own understanding of the report, so they confirm the patch not the user-visible behavior. Verification (incl. mine) checks "item present + suite green", not "consumer transcript now correct".
- **Surface area is large**: CLI verbs x (wrapper, java fast path, .cmd/.sh openers) x MCP tools x guide + detail doc + release notes + packaged copies. Each copy can drift; nothing checks a documented command actually produces the documented output.
- **Release gate** = unit tests + index check. No gate on "documented examples run", exit codes, or timings (S2 regressed 143->164 s unnoticed).
- **Per-item patching**: each roadmap is a list of report items, so fixes land in whichever path the reporter hit, multiplying paths instead of merging them.

## Verdict
**Partly structural.** The code and design are not fundamentally wrong, and most individual issues are minor. But the *process* is structurally guaranteed to keep producing them: we test a different path, OS and shell than the consumer uses, docs are hand-written promises with no executable check, and fixes are per-symptom across duplicated paths. Keep the architecture; change how we verify and shrink the surface.

## Recommendations (ranked by payoff)
1. **Consumer-simulation E2E harness in CI, with a Windows runner** (windows-latest + PowerShell + mvnw.cmd, plus ubuntu bash). Install the built artifact to mavenLocal, then drive a scripted agent session in maven-consumer-project: discover (uncompiled + compiled), isolate, execute-step via b64/file (absolute Windows path), events, query errors/tail, rerun same run-id, confirm, finish. Assert stdout, exit codes, record.json and timings budget. This alone would have caught ~70% of this report.
2. **Golden-transcript tests generated from the guide**: every command block in AGENT-GUIDE/detail doc/release notes is extracted and executed by the harness; output compared to a checked-in golden. Docs can no longer promise what code doesn't do; packaged copies generated, never hand-synced.
3. **Collapse duplicate paths**: one argument parser for all flags (`--x=v` and `--x v`), one launcher for every entry point (openers, wrapper, fast path all call it; unknown verb = exit 2, never GUI), one warning/seed function shared by hint and seed, one event stream for anchor and execute-step steps, one output formatter for CLI and MCP (ASCII, redaction applied centrally).
4. **Run lifecycle as an explicit model**: per-attempt subfolders, run snapshot authoritative for its run-id, record updated on every transition. Fixes N2/N3/N9/B6 as a class.
5. **Change the Build loop/release gate**: Build writes the failing E2E/golden test from the consumer's report text *before* the fix (red-then-green); verifier reruns the consumer's literal commands, not just the suite; no "warn instead of fix" without Dan's sign-off; release blocked unless Windows E2E green and timings within budget.
6. **Freeze features until surface shrinks**: treat O1-O8 as backlog; trim CLI/MCP verbs and doc copies to what the harness covers.
