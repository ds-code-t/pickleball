# 3.0.0 embedded store design (replaces the Dolt sql-server layer)

**Status:** proposed design. Nothing here is implemented. The shipped behavior is still the Dolt sql-server core described in `AGENTS.md` (`## Dolt`) and `docs/maintainer/3.0.0-dolt-core-design.md`. The plan is `docs/roadmaps/3.0.0-embedded-store-roadmap.md`, and the Build prompt is `prompts/build-3.0.0-embedded-store.md`.
**Decision:** Dan Shell, 2026-11-15, about 10:37 PM MST (chat and voice). The Dolt binary is downloaded at runtime from GitHub, not from Maven Central. Locked-down machines that can only reach Maven Central or a corporate mirror cannot get it. Dan asked for a simplified, embedded, Java-only store built from existing libraries, with no server and no runtime download, prepared as a design and roadmap only. **Do not build it until Dan says so.**
**Base SHA:** written against `7666bae655006159b5ab896c4b53b470e8db22af` on `3.0.0`.
**Evidence:** the branch docs and code listed in section 2, the xerial `sqlite-jdbc` Makefile (compile flags), the SQLite session-extension docs, and measurements on the maintainer box on 2026-11-15 (section 14). Items marked **verify in E1** are not yet measured with `sqlite-jdbc` on all three operating systems.

## 1. Short answers

| # | Question | Answer |
|---|---|---|
| Q1 | Which embedded SQL library? | **SQLite through `org.xerial:sqlite-jdbc` 3.47.2.0**, already a published runtime dependency from Maven Central (Apache-2.0). It bundles the native SQLite library for Windows, macOS and Linux (x64 and ARM) inside the jar. It is the only embedded Java-reachable SQL engine evaluated that lets several **processes** read and write one database file at once without a server (section 4). |
| Q2 | How does a branch (sandbox) work? | A sandbox is its own SQLite file, a **snapshot copy** of `main` made with `VACUUM INTO` when the sandbox is created. Edits are recorded in that file's change log. Direct edits to `main` after that cannot leak into the sandbox, because the sandbox never reads `main` (section 6). |
| Q3 | Why not the overlay idea (only changed rows plus tombstones, base attached, views merge)? | It was evaluated and rejected for now. SQLite refuses `INSERT … ON CONFLICT` on a view (measured: `cannot UPSERT a view`), and the store has 10 upsert sites. Every view would also need a base-version filter so base edits do not leak. The copy is simpler and fast at our sizes: 25 ms for 10 MB and about 190 ms for 100 MB (section 14). A measurable trigger for a sharing optimization is in section 6.4. |
| Q4 | How do merge and conflicts work? | New `sandbox merge` with row-level three-way detection: ancestor (the row at snapshot time, from the sandbox change log), base (`main` now), and branch (the sandbox now). Policy `fail` (default, nothing applied), `branch-wins`, or `base-wins`. Conflicts are reported as one JSON object and a text table (section 7). |
| Q5 | History, timeline, rewind? | They already come from run-state tables, never from Dolt commits, so they port unchanged. An append-only change log replaces Dolt commit history (`dolt_log`, `dolt_diff_<table>`, hydrate commits) for source-table edits (section 8). |
| Q6 | Existing libraries for changesets or table versioning? | The SQLite session extension does exactly this, but `sqlite-jdbc` is not compiled with it and has no Java API for it. JGit versions files, not rows. Nessie, XTDB and Javers add weight without branching that fits. The custom part is small: triggers, a change-log table, a snapshot copy and a merge loop (section 5). |
| Q7 | What goes away? | The Dolt binary and its download, the sql-server, the supervisor, ports, `root` with no password, the MariaDB driver (LGPL), and the Windows `journal.idx` wait. Everything comes from Maven Central (section 11). |
| Q8 | What is lost compared with Dolt? | Arbitrary commit history and time travel on source tables, branching from any old commit, structural sharing between branches, Dolt's cell-level merge, and concurrent writers inside one branch (SQLite serializes writers per file). Section 13 lists each with its impact. |
| Q9 | Rough size? | About 15 to 18 engineer-days over phases E1 to E8, or 13 to 16 without the optional rename (roadmap). |

Facts that matter for the design:

- Git files stay the source of truth. The store is rebuilt from files. Real Git is the only project sync, so the store does not need durable history beyond what sandboxes and audits use.
- The existing seam is small. `DoltStore.open(Path, Binding)` returns a `DoltSession`. `DoltConnections` pools per `(project, branch)`. `DoltDialect` owns every SQL fragment. `DoltDialectInventoryTest` fails when literal SQL appears outside the dialect and the store. JDBC URLs and `DriverManager` live only under `tools.dscode.dolt.store`.
- Dolt-specific SQL in main code is limited to: `DOLT_BRANCH` (`DoltStore`, `DoltSandbox`), `DOLT_COMMIT` and `DOLT_ADD` and `dolt_status` and `dolt_log` and `active_branch()` (`DoltDialect`), `dolt_diff_<table>`, `HASHOF('HEAD')` and `DOLT_GC` (`DoltSandbox`), `GET_LOCK` (`DoltSession`, `DoltDialect`, `DoltSandbox`), and `information_schema.PROCESSLIST` (`DoltConnections`).
- The Dolt layer has **no merge** today. Sandboxes leave through `sandbox extract --to=<dir>` (for example a Git worktree) or are dropped. Merge is a new capability Dan's direction adds; extract keeps working.
- Before Dolt, this same layer ran on SQLite (schema versions 1 to 6). The SQLite spelling of every statement exists in Git history and in the dialect table of `docs/maintainer/3.0.0-dolt-core-design.md` section 7. The port back is mechanical.

## 3. Goals and non-goals

**Goals**

1. No server, no child process, no port, no runtime download. Opening the store is opening files.
2. Only Maven Central artifacts. No new dependency at all: `sqlite-jdbc` is already published.
3. Same CLI, same tables, same `--json` shapes, same adapters, same tests (ported, never weakened).
4. Sandboxes isolated from each other and from later edits to `main`.
5. Row-level three-way merge with a clear conflict report and a policy.
6. Works on Windows, macOS and Linux, including paths with spaces, with the Windows file-lock lessons from today's CI built in.

**Non-goals**

- No new consumer feature beyond `sandbox merge` and `changes`.
- No change to Gherkin syntax, step annotations, the engine, the Cucumber adapter, or the diagnostic index.
- No network-shared store (section 9.6).
- The held execution-path audit fixes F1 to F12 stay held.

## 4. Library choice: SQLite via `sqlite-jdbc`

### 4.1 Candidates

| Library | Embedded, pure Maven | Several processes on one store, no server | Branching | Verdict |
|---|---|---|---|---|
| **SQLite (`org.xerial:sqlite-jdbc`)** | Yes. Natives for all target platforms inside the jar, Apache-2.0, already a published runtime dependency (3.47.2.0) | **Yes.** File locking; WAL gives many readers plus one writer at a time across processes | No (we add it, section 6) | **Chosen** |
| H2 (pure Java) | Yes | No. A file database is locked to one process. `AUTO_SERVER=TRUE` lets other processes in by starting a TCP server inside the first process, which is a server again | No | Rejected: parallel agents are separate JVMs |
| HSQLDB | Yes | No. A `.lck` file holds the database for one process | No | Rejected |
| Apache Derby | Yes | No. One JVM boots the database | No | Rejected |
| DuckDB JDBC | Yes (natives in jar) | Only one read-write process; others read-only | No | Rejected: analytics engine, writer limit |
| XTDB (embedded) | Yes, heavy | No | Time travel, no branches | Rejected (also in the 2026-11-15 chat) |
| JGit plus files | Yes | Git locking | Real branches and merges, of **files** | Rejected as the store (section 5.2) |

Deciding facts:

- Parallel agents and test runs are separate processes (`dolt run` worker JVMs, Gradle tasks, Workbench-forwarded CLIs). Only SQLite serves several processes from one file without a server.
- `sqlite-jdbc` 3.47.2.0 bundles SQLite 3.47.2. That build has `concat()` (since 3.44), JSON functions (built in since 3.38), `VACUUM INTO` (since 3.27), FTS5, and `SQLITE_MAX_ATTACHED=125` (xerial Makefile flags, checked 2026-11-15).
- The previous working copy already ran on SQLite with WAL, `busy_timeout=5000` and `foreign_keys=ON`.

### 4.2 Native library extraction (locked-down machines)

`sqlite-jdbc` writes its native library to `java.io.tmpdir` and loads it on first use. Some locked-down machines mount the temp directory `noexec` or block loading libraries from it. The fix is a documented setting, not a download: `-Dorg.sqlite.tmpdir=<dir>` (for example `<project>/.pickleball/native`), or `org.sqlite.lib.path` and `org.sqlite.lib.name` for an IT-approved copy. This is not new exposure: the diagnostic index already loads the same library today. E1 verifies a `noexec` temp directory on Linux and documents the message.

### 4.3 Version

Keep `org.xerial:sqlite-jdbc:3.47.2.0`. The published-POM check in `build.gradle` already pins that exact version and scope `runtime`. A bump (3.54.1.0 is current on Maven Central) is a separate decision for Dan (section 16).

## 5. Libraries evaluated for branching, changesets and history

### 5.1 SQLite session extension

The session extension records row changes into a changeset, inverts changesets, and applies them with a conflict handler (`SQLITE_CHANGESET_DATA`, `CONFLICT`, `NOTFOUND`). That is the merge engine this design needs. It is **not usable**:

- It needs `-DSQLITE_ENABLE_SESSION -DSQLITE_ENABLE_PREUPDATE_HOOK` at compile time. The xerial Makefile does not set them (checked 2026-11-15).
- `sqlite-jdbc` has no Java API for `sqlite3session_*` or `sqlite3changeset_*`. Its maintainers support only runtime-loadable extensions, and the session extension is not loadable.
- Calling the C API ourselves needs our own native build or the Java foreign-function API, which is preview in Java 21. Both bring back a per-platform native artifact, the problem this design removes.

**Decision:** emulate the parts we need with plain SQL triggers and a change-log table (section 8). The format follows the session extension's ideas (per primary key, old and new values, net effect), so a future switch is possible.

### 5.2 JGit

Git versions files. A SQLite database is one binary file, so every Git commit stores a full copy, and two changed copies always conflict. Row-level merge through Git would need every row exported as text, and every query would go through an export and import. That is slower and more complex than section 6. JGit stays rejected unless Dan wants store history inside the project's Git repository, which today's rule (Git holds files, the store is disposable) does not need.

### 5.3 Others

- **Project Nessie** (Java, Apache-2.0): Git-like branches for Apache Iceberg table catalogs. It needs Iceberg and a service. Rejected.
- **Javers** (Java, Apache-2.0): object audit log with snapshots and diffs persisted to SQL. No branches, and it audits Java objects, not our rows. It would replace about 100 lines of trigger code with a large dependency. Rejected.
- **Liquibase, Flyway:** schema migration, not data versioning. The store keeps its own `schema_meta` upgrades.

### 5.4 What is custom, and why

| Custom piece | Size estimate | Why not a library |
|---|---|---|
| Change-log triggers generated from `PRAGMA table_info` | ~150 lines | Session extension not reachable (5.1) |
| Snapshot copy (`VACUUM INTO` to a temp file, atomic move) | ~80 lines | SQLite does it; we only wrap it |
| Three-way merge loop and conflict report | ~400 lines | No Java library merges SQLite rows |
| Leases with OS file locks | ~120 lines | `java.nio` `FileChannel.lock` is the library |
| Dialect port back to SQLite | mechanical | Existing `DoltDialect` catalog |

## 6. Branching model

### 6.1 Files

```
<project>/.pickleball/dolt/            (renamed in E7, section 11.3)
  main.db                              source tables, branch main, change log
  runstate.db                          run-state tables for every sandbox
  sandboxes/<name>/source.db           snapshot copy plus its own change log
  sandboxes/<name>/lease/<pid>.lock    held while a process uses the sandbox
  sandboxes/<name>/worker/, classes/   unchanged from today
  locks/hydrate-<branch>.lock          hydrate and extract mutual exclusion
  store.log, sandboxes/<name>/merge-<iso>.json
```

Each `.db` file runs in WAL mode, so `-wal` and `-shm` files sit next to it. `.pickleball/` is already gitignored.

### 6.2 Create

`sandbox create <name> [--from=main|<sandbox>] [--owner] [--ttl]`:

1. Under `locks/sandboxes.lock` (exclusive `FileChannel.lock`), refuse an existing name.
2. `VACUUM INTO '<dir>/source.db.tmp'` from the source file. `VACUUM INTO` runs in one read transaction, so the copy is consistent even while other processes write, and it does not block writers in WAL mode.
3. In the copy: read `base_seq = MAX(seq)` from `_pkb_changes` (the copy proves which base changes it contains), then `DELETE FROM _pkb_changes`, and set `schema_meta` keys `sandbox`, `base_seq`, `base_source` and `created`.
4. Move the temp file to `source.db` with `ATOMIC_MOVE` and insert the `sandboxes` row in `runstate.db` (`base_commit` column holds `seq:<base_seq>`; the column name stays for compatibility).

### 6.3 Why a copy, and the measurable criteria

The question was whether direct edits to `main` must stay out of an open sandbox. With a copy they cannot leak: the sandbox never reads `main`. An overlay needs a version filter on every view, `INSTEAD OF` triggers for writes, and a rewrite of all 10 upserts, because SQLite refuses an upsert on a view.

Measured on the maintainer box (SQLite 3.46.1, 2026-11-15, section 14): `VACUUM INTO` takes 25 ms for 10 MB, 194 ms for 100 MB and 1,037 ms for 500 MB (about 2 ms per MB). The whole `maven-consumer-project/src` tree is 1.5 MB. Files over 1 MiB are skipped by default discovery (`max-file-size`), and binaries are skipped or stored as references.

**Criteria (recorded by E4 tests and CI):**

| Metric | Target | Action if missed |
|---|---|---|
| `sandbox create` p95 for a store of 100 MB or less | 250 ms or less on Linux CI, 1 s or less on Windows and macOS CI | Investigate before E4 is done |
| Store size in real consumer projects (`store.size` in `status`) | 256 MB or less | Section 6.4 |
| Disk per sandbox | About the size of `main.db` | Section 6.4; `prune` reclaims it |

### 6.4 Sharing optimization (only when a criterion is missed)

If a real project crosses 256 MB or `sandbox create` p95 goes over 1 s, move `files.raw_content` into a shared, append-only, content-addressed `blobs.db` (key: `content_hash`). Blob rows are never updated, only added, so sharing them cannot leak base edits into a sandbox. The sandbox copy then holds only the small row tables. `prune` deletes unreferenced blobs. This is the "only the altered parts, everything else references the original" idea applied where it is safe. It is not in the roadmap's mandatory phases; it is triggered by the measurement.

### 6.5 Binding

`Binding` is unchanged. `Binding.main()` opens `main.db`. `Binding.sandbox(name)` opens `sandboxes/<name>/source.db` and fails with today's unknown-sandbox message when it is missing. `active_branch()` checks become `schema_meta.sandbox` checks.

### 6.6 Run-state from a sandbox

Today, run-state writes go to a pooled `main` session, and joined statements read run-state through qualified names that see only committed rows. Embedded:

- Pure run-state statements run on a `runstate.db` session (the same router as today's main-session router).
- A statement that joins run-state to source tables runs on the bound source session with `runstate.db` attached read-only as `rs`. Unqualified names resolve because no table name exists in both files, so the catalog SQL does not change. The join now sees live run-state, which fixes the committed-only quirk.
- Foreign keys cannot cross files. `step_executions.definition_id` has no cross-file foreign key; the recorder keeps today's rule in code: a `definition_id` missing from the bound branch is stored as null.
- WAL commits are atomic per file, not across attached files. Today's design already writes run-state and source in separate sessions, so nothing relied on cross-file atomicity. **Verify in E1** that `BEGIN IMMEDIATE` on a source session does not take a write lock on a read-only attached `runstate.db`.

### 6.7 Diff, extract, drop, prune

- `sandbox diff <name> [--table] [--json]`: the net effect per primary key from the sandbox change log (first `old`, current row). The JSON shape stays the same; `to_commit = 'WORKING'` rows become `op` values `insert|update|delete`.
- `sandbox extract`: unchanged; reads files from `source.db`.
- `sandbox drop [--force]` and `prune [--older-than] [--owner] [--dry-run] [--with-history]`: close this JVM's pool for the sandbox, check leases (section 9.3), then delete the directory using the Windows release wait (section 9.5). `DOLT_GC` becomes `VACUUM` of `main.db` only when `prune --vacuum` is given or the free-page ratio is over 25%.

## 7. Merge and conflicts

`pickleball dolt sandbox merge <name> [--policy=fail|branch-wins|base-wins] [--dry-run] [--drop] [--json]`. CLI-first; Gradle `doltSandbox`, the Workbench sandbox picker and MCP `dolt` forward it.

### 7.1 What is merged

- **Authoritative tables** are merged row by row: `files` (key `path`) and `entities` (key `entity_type`, `entity_id`).
- **Derived tables** are not merged. `feature_docs`, `scenarios`, `example_blocks` and `steps` are rebuilt for each merged `.feature` path with the same projection `feature put` uses. `step_definitions` is refreshed for merged `.java`, `.js` and `.ts` paths with the catalog code. Merging projections row by row could produce a scenario list that matches no file.
- `schema_meta`, `provenance` and run-state are never merged.
- A merged file row lands in `main` with `db_edited=1` and keeps `main`'s `last_synced_hash`, so a later `extract` still applies its existing "file and database both changed" refusal.

### 7.2 Three-way detection

For each key in the sandbox's net change set:

- **ancestor** = the sandbox change log's first `old` value for that key (absent when the sandbox inserted it).
- **branch** = the row in `source.db` now (absent when deleted).
- **base** = the row in `main.db` now. **Base changed** when `main.db`'s `_pkb_changes` has an entry for that key with `seq > base_seq`.

| Base changed? | Branch vs base now | Result |
|---|---|---|
| No | any | Apply the branch row (insert, update or delete) |
| Yes | Equal (same values, or both deleted) | No-op, counted as `converged` |
| Yes | Different | **Conflict** |

Values are compared by their identity columns: `content_hash` and `binary_ref` for `files`; `payload_json`, `secret_refs` and `content_hash` for `entities`.

### 7.3 Policies

- `fail` (default): if any conflict exists, nothing is written, the report is printed and saved, and the exit code is 1.
- `branch-wins`: conflicting keys take the branch row; others apply normally.
- `base-wins`: conflicting keys keep `main`; others apply normally.

A sandbox merges into its `base_source` (`main`, or the sandbox it was created from); the base change log read in 7.2 is that file's.

The merge is one `BEGIN IMMEDIATE` transaction on the target file with `source.db` attached read-only. A failure rolls back everything. `--dry-run` prints the plan and writes nothing. After success the `sandboxes` row records `merged_seq`. `--drop` drops the sandbox afterwards with the normal in-use check.

### 7.4 Conflict report

One JSON object (stable, `--json`) and the same data as a text table, saved to `sandboxes/<name>/merge-<ISO-8601>.json`:

```
{ "ok": false, "command": "sandbox merge", "sandbox": "fix-login", "policy": "fail",
  "baseSeq": 41, "mainSeq": 57, "applied": 3, "converged": 1,
  "conflicts": [ { "table": "files", "key": "features/login.feature",
                   "ancestor": "sha256:…", "base": "sha256:…", "branch": "sha256:…",
                   "resolution": "none" } ] }
```

Rows are shown as identity hashes and sizes, never raw content, so no secret or large blob reaches the console. Text output ends with `fix:` lines naming `--policy=branch-wins`, `--policy=base-wins`, or `sandbox extract` plus Git.

## 8. Change log and history

### 8.1 Table and triggers

Every source-table file (`main.db` and each `source.db`) has:

```
_pkb_changes(seq INTEGER PRIMARY KEY AUTOINCREMENT, at TEXT NOT NULL,
             tbl TEXT NOT NULL, pk TEXT NOT NULL, op TEXT NOT NULL,
             old TEXT, new TEXT, actor TEXT NOT NULL DEFAULT '')
```

`AFTER INSERT`, `AFTER UPDATE` and `AFTER DELETE` triggers on the authoritative tables (`files`, `entities`) and on `step_definitions` write one row per changed row. `pk` and the values are `json_object(...)` of the columns. The triggers are generated from `PRAGMA table_info` when the schema is created or upgraded, so a new column cannot be forgotten.

- SQLite JSON cannot hold a BLOB (measured: `JSON cannot hold BLOB values`). `files.raw_content` is left out of `old` and `new`; `content_hash`, `binary_ref` and `byte_size` identify it. A guard test fails if any logged table gains a BLOB column without a hash column beside it.
- `actor` is the sandbox name or `main` plus the command (`hydrate`, `feature put`, `merge`), set per connection through a one-row temp table the triggers read.
- Derived tables are not logged; they are rebuilt from `files`.

### 8.2 What it replaces

| Dolt feature used today | Embedded replacement |
|---|---|
| Hydrate commit `hydrate <git sha>[ dirty]`, `status` prints `hydrate commit <hash>` | `schema_meta` `hydrate_generation` (incremented only when hydrate changes rows) and `hydrate_label`; `status` prints `hydrate generation <n> <git sha>[ dirty]` |
| `dolt_status` (anything uncommitted on source tables?) | `_pkb_changes` rows after the last hydrate's `seq` |
| `dolt_diff_<table> WHERE to_commit='WORKING'` | Sandbox change log net effect |
| `HASHOF('HEAD')`, `dolt_log` for a sandbox base | `base_seq` in the sandbox file |
| `--from=<commit hash>` | `--from=main` or `--from=<sandbox>`; a hash is refused with a fix line (section 13) |

### 8.3 Run history, timeline, rewind

They read `runs`, `run_logs`, `scenario_executions`, `step_executions`, `entity_usages`, `log_entity_links` and `artifacts` today, and will read the same tables in `runstate.db`. Paging (`--cursor`, `--before`, `--latest`), filters, `total`, `retain` and Workbench Tracking are unchanged. Rewind stays view-only.

### 8.4 New read command and retention

`pickleball dolt changes [--sandbox] [--since=<seq>] [--table] [--limit] [--json]` lists change-log rows (CLI-first; Gradle `doltQuery` forwards). Retention: `main.db` keeps entries newer than the oldest live sandbox's `base_seq`, and otherwise `pkb_dolt_changes_days` days (default 14). `retain` and `prune` trim it.

## 9. Concurrency and cross-platform behavior

### 9.1 Connections

Every connection sets `PRAGMA journal_mode=WAL` (once per file), `busy_timeout=5000`, `foreign_keys=ON` and `synchronous=NORMAL`. `DoltConnections` keeps its per-JVM pool per `(project, branch)` (max 4, idle close 60 s), now holding SQLite connections.

### 9.2 Writes

- Every write transaction starts with `BEGIN IMMEDIATE`, so the write lock is taken up front and a reader never deadlocks by upgrading. SQLite allows one writer per file, so the lost-update problem that needed `GET_LOCK` on Dolt cannot happen. `GET_LOCK` and `SELECT … FOR UPDATE` (not valid SQLite syntax) are removed.
- `SQLITE_BUSY` after the busy timeout retries 3 times with 50 to 200 ms jitter, then fails with today's `error: concurrent update on <table>`.
- Hydrate and extract per branch are serialized by `locks/hydrate-<branch>.lock` (exclusive `FileChannel.lock`), because hydrate reads the disk for seconds and must not hold the database write lock that long. It writes in one short transaction at the end.
- Measured on the box (Python `sqlite3`, WAL, 2026-11-15): 16 processes each committing 200 `BEGIN IMMEDIATE` inserts finished in 1.3 s with no failures and a p95 of 1.1 ms per transaction. E1 repeats this with `sqlite-jdbc` on three operating systems.

### 9.3 Leases and in-use refusal

A process that binds a sandbox opens `sandboxes/<name>/lease/<pid>.lock` and holds an exclusive `FileChannel.lock` on it until it closes the store or exits. The OS drops the lock when a process dies, so a crashed agent never leaves a stale lease, and no pid-alive check is needed. `drop` and `prune` call `tryLock` on each lease file. A lease another process holds means in use (`skipped <name> in use`, or a refusal without `--force`). This JVM's own leases are tracked in memory, because Java throws `OverlappingFileLockException` for a second lock in one JVM. This replaces `branch-lease/<branch>/<pid>` plus `information_schema.PROCESSLIST`.

### 9.4 One sandbox per JVM

Unchanged: the run id, project and auto-hydrate flag are JVM-global.

### 9.5 Windows file release (lessons from today's CI)

Today's CI showed that Windows keeps a file locked while any handle is open, including a handle a child process inherited, and that release can lag the process exit.

- Deleting a sandbox: close this JVM's pool for it, then wait up to 15 s for `source.db`, `-wal` and `-shm` to be released, probing by renaming each aside and back (the `JOURNAL_RELEASE_MS` technique). A file still held at the deadline leaves the directory marked `pending-delete`; the next `prune` retries, and the warning names it.
- Child processes (`dolt run` worker, glue compile) must not inherit store handles. SQLite opens its files without inheritance, and E1 verifies that a worker started while a connection is open does not block a delete.
- `ATOMIC_MOVE` of the snapshot temp file happens before any connection opens it.
- On the last connection close in a JVM: `PRAGMA wal_checkpoint(TRUNCATE)` so `-wal` files do not grow.
- Paths go through `java.nio`. CI keeps the project-path-with-spaces checks on Windows, macOS and Linux.

### 9.6 Network drives

SQLite WAL needs shared memory and does not work on network file systems. `status` warns when `.pickleball/` is on a network path that Java can identify. `pkb_dolt_journal=delete` switches to rollback-journal mode for that case (slower, still correct).

## 10. Security

- No server, so no port, no `root` without a password, and no firewall prompt. Access is file permissions on `.pickleball/`.
- No runtime download and no checksum handling. The only native code is inside `sqlite-jdbc` from Maven Central.
- Secrets: entities hold references only, as today. The change log stores the same column values as the rows, so it adds no new exposure. Merge reports show hashes. SQL logging records statement shape and timing, never bound values. `DoltSecretsTest` is extended to the change log and merge report.
- The store is not encrypted, as today.

## 12. Migration

- **From the pre-Dolt SQLite working copy:** today's rules stay (first open imports `db_edited=1` rows and drops run history; `migrate --dry-run|--remove-legacy`; `LegacyNames` refusals). `LegacySqlite.openReadOnly` stays.
- **From an existing Dolt store** (`.pickleball/dolt/data/pickleball/.dolt` present, no `embedded-migrated` marker):
  1. Hydrate the embedded store from files (Git is the source of truth).
  2. If a Dolt 2.7.3 binary is already on the machine (`pkb_dolt_bin`, the old cache `~/.pickleball/tools/dolt/2.7.3/`, or `PATH` with exactly 2.7.3), stop a recorded live server by pid, then run `dolt sql -r json -q "<select>"` in the data directory. The Dolt CLI reads the files directly, with no server and no JDBC driver. Import `files` rows with `db_edited=1` (raw content read as `HEX(raw_content)`) on `main` and on each `sbx-*` branch (as embedded sandboxes with the same name, owner and TTL), and import run-state rows (same schema, ids kept).
  3. If no binary is present, nothing is downloaded. Print `warning: Dolt store found; DB-only edits not imported (no local Dolt binary)` and `fix:` lines (extract them with the previous build, or set `pkb_dolt_bin`).
  4. Print `migrated edits=<n> sandboxes=<n> runs=<n>`, write the marker, and leave `.pickleball/dolt/data`. `migrate --remove-legacy` deletes it after success.
- **Verify in E1:** `dolt sql -r json` output for `HEX(...)` and for working-set (uncommitted) run-state rows.

## 13. What is lost compared with Dolt

| Lost | Impact | Mitigation |
|---|---|---|
| Arbitrary commit history and `AS OF` queries on source tables | Small. Git is the real history; nothing in Pickleball reads old commits except a sandbox base | Change log since the oldest live sandbox, plus hydrate generations |
| `sandbox create --from=<any commit>` | Small; no test or doc workflow uses an old hash besides the hardening test | `--from=main` or `--from=<sandbox>`; hashes refused with a fix line |
| Structural sharing between branches | Disk use is about one store size per sandbox | `prune`, TTL, and section 6.4 if criteria are missed |
| Dolt's cell-level merge on any table | Row-level on `files` and `entities` only; derived tables rebuilt | Same practical result: `raw_content` is one cell anyway |
| Concurrent writers inside one branch | SQLite serializes writers per file | Short transactions; measured 1.1 ms p95 at 16 processes |
| A SQL endpoint other tools can connect to while running | Any SQLite tool can still open the files read-only | Documented |
| Network-shared store | Not supported with WAL | `pkb_dolt_journal=delete`, local disk recommended |

Gained: no 0.5 to 5 s server start (measured 457 ms Linux, 711 to 1,835 ms macOS, 2,151 ms Windows), no ~40 MB download per platform, no MariaDB driver or LGPL question, no port or password exposure, no `journal.idx` wait, live run-state in joins, and a simpler CI.
