# 3.0.0 embedded store design (replaces the Dolt sql-server layer)

**Status:** S3 is in the tree. Hydrate, extract, edits, entities, the step catalog, execution recording, history, query, timeline, and `run` use the embedded SQLite store. `hydrate_generation` increments only when a hydrate changes rows. `dolt status` prints `store=embedded` and `hydrate generation <n> <git sha>` with ` dirty` when the working tree was dirty. The Dolt sql-server is not started by the store. Sandbox CLI commands, the `dolt` name, and the server packages are still present. S1 spike is recorded (sqlite-jdbc 3.47.2.0 on Linux, 2026-11-16). The plan is `docs/roadmaps/3.0.0-embedded-store-roadmap.md`, and the Build prompt is `prompts/build-3.0.0-embedded-store.md`.

On 2026-11-16 Dan locked the rules in section 1 and said to build it.
**Base SHA:** written against `f6cd0406` on `3.0.0`. Implementation happens on branch `3.0.0-embedded-store`, cut from `origin/3.0.0`. The orchestrator merges it into `3.0.0` after verification.

## 1. Locked decisions (Dan, 2026-11-16)

| # | Decision |
|---|---|
| D1 | **Every branch (sandbox) is a fully independent, self-contained SQLite copy** and is responsible for itself. It has no reference to a parent, to `main`, or to any other branch: no lineage chain, no overlay, no shared rows. It records only (a) the Git commit it was created from, and (b) for each tracked file its original hash, its current location, and the Git commit of its current version. Merge compares against those base hashes. |
| D2 | **The only exception is large binary files.** While one is unchanged from its Git commit, a database stores only its location, hash and Git commit (a reference, no bytes). When a branch changes one, the branch's new bytes are copied into that branch's database and it stops referencing. | D3 | **Dolt is removed entirely and cleanly.** No import or migration from Dolt, no aliases, no compatibility shims, no ignored-setting warnings, and no leftover references in code, tests, docs, settings, CI or resources. Nobody ever used the Dolt store, even for testing. |

| D5 | **`sandbox merge`** is a three-way compare of base hashes (recorded at branch creation) against `main` now and the branch now. Default policy `fail`: nothing is applied and a JSON plus text-table conflict report is produced. Optional `branch-wins` and `main-wins`. |
| D6 | **Kept:** `org.xerial:sqlite-jdbc:3.47.2.0` from Maven Central (no version bump), the change-log table and a `changes` command, the write lock with retries, Windows-safe delete waits, sandboxes for parallel agents, Git as the only project sync, CLI-first, and toggleable, date-stamped, size-capped logging. |

Facts that shape the design:

- Git files are the source of truth. Every database is a disposable, compiled copy that is synced both ways with the files and can be rebuilt from them. Git is the only project sync.
- The seam is small. The store opens a session for a `(project, Binding)`, connections are pooled per `(project, branch)`, one dialect class owns every SQL fragment, and the dialect inventory test fails on literal SQL elsewhere. JDBC URLs and `DriverManager` live only in the store's SQL package.
- Before Dolt this layer ran on SQLite (schema versions 1 to 6). The SQLite spelling of every statement exists in Git history, so the port back is mechanical (section 4.3).
- Today there is no merge. Sandboxes leave through `sandbox extract --to=<dir>` or are dropped. Extract keeps working; merge is new.

## 3. Goals and non-goals

**Goals**
1. No server, no child process, no port and no runtime download. Opening the store is opening files.
2. Only Maven Central artifacts and no new dependency: `sqlite-jdbc` is already published.
3. Same capabilities, tables, `--json` shapes and adapters under the `store` names. Tests are ported or replaced by equivalents, never weakened or dropped.
4. Each sandbox is independent of `main` and of every other sandbox.
5. A three-way merge with a clear conflict report and a policy.
6. Large binaries never bloat a copy.
7. Windows, macOS and Linux, including project paths with spaces.

**Non-goals**
- No change to Gherkin syntax, step annotations, the engine, the Cucumber adapter or the diagnostic index.
- No network-shared store (section 9.6).
- The held execution-path audit fixes F1 to F12 and the held move of the Cucumber step model stay held.

## 4. Library

### 4.1 Choice

SQLite through `org.xerial:sqlite-jdbc:3.47.2.0` (Apache-2.0; SQLite itself is public domain). It is on Maven Central, already a published runtime dependency, and bundles the native library for Windows, macOS and Linux (x64 and ARM). It is the only embedded engine evaluated that lets several **processes** read and write one database file without a server. H2, HSQLDB and Derby lock a file database to one process; DuckDB allows one read-write process; Datahike, Chronos (ChronoDB, ChronoGraph) and xitdb-java were evaluated on 2026-11-16 and rejected (not on Maven Central or stale there, AGPL, single writer, or no query engine, and none detects merge conflicts). The SQLite session extension is not compiled into `sqlite-jdbc` and has no Java API, so the change log uses triggers.

`sqlite-jdbc` 3.47.2.0 bundles SQLite 3.47.2: `concat()`, JSON functions, `VACUUM INTO`, and up to 125 attached databases.

### 4.2 Native library on locked-down machines

`sqlite-jdbc` extracts its native library to `java.io.tmpdir`. Where the temp directory is mounted `noexec`, the documented fix is `-Dorg.sqlite.tmpdir=<dir>` (for example `<project>/.pickleball/native`), or `org.sqlite.lib.path` and `org.sqlite.lib.name` for an IT-approved copy. Nothing is downloaded. The first phase verifies the error text and the fix on Linux.

### 4.3 Dialect port

Every statement in the dialect and the statement catalog moves to SQLite: `AUTO_INCREMENT` to `INTEGER PRIMARY KEY AUTOINCREMENT`, `LONGBLOB` and `BIGINT` to `BLOB` and `INTEGER`, `ON DUPLICATE KEY UPDATE col = VALUES(col)` to `ON CONFLICT(<key>) DO UPDATE SET col = excluded.col`, `INSERT IGNORE` to `INSERT OR IGNORE`, `information_schema.columns` to `pragma_table_info`, `CAST(… AS SIGNED)` to `CAST(… AS INTEGER)`. `GET_LOCK`, `SELECT … FOR UPDATE`, `DOLT_*` procedures, `dolt_*` system tables, `HASHOF`, `active_branch()` and `information_schema.PROCESSLIST` are removed. `concat()` stays; never `||` in filter fragments.

## 5. Files on disk

```
<project>/.pickleball/store/              gitignored, disposable, rebuilt from files
  main.db                                 source tables for main, change log, _pkb_branch
  runstate.db                             run-state for main and every sandbox (section 6.6)
  sandboxes/<name>/source.db              independent copy: source tables, change log, _pkb_branch, _pkb_base
  sandboxes/<name>/lease/<pid>.lock       held while a process uses the sandbox

  locks/hydrate-<branch>.lock, locks/sandboxes.lock
  store.log                               when logging is on (section 10)
```

Every `.db` runs in WAL mode, so `-wal` and `-shm` files sit beside it.

## 6. Independent branches (sandboxes)

### 6.1 Rule

A sandbox file is complete on its own. Nothing in it points to `main.db`, another sandbox file, or a parent. Deleting `main.db` or any other sandbox never breaks it, and nothing outside it is needed to read, extract or diff it. The only things outside it that it may name are Git objects (a commit and path, or a blob id) and, for an unchanged large binary, the project file it references (section 7).

### 6.2 Branch tables (in every database file, including `main.db`)

```
_pkb_branch(key TEXT PRIMARY KEY, value TEXT NOT NULL)
  name, created_at (ISO-8601), created_from_commit (git sha, or '' outside Git),
  created_from_dirty (0|1), owner, ttl, store_schema
_pkb_base(tbl TEXT NOT NULL, pk TEXT NOT NULL, base_hash TEXT,
          location TEXT, git_commit TEXT, PRIMARY KEY (tbl, pk))
```

`_pkb_base` is written once at creation: one row per `files` row (`pk` = path) and per `entities` row (`pk` = `entity_type#entity_id`), holding the hash, location and Git commit at that moment. `main.db` has `_pkb_branch` (name `main`) and an empty `_pkb_base`.

### 6.3 Create

`sandbox create <name> [--owner=<id>] [--ttl=<duration>]`. A sandbox is always created from `main`. `--from=<anything other than main>` is refused with a `fix:` line (create from `main`, or `extract` a sandbox and hydrate it).

1. Take `locks/sandboxes.lock`. Refuse an existing name.
2. `VACUUM INTO 'sandboxes/<name>/source.db.tmp'` from `main.db`. It runs in one read transaction, so the copy is consistent while other processes write, and it does not block writers in WAL mode.
3. In the copy: `DELETE FROM _pkb_changes`, write `_pkb_branch`, and fill `_pkb_base` from the copied `files` and `entities` rows.
4. Move the temp file to `source.db` with `ATOMIC_MOVE` before any connection opens it.

Measured on the maintainer box (SQLite 3.46.1, 2026-11-15): `VACUUM INTO` takes 25 ms for 10 MB, 194 ms for 100 MB and 1,037 ms for 500 MB. `maven-consumer-project/src` is 1.5 MB. Large binaries are references (section 7), so copies stay small.

### 6.4 Binding

`Binding.main()` opens `main.db`. `Binding.sandbox(name)` opens `sandboxes/<name>/source.db` and fails with today's unknown-sandbox message when it is missing. "Which branch am I on" reads `_pkb_branch.name`.

### 6.5 List, diff, extract, drop, prune

- `sandbox list` scans `sandboxes/*/source.db` and reads each `_pkb_branch` (name, owner, TTL, created, created-from commit) plus lease state. There is no central registry: each sandbox describes itself.
- `sandbox diff <name> [--table] [--json]` compares the sandbox's current rows with its own `_pkb_base` (`op` is `insert`, `update` or `delete`, values shown as hashes). It reads only the sandbox file.
- `sandbox extract` writes files from the sandbox file. A referenced large binary is left in place (section 7.4).
- `sandbox drop [--force]` and `prune [--older-than] [--owner] [--dry-run] [--with-history] [--vacuum]` close this JVM's pool for the sandbox, check leases (9.3), delete the directory with the Windows release wait (9.5), and with `--with-history` delete that sandbox's run-state rows. `VACUUM` of `main.db` runs on `prune --vacuum` or when the free-page ratio is over 25%.

### 6.6 Run-state

Run-state is project-level run history, not branch data, so all branches write to one `runstate.db` with the `sandbox` column, as today. No branch file holds a pointer to it.

- Pure run-state statements run on a `runstate.db` session.
- A statement that joins run-state to source tables runs on the bound source session with `runstate.db` attached read-only as `rs`. No table name exists in both files, so catalog SQL does not change, and joins see live run-state.
- `step_executions.definition_id` has no cross-file foreign key. A `definition_id` missing from the bound branch is stored as null, in code.
- The first phase verifies that `BEGIN IMMEDIATE` on a source session takes no write lock on the read-only attached `runstate.db`.

## 7. Files and large binaries

### 7.1 Per-file tracking

`files` keeps its columns (`path`, `content_hash`, `raw_content`, `mtime`, `source_type`, `last_hydrated_at`, `last_synced_hash`, `db_edited`, `git_blob`, `binary_ref`, `byte_size`) and adds:

- `location`: `db` when the bytes are in this database, or the project-relative path of the referenced file.
- `git_commit`: the commit whose blob equals the current bytes (the `HEAD` sha when the worktree file matches `HEAD` at hydrate time), or `''` when the current bytes exist only in this database.

Together with `_pkb_base` that is exactly D1: original hash, current location, Git commit of the current version.

### 7.2 Which files are references

- Binary detection is today's: the extension list plus the content sniff.
- `pkb_store_binary_policy` (`store.properties` key `binary-policy`): `skip` (default, as today: binaries are not tracked) or `include`. `hash-only` is replaced by `include` (no alias).
- With `include`, a binary file of `pkb_store_large_file_bytes` bytes or more (default `262144`, 256 KiB; `store.properties` key `large-file-bytes`; `0` means every binary) is a **large binary**. Every other tracked file, including a smaller binary, is stored in the database.
- A large binary is stored as a reference only when its bytes equal the Git blob at `git_commit`. Then `binary_ref=1`, `raw_content` is empty, `location` is its path, and `content_hash`, `git_blob`, `git_commit` and `byte_size` are set. A large binary that is not committed (dirty or untracked) is stored with its bytes (`binary_ref=0`, `location='db'`, `git_commit=''`), because nothing else can restore it.
- `max-file-size` (`pkb_store_max_file_size`, default 1 MiB) applies to files stored in the database. A reference costs no bytes, so references are exempt.

### 7.3 Reading a reference

Read the file at `location` and check its hash. If it is missing or its hash differs, read the original from Git by blob id (`git cat-file blob <git_blob>`, or `git show <git_commit>:<path>`) through the existing Git helper. If both fail, fail with `error: large file <path> unavailable (hash <h>, commit <c>)` and a `fix:` line. Opening the store never starts a process; only this on-demand fallback may run `git`.

### 7.4 Changing a large binary in a branch

Any store write that changes a referenced file's bytes in a branch (`file put`, an edit command, `merge`, or hydrate of a changed worktree file) copies the new bytes into that branch's database: `binary_ref=0`, `location='db'`, `git_commit=''`, new `content_hash`, `db_edited=1`. That branch stops referencing. Other branches and the project file are untouched. Extract writes owned bytes to disk with the normal both-changed refusal, and leaves an unchanged reference alone (today's `binary_ref_changed` notice stays).

## 8. Merge

`pickleball store sandbox merge <name> [--policy=fail|branch-wins|main-wins] [--dry-run] [--drop] [--json]`. CLI-first: the Gradle sandbox task, the Workbench sandbox picker and MCP `store` forward it. A sandbox always merges into `main`.

### 8.1 What is merged

- `files` (key `path`) and `entities` (key `entity_type#entity_id`) row by row.
- Derived tables (`feature_docs`, `scenarios`, `example_blocks`, `steps`) are rebuilt for each merged `.feature` path with the projection `feature put` uses. `step_definitions` is refreshed for merged `.java`, `.js` and `.ts` paths.
- `schema_meta`, `provenance`, `_pkb_branch`, `_pkb_base`, the change log and run-state are never merged.
- A merged file lands in `main` with `db_edited=1` and keeps `main`'s `last_synced_hash`, so `extract` keeps its both-changed refusal. A merged large binary that the sandbox owned lands in `main` as owned bytes.

### 8.2 Three-way compare by hash

For each key in the union of the sandbox's `_pkb_base`, the sandbox's current rows and `main`'s current rows:

- **base** = `_pkb_base.base_hash` (absent if the key did not exist at creation).
- **branch** = the sandbox's current hash (absent if deleted).
- **main** = `main`'s current hash (absent if deleted).

The identity hash is `content_hash` for `files` and the hash of (`payload_json`, `secret_refs`, `content_hash`) for `entities`.

| Branch vs base | Main vs base | Branch vs main | Result |
|---|---|---|---|
| Same | any | any | Nothing to do |
| Different | Same | any | Apply the branch row (insert, update or delete) |
| Different | Different | Same | `converged`, nothing to do |
| Different | Different | Different | **Conflict** |

### 8.3 Policies

- `fail` (default): if any conflict exists, nothing is written to `main`, the report is printed and saved, and the exit code is 1.
- `branch-wins`: conflicting keys take the branch row; the rest apply normally.
- `main-wins`: conflicting keys keep `main`; the rest apply normally.

The merge is one `BEGIN IMMEDIATE` transaction on `main.db` with the sandbox file attached read-only; any failure rolls back everything. `--dry-run` prints the plan and writes nothing. After a successful merge the sandbox's `_pkb_base` is rewritten to the merged hashes, so repeating the merge is a no-op. `--drop` then drops the sandbox with the normal in-use check.

### 8.4 Report

One JSON object (`--json`), the same data as a text table, saved to `sandboxes/<name>/merge-<ISO-8601>.json`:

```
{ "ok": false, "command": "sandbox merge", "sandbox": "fix-login", "policy": "fail",
  "createdFromCommit": "<sha>", "applied": 0, "converged": 1, "wouldApply": 3,
  "conflicts": [ { "table": "files", "key": "features/login.feature",
                   "base": "sha256:…", "main": "sha256:…", "branch": "sha256:…",
                   "resolution": "none" } ] }
```

Rows appear as hashes and sizes, never raw content or secret values. Text output ends with `fix:` lines naming `--policy=branch-wins`, `--policy=main-wins`, or `sandbox extract` plus Git.

## 9. Concurrency and platforms

### 9.1 Connections
Every connection sets `journal_mode=WAL` (once per file), `busy_timeout=5000`, `foreign_keys=ON` and `synchronous=NORMAL`. The per-JVM pool per `(project, branch)` stays (max 4, idle close 60 s).

### 9.2 Write lock and retries
- Every write transaction starts with `BEGIN IMMEDIATE`, so the write lock is taken up front. SQLite allows one writer per file.
- `SQLITE_BUSY` after the busy timeout retries 3 times with 50 to 200 ms jitter, then fails with `error: concurrent update on <table>`.
- Hydrate and extract per branch are serialized by `locks/hydrate-<branch>.lock` (exclusive `FileChannel.lock`); hydrate reads the disk first and writes in one short transaction at the end.
- Measured on the box (Python `sqlite3`, WAL, 2026-11-15): 16 processes x 200 `BEGIN IMMEDIATE` inserts, no failures, p95 1.1 ms. The first phase repeats this with `sqlite-jdbc` on three operating systems.

### 9.3 Leases and in-use refusal
A process that binds a sandbox holds an exclusive `FileChannel.lock` on `sandboxes/<name>/lease/<pid>.lock` until it closes the store or exits. The OS drops it when a process dies, so no stale lease remains. `drop` and `prune` `tryLock` each lease; a held lease means in use (`skipped <name> in use`, or a refusal without `--force`). This JVM's own leases are tracked in memory.

### 9.4 One sandbox per JVM
Unchanged.

### 9.5 Windows-safe delete
Close this JVM's pool for the sandbox, then wait up to 15 s for `source.db`, `-wal` and `-shm` to be released, probing by renaming each aside and back. A file still held at the deadline leaves the directory marked `pending-delete`; the next `prune` retries and the warning names it. Child processes (warm worker, glue compile) must not inherit store handles; the first phase verifies a worker started while a connection is open does not block a delete. On the last close in a JVM run `PRAGMA wal_checkpoint(TRUNCATE)`. All paths go through `java.nio`.

### 9.6 Network drives
WAL does not work on network file systems. `status` warns when `.pickleball/` is on a network path Java can identify. `pkb_store_journal=delete` switches to rollback-journal mode for that case.

## 10. Change log, history and logging

### 10.1 Change log
Every source database has:
```
_pkb_changes(seq INTEGER PRIMARY KEY AUTOINCREMENT, at TEXT NOT NULL, tbl TEXT NOT NULL,
             pk TEXT NOT NULL, op TEXT NOT NULL, old TEXT, new TEXT, actor TEXT NOT NULL DEFAULT '')
```
`AFTER INSERT|UPDATE|DELETE` triggers on `files`, `entities` and `step_definitions`, generated from `PRAGMA table_info` at schema create or upgrade, write one row per changed row (`json_object` of the columns). JSON cannot hold a BLOB, so `raw_content` is left out and `content_hash`, `binary_ref`, `location` and `byte_size` identify it; a guard test fails if a logged table gains a BLOB column without a hash column. `actor` is the branch name plus the command (`hydrate`, `feature put`, `merge`), set per connection through a one-row temp table. The change log is an audit trail and feeds `changes`; merge does not depend on it (merge uses `_pkb_base`).

### 10.2 `changes` command and retention
`pickleball store changes [--sandbox=<name>] [--since=<seq>] [--table=<t>] [--limit=<n>] [--json]`. Retention: `pkb_store_changes_days` (default 14); `retain` and `prune` trim it.

### 10.3 Hydrate generations
`schema_meta` keys `hydrate_generation` (incremented only when a hydrate changes rows) and `hydrate_label`. `status` prints `hydrate generation <n> <git sha>[ dirty]` and `store=embedded`.

### 10.4 Run history, timeline, rewind
Same tables in `runstate.db`. Paging, filters, `total`, `retain` and Workbench Tracking unchanged. Rewind stays view-only.

### 10.5 Logging
Off unless `pkb_store_log` (or `PKB_STORE_LOG`) names capabilities (`all`, or a list of `hydrate`, `extract`, `sql`, `sandbox`, `merge`, `changes`, `refs`, `glue`, `migrate`, `run`). `pkb_store_log_entity` limits lines to named entities. `pkb_store_log_max_bytes` caps `.pickleball/store/store.log` (oldest bytes dropped). Every line starts with an ISO-8601 timestamp and carries the branch name. SQL logging records statement shape and timing, never bound values.

## 12. Removal of Dolt

### 12.1 Removed with no replacement
- Packages and classes: the server (`DoltServer`, `DoltServerSupervisor`), the installer (`DoltInstaller`, `DoltPlatform`, `DoltReleaseCatalog`), `DoltJdbc`, `META-INF/pickleball/dolt-release.properties`, port handling, the binary download and checksum code, `GET_LOCK` and `PROCESSLIST` code.
- `org.mariadb.jdbc:mariadb-java-client` from `build.gradle`, the published POM, task classpaths, `THIRD-PARTY-NOTICES.md` and the POM check.
- Commands `install` and `server start|stop|status`, Gradle `doltInstall` and `doltServer`, the Workbench server forwarding, and their help text. A removed command gets the normal unknown-command error.
- Settings `pkb_dolt_bin`, `pkb_dolt_auto_install`, `pkb_dolt_port`, `pkb_dolt_server_start_ms`, `pkb_dolt_server_idle_minutes`, `pkb_dolt_server_log_max_bytes`, `pkb_dolt_tool_cache`. No warning shim: like any unknown setting they are simply not read.
- CI: the Dolt cache and install steps and the server-start timing steps on every job, replaced by store-open timing and the store test steps.
- No import or migration from a Dolt data directory.
- Docs: `docs/maintainer/3.0.0-dolt-core-design.md`, `docs/maintainer/3.0.0-dolt-working-copy-design.md` (its still-true content moves into this design) and `docs/maintainer/dolt-isolation-analysis-2026-11-15.md` are deleted from the tree (Git history keeps them). `docs/roadmaps/3.0.0-dolt-core-roadmap.md` and `prompts/build-3.0.0-dolt-core.md` are deleted the same way. Every other doc is edited in place.

- `docs/release-notes.md`: past entries stay intact as history. The 3.0.0 Dolt entries get one leading line, `Superseded: the embedded store replaced this before release.` The new store entry may name what it replaced.
- The roadmap and Build prompt are the planning record of the removal and are the only other exceptions.
- This design doc is rewritten as-built in the last phase and then contains none of the words.
- The pattern is case-insensitive, so `Dolt`, `DOLT` and `dolt` all count. The pre-Dolt former name does not match it and stays governed by `RenameGateTest`.
- A test, `tools.dscode.store.NoDoltLeftTest`, enforces the same rule in CI. It builds its pattern from pieces so it does not match itself, like `NoRustLeftTest`.

## 13. Security
- No server: no port, no password-less `root`, no firewall prompt. Access is file permissions on `.pickleball/`.
- No runtime download. The only native code is inside `sqlite-jdbc` from Maven Central.
- Entities hold secret references only. The change log, `_pkb_base` and merge reports hold the same columns or only hashes, so they add no exposure. SQL logging never logs bound values. `StoreSecretsTest` covers the change log, branch tables and merge report.
- The store is not encrypted, as today.

## 14. Compared with Dolt
Lost: commit history and `AS OF` queries on source tables (Git is the history; the change log covers audits), branching from an arbitrary commit (sandboxes come from `main`), structural sharing between branches (copies are small; large binaries are references), Dolt's cell-level merge (row level on `files` and `entities`, derived tables rebuilt), concurrent writers inside one branch (SQLite serializes writers per file; transactions are short), and a network SQL endpoint.
Gained: no 0.5 to 5 s server start, no ~40 MB per-platform download from GitHub, no LGPL driver question, no port or password exposure, no journal wait, independent branches, a real merge, live run-state in joins, and simpler CI.

## 15. Performance targets

| Record one step execution, 16 concurrent processes | 5 ms (`STORE_MP_P95_MS`) | 16 processes × 200 `BEGIN IMMEDIATE` inserts, no lost rows. p95 was 0 ms (sub-millisecond). One sample reached 756 ms. |
