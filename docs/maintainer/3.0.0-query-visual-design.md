# Pickleball 3.0.0 Query-Visual Design

**Status:** Design locked 2026-11-12. Implementation on branch `3.0.0-query-visual` only (off tip of origin/3.0.0). Do not push to 3.0.0 itself.

## Locked Direction

Additive, backward-compatible extension of the Java engine query language (`dev.domengine.query`) and the Pickleball EngineQuery / dynamic-step path.

### Boolean Combination (AND / OR / NOT)
- Existing `>>` pipeline remains pure sequential: each stage receives the previous node set and returns the next set. Semantics unchanged.
- Boolean operators are an expression layer that combines node-set results of stages or parenthesized sub-expressions.
- Precedence: parentheses highest, then NOT, AND, OR; `>>` is lowest (outer sequential pipeline).
- AND is intersection of the node sets produced by each side applied to the same starting scope (or previous stage result). OR is union. NOT is complement relative to the current scope.
- Parentheses required for mixed expressions to avoid ambiguity. EngineQuery.seleniumFallback already returns null on AND/OR/NOT, so Selenium path is unaffected.
- CLI: `domengine query --selector "(css=button AND text=\"Submit\") >> near=50"` or equivalent flags.

### Visual Relatives (above, left-of, right-of)
- New pipeline engines parallel to existing `near` and `below`.
- Geometry: bounding box in document_css_px (or visual-viewport-relative when exposure=human). Requires hasBox and displayed.
- Definitions (consistent with below):
  - above: candidate.y + candidate.height <= anchor.y
  - left-of: candidate.x + candidate.width <= anchor.x
  - right-of: candidate.x >= anchor.x + anchor.width
- Sort by distance (like near). Pierce/shadow/frames as today. near and below unchanged.
- EngineQuery.visualRelative already recognizes them; engine now implements.

### Visual Property: "look"
- Name chosen: **look** (not "attribute", "style", or "visual").
- Reasons: zero collision with step-grammar existence keyword "attribute"/"noattribute", with CSS/XPath/a11y treating "attribute" as a real HTML attribute name, or with existing engines. Natural English ("the button that looks red").
- What it measures: computed style properties (color, background-color, opacity, display, visibility, font-size, font-weight, etc.) plus simple derived metrics (e.g. contrast if cheap to compute). Not screenshot pixels (image engine already covers template matching).
- Engine syntax (pipeline stage): `look=color=red` or `look=opacity>0.5,background-color=#fff` (comma AND, pipe OR inside the stage, similar to a11y).
- Pickleball step text: additive only. New optional clause "with look <prop> <predicate>" (e.g. "with look color equaling red" or "with look opacity greater than 0.5") that SelectorTranslator / adapter maps to a look= stage. Existing "with id attribute" / "with id noattribute" and all Gherkin unchanged. Cucumber annotations remain single string literals.

### EngineQuery and Adapters
- EngineQuery record does **not** grow. The Java engine simply honors more of the existing `query.text()` language (Boolean operators, the three new relative engines, and look stages).
- DomCompositeAdapter.findEngine / queryEngine and PageElementQuery.find(EngineQuery) continue to forward `query.text()` as the selector string. No new fields required on the wire.
- CLI-first: every new capability reachable from `domengine` CLI. Workbench / MCP / Gradle only forward.

### Backward-Compatibility Guarantees
- Existing `>>` pipelines keep identical meaning.
- Existing a11y `|` (OR groups) and `,` (AND predicates) unchanged.
- CSS/XPath/a11y attribute matching unchanged. There is still no engine named "attribute".
- Dynamic-step grammar and all existing Gherkin phrases unchanged. New look syntax is purely additive.
- YAML Selenium browser configs and the ordinary Selenium path unchanged.
- Element-type dictionary / XPathyAssembly unchanged.
- Logging remains off by default, toggleable, per-entity, date-stamped, size-capped (COMPOSITE_LOG / DOMENGINE_LOG, 10 MB front-trim).

## Breaking-Change List
None. All changes are additive. No existing token is reinterpreted. No existing test is weakened or deleted.
