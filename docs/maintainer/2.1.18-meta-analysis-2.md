## 2. Common patterns

1. **Partial or non-landing of structural claims**: Phase 5 per-attempt isolation is described in release notes (.pickleball/runs/.../attempts/) but consumer still sees accumulation under reports/diagnostic-runs/<run-id>/. Query/summary readers and the diagnostic pack writer are not on the same path. B1 is the clearest example of a "done" item that did not survive the real consumer workflow.

2. **Failure reporting still multi-path and lossy**: Phase 7 claimed filling of phrase/message/stackHead and dropping empty failure rows, yet B2/B3/B4 show nulls, internal stackHeads, missing real cause, and duplicate empty rows. The execute-step worker path, the event recorder, and DiagnosticQuery each transform the failure differently. Real cause is lost before it reaches the consumer-facing surfaces.

3. **Duplicate launch / exit-code paths**: mvnw exec:java, java -cp @classpath.cache, and .pickleball/open/ scripts still disagree on usage-error exit codes (B9). One shared launcher was the Phase 4 goal; residual wrappers re-introduce divergence.

4. **String-formatted outputs that cannot be parsed safely**: failedScenarios comma-joined when names contain commas (B5); long lines (U5); circular fix text (B7); fix lines that name a folder instead of a remedy (U4).

5. **Lifecycle / state across attempts and seeds**: retained profiles replay protected references that the seed warning says will fail (B6); hint on uncompiled still silent (B10, vs discover); computed marking does not match hook-computed values that differ per seed (U2). Snapshot vs ambient, attempt vs current, and seed-time vs launch-time values keep diverging.

6. **Windows / shell / wrapper-only defects still appear**: quoting (U3), exit codes, cold start times. Even with a Windows CI harness, the exact consumer combination (PowerShell + mvnw exec:java + open scripts + absolute paths) is not fully covered, or the harness asserts a different path than the one the reporter hits.

7. **Docs / release-note promises vs code**: AGENT-GUIDE size (D2), pointer-eval still exported (D1), status idle, exit 2, under-5KB. Goldens and harness catch some but not the exact consumer transcript.

8. **Complexity tax**: multiple launch styles, string-formatted summaries, layered diagnostic stores (reports/ vs .pickleball/runs/ vs attempts/), and per-surface failure munging make each individual fix hard to verify and easy to regress. Agent confusion from any of these is itself a bug.

Past fixes that regressed or only partly landed: B1 (vs Phase 5), B2/B3/B4 (vs Phase 7 B9/B13), U2 (vs Phase 7 N13), B8 (vs status idle), B9 (vs Phase 7 exit-code), B10 (vs Phase 4 hint warn).

## 4. Simpler approach recommendations (Dan's philosophy)

Fix bugginess through simplicity, elegance, and one shared code path, not one tweak per bug. Agent confusion counts as a bug.

Concrete simplifications that would delete or unify:

1. **One diagnostic attempt store used by writer and every reader**. Delete the dual paths (reports/diagnostic-runs/ vs .pickleball/runs/<id>/diagnostic vs attempts/). On relaunch, archive or replace atomically; every query, summary, and events reader opens only the current attempt. This collapses B1 as a class and removes the need for per-surface "count only latest" patches.

2. **One failure event model**. A single structured failure object (phrase, message, cause chain, stackHead, step text) is written once by the worker and read unchanged by execute-step JSON, events, query errors/tail, and summary. Delete the per-surface munging that currently drops the real cause or inserts empty rows. This collapses B2/B3/B4.

3. **One launcher and one exit-code contract**. All entry points (mvnw exec:java, java -cp, openers, MCP) call the same PickleballWorkbenchLauncher; usage errors always exit 2. Delete residual wrappers that re-map exit codes. Collapses B9.

4. **Structured outputs instead of free-text summaries**. failedScenarios as a JSON array (or quoted fields), not comma-joined. Fix texts that are machine-parseable and non-circular. Status as a structured state (idle / running / step-ms). This removes B5, U5, B7, B8 parsing fragility.

5. **One seed-to-launch profile path**. Retained pkb_run_profile is either fully replayable or explicitly rejected at seed time with a single warning shared by hint and seed. No form that the warning says will fail is ever written. Collapses B6/B10.

6. **Shrink the surface**. Freeze new verbs and feature ideas (O1-O7) until the diagnostic store, failure model, and launcher are unified. The consumer harness should drive the exact commands the reporter uses and assert the exact transcripts; goldens cover the remaining docs.

These changes delete more code (duplicate writers/readers, string formatters, exit-code special cases) than they add, and make future reports harder to generate.

## 5. Suggested shape for the next roadmap (not the roadmap)

Do not list individual B/U/S items. Shape it as three structural phases plus a verification gate:

- Phase A: Unify the diagnostic attempt store (writer + all readers). Prove with a harness rerun that counts and query results never accumulate.
- Phase B: Unify the failure event model end-to-end (worker → execute-step / events / query). Prove real cause survives for both defined and undefined steps; no empty duplicates.
- Phase C: Unify launcher + exit codes + structured summary/status. Prove usage errors exit 2 on every entry point; failedScenarios is structured.
- Gate: Consumer-sim harness on Windows (exact PowerShell + mvnw + open/ + absolute paths) and Linux must pass the new structural assertions before any further feature work.

Everything else (perf stages, docs size, feature ideas) waits until A-C are green.
