# Pickleball 3.0.0 Workbench Full-Edit + DOM Engine Core Design

**Branch:** `3.0.0` only. Start SHA: `6a1bf40d`. Updated tip: `00e51db`.

**Version:** stays `3.0.0`.

**Locked direction (2026-11-12, final for this round):** Single consistent CLI-first edit model for four Workbench surfaces, Java DOM engine packaged as core of the pickleball jar, and live native desktop access (Windows UIA, macOS AX, Linux AT-SPI) with a single consistent query/verb/walk model shared with the browser DOM. Fixture backend retained. All surfaces CLI-first via thin forwarders. No business logic in Workbench. No change to existing Gherkin syntax or Cucumber annotation rules. Selenium fallback remains. Breaking-change list empty.

## Single edit model (Workbench GUI surfaces)

One CLI family with stable `--json`:

- `dalton category list|show|put|remove`
- `dalton feature scenario-add|scenario-modify|scenario-delete|step-add|step-modify|step-delete` (regenerate valid Gherkin then existing `feature put`)
- `dalton file put|delete`
- `dalton glue list|show|put|remove`

Workbench: unified Editor reusing DaltonPanel list+text pattern. All actions via `DaltonCliForwarder` only. Deletes confirmed. Validation before write. Conflicts via existing `db_edited`/untracked. Logging checklist every phase.

## 1. Element categories

Project categories as editable YAML entities under `dalton-entities/ElementCategory/`, loaded after built-ins. Built-ins immutable (overlay only). Reserved blocked. `Loading`/`ALL_CONTEXTS` special-cased. Next-run effect. Dalton-on uses entity put; Dalton-off writes file.

## 2. Scenarios and scenario steps

Structured helpers parse, apply change, regenerate Gherkin (normalize indent on edited regions, preserve comments where possible, always valid), then existing `feature put` or direct file write. No direct row updates. Conflicts preserved. Gherkin syntax unchanged.

## 3. General configuration and data files

Extend file put/delete for configs, dalton.properties, run vars, JSON/YAML/CSV data. Secret redaction via existing path. Dalton-on through DB where applicable.

## 4. Java and JS/TS step-definition functions

Java: glue put validates single-string-literal annotations, triggers fingerprint/restart. Compile fail leaves prior worker. JS/TS: source-only first slice; document future binding. No break to Java.

## 5. Java DOM engine as core of Pickleball (packaging and integration)

Fix `shadowJar from(...)` so `dev.domengine` classes and sources are in the pickleball jar and sources jar. Verification test fails if missing. No separate published `dom-engine` artifact. Engine is default path; Workbench reaches it CLI-first via thin forwarders. API stays general-purpose (`dev.domengine`). Selenium fallback (`pkb_composite=off`) works. ## 6. Live native desktop access and consistent browser/desktop model (mandatory)

**Current:** `dev.domengine.desktop.DesktopTree` is fixture-only. Comment states fixture replays a recorded tree on every OS; native AT-SPI / UIA / AX not required for that path. `attach` requires a fixture file. `click` and `type` only mutate or report on the in-memory tree; they do not drive real OS windows. CLI verbs already exist: desktop list, attach, walk, query, resolve, close, click, type. Old Rust composite shipped native binaries for linux-x64, linux-aarch64, windows-x64, macos-aarch64, macos-x64. Locked Java design called for DesktopTree (accessibility via Java/AT or fixture fallback; native desktop verbs where possible). Phase 0: fixture path; native AT where feasible. Phase 3 scored done with only the fixture backend.

**Design:**
- Implement live native desktop access on the machine where the engine is running:
  - Windows: UI Automation (UIA)
  - macOS: Accessibility (AX)
  - Linux: AT-SPI
- Keep the fixture backend for tests and offline use. Live attach must work without a fixture against real desktop windows.
- Live click, type, and the other desktop verbs must actually act on the real UI, not only return ok on a recorded tree.
- CLI-first: every live desktop capability is on the CLI; GUI/MCP only forward. Logging checklist applies.
- Targeted tests for the live path where the OS allows, plus fixture tests so CI on a headless runner still proves the API. Do not weaken existing tests.
- Package this as part of the pickleball jar (same as the rest of the Java engine).

**Consistency rule (mandatory):**
- One query language, one verb set, and one walk/attach/resolve model for the browser DOM and for live native desktop UI on Windows (UIA), macOS (AX), and Linux (AT-SPI).
- Functionality, syntax, and logic should match as closely as the platforms allow. A step or CLI invocation that finds or acts on a browser element should look and behave the same way when the target is a desktop window or control, except where a real platform difference makes that impossible — and those exceptions must be named and justified in the design, not left implicit.
- Do not invent a second parallel API or a different selector dialect for desktop.
- Keep the fixture backend for tests. Live paths and the browser path share the same CLI surface and the same core logic.

Named platform exceptions (to be expanded in implementation if more arise):
- Accessibility tree shapes differ (role names, hierarchy depth, bounds units). Map to the shared model; document unmappable attributes.
- Input injection (click/type) may require elevated permissions or focus on some platforms; fail clearly rather than silently no-op.
- Shadow/pierce and frame contexts are browser-only; desktop has no equivalent and must not invent one.
- Image/OCR template matching may differ in precision; share the same CLI verb and document the backend difference.

## Backward-compatibility guarantees

- Existing Gherkin syntax unchanged.
- Cucumber step annotations stay single string literals.
- Dalton `db_edited` / extract / conflict behavior preserved.
- Existing Workbench collaboration features left alone unless a small non-breaking hook is required.
- Dalton-off remains file-only except new optional CLI writes.
- Selenium fallback (`pkb_composite=off`) works.
- Fixture desktop backend continues to work for tests/CI.
- No separate published `dom-engine` artifact.
- Engine API remains general-purpose (`dev.domengine`).

## Breaking-change list

(Empty.) All changes are additive. No reinterpretation of existing syntax, annotations, Dalton semantics, Selenium fallback, or fixture path.

## CLI-first and logging checklist

Every new capability reachable from the CLI. Workbench, MCP, and Gradle only forward. No business logic or SQLite/core calls in Workbench. Toggleable, per-entity, date-stamped, size-capped logging.

Checklist at end of every phase:
- [ ] CLI command exists and is documented
- [ ] Workbench action forwards to CLI
- [ ] MCP tool forwards to CLI
- [ ] Gradle task (if any) forwards to CLI
- [ ] Logging is toggleable, per-entity, date-stamped, and size-capped
- [ ] Existing tests still pass; no regressions in file-only / Dalton-off / Selenium fallback / fixture desktop
- [ ] For engine packaging: verification test fails if `dev.domengine` classes or sources missing from jar / sources jar
- [ ] For live desktop: fixture tests pass on headless CI; live tests run where OS allows and fail clearly otherwise
