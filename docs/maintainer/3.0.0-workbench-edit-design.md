# Pickleball 3.0.0 Workbench Full-Edit Design

**Branch:** `3.0.0` only. Start SHA: `6a1bf40d` ("Record the fix-back 1 scoreboard commit").

**Version:** stays `3.0.0`.

**Locked direction (2026-11-12):** Single consistent CLI-first edit model for four surfaces so the Workbench GUI can add, delete, and modify everything. All surfaces reuse or extend existing Dalton CLI and DaltonPanel patterns. No business logic in the Workbench. No change to existing Gherkin syntax or Cucumber annotation rules.

## Single edit model

One CLI family with stable `--json` output:

- `dalton category list|show|put|remove`
- `dalton feature scenario-add|scenario-modify|scenario-delete|step-add|step-modify|step-delete` (helpers that regenerate feature text then call existing `feature put`)
- `dalton file put|delete` (extends existing files for configs and data)
- `dalton glue list|show|put|remove`

Workbench: one unified Editor area that reuses the DaltonPanel list + text editor pattern. All actions forward exclusively through `DaltonCliForwarder`. Deletes require confirmation (`--force` on CLI, dialog in GUI). Validation before write. Conflicts use existing `db_edited` / untracked detection. Undo is extract + git or re-hydrate; no separate undo stack in v1.

Logging checklist on every phase: toggleable, per-entity, date-stamped, size-capped.

## 1. Element categories

**Current:** Pure Java registration in `ExecutionDictionary` / `DefinitionContext`. Built-ins in code. Project overlays in Java (see `docs/custom-element-definitions.md`). Reserved names warn and are ignored. No data path, no CLI, no Workbench screen.

**Design:** Project categories become editable data. New entity type `ElementCategory` stored as YAML under `dalton-entities/ElementCategory/<name>.entity` (or a dedicated `element-categories/*.yaml` that Dalton hydrates). Loaded at startup after built-in registration. Built-ins are immutable (show-only; overlay via `addBase`/`reset` semantics only). Project can add, overlay, or delete custom categories. Reserved names (`Step *`, Data Elements, `Loading` special, browser names, etc.) are blocked at put time. `Loading` / `ALL_CONTEXTS` protected: only allow additional `or` clauses or explicit `restoreBuiltinLoading`. Changing a category takes effect on the next run (dictionary rebuilt; no mysterious cache). Dalton-on uses entity put path and sets `db_edited`. Dalton-off writes the YAML file directly.

CLI: `dalton category list|show|put --payload-file|remove`. GUI view in the Editor.

## 2. Scenarios and scenario steps

**Current:** Round 2 rejected direct scenario/step row updates. Only full feature text via `dalton feature put` (validates Gherkin, sets `db_edited`, reprojects). Byte-stability of comments/whitespace was the risk.

**Design:** Structured helpers that:
1. Load current feature text (DB or file).
2. Parse to model.
3. Apply add/modify/delete of scenario or step.
4. Regenerate full Gherkin text with documented policy: normalize indentation to 2 spaces in edited regions, preserve leading comments and unedited blocks where the AST allows, otherwise document that whitespace may normalize. Always produce valid Gherkin.
5. Call existing `feature put` (or write the `.feature` file when Dalton is off).

No silent clobber of unflagged or file-side changes. Conflict detection remains. Dalton-off projects can still edit files. Existing Gherkin syntax unchanged.

## 3. General configuration and data files

**Current:** Config tab edits run-workspace configs only. Run vars via panels. Data files browsable via Dalton files. No full add/delete/modify for project configs and data.

**Design:** Extend Dalton file discovery and add `dalton file put <relative-path> [--text|--file] [--force]` and `dalton file delete <relative-path> [--force]`. Covers YAML Selenium configs, `dalton.properties`, run vars files, project test data (JSON, YAML, CSV, example tables, etc.). Secrets: reuse existing `secret-fields` redaction; never display or write cleartext secrets if a redaction path exists. Dalton-on persists through the DB edit path when the file is in the database. Dalton-off writes the file.

## 4. Java and JS/TS step-definition functions

**Current:** Java glue only. Cucumber annotations must stay single string literals with identical values. Glue fingerprint change restarts the warm worker. No JS/TS step-definition runtime exists.

**Design:** 
- Java: `dalton glue list|show|put|remove`. Put writes the `.java` file, validates that step annotations remain single string literals, then triggers the existing fingerprint/restart behavior. Compile failure leaves the previous worker running and reports the error.
- JS/TS: **Major issue.** No runtime exists. Recommended first slice: store editable `.js` / `.ts` source under a `glue/js` (or similar) directory via the same CLI. Document that binding to the native engine is a later phase. Do not break existing Java glue or Gherkin. If a simple binder is feasible without major risk, include a minimal stub; otherwise flag clearly and ship the source editor.

A glue edit must keep the existing restart-on-change behavior.

## Backward-compatibility guarantees

- Existing Gherkin syntax unchanged.
- Cucumber step annotations stay single string literals (no constants or concatenation).
- Dalton `db_edited`, extract, hydrate, and conflict behavior preserved.
- Existing Workbench tabs and collaboration features (chat, overlays, highlights, launch templates, HTML-on-the-fly) left alone unless a small hook is required.
- Dalton-off path remains file-only and unchanged except for new optional CLI writes.
- Built-in categories and reserved names stay protected.

## Breaking-change list

(Empty.) All changes are additive. No reinterpretation of existing syntax, annotations, or Dalton semantics.

## CLI-first and logging checklist

Every new capability is reachable from the CLI. Workbench, MCP, and Gradle only forward to the CLI. No business logic and no direct SQLite or core library calls in the Workbench. Toggleable, per-entity, date-stamped, size-capped logging on new or changed code.

Checklist at the end of every phase:
- [ ] CLI command exists and is documented
- [ ] Workbench action forwards to CLI
- [ ] MCP tool forwards to CLI
- [ ] Gradle task (if any) forwards to CLI
- [ ] Logging is toggleable, per-entity, date-stamped, and size-capped
- [ ] Existing tests still pass; no regressions in file-only / Dalton-off mode
