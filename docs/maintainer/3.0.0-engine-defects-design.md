**Pickleball 3.0.0 Engine Defects Design**

**Tip verified against:** `8624a2097f0844b966f827b19eb6423bfbf68a55` (2026-11-13). Re-verify on any later tip before implementation. When this document and the tip disagree, the tip wins.

**Status:** Design locked. The behavior below is what 3.0.0 does. History of the audit tip stays in `docs/release-notes.md`.

### Architecture note (from tip)

Java DOM engine (`dom-engine`, `dev.domengine`) is the default, general-purpose, and bundled in the pickleball jar. Pickleball locates it through the shared explicit-binary order, then the Java launcher. Rust is an explicit override only (`pkb_composite_engine=rust` or an explicit binary). The default element path is `ElementOperations` → `DomCompositeAdapter` → the Java engine when `pkb_composite=auto`. The native execution engine is the default (`EngineConfig`); `pkb_engine=cucumber` keeps the Cucumber adapter. Dalton is on by default. Workbench does not compile against Pickleball core. `installDist`, `:run`, and Workbench tests carry a non-transitive `dom-engine` runtime jar. That jar is not a compile dependency and it is not published.

### Locked designs (D1, D2, D11)

**D1 Page/tab attach.** At attach and join time, if the CDP URL is browser-level (`/devtools/browser/`), resolve the current tab's page target (via `/json/list` matching the window handle, or `Target.getTargets`) and join the page WebSocket instead. Must cover Cucumber adapter, native engine, Workbench, direct control, attach and `focusPage` paths. Live test required with real ChromeDriver + `DriverConstruction.ready()` + composite find/click.

**D2 Full XPath 1.0.** Delegate to the browser's `document.evaluate` via CDP `Runtime.evaluate` (ORDERED_NODE_SNAPSHOT_TYPE), then map result nodes to backend node ids via `DOM.requestNode` / `describeNode`. Raise an error on evaluation failure or unsupported expression; never return 0 matches for an unsupported expression. Required expressions include `or`, `and`, `normalize-space`, positional predicates, `(//x)[n]`, `//li/a`, descendant paths, `self::`, etc.

**D11 Suite-level hooks.** Native engine must fire suite-level `BEFORE_CUCUMBER_RUN` / `AFTER_CUCUMBER_RUN` (and equivalent `@BeforeAll` / `@AfterAll` work) with Cucumber-adapter parity: consumer site startup, element-name registration, `Log.global().closeAll()`, `ReportPortalBridge.finishLaunch`, `pickleballLog.stop()`, `AgentCoordination.finishCurrent`. Implement in `NativeSuiteExecution` (before the walk, and in a finally after).

## Locked designs (D3-D10, D12)

Shared rule for every item in this section: the engine stays general-purpose. Flags, verbs, states, and capabilities are CDP/DOM concepts named in the engine's own CLI. No Pickleball type, setting, or behavior goes into `dom-engine`. Pickleball reads `capabilities` and gates in `DomCompositeAdapter`.

### D3. Unknown flags are silently accepted (enabler for D4-D9)

**Problem.** The engine parser stores any `--name value` pair, and verbs read only the flags they know. A flag the adapter relies on is dropped without an error. The adapter's fallback detection looks for "unexpected" / "unrecognized" in the error text, which the Java engine never produces for a `--name`.

**Evidence.**
- `dom-engine/src/main/java/dev/domengine/cli/DomEngineMain.java:540-560` (`flags()` accepts every `--name`; only a bare token gives `unexpected argument`).
- `DomEngineMain.java:562-567` (`isBoolean` list; no per-verb allow-list).
- `src/main/java/tools/dscode/common/composite/DomCompositeAdapter.java:572` (`waitOn` fallback matches `unexpected` / `unrecognized` / `poll-ms`), `:401-404` (`queryAllContexts` catch-all fallback).
- Audit probe: `waitVisible returned after 6 ms`, `hover -> textContent=nohover`, `iframe #inner engine(after enterFrame)=0`.

**Fix (locked).**
1. Each engine verb declares the flags it accepts (one static set per verb next to the verb's code). Before the verb runs, `DomEngineMain` rejects any other flag with exit 2, `{"ok":false,"error":"unrecognized flag --<name> for <verb>","code":"usage"}`. That text contains "unrecognized", so the adapter's existing fallback detection works unchanged.
2. `capabilities` gains `verb_flags`: an object from verb name to its accepted flag list. `query_flags` and `actions` stay as they are (existing consumers read them).
3. Each relied-on flag in D4-D9 is implemented in the engine and listed in `verb_flags`. A flag is listed only when it works. Listing without implementing is the bug this item fixes.
4. The adapter gates each relied-on flag on `verb_flags` (via the same cached capability read as `queryFlag`), and keeps its current fallback when the flag is absent. That is the "reported" path for an older Rust override that never listed `verb_flags`.

**Tests.**
- `dom-engine` unit: every verb rejects an unknown flag with exit 2 and the "unrecognized flag" message; every flag in `verb_flags` is accepted; `capabilities` contains `verb_flags` and its lists match the per-verb sets (one test that iterates the sets, so they cannot drift).
- Root: an adapter test (fake binary is fine here) that a "unrecognized flag" error from `waitOn` still returns false and keeps the Java loop.
- Existing fake-binary / argv tests stay unchanged.

### D4. Waits return at once

**Problem.** The adapter sends `wait_for` / `timeout_ms` / `poll_ms` / `stability_ms` on a `query`. `query` ignores them and returns at once. The engine's own `wait` verb (`observe`/`wait`) polls the same tree snapshot again and again, so it cannot see a DOM change, and it checks presence only, not visibility.

**Evidence.**
- `DomCompositeAdapter.java:556-580` (`waitOn` sends the wait keys on `query`; returns true on any non-error result).
- `src/main/java/tools/dscode/common/domoperations/LeanWaits.java:154` (visible), `:178` (attached), `:199-204` (`compositeWait`).
- `dom-engine/src/main/java/dev/domengine/action/Observe.java:22-35` (`waitFor` loops `Query.run(root, flags)` on one `root`; `waitSession` at `:38-42` snapshots the tree once).
- `DomEngineMain.java:115` (`observe`, `wait` → `observe`).
- Audit probe: `waitVisible returned after 6 ms; selenium says displayed=false`; a missing node returned ok and empty.

**Fix (locked).**
1. `query` accepts `--wait-for <attached|visible|hidden|detached>`, `--timeout-ms`, `--poll-ms`, `--stability-ms`. With `--wait-for`, the engine re-reads the live tree on every poll (fresh `DOM.getDocument` or the live-tree refresh `LiveTree` already uses for actions), evaluates the same selector, and applies the rule: `attached` = at least one hit; `visible` = at least one hit with the D6 displayed test true; `hidden` = no displayed hit; `detached` = no hit. `--stability-ms N` requires the same answer for N ms before returning.
2. On timeout the engine returns `{"ok":false,"error":"<message>","code":"timeout"}`, exit 1. The message contains `timeout`. The adapter maps that to Selenium `TimeoutException`.
3. `Observe.waitFor` / `waitSession` re-read the tree per poll too (same helper). `wait` stays a verb.
4. `verb_flags.query` lists the four flags only after this works. The adapter sends them only when listed; otherwise `waitOn` returns false and `LeanWaits` keeps its loop.

**Tests.**
- `dom-engine` live (real Chrome): an element made visible by `setTimeout` after 400 ms; `query --wait-for visible --timeout-ms 3000 --poll-ms 50` returns after at least 350 ms with one hit. The same element never shown with `--timeout-ms 300` gives `timeout`. A node added later passes `attached`; a removed node passes `detached`.
- Root live through the real adapter (see G6 harness): `LeanWaits` visible and attached waits on the same page; assert elapsed time and that a hidden element raises `TimeoutException`.

### D5. Hover is a no-op

**Problem.** `hover` sends a `query` with a `force_hover` key. `query` ignores it. No mouse event is dispatched, so `mouseover` handlers and `:hover` styles do not apply.

**Evidence.** `DomCompositeAdapter.java:423-430` (`hover` → `act("query", ...)` with `force_hover`); `ElementOperations.hover`; `dom-engine/.../action/PageActions.java` `VERBS` has no `hover`. Audit probe: `hover -> textContent=nohover`; Selenium hover worked.

**Fix (locked).**
1. Add an engine action verb `hover`: resolve the node (D8 identity first, then selector), scroll it into view, read its content quad, and send `Input.dispatchMouseEvent` `type=mouseMoved` at the quad centre. With `--force-hover`, also call `CSS.forcePseudoState` with `["hover"]` on that node, and clear it on the next `hover` or `session close`.
2. List `hover` in `capabilities.actions` and `verb_flags.hover`.
3. The adapter sends `hover` when `actions` lists it, else falls back to Selenium `Actions.moveToElement` (it does not send a fake `query`).

**Tests.** `dom-engine` live: `mouseover` handler changes text to `hovered`; a `:hover` CSS rule applies with `--force-hover` (`getComputedStyle` read via `eval`). Root live through the adapter: `ElementOperations.hover` fires the handler. Fake-binary test: a binary without `hover` in `actions` gets the Selenium path.

### D6. `filter displayed` is ignored

**Problem.** The adapter sends `filter=displayed` on scoped and nested queries. The engine does not read it, so `display:none` and `visibility:hidden` nodes match, and "is displayed" phrases accept hidden items.

**Evidence.** `src/main/java/tools/dscode/common/domoperations/NestedByLocator.java:242-252` (`engineNest`, `filter = displayedElementsOnly ? "displayed" : null`), `:331` (`engineNest`); `DomCompositeAdapter.java:173` (`body.put("filter", filter)`), `:107-160` (`findScoped` / `countQuery`). Audit probe: `displayedOnly+outermost .b -> [hid(shown), vis(shown)]`.

**Fix (locked).**
1. One engine displayed test, used by `--filter displayed`, by `--wait-for visible`, and by the D10 `hidden` state: a node is displayed when it has a non-empty box model (`DOM.getBoxModel` or the snapshot box), its computed `display` is not `none` on it or any ancestor, `visibility` is not `hidden`/`collapse`, and `opacity` is not `0`. That matches the WebDriver "element displayed" rule closely enough for the tests below. Compute it in the same pass that already reads geometry, not per node per call.
2. `--filter displayed` drops non-displayed hits before `nth`, `every`, and `count-only` are applied, so positions and counts match Selenium.
3. List `filter` in `verb_flags.query`. The adapter's post-filter on `states` (after D10) is a safety net only when `filter` is not listed.

**Tests.** `dom-engine` live: `display:none`, `visibility:hidden`, `opacity:0`, a hidden ancestor, and a zero-size element are all dropped; a visible sibling is kept; `count-only` with the filter counts only visible ones; `nth 2` picks the 2nd visible one. Root live: `NestedByLocator` displayed-only nest returns only the visible element.

### D7. Frame and shadow scoping is ignored

**Problem.** The adapter keeps a frame and shadow stack and sends it in `actionBody`. The engine does not descend into an iframe's document from that stack, and an `--pierce open` CSS query misses open shadow content. `getShadowRoot` pushes a shadow scope and never pops it, so later finds stay scoped.

**Evidence.**
- `src/main/java/tools/dscode/common/composite/CompositeWebElement.java:193-204` (`actionBody(frames, shadows)`), `:318-335` (`getShadowRoot` → `pushShadow` with no pop), `:366-369` (`enterFrame` → `pushFrame`).
- `DomCompositeAdapter.java:793-800` (`pushFrame`, `pushShadow`; no pop), `find` / `findScoped` send the stacks.
- `dom-engine/.../query/Engines.java:42-43` (`frame` / `shadow` engines), `dom-engine/.../tree/LiveTree.java:152` (frame subtree), `dom-engine/.../query/HtmlTree.java:116` (iframe flag).
- Audit probe: `iframe #inner selenium(after switch)=1`, `engine(after enterFrame)=0`; CSS `--pierce open` gave 0 while an XPath pierce form worked.

**Fix (locked).**
1. **Cause (U2), both.** Light-tree descent skipped iframe content documents (`nodeType` 9) even though `DOM.getDocument {depth:-1, pierce:true}` already attached same-origin `contentDocument`. A frame whose content is not in the snapshot yet is timing: `query --wait-for attached` re-reads the tree and treats not-found during the poll as empty. Cross-origin frames are grafted with `Target.setAutoAttach {autoAttach:true, flatten:true}`, `Target.attachToTarget`, and `DOM.getDocument` on that session. Proved by `LiveChromeQueryFlagsTest` (same-origin, a 300 ms late iframe, and a second-port cross-origin frame) and `JavaEngineFlagsLiveTest` (`enterFrame` then `#inner`).
2. The engine reads the full tree with `DOM.getDocument {depth:-1, pierce:true}`, so same-origin iframe documents and open shadow roots are in the tree. For an out-of-process (cross-origin) iframe, the engine attaches to the child target with `Target.setAutoAttach {autoAttach:true, flatten:true}` and reads that target's document on its own session. Frame scoping then picks the frame owner's `contentDocument` (or the child target's document) as the query root.
3. `--frame <id-or-node>` (repeatable, outer first) and `--shadow <node>` (repeatable) set the query root for `query` and every action. A frame or shadow host that cannot be found is an error (`not_found`), never a silent main-document query.
4. CSS with `--pierce open` matches inside open shadow roots, the same as the XPath form.
5. Adapter: `getShadowRoot()` scope is popped after each `findElements` (push, find, pop in a `finally`), so it never leaks to later finds. There is no pop or clear for either stack today: `DomCompositeAdapter` has only `pushFrame` / `pushShadow` (`:793`, `:798`), and `ElementOperations.defaultContent` (`ElementOperations.java:347-348`) switches the Selenium driver only. Add `popFrame`, `clearFrames`, and `popShadow`, and call them from `defaultContent`, `parentFrame`, and the shadow `finally`.

**Tests.** `dom-engine` live: same-origin iframe, an iframe whose content loads 300 ms late, a cross-origin iframe served from a second local port, nested iframes, open shadow root via CSS pierce and via `--shadow`. Root live: `enterFrame` then find returns the frame element; after `getShadowRoot().findElements`, a normal find is back in the light DOM.

### D8. Node identity is ignored

**Problem.** The adapter sends `node_id` for `eval` and `live`. The engine re-resolves by selector instead, so with duplicate elements it raises "ambiguous" or picks the first one. `live(second)` returns false for a live element, and eval or click on the second duplicate fails. Element snapshots break on non-unique elements.

**Evidence.** `DomCompositeAdapter.java:538-542` (`eval` sends `node_id`), `:586-588` (`live`), `:212-229` (`evalAll` joins node ids); `src/main/java/tools/dscode/common/seleniumextensions/ElementSnapshotScript.java:294` (`onEval`), `:312` (`onEvalAll`); `CompositeSnapshotProducer.java`; `dom-engine/.../action/PageActions.java:83` (`one(tree, flags)` resolves by selector). Audit probe: `dels=2`, `live(second)=false`, `eval(second) threw NotFoundException`.

**Fix (locked).**
1. The engine treats `--node-id <backend_node_id>` (and `--node-ids a,b,c` for G4) as the target for every action, `eval`, and `live`. It resolves with `DOM.resolveNode {backendNodeId}`. The selector is then only a fallback when the id is gone, and only when `--refind` is passed.
2. Query rows keep `backend_node_id` (`Query.java:301-302`); the adapter uses that value, never the transient `nodeId`, as `CompositeWebElement.nodeId()`.
3. A node id that no longer resolves is `{"ok":false,"error":"<message>","code":"stale"}`. The message contains `stale`. The adapter maps that to Selenium `StaleElementReferenceException`. `live` returns false only for `stale`.
4. List `node-id` in `verb_flags` for every action verb, `eval`, and `live`.

**Tests.** `dom-engine` live: two identical `.del` links; click the second by node id and assert only the second's handler ran; `live` true for both; remove the second and `live` is `stale`. Root live through the adapter: an element snapshot of the second duplicate evaluates and clicks the right element; `ElementSnapshotEvalTest` fake-binary assertions stay.

### D9. `all_frames` is ignored

**Problem.** `queryAllContexts` sends `all_frames` with `pierce open`. The engine searches the main document only. The adapter's catch-all fallback never fires because no error is raised.

**Evidence.** `DomCompositeAdapter.java:380-404` (`queryAllContexts`); `dom-engine/.../desktop/DesktopTree.java:255` (desktop refuses `all-frames`, browser path ignores it); `DomEngineMain.java:565` (`all-frames` is a boolean flag, accepted and unused). Audit probe: only main-frame buttons returned; iframe `#inner` missing.

**Fix (locked).** With `--all-frames`, the engine runs the query over the main document and every frame document from D7 (same-origin and child targets), in document order: main document first, then frames depth-first in DOM order. Each hit carries `frame` (the frame owner's backend node id path) so the adapter can enter it. List `all-frames` in `verb_flags.query`. The adapter's per-frame Java walk stays the fallback when it is not listed.

**Tests.** `dom-engine` live: buttons in the main page, a same-origin iframe, and a nested iframe all return in order with frame paths. Root live: the all-contexts Loading scan (`AllContextsPositionTest` semantics) finds the 3rd hit inside the iframe; `AllContextsPlanTest` fake-binary assertions stay.

### D10. Displayed and selected state are not reported

**Problem.** `CompositeWebElement` reads `hidden`, `checked`, and `selected` from the row's `states`. The engine emits only `disabled`. `isDisplayed()` is always true and `isSelected()` always false.

**Evidence.** `src/main/java/tools/dscode/common/composite/CompositeWebElement.java:75-77`, `:282` (`isSelected`), `:337` (`isDisplayed`); `dom-engine/src/main/java/dev/domengine/query/Query.java:335-336` (`states` has only `disabled`). Audit probe: `hid(shown)` for a `display:none` element. `isSelected` wrong by code reading.

**Fix (locked).** `compositeJson` emits, in `states`: `hidden` (the D6 displayed test is false), `disabled` (attribute or inherited from a disabled `fieldset`), `checked` (the live `checked` property for checkbox/radio, read with one batched `Runtime.callFunctionOn` per query, not per node), `selected` (the live `selected` property for `option`), `readonly`, `required`, `expanded` / `collapsed` (from `aria-expanded`), and `focused` (`document.activeElement`). Each state is a lower-case word. `capabilities` gains `row_states` listing them, so the adapter can tell an engine that reports `hidden` from one that does not.

**Tests.** `dom-engine` contract test: a row-fields test that lists every key and state the engine emits and fails if one is dropped. `dom-engine` live: hidden, checked (set by click, not by attribute), selected option, disabled via fieldset. Root live: `isDisplayed()` false for a hidden element and `isSelected()` true for a checked box and a selected option; `ElementStateRoundTripTest` stays.

### D12. Driver creation outside a scenario throws NullPointerException

**Problem.** `applyDebugPort` reads `getCurrentScenarioState().debugBrowser` with no null check. When a driver is built outside a running scenario, this throws.

**Evidence.** `src/main/java/tools/dscode/common/driver/DriverConstruction.java:720-721` (`if (!getCurrentScenarioState().debugBrowser)`), called at `:351` (chrome) and `:372` (edge). Reach: `src/main/java/tools/dscode/common/agentcontrol/AgentControl.java:144` builds a driver through `DriverConstruction.createLocalDriver(...)` for agent `launch --start`, which can run with no scenario state; the audit's standalone probe hit the NPE. Workbench reach is through the same agent path.

**Fix (locked).** Read the debug flag through one helper: scenario state when present, else the global flag that scenario state copies (`CurrentScenarioState.globalDebugBrowser`, read at `CurrentScenarioState.java:154-155`), else false. No other behavior change. If the reach check shows the agent path already sets a scenario state, still add the guard and record what was found.

**Tests.** Root unit: `applyDebugPort` with no scenario state and `debugBrowser` unset does not throw and adds no `debuggerAddress`; with the global run var true and a listening port it sets `debuggerAddress`. Agent path: a test that calls the `AgentControl` local-driver build path with a fake/headless config (or the narrowest seam that reaches `applyDebugPort`) and no scenario state.

## Locked designs (G1-G6)

### G1. Silent Selenium fallback in `auto`

**Status.** Shipped. `pkb_composite_fallback_log` is `warn` by default. Each `auto` reason (missing, client, join) logs once per run, with the engine path or `none` and the fix, on stderr, the Pickleball log, and a `composite.fallback` run event (`run-events.jsonl`, `compositeFallbacks` on `run-index.json`). `pkb_composite=off` stays quiet. `pkb_composite=on` still prints `error:` and `fix:`. An explicit binary that is not the Java launcher, or `pkb_composite_engine=rust`, logs one INFO line naming the source key.

**Problem.** In `pkb_composite=auto`, a missing engine, a client that fails to start, or a failed join quietly switches the run to the Selenium element path. The message prints only with `pkb_composite_log=fallback` or `pkb_composite=on`. With the Java engine always bundled, any `auto` fallback means something is broken, and today nobody sees it.

**Evidence.** `src/main/java/tools/dscode/common/composite/CompositeRuntime.java:355-380` (`decide`: `fallbackOnce(MISSING, ...)` at `:363`, "client failed" at `:374-375`), `:290-295` (join `errorFix`, then `forceLegacy()` when no session joined), `:314`, `:400` (`forceLegacy`); `CompositeLog.java:87-92` (`fallbackOnce` prints only when `enabled("fallback")` or `required()`), `:110-111` (`errorFix` same gate).

**Fix (locked).**
1. New run variable `pkb_composite_fallback_log` with values `warn` (default), `info`, `off`. Read through `CompositeMode.read` (same order as `pkb_composite`: system property, `pkb_runvars.` property, env `PKB_COMPOSITE_FALLBACK_LOG`, run variable).
2. Every `auto` fallback (missing, client failed, join failed, `forceLegacy`) logs exactly one line per run and reason at that level, with the reason, the located engine path (or "none"), and the `fix:` text. It goes to the normal Pickleball log and to stderr, and is also recorded as a run-level diagnostic event (`composite.fallback`) so `run-index.json` / `summary.json` show it.
3. `pkb_composite=off` stays silent (DEBUG only). `pkb_composite=on` keeps its `error:` / `fix:` behavior.
4. Explicit Rust override (`pkb_composite_engine=rust`, or an explicit bin that is not the Java launcher) logs one INFO line naming the source key, so a stale `COMPOSITE_BIN` in a shell is visible.

**Tests.** Root unit (with `CompositeRuntime.decide(Sources)` and the log seam): missing engine logs one WARN by default and none with `off`; `info` level logs INFO; client failure and join failure each log once per run, not per element; `pkb_composite=off` logs nothing at WARN; explicit `COMPOSITE_BIN` logs the INFO override line; the diagnostic event appears in the run summary.

**Docs.** `docs/configuration.md` row for `pkb_composite_fallback_log`; one sentence in `docs/dynamic-steps.md` "DOM engine translation".

### G2. Lookup order (already fixed; guard only)

**Status.** Guard shipped. With only a relative `COMPOSITE_BIN`, `CompositeBinaryLocator.locate` and `DirectControlProvider.resolveBinary` return the same absolute path. `COMPOSITE_BIN` stays working-directory relative. The other explicit slots stay project-relative. No second resolver.

**Problem.** At `1059667f` the control protocol checked `COMPOSITE_BIN` first and the runtime checked `pkb_composite_bin` first.

### G4. `eval_nodes` and `limit` are missing

**Problem.** The engine does not list `eval_nodes`, so `evalAll` makes one round trip per node. It does not support `limit`, and the adapter's fallback logs "limit fallback" but does not slice, so callers get every hit.

**Evidence.** `DomCompositeAdapter.java:95-100` (`multiEval` reads `capabilities.eval_nodes`), `:210-229` (`evalAll`: "A binary without eval_nodes evaluates the first node only"), `:275-282` (`limit` fallback logs but does not slice), `:761-762`. Audit probe: `multiEval=false limitFlag=false`. Rust 2.4.0 lacked both, so this is not a regression.

**Fix (locked).**
1. Engine `eval --node-ids a,b,c` runs the function once per node in one CDP round trip (`Runtime.callFunctionOn` over an array built from `DOM.resolveNode` objects) and returns results in input order; a missing node gives `{"stale":true}` in its slot. `capabilities.eval_nodes` is set to the max batch size (for example `"256"`).
2. Engine `query --limit N` stops after N hits, after `filter` and before `count-only` (`count-only` with `limit` returns `min(count, N)`). List `limit` in `query_flags` and `verb_flags.query`.
3. Adapter: when `limit` is not listed, slice the result list to N in Java (the fallback must give the same answer). When `eval_nodes` is not listed, keep the per-node loop over **every** node (fix the "first node only" behavior described in the javadoc at `:210`).

**Tests.** `dom-engine` live: `eval --node-ids` over 3 nodes returns 3 results in order with one CDP call (count calls through the engine log); `query --limit 2` over 5 hits returns 2. Root: fake-binary test that without `limit` the adapter returns N; without `eval_nodes` every node is evaluated; existing `ElementSnapshotEvalTest` assertions stay.

### G5. A failed capability read caches Rust 2.4.0 assumptions

**Problem.** When no client is open, or the `capabilities` call throws, the adapter falls back to the hard-coded Rust 2.4.0 sets and caches them for the JVM. The Java engine is then treated as Rust 2.4.0 (for example desktop click and type are refused with Rust guidance).

**Evidence.** `DomCompositeAdapter.java:25` (`DESKTOP_VERBS_2_4_0`), `:710-718` (`desktopVerbs`: no client → 2.4.0 set; loaded set cached in `desktopVerbs`), `:720-730` (`actionVerbs` with `VerbPlan.ACTIONS_2_4_0`), `:768-781` (`loadNamedVerbs` returns the fallback on any `RuntimeException`, and the caller caches it); `VerbPlan.java:14`.

**Fix (locked).** A failed or missing capability read is never cached. `loadNamedVerbs` returns `Optional.empty()` on failure; the caller then uses the fallback for this call only and retries on the next call (at most one retry per 5 s, so a dead engine is not hammered). The fallback set for an engine whose `version` reports `domengine` (the Java engine) is the Java engine's own list (`PageActions.VERBS`, `DesktopTree.VERBS`, `Query.QUERY_FLAGS`), not 2.4.0. The 2.4.0 sets stay only for a client that reports a Rust 2.4.x version. Log one DEBUG line per failed read.

**Tests.** Root unit with a fake client: first `capabilities` throws, second succeeds → second call sees the real list (no cache of the failure); a Java-engine version string with a failing read gets the Java lists; a Rust 2.4.0 version keeps the 2.4.0 sets; existing `SelectorAndAdapterTest` assertions (including `dev.domcomposite:composite-native:2.4.0` in the refusal) stay.

## CLI-first and logging checklist (applies to every phase)

- Every new engine capability (wait flags, `hover`, `filter`, `frame` / `shadow` / `pierce` CSS, `node-id` / `node-ids`, `all-frames`, row states, `limit`, `verb_flags`, `row_states`) works from `domengine` on the CLI first (`java -jar pickleball-<version>.jar domengine ...`, Gradle `domengine`, `:dom-engine:installDist`). Workbench, MCP, and Gradle only forward.
- `capabilities` lists a flag or verb only after it works, and its lists are checked by a test against the code's own sets.
- Errors use `{"ok":false,"error":"<message>","code":"<code>"}` (`Jsons.error`) and `error:` / `fix:` lines. `error` is a string, not an object. New codes: `usage` (unrecognized flag), `timeout`, `stale`, `not_found` (frame or shadow host). `code` is chosen with `stale` first, then not found, invalid, and timeout.
- Engine logging reuses `EngineLog` (toggleable per entity, date-stamped, size-capped). New entities: `wait`, `hover`, `frame`, `identity`, `state`, `batch`. Pickleball-side logging reuses `CompositeLog` entities (`fallback`, `adapter`, `query`, `session`). Nothing logs at INFO or above by default except the G1 fallback line.
- The engine stays general-purpose: no Pickleball types, keys, or behavior in `dom-engine`.

## Locked choices (from the Heavy brief; do not reopen)

- XPath goes through the browser's `document.evaluate` (D2). No new hand-rolled subset.
- Unsupported flags are rejected or reported (D3), never silently ignored.
- The `auto` fallback is loud and configurable (G1). Only `pkb_composite=off` is silent.
- Lookup order is `pkb_composite_bin`, then `COMPOSITE_BIN`, then the bundled Java engine (G2, already in code).
- The Workbench classpath stays isolated (G3); `verifyStrictControllerIsolation` stays green.
- Live-Chrome tests run in CI and gate the build (G6).
- Making Dalton the default is out of scope.
