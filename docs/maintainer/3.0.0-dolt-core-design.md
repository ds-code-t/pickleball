# 3.0.0 Dolt core design

**Status:** implemented. The default working copy is the Dolt sql-server (`dolt_schema=1` on `main`). The CLI first argument is `dolt`. Old names are refused. `sqlite-jdbc` remains for migrate and the diagnostic index. Sandboxes, glue compile, and Workbench, MCP, and Gradle forwarding are implemented. The record of the work is `docs/roadmaps/3.0.0-dolt-core-roadmap.md`.
**Decision:** Dan Shell, 2026-11-15 (voice). Pickleball 3.0.0's core is [Dolt](https://www.dolthub.com/), the SQL database with Git-style branches. The SQLite-backed layer named "Dalton" is replaced. "Dalton" was a voice mis-transcription of "Dolt", so the name is removed everywhere outside history files, with no aliases. This overrides the recommendation in `docs/maintainer/dolt-isolation-analysis-2026-11-15.md`.
**Base SHA:** written against `9d54d9b2` on `3.0.0`. Dolt facts come from that analysis (sections 3–5, Dolt 2.7.3 measured on Linux) and from the v2.7.3 GitHub release API (asset digests, captured 2026-11-15). P1 recorded the verification answers in section 17.

## 1. Philosophy

- **One spine, multiple adapters.** The Dolt-backed execution core is the single spine. CLI, Workbench, MCP, the native suite, feature files and GUI/DOM triggers are thin adapters. After an adapter selects its input, every path uses the same engine, the same query definition dictionaries and the same execution path.
- **Adapter-agnostic.** The core makes no distinction between current and future adapters. It exposes neutral operations (hydrate, extract, read, edit, run, record, sandbox) and knows nothing about who called it.
- **Cucumber stays outside.** The Cucumber adapter (`pkb_engine=cucumber`) is the one isolated legacy side branch. Its language, syntax, types and functionality never become part of the Dolt core. Other file kinds may later be unwrapped into the spine; Cucumber is not one of them.
- **CLI-first.** Every capability is a `pickleball dolt <cmd>` command. Workbench, MCP and Gradle forward to it.
- **Git is the source of truth.** Real Git and GitHub stay the only project sync. Dolt is never used to save or share the project. The database is disposable, rebuilt from files, and never committed.
- **Dolt branches are sandboxes.** An agent or test branches, changes a Java step definition, a feature file or data, and runs that closed project state without affecting parallel agents or `main`.

## 2. Naming (locked)

"Pickleball's `dolt` commands" means Pickleball's layer backed by the real Dolt database. It is not Dolt's own `dolt` binary, which Pickleball runs as a child process. Docs always say "Pickleball `dolt` command" or "the Dolt binary" when it could be ambiguous.

**No aliases.** An old name is never honored. One class, `tools.dscode.dolt.LegacyNames`, holds the old strings so a stale setting fails loudly instead of being silently ignored: a set `pkb_dalton*` property or `PKB_DALTON*` variable, a `dalton.properties` file, or a `dalton-entities/` directory without `dolt-entities/` stops the run with `error: <old> is no longer read` and `fix: use <new>`. That class, its test, and the history files in section 15 are the only places the old name may appear.

## 3. Storage abstraction (locked)

- **One store.** `tools.dscode.dolt.store.DoltStore` is the only way the spine reaches persisted state. `DoltStore.open(Path project, Binding binding)` returns a `DoltSession` (a JDBC connection already bound to a branch, plus `dialect()` and `branch()`). There is exactly one production implementation, the Dolt sql-server. There is no SQLite backend and no backend switch.
- **One dialect.** `tools.dscode.dolt.store.DoltDialect` owns every SQL fragment that SQLite and MySQL spell differently (section 7). Callers keep plain JDBC with `?` parameters.
- **Gate.** `DriverManager`, `jdbc:` URLs and `information_schema` appear only under `tools.dscode.dolt.store`. The diagnostic-report SQLite index is outside this rule.
- **Pool.** `DoltConnections` keeps a small per-JVM pool per `(project, branch)` (max 4, idle close 60 s). No new pool library. This also removes the per-call reopen noted as audit F3.
- **Spine callers.** Hydrate, extract, edit, entities, step catalog, execution recording, history, query, timeline, `DoltFeatureSource` and `DoltScenarioSource` call `DoltStore`. Engine code calls neutral source and recorder interfaces, not the store.

## 4. Dolt sql-server lifecycle (locked)

- **Data dir.** `<project>/.pickleball/dolt/data/`. The database directory is `data/pickleball/`, created by `dolt init --name pickleball --email pickleball@localhost` (verified P1: both flags exist and the server starts from that directory). `.pickleball/` is already gitignored; P4 changes the explicit `.pickleball/dalton/` line to `.pickleball/dolt/`.
- **Owner.** A small Pickleball JVM, `tools.dscode.dolt.server.DoltServerSupervisor`, starts `dolt sql-server --host 127.0.0.1 --port <port> --data-dir <data>` as its child, writes `.pickleball/dolt/server.json` (`pid`, `supervisorPid`, `port`, `doltVersion`, `startedAt`, `project`), and stops the child. Any Pickleball process that needs the store calls `DoltServer.ensure(project)`.
- **Lock.** `ensure` takes an exclusive `FileChannel.tryLock` on `.pickleball/dolt/server.lock` (works on Windows, macOS, Linux), re-reads `server.json`, and reuses the server when the pid is alive and `SELECT 1` answers within 2 s. Otherwise it deletes stale state, starts a supervisor, waits for `SELECT 1` (timeout `pkb_dolt_server_start_ms`, default 15000), then releases the lock.
- **Port.** Loopback only. The supervisor binds `ServerSocket(0)` on 127.0.0.1, reads the port, closes it and passes it to Dolt. If Dolt fails to bind, it retries with a new port up to 3 times. `pkb_dolt_port` pins a port for debugging.
- **Reuse across processes.** One server per project root, shared by every process and every sandbox (branches are per connection). Each user of the store touches `.pickleball/dolt/lease/<pid>` while it holds a session.
- **Shutdown.** `pickleball dolt server stop` (graceful destroy, then forced after 10 s), `server status`, and `server start`. The supervisor also stops the child when no live lease has been touched for `pkb_dolt_server_idle_minutes` (default 30) and on its own JVM shutdown hook. Windows does not kill children with the parent, so `stop` also kills by the recorded pid through `ProcessHandle`.
- **Cross-OS.** Paths through `java.nio`; the binary is `dolt.exe` on Windows. Linux start in P1 was well under the 15 s `SELECT 1` budget (the earlier scratch check was about 0.1 s and about 143 MB). macOS and Windows start time and memory were not measured in P1 (no macOS or Windows runner in that session). `--data-dir` with a space in the path succeeded on Linux. Windows with a space was not run.

- **Explicit install:** `pickleball dolt install [--force] [--dir=<path>]` downloads the asset for this OS and arch, checks SHA-256, unpacks into the cache, and prints the path. `pickleball dolt install --check` reports what would be used and exits 1 when nothing is.

- **CI:** each Agent Contract job runs `pickleball dolt install` (through Gradle `doltInstall`) and caches `~/.pickleball/tools/dolt` keyed on the version.
- **Not shaded.** The binary is never put in the jar.

## 6. JDBC driver (locked, license sign-off is Dan's)

- **Choice:** MariaDB Connector/J (`org.mariadb.jdbc:mariadb-java-client`, LGPL-2.1-or-later), a published `runtime` dependency, not shaded, listed in `THIRD-PARTY-NOTICES.md`. Dolt's docs list it as a supported Java client. LGPL as an unmodified, unshaded runtime dependency of an Apache-2.0 library is the lower-risk option; `mysql-connector-j` is GPL-2.0 with the Universal FOSS Exception.
- **Version:** `org.mariadb.jdbc:mariadb-java-client:3.5.11`, the newest 3.5.x on Maven Central at P1 (3.5.0 through 3.5.11; 4.0.0 exists and was not taken). Pinned. The P1 spike connected, ran `USE`, and bound a branch with the URL path. No fallback to `mysql-connector-j`.
- **Fallback rule:** if the P1 spike shows MariaDB Connector/J cannot bind a branch or breaks on Dolt session setup, switch to `mysql-connector-j`, record why here, and add its notice. No other driver. P1 did not switch: MariaDB Connector/J 3.5.11 binds with ``USE `pickleball/sbx-<name>` `` and with the JDBC URL path `pickleball/sbx-<name>`. `active_branch()` matches. Two connections on two branches do not see each other's uncommitted edits. `main` stays on the committed row.
- **Driver missing:** same loud-failure rule as today's `MISSING_DRIVER`, with the new names.
- `sqlite-jdbc` stays for the diagnostic-report index and Workbench. The Dolt core no longer uses it, except `pickleball dolt migrate` reading an old database (section 9).

## 7. Schema and SQL dialect port (locked)

- **Tables keep their names and columns:** `schema_meta`, `files`, `provenance`, `feature_docs`, `scenarios`, `example_blocks`, `steps`, `entities`, `runs`, `run_logs`, `step_definitions`, `scenario_executions`, `step_executions`, `entity_usages`, `log_entity_links`, `artifacts`, plus new `sandboxes`.
- **Schema version:** a fresh Dolt store starts at `dolt_schema=1` in `schema_meta`. There is no in-place upgrade from SQLite schemas 1–6; an old database is rehydrated (section 9). Later Dolt schema changes migrate in place through `information_schema.columns`.
- **Every SQLite construct to translate** (sites from the analysis, at `ca811fe8`):

  | SQLite | Sites | Dolt / MySQL |
  |---|---|---|
  | `TEXT PRIMARY KEY` and text keys | 7 tables (`DaltonDatabase.java:107`, `:113`, `:192`, `:214`, …) | `VARCHAR(n)` keys. P1: a `VARCHAR(3072)` primary key inserted on Dolt 2.7.3. Paths use `VARCHAR(1024)`. |
  | `BLOB` (`files.raw_content`) | `DaltonDatabase.java:115` | `LONGBLOB` (a 70,000-byte insert fails on `BLOB`) |
  | `INTEGER PRIMARY KEY AUTOINCREMENT` | `DaltonDatabase.java:204`, `:254` | `BIGINT PRIMARY KEY AUTO_INCREMENT`. Ids are unique across branches but not contiguous (Dolt keeps one counter per server) |

  | `INSERT … ON CONFLICT … DO UPDATE` with `excluded.` | 10 sites (`DaltonArtifacts:58`, `DaltonDatabase:298`, `:300`, `DaltonEntities:405`, `DaltonExecution:411`, `:435`, `:467`, `DaltonFiles:70`, `DaltonHistory:98`, `DaltonStepCatalog:78`) | `INSERT … ON DUPLICATE KEY UPDATE col = VALUES(col)`. - **Inventory:** about 114 statements in 15 files (46 SELECT, 19 INSERT, 18 DELETE, 16 CREATE TABLE, 9 UPDATE, 5 PRAGMA, 1 ALTER) and 12 explicit transactions. P2 lists every statement in `DoltDialectInventoryTest`, which fails if a new literal SQL string appears outside `DoltDialect` and the store.
- **Final column types (P2, Dolt 2.7.3):** path and file keys are `VARCHAR(1024)`. `schema_meta.key` is `VARCHAR(128)` and quoted, because `KEY` is reserved. `files.raw_content` is `LONGBLOB`. Other integer columns are `BIGINT`. `run_logs.id` and `entity_usages.usage_id` are `BIGINT AUTO_INCREMENT` (one server-wide counter; a new branch does not restart at 1). Every run-state table, including `sandboxes`, has `sandbox VARCHAR(64) NOT NULL DEFAULT ''`. `provenance.id` keeps `CHECK (id = 1)`. A fresh store writes `dolt_schema=1` and `schema_version=1`. Source tables are `DOLT_ADD`ed by name and committed as `schema dolt_schema=1` only when that row is first written. Run-state tables are created after that commit, so a branch from `HEAD` does not have them. Upserts use `ON DUPLICATE KEY UPDATE col = VALUES(col)`. Tag and feature filters use `CONCAT` and `CAST(... AS SIGNED)`. The catalog does not contain `||`. The port is `DoltDialect.statements()` (schema DDL, the filter fragments, and the translated Dalton DML). The Dalton sources have 11 `setAutoCommit(false)` sites: `DaltonContent.put`, `DaltonContent.delete`, `DaltonEntities.put`, `DaltonEntities.remove`, `DaltonExecution.recordStep`, `DaltonExecution.beforeStep`, `DaltonExtractor.extract`, `DaltonHistory.record`, `DaltonHistory.retain`, `DaltonHydrator.hydrate`, `DaltonStepCatalog.refresh`. `DoltDialect.ensureSchema` is the twelfth and takes `GET_LOCK('pkb:hydrate:main', 30)`. JDBC URLs and `DriverManager` live only under `tools.dscode.dolt.store`. A conflicting write retries 3 times with 50–200 ms jitter, then fails with `error: concurrent update on <table>`. `sql` logging records statement shape and timing, never bound values.

## 8. Fresh clone, hydrate commit, CI (locked)

- A fresh clone has no `.pickleball/dolt/`. The first store use resolves the binary (section 5), starts the server (section 4), creates the schema on `main`, hydrates from files, and ends with `CALL DOLT_ADD(<source tables>)` and `CALL DOLT_COMMIT('-m', 'hydrate <git sha>[ dirty]')`.
- **Source tables** (committed): `schema_meta`, `files`, `provenance`, `feature_docs`, `scenarios`, `example_blocks`, `steps`, `entities`, `step_definitions`. Hydrate stages them by name, never `-A`.
- **Run-state tables** (never committed, written only on `main`): `runs`, `run_logs`, `scenario_executions`, `step_executions`, `entity_usages`, `log_entity_links`, `artifacts`, `sandboxes`. Each row has a `sandbox` column (empty for `main`). History therefore survives a dropped sandbox. P1: an uncommitted table on `main` is still there after a sql-server restart, and a branch created from `HEAD` does not have that table. Run-state stays in database `pickleball`. A second database is not required. Hydrate must `DOLT_ADD` source tables by name so a later commit cannot sweep run-state in with `-A`.
- A hydrate that changes nothing makes no new commit. `pickleball dolt status` shows the last hydrate commit.
- `pkb_dolt=false` keeps today's file-only path: no binary, no server, no database.
- CI never needs a committed database. Jobs install the pinned binary and hydrate like a fresh clone.

## 9. Migration of an existing `.pickleball/dalton/dalton.db` (locked)

- **P3 as built:** the first open of a project that still has `.pickleball/dalton/dalton.db` and no `.pickleball/dolt/legacy-migrated` marker runs this migrate, then writes the marker. A static guard stops hydrate from re-entering it. The explicit command is `pickleball dolt migrate [--dry-run] [--remove-legacy]`. `--dry-run` does not create the store. Edited file rows (`db_edited=1`) are imported after hydrate and left uncommitted, the same as a normal database edit. Git blob, binary-ref, and byte-size columns are copied when the old table has them. Run rows are counted and not imported.
- Detected on first store use when the old SQLite file is present, and run explicitly by `pickleball dolt migrate [--dry-run]`. `LegacyNames` is the P4 loud-failure class; P3 does not refuse the older keys on the automatic path.
- Steps: hydrate the Dolt store from files; then read `files` rows with `db_edited=1` from the old SQLite file (read-only, through `sqlite-jdbc`, URL `jdbc:sqlite:file:<absolute>?mode=ro`) and import them as DB-edited rows on `main`, keeping `db_edited` and `last_synced_hash`, so an unextracted edit is not lost; report `migrated edits=<n>`.
- **Old run history is dropped, not imported.** It is retention-limited diagnostic data, the diagnostic reports on disk stay, and the old row ids and schemas do not map cleanly. Migrate prints `history not imported: <runs> runs`.
- The old file is left in place. `pickleball dolt migrate --remove-legacy` deletes `.pickleball/dalton/` after a successful migrate.
- `dalton.properties` and `dalton-entities/` are not moved automatically, since they are Git-tracked. The explicit migrate prints the exact `git mv` lines (`git mv dalton.properties dolt.properties`, `git mv dalton-entities dolt-entities`) and exits 1 with `error: legacy names are still in the project` before it writes. The automatic path still imports the database so existing projects keep working until the rename.

## 10. Sandboxes (locked)

- **Model.** A sandbox is a Dolt branch `sbx-<name>` in database `pickleball`, created from the latest hydrate commit on `main` (or `--from=<commit>`). Names match `[a-z0-9][a-z0-9-]{0,47}`. Metadata lives in `sandboxes` on `main`: name, owner, base commit, created, last used, TTL.
- **CLI:**
  - `pickleball dolt sandbox create <name> [--from=<commit>] [--owner=<id>] [--ttl=<duration>]` (default TTL 24h)
  - `sandbox list [--json]`
  - `sandbox use <name>` prints `PKB_DOLT_SANDBOX=<name>` export lines for sh, PowerShell and cmd. It does not persist any state, so parallel agents in one checkout never share a selection.
  - `sandbox diff <name> [--table=<t>] [--json]` compares the base commit with the sandbox working set through `dolt_diff_<table>` where `to_commit = 'WORKING'` (P1: `SELECT to_body FROM dolt_diff_diff_probe WHERE to_commit = 'WORKING'` returned the uncommitted value)
  - `sandbox extract <name> --to=<dir>` writes the sandbox's files into another directory (for example a Git worktree). Writing into the project root needs `--into-project`.
  - `sandbox drop <name> [--force]` runs `DOLT_BRANCH('-D', …)`. `--force` is needed when another session uses it.
  - `sandbox prune [--older-than=<duration>] [--owner=<id>] [--dry-run]` drops expired sandboxes, deletes their `.pickleball/dolt/sandboxes/<name>/` directories, then runs `DOLT_GC` (P1: `CALL DOLT_GC()` succeeded while the sql-server was serving connections). `--with-history` also deletes their run-state rows.
- **Per-connection binding.** `DoltStore.open` binds each connection to one branch with the JDBC URL path `pickleball/sbx-<name>` (P1: MariaDB Connector/J 3.5.11 accepts it and `active_branch()` matches). ``USE `pickleball/sbx-<name>` `` is the same bind. A transaction never spans two branches; run-state writes use a separate `main` session.
- **How a run binds.** `--sandbox=<name>` on any `pickleball dolt` or `engine` command, then `pkb_dolt_sandbox`, then `PKB_DOLT_SANDBOX`, else `main`. An unknown sandbox fails. One sandbox per JVM: the run id, project and auto-hydrate flag are JVM-global, so binding a second sandbox in the same JVM fails.
- **Edits.** `feature put`, `entity put`, `file put`, `glue put`, `category` and the scenario/step edit commands write to the bound branch. `main` and other sandboxes never see them.
- **Run-state writes use a main session.** A statement whose tables are all run-state tables is executed on a pooled `main` connection, not by rewriting the SQL onto the sandbox connection. `LAST_INSERT_ID()` stays on that same connection. A statement that joins run-state to a source table cannot read two branches, so that text stays on the sandbox connection and the run-state names are qualified `pickleball.<table>`. That qualified form sees committed revisions, not `main`'s uncommitted working set. History list is pure run-state and therefore reads `main`. The `sandbox` column on those rows is `Binding.sandboxColumn()` (empty on `main`). A sandbox-only `definition_id` that fails the foreign key is stored as null so recording does not abort the scenario.
- **Own warm worker.** `pickleball dolt run --sandbox=<name>` keeps worker state, fingerprint and port under `.pickleball/dolt/sandboxes/<name>/worker/` and starts a separate worker JVM with `-Dpkb_dolt_sandbox=<name>`. `main` uses `.pickleball/dolt/sandboxes/main/`.
- **Own compiled glue.** Before a run, the fingerprint covers `.java`/`.class` on disk plus every `.java` row with `db_edited=1` on the bound branch. When edited rows exist, `DoltGlueCompiler` compiles them with `javax.tools.JavaCompiler` against the cached classpath into `.pickleball/dolt/sandboxes/<name>/classes/` (sources also written to `…/src/` for diagnostics). That directory goes first on the worker classpath, which `StepRegistry.scanPackage` reads as `file:` URLs. `pickleball dolt glue compile [--sandbox=<name>]` runs the same compile on its own and prints diagnostics. No JDK (`ToolProvider.getSystemJavaCompiler()` is null) fails with a fix line. Deleting a class through a sandbox is refused (prepending cannot hide a class); the message says to use a Git worktree.
- **The `.java` gap is closed, including `main`.** A DB-only `.java` edit is compiled. `glue put` on a `.java` path reports `glue compile pending`, and the next run (or `glue compile`) compiles it into `sandboxes/<name>/classes/` (`main` uses `sandboxes/main/classes/`). Stale class files in that directory are deleted before the compile. `classpath.cache` is rewritten when that directory changes, and the worker is restarted.
- **JS/TS glue.** There is still no JS/TS step runtime. Sandboxes store and catalog JS/TS edits only; nothing executes them. If a runtime is added, it reads sandbox bytes straight from the store.
- **What a sandbox does not isolate.** Anything outside the store and the worker JVM: the browser, services under test, files the glue writes, and the Gradle/Maven build cache. A build-tool change (plugins, annotation processors, resources) needs a Git worktree.

## 11. Concurrency (locked)

- Many processes and threads share one server. Branches isolate sandboxes; inside one branch, Dolt merges concurrent transactions at commit.
- A write that fails with a Dolt transaction conflict or serialization error retries up to 3 times with 50–200 ms jitter, then fails with `error: concurrent update on <table>`. Dolt's merge treats two commits that store the same cell value as success, so a read-modify-write can lose an update without an error and without `SELECT … FOR UPDATE` stopping it. `DoltSession.transaction` takes `GET_LOCK` for that branch and table around the attempt, so the next writer reads the committed row. The lock name is `pkb:w:<branch>:<table>`, hashed when that exceeds 64 characters.
- Hydrate and extract on one branch are serialized by `GET_LOCK('pkb:hydrate:<branch>', 30)`. P1: `SELECT GET_LOCK('pkb:hydrate:main', 2)` returned `1` and `RELEASE_LOCK` returned `1`.
- Sandbox create and drop take `GET_LOCK('pkb:sandboxes', 30)` and `SELECT … FROM sandboxes … FOR UPDATE` on `main`. `--from` must be a Dolt commit hash (`[0-9a-zA-Z]{6,64}`) and is bound as a parameter (`CALL DOLT_BRANCH(?, ?)`), not concatenated into SQL. `sandbox extract` rejects a stored path that is absolute or contains `..`.
- A branch is in use when this JVM has borrowed a connection to it, when `.pickleball/dolt/branch-lease/<branch>/<pid>` names another live process, or when `information_schema.PROCESSLIST` shows a connection whose database is that branch and whose id this JVM did not open. Idle connections from this JVM do not count. `sandbox drop` without `--force` fails while another live process holds the branch.
- Server start is serialized by `server.lock` (section 4). Auto-install is serialized by a lock in the cache directory.
