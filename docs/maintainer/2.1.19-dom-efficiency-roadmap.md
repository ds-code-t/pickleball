# Pickleball 2.1.19 DOM Efficiency Roadmap

**Goal (Dan):** Cut browser round trips by using dom-composite more fully. Existing Gherkin/step syntax and behavior must not change. dom-composite may be changed (breaking changes allowed; no other app uses it), but it must stay a decoupled, general-purpose engine with no knowledge of pickleball.

**Baseline:** SHA `195151c7` on branch `2.1.19`. Composite is already the primary path via `ElementOperations` / `DomCompositeAdapter` / `ElementReads` when the 2.4.0 binary is present (`pkb_composite=auto`). Snapshots, batched describe, and guard exist. This round removes remaining extra round trips.

**HARD RULES:** never commit, push or merge to master; no force-push; no failing or weakened tests; docs updated with every change; simplicity and ONE shared code path (extend `ElementOperations`, `ElementReads` and `DomCompositeAdapter`, not per-call-site patches). Group changes by shared root cause, verified in code. AI-agent confusion from syntax/controls counts as a bug. CLI-first and toggleable per-entity logging checklist in every phase. Between phases run ONLY targeted tests tied to the changed code. The final full regression (Gradle `:test :pickleball-control-protocol:test :pickleball-control-api:test :pickleball-workbench:test --rerun-tasks`, `consumer_sim`, `verify_agent_contract.py`, Windows CI) runs ONCE at the very end of all phases. After the last implementation push, Build must STOP and report the head commit, and run the final regression only when told to continue. CI runs the Windows job only. Keep agent index synced.

**Verified candidates (code at 195151c7):**
1. Element states (enabled/blank/required/on/collapsed) do an extra `self::*` find per check via `ElementOperations.findElements`. Read them from the snapshot or `ElementView` the wrapper already holds. Pickleball only, low risk.
2. Fake actions while composite is primary: submit becomes click, dblclick becomes two clicks, contextclick becomes click, drag becomes click/scroll/click, named keys go through Actions. Add real general-purpose submit, dblclick, contextclick, drag and keydown/chord verbs to dom-composite. Pickleball uses them when capabilities lists them.
3. `CompositeSnapshotProducer` runs a WebDriver JS script per matched element after the composite hit. Add a general-purpose describe-many-by-node-id or element-scoped eval to dom-composite returning selectedValue, siblingIndex, sameTagIndex and stable selector, then drop the workaround.
4. `AllContextsScan` walks frames and shadow roots in Java with many `findElements` / `enterFrame` / describe calls. Replace it with one adapter query using composite's all-frames and shadow pierce, keeping foreign-frame and closed-shadow semantics.
5. `LeanWaits` polls visibility every 150 ms. Use composite auto-wait/wait-for/stability through the adapter, with matching timing.
6. `NestedByLocator` containment in one batch; a node-liveness query before the stale-element re-find by `stableSelector`; desktop click/type plus native classifier jars (see prompts/domc-asks.md if needed).

**Architecture:** All changes go through the single shared path (`ElementOperations` → `DomCompositeAdapter` / `ElementReads`). Composite remains decoupled. Fallback to Selenium only when composite is off or capability missing. Parity tests (Selenium vs composite, and across launch modes) assert identical contracts. Measured round-trip or timing before/after for each efficiency change.

**Every phase is mandatory and must be completed in full. Nothing is optional or deferred.**

## Phase 1: Element states from snapshot / ElementView (no extra finds)
**Functionality:**
- In `elementstates/*` (EnabledDisabledConditions, BlankElementConditions, RequiredInputConditions, CollapsedExpandedConditions, BinaryStateConditions, VisibilityConditions as applicable), replace the `self::*` `findElements` with a read from the already-held `ElementView` or `ElementSnapshot` (attributes, states, displayed, enabled, etc.).
- Extend `ElementReads` / `ElementView` if a missing field is needed (one shared path).
- No behavior change: same truth values for enabled/blank/required/collapsed/etc.

**Docs:** Update this roadmap. Note in `docs/dynamic-steps.md` or agent feature-map that state checks are snapshot reads when composite is primary.

**Tests:**
- Unit tests asserting identical results for representative elements (enabled, disabled, blank, required, collapsed) on Selenium path vs composite path.
- Measured round-trips: before (extra find) vs after (zero extra) for a state check after a find.
- Existing consumer scenarios that use element states remain green (targeted).

**Logging checklist:** Trace-level only; toggleable via `pkb_composite_log`. One line if a snapshot miss falls back (should not happen).

**Regression risk:** Low. Other callers of elementstates go through the same conditions. Launch modes covered by parity. Existing tests lock the predicates.

## Phase 2: Real action verbs in dom-composite + adapter use
**Functionality:**
- In dom-composite (vendored or sibling; breaking changes OK): add general-purpose verbs `submit`, `dblclick`, `contextclick`, `drag`, `keydown` / chord. No pickleball knowledge. Capabilities list reports them.
- In `DomCompositeAdapter` / `ElementOperations`: when capabilities lists the verb, use the real verb. Fake mappings (submit=click, drag=click/scroll/click, etc.) remain only as fallback when the verb is absent.
- Named keys and chords use the new keydown/chord when available; otherwise existing Actions path after focus.
- Desktop click/type: use when `capabilities.desktop` lists them (native classifiers as needed).

**Docs:** Update AGENTS.md public contracts section. Note new verbs and fallback rules. Update this roadmap.

**Tests:**
- Parity tests: same click/submit/dblclick/contextclick/drag/key behavior on composite (real verb) vs Selenium.
- Capability-missing fallback tests.
- Measured round-trips for a submit or drag that previously was multi-call.
- Targeted consumer scenarios for form submit, drag, keys.

**Logging checklist:** Info-level verb selection (real vs fallback); toggleable per-entity.

**Regression risk:** Medium. Other callers of submit/drag/keys go through ElementOperations. Launch modes and existing tests lock semantics. Fake path preserved when capability missing.

## Phase 3: describe-many-by-node-id / element-scoped eval; drop CompositeSnapshotProducer JS

- In `CompositeSnapshotProducer` / `ElementSnapshotScript`: use the new verb/query; drop the per-element WebDriver JS script workaround.
- Snapshot fields remain identical. One shared path via ElementReads/describe.

**Docs:** Update snapshot docs and this roadmap. AGENTS.md note if contracts change (they should not).

**Tests:**

**Logging checklist:** Batch describe log already exists; extend if needed.

**Regression risk:** Low-medium. Snapshot consumers (ElementWrapper, inspect) must see identical data. Existing tests lock fields.

- Preserve foreign-frame and closed-shadow semantics exactly. Window lifecycle stays outside.
- Shared path through DomCompositeAdapter / ElementOperations.

**Docs:** Update this roadmap and any scan/inspect docs.

**Tests:**

**Logging checklist:** One line for the scan query; toggleable.

**Regression risk:** Medium. Other callers of AllContextsScan (context search). Existing tests and consumer scenarios with frames/shadows lock results.
