# Pickleball 2.1.19 Dom-Composite Full Integration Roadmap

**Goal (Dan, explicit):** FULL integration of dom-composite (https://github.com/ds-code-t/dom-composite, Rust 2.4.0) into Pickleball. dom-composite becomes THE single entry point for ALL Pickleball DOM and OS-desktop interaction (Windows, Linux, Mac). It replaces direct WebDriver/Playwright/XPath as the primary path. Its flexible selectors apply to both web and desktop elements. Future alternative backends must remain possible, but behind dom-composite as the one entry point.

**Existing context:** 2.1.18 shipped the direct-control handoff (docs/direct-control-handoff.md, session-descriptor.v1). A live Workbench session publishes a descriptor so dom-composite can attach to the browser Pickleball owns, act, and detach. Only active when `pkb_direct_control_provider` is set. Normal mvn/gradle runs unchanged. Workbench controls remain Java; dom-composite is not bundled by default.

**HARD RULES:** never commit, push or merge to master; no force-push; no failing or weakened tests; docs updated with every change; simplicity and one shared code path (fix by streamlining, not per-bug tweaks); AI-agent confusion caused by syntax/controls/instructions counts as a bug; CLI-first and toggleable per-entity logging checklist in every roadmap.

**Architecture decision (locked):**
- Primary call path: official Java bindings (`dev.domcomposite.Client` / `Session` from dom-composite 2.4.0). Prefer in-process or low-latency binding calls over per-op sidecar process spawn.
- Distribution: Maven artifact(s) for the Java binding + native binaries/libs via classifiers (e.g. `windows-x64`, `linux-x64`, `macos-aarch64`, `macos-x64`). Runtime extracts or locates the `composite` binary. Fallback to `COMPOSITE_BIN` / `COMPOSITE_HOME` / sibling checkout as today.
- Single entry: new `DomCompositeAdapter` (or equivalent) is the ONLY path for element resolution, click, type, wait, hover, scroll, inspect, and desktop ops. Existing Pickleball element phrases, text matching, XPath, CSS, and custom categories are translated into composite pipeline/selector queries. No direct `WebDriver.findElement` / Actions for element ops once complete.
- Desktop: same adapter, `source=desktop` (or equivalent) using composite's OS desktop, OCR, and template matching. Window handles and CDP attach remain available via the existing session descriptor.
- Backward compatibility: all existing consumer feature files and Gherkin element syntax continue to work unchanged. Translation layer preserves semantics (full match, quote types, context words `in`/`from`/`for`/`after`/`before`, etc.).
- Fallback rules: if binding/binary unavailable, log once and fall back to legacy Selenium path for that run (configurable); primary path is always composite when present. No dual maintenance of selector logic.
- Workbench: `inspect-page`, `find-element`, and related CLI/MCP/GUI routes go through the same adapter.
- Logging: CLI-first. Toggleable per-entity logging (existing `pkb_` style or `COMPOSITE_LOG` / per-adapter flags). One shared checklist in every phase.

**Every phase is mandatory and must be completed in full. Nothing is optional or deferred.**

**Functionality:**
- Add Maven dependency on dom-composite Java bindings (version 2.4.0 or matching).
- Configure classifiers for native binaries per OS/arch. Document extraction/location logic that mirrors existing `COMPOSITE_BIN` discovery.
- Runtime check: locate binary or binding on startup of a browser session. Fail soft with clear `error:`/`fix:` if missing for a composite-required path.
- Preserve existing direct-control handoff; extend it so the adapter can join an already-attached session.

**Docs:**
- Update `docs/direct-control-handoff.md`, `docs/getting-started.md`, `docs/configuration.md`, `docs/pickleball-workbench.md`, and this roadmap with the dependency and location rules.
- Add a short consumer note: how to ensure the binary is available (or that it is bundled via classifiers).

**Tests:**
- Unit tests for binary location logic (happy path, missing, classifier extraction stub).
- Consumer feature or internal check that starts a session and asserts the adapter can open a Client without error when binary is present.
- No failing tests; existing suite remains green.

**Logging checklist:** CLI-first location messages; toggleable via `pkb_composite_log` or equivalent; per-entity (adapter, session, element) flags documented.

## Phase 2: DomCompositeAdapter and selector translation
**Functionality:**
- Introduce `DomCompositeAdapter` as the single shared code path for all element lookup and actions.
- Translation layer: map Pickleball element descriptors (visible text, type, state, position, surrounding context, XPath, CSS, custom categories) to composite flexible selectors / pipeline queries. Preserve existing matching rules (full match, quote types, context words).
- Route core entry points (`BrowserSteps`, `ElementWrapper`, `HumanInteractions`, `ElementControl`, etc.) through the adapter. Keep WebDriver only for browser lifecycle (get, window handles, CDP address).
- Basic desktop source support stubbed.

**Docs:**
- New section in `docs/dynamic-steps.md` or `docs/custom-element-definitions.md` describing the translation.
- Update `docs/agent/feature-map.md` and `docs/agent/repository-index.md`.
- AGENTS.md note that element ops go through the adapter.

**Tests:**
- Unit tests for translation of representative element phrases (text, XPath, CSS, context, custom category).
- Internal Java checks and consumer scenarios that exercise the adapter path (click, type, assert presence) against the local test site.
- Regression: existing `@all` consumer features still pass.

**Logging checklist:** Adapter entry/exit and translation decisions logged at debug; toggleable per-entity.

- Workbench `inspect-page`, `find-element`, element inspect CLI/MCP, and GUI routes all go through the adapter (joining the live session descriptor when present).
- One shared code path for web and desktop.

**Docs:**

- Desktop smoke tests (where feasible in CI; otherwise documented manual + unit stubs).
- Workbench element inspect tests assert routing through adapter.
- Full suite green; no weakened assertions.

**Logging checklist:** Per-action and per-entity logging; CLI-first error messages with `error:`/`fix:`.
