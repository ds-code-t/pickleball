# Pickleball 2.1.19: Full dom-composite Integration Roadmap

**Status: Mandatory.** Every phase listed below is required and must be completed in full before the next phase begins. Nothing is optional, deferred, or partial. A phase is done only when its functionality, documentation, and tests are all green, committed, and pushed to branch `2.1.19`.

**Goal (Dan, explicit):** FULL integration of dom-composite into Pickleball. dom-composite becomes THE single entry point for ALL Pickleball DOM and OS-desktop interaction (Windows, Linux, Mac). It replaces direct WebDriver/Playwright/XPath as the primary path. Its flexible selectors apply to both web and desktop elements. Future alternative backends must remain possible, but behind dom-composite as the one entry point.

**Architecture (locked):**
- Java calls the Rust core via the existing `dev.domcomposite.Client` / `Session` binding (stdio/CLI under the hood; low-latency process management). No raw JNI required for v1.
- Distribution: Pickleball depends on the Java client. The native `composite` binary is located at runtime via `COMPOSITE_BIN`, `COMPOSITE_HOME`, sibling checkout, or extracted from Maven platform-classifier artifacts (`tools.dscode:dom-composite-native:<version>:<os>-<arch>`). Ordinary `mvn`/`gradle` runs remain unchanged when the binary is absent (graceful skip for non-desktop paths).
- Single entry point: new `DomCompositeFacade` (or equivalent) in Pickleball core. All element lookup, click, type, wait, scroll, inspect, and Workbench `inspect-page` / `find-element` route through it. Existing Pickleball element syntax (text, type/category, position, XPath, CSS, role, etc.) is translated to composite pipelines / expressions / element descriptions. Desktop elements use the same facade with `source=desktop` (or equivalent).
- WebDriver remains only for browser lifecycle (launch, CDP attach, quit) where still required. Element operations no longer call WebDriver directly as the primary path.
- Backward compatibility: all existing consumer Gherkin feature files continue to work without modification. Translation layer is the only adapter.
- Logging: toggleable per-entity via existing `COMPOSITE_LOG` / `COMPOSITE_LOG_LEVEL` (and Pickleball RunVars that forward them). CLI-first checklist in every phase.
- Fallback: if composite binary unavailable, web paths fall back to prior Selenium path only during transition phases; desktop requires composite. Final state has no Selenium element fallback.

**CLI-first and toggleable per-entity logging checklist (apply to every phase):**
- All new behavior is reachable via CLI or Workbench session commands first.
- Logging entities (`capture`, `query`, `resolve`, `action`, `desktop`, `session`, etc.) are off by default and controllable via `COMPOSITE_LOG` or equivalent RunVar.
- Agent-log and diagnostic evidence include composite session ids and key outcomes.
