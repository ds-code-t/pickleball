## Done

### A1. Workbench window freeze + JVM-exit/reuse

`FeaturePickerPanel.setCatalog` builds each `DefaultListModel` offline and calls `setModel` once. Both lists use `setFixedCellHeight(20)`. Feature selection is one `setSelectedIndices`. Each renderer is one `DefaultListCellRenderer` (one `JLabel`). The full catalog stays in the list. Paging was not added: fixed height is what removes the per-row measure.

A dedicated `ui` process (`WorkbenchApplication.ui` → `WorkbenchWindowLifecycle.armDedicatedProcess`) exits when its last window closes (`WorkbenchFrame.finishClose`). `open-ui` calls `armSharedController` and does not exit the session JVM. `open-window` already reuses a healthy `ui-attach`; the exit removes the closed process that used to sit beside the next launch.

Tests: `WorkbenchFrameLoadTest`, `WorkbenchWindowLifecycleTest`.

### A2. Worker lock-up + watchdog + working restart

`SelectorWatchdog` marks the worker unhealthy when a JDK `HttpClient` `SelectorManager` thread holds at least 80% CPU for 15 seconds. `GET /v1/health` returns 503 with `selector-spin` immediately. `ControlBridgeClient.health` uses a 2 second timeout. `WorkbenchWorkerManager.restartInteractive` starts a new worker after the old process is dead, including a non-zero kill exit. Two failed health reads restart the worker. CLI `worker-restart` and MCP `workbench_worker_restart` call that restart.

Tests: `WorkerWatchdogTest`, `BridgeHealthTest`.

### A3. Warm-JVM glue

`StepRegistry` scans consumer glue, including package-private methods and `@Before` / `@After` hooks that take a `Scenario`, before any step. Those hooks run on the same glue instance as the steps. `@DataTableType` and the default table transformers are registered on that scan. Step tables from `CucumberModelConverter.dataTable` use that converter, so `asList` and `asMaps` are not "created without a converter". The warm JVM (`WorkbenchWarmMain` fresh class loader, then `WorkbenchDirectRun`) and `store run` both go through that engine.

Tests: `WarmJvmGlueTest`.

### A4. Accurate run history

`StoreExecution` stores a skipped step as `SKIPPED`. A run whose steps are only skipped is `SKIPPED`, not `PASSED`. `NativeScenarioRun` records nested component and `RUN SCENARIOS` steps. A failure inside those steps is `FAILED`, and the run's failed count is not zero. `RunCatalog` writes agent runs into `reports/diagnostic-runs/run-catalog.json`. `query` reads `.pickleball/store/runstate.db` for that run's status and steps. The store is the source of truth. The catalog and `query` are views.

Tests: `RunHistoryAccuracyTest`.

### A5. Entity reference resolution

`StoreEntities.lookup` accepts an id that contains dots (`ae-mgr-all.app`). It tries the longest stored id first and uses the remainder as the field path. `<entity:Operator#ae-mgr-all.app>` resolves from `store-entities/Operator/ae-mgr-all.app.entity` while a step runs when Store is on. `<entity:Account#ada.name>` is still the `name` field of `ada`. With Store off the reference text is unchanged.

Tests: `EntityResolutionTest`.

### A6. Run-id reuse never overwrites a finished run

`AgentCoordination.begin` throws if that run id is already finished. It does not reset the record to `RUNNING`. Isolate on a finished discover id leaves the `FAILED` record in place. A later finish of `PASSED` does not replace that status. An in-progress `RUNNING` record can still be adopted.

Tests: `RunIdReuseGuardTest`.

### A8. Store tests from the 2026-11-16 regression

`SqlDialect.ensureSchema` installs changelog triggers under a per-database lock. `CREATE TRIGGER IF NOT EXISTS` plus a retry covers `SQLITE_BUSY` and "already exists". The fast path is unchanged: it returns only when `store_schema` is exactly `1` and trigger `files_pkb_insert` exists. A newer schema still throws. `Sql.setAutoCommit`, `commit`, and `rollback` retry when the WAL file is locked. A commit or rollback that SQLite already finished, including "no transaction is active", leaves the connection usable so parallel history writes can share that database. `StoreEntityUsageTest.aRealStepRecordsTheLookup` and `StoreExecutionRecordingTest.aRunRecordsStepsAndLinksTheMatchingDefinition` clear a bound sandbox and the definition catalog and use their own temp store. The usage test takes a new run id so a finished record in the repo cannot block it. Assertions are unchanged.

Tests: `StoreEdgeTest.parallelHistoryWritesShareTheWalDatabase`, `StoreEntityUsageTest.aRealStepRecordsTheLookup`, `StoreExecutionRecordingTest.aRunRecordsStepsAndLinksTheMatchingDefinition`.

### A9. Tracking and Store tabs empty (P2-24)

`StoreCliForwarder` and `DomEngineCliForwarder` no longer run `java -jar` on the thin pickleball jar. They run:

`java -cp <resolved consumer classpath> tools.dscode.launcher.PickleballWorkbenchLauncher store|domengine ...`

The classpath is `classpath.txt` under the Workbench state root when that file has a real entry, otherwise `classpath.cache`. The thin jar is first. If sqlite-jdbc or Jackson is still missing, those jars are taken from the controller JVM classpath (already resolved; not shaded). The published jar stays thin.

A non-zero forward (stderr, else stdout, plus the exit code) is a row in the Tracking list and the Store list (or the conflicts area). It is not only the status label.

Live examples that told a consumer to `java -jar ... store` or `java -jar ... domengine` now use the classpath form: `docs/pickleball-workbench.md`, `docs/direct-control-handoff.md`, `docs/release-notes.md`, `AGENTS.md`, `docs/agent/feature-map.md`.

Tests: `StoreCliForwarderTest.classpathCommandIncludesSqliteAndJackson`, `DomEngineCliForwarderTest.commandForwardsDesktopVerbsAndDoesNotEmbedEngineTypes`, `WorkbenchTrackingForwarderTest.populatedTimelineShowsRowsAndAFailureIsVisibleInTheTable`, `StorePanelTest.populatedStoreShowsRowsAndAFailureIsVisibleInTheTable`.

### B1. Ready-made CLI

`start --url= --browser= --env=` writes `.pickleball/consumer-session.json` and does not launch a browser. Later page commands with no `--run-id` use that session (`WorkbenchAgentCommands.boundRunId`). `chat_wait` blocks on `chat-poll` until a message arrives or `--timeout` (default 30 seconds, max 120). `history-summary` counts run records and store history. `history-query` is the existing `query` read. `entity-lookup --ref=` resolves one entity. `open-run --tab=explorer|tracking` writes `.pickleball/workbench/open-run.json`. `bridge-health --url=` reads `GET /v1/health` with a 2 second timeout. MCP tools `workbench_start`, `workbench_chat_wait`, `workbench_history_summary`, `workbench_history_query`, `workbench_entity_lookup`, `workbench_open_run`, and `workbench_bridge_health` forward through `ConsumerReadyForwarder.command`, which calls `ConsumerClasspath.entries`. The published jar stays thin. Log: `.pickleball/logs/consumer-cli.log`, off when `pkb_consumer_log=off`, capped at 1 MiB.

Tests: `ConsumerReadyCliTest`, `WorkbenchCliCoverageGateTest`, `ConsumerReadyForwarderTest`, `WorkbenchMcpServerTest.consumerVerbsForwardThroughConsumerClasspath`.
