# Pickleball 2.1.19 Find Interface Roadmap

**Goal (Dan, 2026-11-05, locked after investigation; deferred to pickleball judgement on all implementations):** Full exposure of the existing dom-composite engine query object (pipeline string and/or expression with css=, xpath=, text=, image=, near=, below=, >> stages, AND/OR/NOT with scores, --explain) on the shared Workbench / direct-control / MCP / composite-CLI path. Workbench, MCP, control-bridge, and CLI are thin forwarders through ElementOperations → DomCompositeAdapter. No second locator language. No new query language. Existing Gherkin stays locked phrase sugar via SelectorTranslator (after/before = document order). Visual left/right/above/below/near is pure visual distance consuming the shared Geometry view (document_css_px, visual-viewport-relative, layout-viewport-relative, nearest-scrollport-relative, frame-document-relative). Dual mode (human-viewable default for interact vs lower-level opt-in per query) with mandatory human-limitation labels. Ranked candidates with explain. Image reconcile prefers DOM/CompositeNode bind when promotable. Fast surfing: one query + mode + optional limit returns rich labeled batch + stable handles.

**Baseline:** pickleball 2.1.19 (fetch origin/2.1.19 before any commit; mapping-geometry commits may already be present — do not overwrite them or docs/maintainer/2.1.19-mapping-geometry-roadmap.md). dom-composite main 2.10.0 at 9029e0c5. Composite is primary via ElementOperations / DomCompositeAdapter when binary present (`pkb_composite=auto`). Current control path (ElementControl.inspect, PageElementQuery.find/inspect, Workbench find-element/inspect-page) builds XPath only from ExecutionDictionary category+text vocabulary then calls ElementOperations.describe. Visibility is ElementView.displayed() (Selenium isDisplayed or the composite displayed filter). Agents get rawMatchCount + visibleCount. No raw engine pipeline/expression is forwarded. Visual relatives not wired. Geometry view is in progress on the same branch.

Existing Gherkin/step syntax and behavior must not change unless a forced consumer-visible contract change is discovered (call it out explicitly). dom-composite may change (breaking OK, no other app uses it) but stays a decoupled general-purpose engine with no knowledge of pickleball; engine work goes on a non-primary branch + PR into main. Between phases run ONLY targeted tests tied to the changed code. Final full regression (Gradle :test :pickleball-control-protocol:test :pickleball-control-api:test :pickleball-workbench:test --rerun-tasks, consumer_sim, verify_agent_contract.py, Windows CI) runs ONCE at the very end of all phases. CLI-first and toggleable per-entity date-stamped size-capped logging for any new engine capability (existing pkb_composite_log / COMPOSITE_LOG style). Hold validate --all unless a controlled compare shows a code cause. Do not treat a held validate --all as part of this roadmap. ## Phase 1: Shared engine query object on the control / Workbench / MCP path + vocabulary policy update
**Functionality:**
- Introduce a shared query object (the engine pipeline string and/or expression) that ElementControl, PageElementQuery, Workbench find-element / inspect-page, MCP, and control-bridge forward through ElementOperations → DomCompositeAdapter. No second locator language. Category+text remains available as convenience sugar that translates to the same object via the existing dictionary path when used.
- DomCompositeAdapter accepts the object as --pipeline / --expr (plus --explain, --promote-visual, flags already supported by the engine) and returns ranked candidates with scores and explain when requested.
- Update docs/dynamic-control-api.md and related Workbench / agent / direct-control docs: inspection/find may use CSS, XPath, image, nesting, and relative location in any combination. The previous policy that restricted to Pickleball category+text vocabulary is replaced by full exposure of the engine query object.
- Engine stays general-purpose; any needed capability flags or payload fields (e.g. richer explain, stable node handles) go on a working branch + PR. Update prompts/domc-asks.md.
- Capability-gate; fallback when binary lacks the flags keeps current category+text XPath behavior for the old callers.

**Docs:** Update this roadmap. Update dynamic-control-api.md, pickleball-workbench.md, workbench-agent-detail.md, direct-control-handoff.md, AGENTS.md / feature-map as needed. Note the policy change.

**Tests:**
- Unit / parity: existing category+text inspect/find still produces the same XPath contract and displayed counts on both Selenium and composite paths.
- New consumer-shaped repro: a Workbench/MCP query with a raw pipeline or expression (e.g. css=button >> text="Save" or an AND expression) returns the expected ranked hits with explain when --explain is requested.
- Measured: one query path; no second locator system.
- Existing Gherkin Ambiguous / first / nth / nesting / within tests stay green and locked.

**Logging checklist:** Trace/info on the adapter when a raw pipeline/expr is forwarded vs dictionary sugar. Toggleable via pkb_composite_log. CLI-first: the same query object is reachable from the composite CLI.

**Regression risk:** Low. Existing Gherkin and old category+text callers unchanged. Additive path for the new object. Launch modes covered by parity.

## Phase 2: Dual visibility mode + mandatory human-limitation labels
**Functionality:**
- Add a mode parameter (not a session-level sticky setting) on the same query path: human-viewable / human-interactive (default for interact: click, type, “what is on screen”) vs lower-level view/interact.
- Human mode: displayed, intersects the visual viewport, non-zero size, topmost/interactable. MUST exclude nodes that are isDisplayed but outside the current visual viewport. Humans do not see outside the viewport.
- Lower-level mode (opt-in per query): source, hidden, invisible, off-viewport, zero-size, aria-hidden, clipped, occluded, pointer-events:none, and similar. Same path, relaxed filter.
- Human-limitation labels are mandatory on every lower-level result AND action. Both machine-readable reason codes (human_could_not_see / human_could_not_click / human_could_not_follow plus off_visual_viewport, display_none, visibility_hidden, opacity_zero, aria_hidden, zero_size, clipped, occluded, pointer_events_none, source_only, etc.) and a short sentence. Example: “acted on node X; a person could not have seen or clicked it because it is scrolled out of the visual viewport and has opacity:0.” Extra power must never be confused with a human-replicable path.
- Interact defaults to human-visible mode. An agent must opt in per action to act on a non-human-visible target, and that action still carries the labels.
- Inspect/find in human mode returns only human-visible nodes. Inspect/find in lower-level mode may return the extra layer, and every node is labeled. Page source remains a separately labeled read (offline --html or an explicit source dump).
- Occlusion / clipping / corner interactability: consume mapping-geometry Phase 3 hit_grid / hit_at / topmost when those capabilities exist; until then, capability-gate a coarser fallback (intersects visual viewport and not display:none / visibility:hidden). Do not block this roadmap on mapping Phase 3 being finished. Closed-shadow and cross-origin fail closed as today.
- Through the one shared ElementOperations → DomCompositeAdapter path. Geometry view used for viewport intersection when present; capability-gate and fall back without fake quads.

**Docs:** Update this roadmap and the control/Workbench docs with the mode parameter, defaults, and label contract.

**Tests:**
- Unit / parity: human mode excludes off-viewport isDisplayed nodes; lower-level includes them with labels. Selenium path for unchanged Gherkin still uses isDisplayed.
- Consumer-shaped repros: interact on a scrolled-out node requires opt-in and carries the sentence label; human-mode inspect does not return it; lower-level does with codes.
- Measured: mode is per-query; no sticky session state.

**Logging checklist:** Info when human vs lower-level filter applied; labels logged at debug/trace. Toggleable.

**Regression risk:** Medium for new callers; low for existing Gherkin (locked by tests). Default for interact is human-safe.

## Phase 3: Visual relative location stages via the shared Geometry view
**Functionality:**
- Visual relative location (left-of / right-of / above / below / near) is pure visual distance using the Geometry view — not document or tree order. Consume all five Geometry spaces through that one view: use visual-viewport-relative when asking what a person sees; nearest-scrollport-relative when the reference lives inside a scroller; document_css_px as the global space; layout-viewport-relative and frame-document-relative as already planned. Ties use existing paint order / top-layer / hit_grid / topmost sampling. Overflow uses nearest-scrollport. Closed-shadow and cross-origin fail closed as today.
- If current engine near=/below= still has tree-order residue, make visual distance the contract for these exposed relative stages on the shared path. Do not invent a parallel geometry system; if mapping-geometry has not landed yet, capability-gate and fall back without fake quads.
- Existing Gherkin after/before stay document order (locked). New power lives only on the Workbench / direct-control / MCP / composite-CLI surface.
- Engine general-purpose updates (if near=/below= need a visual-distance mode or new stage names) on working branch + PR. Update prompts/domc-asks.md.

**Docs:** Update this roadmap. Note the visual-distance contract and the Geometry consumption.

**Tests:**
- Unit / parity: a relative query using Geometry returns pure visual-distance ranking when capability present; document-order Gherkin after/before unchanged.
- Consumer-shaped repro: left-of a visible button finds the expected visual neighbor; falls back cleanly when Geometry absent.
- Measured: one Geometry path; no second system.

**Logging checklist:** Geometry-relative distance logged when used; capability fallback noted.

**Regression risk:** Low. Additive relative stages on the exposed path. Gherkin locked.

## Phase 4: Ranked candidates + explain, image reconcile priority, and fast surfing batch
**Functionality:**
- For agent / Workbench / direct queries, return ranked candidates with explain / why-matched (engine scores and --explain). Existing Gherkin Ambiguous / first / nth / nesting / within behavior stays locked by tests.
- Image reconcile priority: bind to a DOM / CompositeNode first when the match can promote (engine --promote-visual). If no node can be bound (desktop/screenshot-only, or closed-shadow / cross-origin fail-closed), keep a labeled visual-only hit. Never pretend a visual hit is a DOM node.
- Fast surfing, in scope: one query + mode + optional limit that returns a rich labeled batch (text, geometry when available, visibility labels) and stable node handles for follow-up reads/acts without re-walking the tree. Out of scope for this roadmap: a batch action primitive (“click these N links and report which succeeded”). Each act stays a single labeled call through the human-visible default.
- Through the shared path. Stable handles are the existing node ids or engine-provided stable identifiers; capability-gate.

**Docs:** Update this roadmap and control docs with ranked explain contract, image promote priority, and the fast-surfing batch shape.

**Tests:**
- Unit / parity: ranked explain present on the new query path; Gherkin Ambiguous etc. unchanged.
- Consumer-shaped: image query prefers DOM bind when promotable, else labeled visual-only; fast-surfing batch returns labeled nodes + handles usable for a follow-up single act.
- Measured: one query for the batch; handles stable until re-render.

**Logging checklist:** Explain scores and promote decisions logged. Toggleable.

**Regression risk:** Low. Additive return fields. Existing Ambiguous contract locked.
