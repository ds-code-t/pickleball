## Phase 1: Observe-buffer exposure + launch templates + window/tab commands

**Functionality:**
- Expose the already-buffered engine CDP events (`Network.*`, `Runtime.consoleAPICalled`, `Log.entryAdded`) on the shared CLI / Workbench / MCP / control-bridge path. Support filter by type, URL substring, time window, and limit. Do not re-investigate CDP buffering and do not re-implement a second buffer if Session already has one; add the thinnest pickleball-side read/adapter needed to surface those events.
- Named browser launch templates for Chrome, Edge, and other Chromium browsers, headless and non-headless, with and without verbose logs. Ship at least: `chrome-headed-verbose`, `chrome-headed-quiet`, `chrome-headless-verbose`, `chrome-headless-quiet`, `edge-headed-quiet`, `edge-headless-quiet`, and a with-logs variant. Selectable on the fly (`launch --template=NAME`) with additive `--arg=` overrides. Build on the existing local Chrome/Edge startup path (`pkb_browser`, Selenium Manager, fallback drivers, existing launch selection). Do not invent a second launcher.
- First-class window/tab list, switch, and close commands on top of existing window-handle management, including additional instances started from templates.

**Docs:** This roadmap. `docs/dynamic-control-api.md`, workbench / agent docs, CLI help. Sync agent index.

**Tests:** Targeted only: observe-buffer read/filter tests; launch-template selection and override tests; window/tab command tests. Consumer-shaped repros for the new commands. Do not run the full unrelated suite.

**CLI-first checklist:** Every new capability is reachable from the CLI. Workbench / MCP / control-bridge only forward that path.

**Logging checklist:** Toggleable, per-entity, date-stamped, size-capped (`pkb_composite_log` style). Log template used, observe filter, and window actions.

## Phase 2: Live chat panel

**Functionality:**
- Shared commands such as `chat-send`, `chat-history`, and `chat-poll` (match existing CLI naming style). Messages tagged by source (agent id, human, system).
- Persistence under the `.pickleball` session or run directory so multiple agents and the human can share context. Per-run channels so concurrent agents do not race on one undifferentiated stream.
- Workbench UI panel that only forwards the same commands (no second chat implementation).

**Docs:** This roadmap plus dynamic-control / workbench / agent docs and CLI help. Sync agent index.

**Tests:** Targeted chat send/history/poll persistence tests and a Workbench-forwarding test. Consumer-shaped repro.

**CLI-first checklist:** Chat is fully usable from the CLI. The Workbench panel only forwards.

**Logging checklist:** Log chat send/receive with source tags; toggleable and size-capped.

## Phase 3: CSS highlight helpers

**Functionality:**
- Predefined helpers such as `highlight --handle=H --preset=yellow` and `highlight --handle=H --preset=outline-red`, plus `unhighlight` / clear. Presets are required. An explicit style string may also be accepted because agents have full access; still no arbitrary JavaScript.
- Prefer non-mutating CDP `Overlay.highlightNode` when available for pure visual highlighting. DOM class or style presets are also fine.
- Reversible, logged, and labeled (`style_modified` plus a short sentence). Uses existing ranked handles from find-interface.

**Docs:** This roadmap plus dynamic-control / workbench / agent docs and CLI help. Sync agent index.

**Tests:** Targeted highlight / unhighlight / label tests using handles. Consumer-shaped repro.

**CLI-first checklist:** Highlight and clear are reachable from the CLI.

**Logging checklist:** Log handle, preset, and reverse; toggleable.

## Phase 4: Overlays with bidirectional input

**Functionality:**
- Predefined helpers that place guidance on elements using the Geometry view (visual-viewport-relative for what a person sees): callouts such as "click here", short explanations, temporary surfaces.
- In-page injection is mandatory (this is writing HTML on the fly): place a temporary overlay via a predefined helper (not free-form agent JavaScript). Capture clicks and form inputs and forward them as structured events the agent can poll or receive via chat.
- Also implement a Workbench-native overlay path if it can share the same command object. In-page is the agent-privileged path and is required.
- Reversible: remove on demand and on scenario or session end.
- Every injected surface carries labels (`agent_injected`, `overlay`) as a data attribute and in the return value, plus a short sentence ("agent-injected overlay; a person did not author this UI").
- Agents with full / lower-level access see injected nodes labeled. Do not hide them from agents. Existing Gherkin find behavior is unchanged.

**Docs:** This roadmap plus dynamic-control / workbench / agent docs and CLI help. Sync agent index.

**Tests:** Targeted place / input-forward / remove / label tests, including Geometry placement. Consumer-shaped repro.

**CLI-first checklist:** Place, poll input, and remove are reachable from the CLI.

**Logging checklist:** Log place/remove and forwarded input events; toggleable.

## Phase 5: Full HTML write helpers

**Functionality:**
- Predefined write / replace / insert / remove HTML helpers so agents can write HTML on the fly into pages. Agents may supply HTML snippets (full access). Do not neuter this with a tiny tag allowlist. Do not execute agent-supplied JavaScript.
- Mandatory labels and data attributes on every injected node and on the action result (`agent_injected` plus a short sentence).
- Reversible by design: every write has a matching remove; an explicit cleanup command removes agent surfaces; scenario or session end also cleans up.
- Log every inject and remove (snippet hash or summary).
- Geometry-aware placement when the write is an overlay-like surface.

**Docs:** This roadmap plus dynamic-control / workbench / agent docs and CLI help. Sync agent index.

**Tests:** Targeted write / replace / remove / cleanup / label tests. Consumer-shaped repro that writes HTML and reads it back labeled, then cleans it up.

**CLI-first checklist:** Write, replace, insert, remove, and cleanup are reachable from the CLI.

**Logging checklist:** Log inject/remove with snippet hash or summary; toggleable and size-capped.

## Phase 6: Capture-to-scenario

**Functionality:**
- Convert observed page traffic from the Phase 1 observe buffers into regular pickleball service-call component scenarios. Use existing service-call / component scenario syntax. Do not invent a new Gherkin language or change existing phrases.
- CLI (and thin forwarders) to generate a scenario file from a filter of observed requests (for example by URL substring or time window).
- Document the agent loop: observe buffers → filter → capture-to-scenario.

**Docs:** This roadmap plus dynamic-control / workbench / agent docs and CLI help. Sync agent index.

**Tests:** Targeted tests that feed recorded/fixture observe events and assert a generated scenario in the existing service-call shape. Consumer-shaped repro. Do not run the full unrelated suite in this phase.

**CLI-first checklist:** Capture is reachable from the CLI.

**Logging checklist:** Log filter and output path; toggleable.
