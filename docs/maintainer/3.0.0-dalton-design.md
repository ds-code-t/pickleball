# Pickleball 3.0.0 Dalton Design

**Subsystem name:** Dalton (Dan's working name; used as the subsystem name; "Dalton" is also the alias).

**Status:** Design locked 2026-11-11. Implementation begins on branch `3.0.0`.

## Purpose

Dalton makes Git the durable source of truth for feature files, configuration, resource maps, templates, and business entities while giving humans, the Workbench, and AI agents a fast, queryable, editable local working copy.

Each run (or explicit command) hydrates the files into a local embedded database. Execution and editing happen against the database. Changes are hydrated out (extracted) back to files. Those file changes are what Git, GitHub PRs, and CI see.

The database is a disposable, rebuildable build artifact. It is never committed.

## Core Principles

1. **Files are the source of truth.** Git history, PRs, and CI operate only on files.
2. **Database is a hydrated working copy + runtime store.** Disposable, incremental by content hash, gitignored.
3. **Round-trip is lossless and deterministic.** Comments, tags, docstrings, data tables, ordering, and whitespace that carries meaning are preserved. Byte-stable when no semantic edit occurred.
4. **Conflicts are detected.** When both the file and the database copy have changed since the last sync, hydrate-out refuses to overwrite silently.
5. **Existing Gherkin and step behavior are unchanged.** New entity lookups are additive only.
6. **Zero-config default.** Existing consumer projects continue to work with the file-only path. Dalton is opt-in (or transparently additive when enabled).
7. **CLI-first.** Every Dalton capability is reachable from the CLI. Workbench, MCP, and Gradle tasks only forward to the CLI.
8. **No cleartext secrets.** Entities hold secret references only, using Pickleball's existing secrets/config approach.
9. **One shared code path.** When Dalton is disabled, the existing file-loading path is used unchanged.

## Alternative Framings Considered

- **DB as pure cache:** Files always win; DB is only a compiled artifact. Rejected because agents and Workbench need to edit and have those edits survive to Git.
- **DB as primary working copy with files as export only:** Attractive for agents, but weakens Git as the durable SoT and complicates CI/fresh-clone stories.
- **Event log / append-only:** Too complex for reliable lossless Gherkin round-trip and conflict detection.
- **Chosen: Hybrid.** Files are the Git source of truth. The database is the hydrated working copy, runtime execution store, entity store, and run-history store. Content hashes provide provenance and conflict detection.

## Storage Engine

**Embedded SQLite** via `org.xerial:sqlite-jdbc` (already used for diagnostic index parity tests; testRuntimeOnly today, not published to consumers).

Reasons:
- Java 17+ embedded, no server process.
- Proven on Windows CI (existing `sqlite-index.yml` workflow on `windows-latest`).
- WAL mode + `busy_timeout` supports concurrent readers during parallel Cucumber runs.
- FTS5 available if we later unify diagnostic search.
- Single-file database is easy to treat as a build artifact.
- Alternatives rejected: H2 (more configuration, less existing usage), DuckDB (analytical overkill), pure file-index (insufficient for entities, AST queries, and run history).

**Location:** `.pickleball/dalton/dalton.db` (parent `.pickleball/` is already gitignored). Schema is versioned. The database is deleted and rebuilt from files at any time.

## Schema Shape (High Level)

- `files` — path, content_hash (SHA-256), raw_content, mtime, last_hydrated_at, source_type (feature|config|call|component|template|entity|other)
- `gherkin_ast` / scenarios / steps / tags / data_tables / docstrings — derived from parsed features; original raw always retained
- `entities` — entity_type, entity_id, version, payload_json (or text), secret_references only, source_file, content_hash
- `runs` / `step_results` / `logs` — run history and logs (integrates with or parallels existing diagnostic reporting)
- `provenance` — last_synced_hash, db_version, hydration_id for conflict detection

Incremental hydration compares content hashes and skips unchanged files.

## Hydrate-in

Triggers (all optional except the CLI):
- CLI: `pickleball dalton hydrate` (primary)
- Gradle task `daltonHydrate` that only forwards to the CLI
- Auto on run when Dalton is enabled and the DB is missing or any source hash is stale
- File watcher is out of scope for initial phases (can be added later as a pure CLI forwarder)

Hydration is incremental by content hash. A fresh clone has zero DB and works (either auto-hydrates or falls back to files until the first hydrate).

## Hydrate-out (Extract)

CLI: `pickleball dalton extract` (or `hydrate-out`).

Semantics:
- If a file is unchanged in both Git and the DB since last sync, no write.
- If only the DB changed, write the regenerated (or original-if-unedited) content.
- If only the file changed, leave it (or re-hydrate on next in).
- If both changed, detect conflict, refuse overwrite, emit a clear diagnostic. `--force` or an explicit merge path is required.
- Formatting is byte-stable and deterministic. When no semantic edit occurred, the original raw bytes are preferred. When an edit occurred, a stable formatter preserves comments, tags, ordering, data tables, and docstrings.

After a successful extract, `git status` is clean except for the intentional file changes.

## Business Entities

Entities are first-class data that scenarios reference but that are not part of scenario text: case IDs, user IDs, account numbers, login references, test data records.

- Stored in the database.
- Always hydrate out to files (one stable text file per entity or per collection, YAML or JSON).
- Each project chooses, per entity type, whether those files are committed or gitignored (via normal `.gitignore` or a Dalton config).
- Reference syntax is additive only. Existing Gherkin, `<config:>`, `<file:>`, `<data:>`, etc. are unchanged.
  Proposed syntax (to be locked in Phase 4): `<entity:Type:id.field>` or `<entity:Type#id.field>`.
- Never store real passwords or secrets in clear text. Entities hold secret *references* only (e.g. existing `<password:qaDb>` or `~MASK;` style).

## Git and CI Compatibility

- Database folder is gitignored. Never versioned.
- Fresh clone and CI work with zero DB present.
- `git status` is clean after hydrate-in.
- CI workflows continue to use the file-only path or auto-hydrate as needed; the DB is never a required artifact.

## Migration

Zero-config default: existing consumer projects keep working unchanged. Dalton is opt-in via:
- `pkb_dalton=true` (or equivalent config), or
- Presence of a Dalton configuration file, or
- Explicit CLI use.

When disabled, the existing file-loading, config-mapping, and execution paths are used exactly as today. No tests are weakened, deleted, or skipped.

## Workbench and Agent Integration

CLI-first:
- Every capability (hydrate, extract, entity CRUD, status, query, logging controls) is a CLI command.
- Workbench UI, MCP tools, and Gradle tasks only forward to the CLI (or to the same internal service the CLI uses).
- Agents interact via the CLI or MCP that forwards to the CLI.

## Logging

New Dalton code has toggleable, per-entity (or per-capability), date-stamped, size-capped logging. Existing diagnostic logging remains unchanged.

## Holes and Decisions

- Lossless Gherkin round-trip is the hardest part. Store original raw always; regenerate only on semantic edit; attach comments to AST nodes or store them separately so the formatter can restore them.
- Concurrent writers during parallel runs: WAL + busy_timeout + a short critical section or last-write-wins with conflict detection on extract.
- Scale to thousands of files: content-hash incremental hydration is mandatory.
- Windows path and encoding: use the same rules already proven in the SQLite parity CI and existing resource mapping.

## Non-Goals for 3.0.0

- Replacing existing diagnostic reporting (Dalton run history may integrate or sit beside it).
- Changing any existing Gherkin step annotation or phrase.
- Publishing the database or making it required for CI.
- Force-push, release, or merge to other branches.
