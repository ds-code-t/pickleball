**Dalton Design Summary (Pickleball 3.0.0)**

**Subsystem:** Dalton  
**Status:** Design locked 2026-11-11; implementation begins on branch `3.0.0`.

---

### **Purpose**
Dalton establishes Git as the durable source of truth for feature files, configuration, resource maps, templates, and business entities. It provides humans, the Workbench, and AI agents with a fast, queryable, editable local working copy via an embedded database.

- Files are the source of truth; Git, PRs, and CI operate only on files.
- A local embedded database is hydrated from files during each run or command.
- Execution and editing occur against the database.
- Changes are extracted back to files for Git tracking.
- The database is disposable, rebuildable, and never committed.

---

### **Architecture**

- **Storage Engine:** Embedded SQLite (`org.xerial:sqlite-jdbc`)  
  - Location: `.pickleball/dalton/dalton.db` (gitignored)
  - Schema versioned; deleted and rebuilt as needed
  - WAL mode + `busy_timeout` for concurrent readers
  - Single-file DB treated as build artifact
  - Chosen over H2, DuckDB, or pure file-index due to simplicity, existing usage, and concurrency support

- **Schema (High-Level):**
  - `files`: path, content_hash (SHA-256), raw_content, mtime, last_hydrated_at, source_type, last_synced_hash, db_edited
  - `gherkin_ast` / scenarios / steps / tags / data_tables / docstrings: derived from parsed features; original raw retained
  - `entities`: entity_type, entity_id, version, payload_json/text, secret_references, source_file, content_hash
  - `runs`, `step_results`, `logs`: run history and logs
  - `provenance`: last_synced_hash, db_version, hydration_id for conflict detection

- **Hydration (In):**
  - Incremental by content hash
  - Triggers: CLI (`dalton hydrate`), Gradle task (forwards to CLI), auto on run if DB missing or stale (via AspectJ hooks)
  - Fresh clone works with no DB (falls back to files until first hydrate)

- **Extraction (Out):**
  - CLI: `dalton extract`
  - Lossless, deterministic round-trip: preserves comments, tags, docstrings, data tables, ordering, meaningful whitespace when no semantic edit
  - Byte-stable when no semantic edit
  - Conflict detection: if both file and DB changed since last sync, refuse overwrite without `--force`
  - After extract, `git status` is clean except for intentional changes

---

### **Decisions for Round 1**

- **Hybrid Model Chosen:**
  - Files = Git source of truth
  - DB = hydrated working copy, runtime store, entity store, run-history store
  - Content hashes enable provenance and conflict detection
  - Rejected: DB as pure cache (agents need edits to survive to Git); DB as primary (weakens Git SoT); event log (too complex for lossless Gherkin)

- **CLI-First Design:**
  - All capabilities (hydrate, extract, entity CRUD, status, query) exposed via CLI
  - Workbench, MCP, Gradle tasks only forward to CLI
  - Ensures consistency and testability

- **Zero-Config Default:**
  - Existing projects work unchanged (file-only path)
  - Dalton is opt-in via `pkb_dalton=true`, config file, or CLI
  - When disabled, existing file-loading paths used exactly as before

- **Business Entities:**
  - Stored in DB, extracted to files (YAML/JSON)
  - Project chooses commit/gitignore per entity type
  - Additive syntax only: `<entity:Type#id.field>`
  - No cleartext secrets: only references (e.g., `<password:qaDb>`, `~MASK;`)

- **Git & CI Compatibility:**
  - DB folder gitignored
  - Fresh clones and CI work without DB
  - `git status` clean after hydrate
  - CI uses file-only path or auto-hydrates; DB never required

---

### **Limitations (Round 1)**

- **Lossless Gherkin Round-Trip:**
  - Most complex aspect
  - Solution: store original raw content; regenerate only on semantic edit; preserve comments/tags via AST attachment or separate storage

- **Concurrent Writers:**
  - Parallel Cucumber runs supported via WAL + `busy_timeout`
  - Short critical sections or last-write-wins with extract-time conflict detection

- **Scale:**
  - Thousands of files supported via content-hash incremental hydration

- **Windows Compatibility:**
  - Uses proven SQLite CI rules for paths and encoding

- **Non-Goals for 3.0.0 Round 1:**
  - No replacement of existing diagnostic reporting
  - No changes to Gherkin step annotations or phrases
  - DB not published or required for CI
  - No support for force-push, release, or cross-branch merge

## Round 2 Decisions (2026-11-11)

Round 2 adds a real edit path, GUI browse/edit (CLI-first), discovery configuration, packaging fixes for consumers, and a fast warm run path. All design choices delegated and locked here.

### A. Real DB edit path
- Shared core operation writes `raw_content` + `content_hash`, sets `db_edited=1`, leaves `last_synced_hash` untouched, re-projects parsed Gherkin tables in the same transaction, and validates Gherkin before commit.
- Exposed as CLI `dalton feature put <path> [--text=...] [--file=...]`. `dalton entity put` uses the same core.
- Structured edits (scenario/step row updates) are explicitly rejected. No regenerate-raw path (cannot guarantee byte-stability with comments/whitespace without risk of silent divergence).
- Unflagged / raw-SQL edits are detectable: hydrate sees `content_hash != last_synced_hash && db_edited=0` and reports "untracked DB edit" as a conflict (no silent clobber unless `--force`).
- A flagged edit (`db_edited=1`) whose file still matches `last_synced_hash` is kept on hydrate. The file is not copied back over the working copy.
- `dalton scenario put` and `dalton step put` fail with: Structured edits are not supported. Bad Gherkin fails with `Gherkin is not valid: <path>` and the transaction rolls back.

### B. Workbench GUI browse/edit
- Browse files, features, scenarios, steps, entities, run history/logs; view/edit feature text and entities; run hydrate/extract/status; show conflicts.
- CLI-first rule strictly enforced: GUI only shells out to Dalton CLI (new list/show/query/put commands with JSON). Never touches SQLite or Dalton classes directly.
- Read commands: `dalton files list|show`, `dalton features list|show`, `dalton scenarios list --feature=`, `dalton steps list --feature= --scenario=`, `dalton conflicts`. `--json` is one object with stable key order. Text mode is labels. A missing database stays missing.
- Human-viewable labels.
- Implemented: the Workbench Dalton tab calls `DaltonCliForwarder` only. `DaltonBrowser` turns `--json` into labels and feature text. Save writes a temp file and forwards `feature put --file` or `entity put --payload-file`. No SQLite and no `tools.dscode.dalton` types in that module.

### C. Discovery config
- `dalton.properties` / system properties: include/exclude globs, max-file-size (default 1 MiB), binary-policy=skip (default; log reason). Content sniff + extension list.
- Sensible default excludes. Existing users with no config keep current fixed-directory behavior plus new size/binary skips.
- Reported in `dalton status`. `--path` respects limits unless forced.
- Implemented: empty `include` keeps the fixed directories. User `exclude` is added to the defaults and cannot drop them. `ignored=` on the hydrate line is the discovery skip count (`skipped=` stays the unchanged-hash count). `--path --force` is the only limit bypass. `hash-only` is accepted and still skips. Status prints `skipped` plus up to five `sample <path> <reason>` lines without creating a database. UTF-8 bytes above 127 are not a binary sniff. The control-byte ratio applies only when the sample is at least 32 bytes, so a short non-UTF-8 config is still stored.

### D. Packaging
- `sqlite-jdbc` remains not published or shaded.
- Enabling Dalton without the driver on the classpath fails loudly with an actionable message instead of silently falling back to files.
- Document clearly for Maven and Gradle consumers. Gradle dalton* tasks already supply the driver.
- Implemented: `DaltonDatabase.MISSING_DRIVER` is that message. `DaltonRuntime.beforeFeatureLoad` throws it whenever Dalton is enabled and `org.sqlite.JDBC` is absent, including on later feature loads, so a caught failure cannot continue on the files. CLI hydrate, extract, and enabled status use the same sentence and do not create a database.

### E. Fast Dalton-first run path
- `dalton run` launches or reuses a warm worker (reuse Workbench worker model) holding a cached prebuilt classpath. Executes from DB. Recompiles Java glue only when fingerprint changes, then restarts worker.
- Timing comparison script/tool included.
- Maven wrapper added to consumer template if useful.
- Full Gradle/Maven remain CI and source-of-truth. Fast path runs the same engine and produces identical results.
- Goal: avoid full Gradle/Maven startup cost per edit-run cycle.
- Implemented: `dalton run` starts or reuses `DaltonRunWorker` on loopback. That process is not the Workbench owner JVM. It calls `WorkbenchDirectRun`, so the engine id stays `pickleball-test-engine` and the run sets `pkb_dalton=true`. The worker prints `scenario PASSED|FAILED <name>` and `step PASSED|FAILED <text>` for each pickle step, then `dalton run exit=` with reuse, millis, and the plan. The glue fingerprint is SHA-256 of path, size, and mtime for `.java` under `src/main/java` and `src/test/java` and `.class` under the Maven and Gradle output trees. A change runs one `mvnw -q test-compile` or `gradlew testClasses --no-daemon`, then restarts the worker. The classpath is `pkb_dalton_run_classpath` or the Workbench `classpath.cache`. `--dry-run` prints the plan and writes nothing. `scripts/time_dalton_run.py --self-check` documents the cold-versus-warm comparison; `--project` runs it and requires the same exit code. `mvnw` was already in `maven-consumer-project`. Gradle `daltonRun`, the Workbench Run button, and MCP `dalton` forward to the CLI. `pkb_dalton_log=run` records the worker.

### F. Optional items decided
- File watcher (`dalton watch`): **OUT** for Round 2. Reasons: Windows WatchService flakiness, parallel-run + WAL locking contention, complexity versus gain (auto-hydrate + manual hydrate already exist). Dalton-first prefers DB edits. Can be added later as pure CLI forwarder.
- Secrets: keep reference-only, no encryption at rest. Broaden detection with configurable `secret-fields=` list in `dalton.properties` (appends to name-based list). Optional heuristic warning. Document clearly.
- Implemented: `DaltonSecrets` appends `secret-fields` (or `pkb_dalton_secret_fields`) to the built-in names. Cleartext on those names is still rejected in entity payloads and in history notes. A value of at least 32 characters with no spaces warns with `warn: high-entropy value on <field>` and is stored. The warning does not include the value. There is no encryption at rest.

**Long-term Dalton-first meaning:** DB is the primary store for interactive editing and fast execution. Files are the durable Git/CI export. Hydrate is bootstrap from clone. Warm `dalton run` is the normal iteration path.

---

**Conclusion:**  
Dalton introduces a Git-backed, database-augmented workflow for Pickleball 3.0.0, prioritizing lossless file synchronization, conflict detection, and zero disruption to existing systems. Round 2 adds the missing real edit path, GUI, configurable discovery, consumer packaging, and fast run foundation while preserving CLI-first and Git-as-SoT.
