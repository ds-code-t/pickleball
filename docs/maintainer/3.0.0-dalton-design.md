# Pickleball 3.0.0 Dalton Design

**Subsystem name:** Dalton (working name from Dan; keep as primary, "Dalton" is the alias if a better name emerges later).  
**Status:** Design locked for implementation on branch 3.0.0.  
**Version target:** 3.0.0 (starts from current 2.2.0).

## Concept summary

Files in Git remain the source of truth: feature files (`.feature`), config, resource maps, templates, entity files, and any other project resources (potentially thousands of files).  
Each run hydrates those files into a local disposable database (the way Java source or feature files are compiled before running). Runs execute from the hydrated database.  
The database folder is gitignored and never versioned. It is a rebuildable build artifact. Incremental re-hydration is by content hash.  
Edits can be made directly in the database (by humans via tools, by the Workbench, by AI agents through the CLI/MCP) and then "hydrated out" (extracted) back to files. Those file changes are what Git history, GitHub PRs and Actions see.  
Round-trip must be lossless and deterministic (byte-stable formatting, comments, tags, docstrings, data tables, ordering) and must detect conflicts when both the file and the DB copy changed.  
The database also holds run logs / run history and separate BUSINESS ENTITIES that scenarios use but that are not part of scenario text: case IDs, user IDs, account numbers, login info, test data records. Scenarios reference them. Existing Gherkin syntax and behavior are unchanged; new lookups are additive only.  
Entities always hydrate out to files too (e.g. one stable text file per entity or per collection). Each project chooses per entity type whether those files are committed or gitignored.  
Never store real passwords or secrets in clear text anywhere (DB or files). Use pickleball's existing secrets/config approach; entities may hold secret REFERENCES only.

## Framing decision

**Hybrid working copy + cache.**  
Files are the Git source of truth. The DB is the hydrated working copy used for execution, editing, entities, and run history. Content hashes provide provenance and enable conflict detection on round-trip. This is not a pure event log (too complex for lossless Gherkin) and not a pure ephemeral cache (agents and Workbench need a durable working store for edits).

## Storage engine

**Embedded SQLite** via `org.xerial:sqlite-jdbc` (already present as `testRuntimeOnly` for diagnostic parity CI; never published to consumers).  
Reasons:  
- Java 17+ embedded, no server process.  
- Proven on Windows CI via existing `.github/workflows/sqlite-index.yml` parity tests.  
- WAL mode + busy_timeout supports concurrent readers during parallel runs and controlled writers.  
- Lightweight, excellent for content-hash lookups and FTS if diagnostics integrate later.  
- H2 considered but SQLite already has the parity path and better FTS. DuckDB is analytical overkill. Pure file-index insufficient for entities, runs, and AST queries.

**Location:** `.pickleball/dalton/dalton.db` (parent `.pickleball/` already gitignored). Explicit ignore entry added for clarity. Schema is versioned.

## Schema shape (high-level)

- `files`: path, content_hash (SHA-256), raw_content (TEXT/BLOB), parsed_ast_json (optional), last_hydrated_at, source_mtime, last_synced_hash.  
- `scenarios`, `steps`, `tags`, `data_tables`, `docstrings`: extracted from AST for query and execution.  
- `entities`: entity_type, entity_id, version, payload_json (or text), secret_references (list only, never cleartext), source_file, content_hash.  
- `runs`, `step_results`, `logs`: run history (integrates with existing diagnostic layout where practical).  
- `provenance`: hashes, timestamps, origin (file vs db-edit).

Incremental hydration: skip files whose content_hash matches the stored hash.

## Hydrate-in triggers

1. CLI primary: `pickleball dalton hydrate` (or equivalent subcommand).  
2. Gradle task `daltonHydrate` that only forwards to the CLI.  
3. Auto on run when `pkb_dalton=true` and DB is missing or any watched file hash is stale.  
4. Optional file watcher (later phase, not required for core).  
Fresh clone and CI always work with zero DB present; hydration is on-demand or explicit.

## Hydrate-out semantics and conflict rules

CLI: `pickleball dalton extract` (or `hydrate-out`).  
- Store original raw bytes always.  
- On extract: if no DB edits since last sync, write the original bytes (byte-stable).  
- If DB edited, regenerate with a deterministic formatter that preserves comments, tags, ordering, data tables, and docstrings as far as the parser allows (AST + attached comments or parallel comment store).  
- Conflict: if file content_hash != last_synced_hash AND db content differs from last_synced, refuse overwrite. Report clear conflict; require explicit `--force` or a merge step. Never silent overwrite.  
- `git status` remains clean after a pure hydrate-in (DB is ignored).

## Entities and reference syntax

Business entities live in the DB and always hydrate out to stable text files (default: one YAML/JSON file per entity under `entities/<type>/<id>.yaml`, or one collection file per type). Project config or `.gitignore` patterns decide commit vs ignore per type.  
Reference syntax is **additive only**. Existing Gherkin, `<config:...>`, `<file:...>`, `<data:...>`, etc. are unchanged.  
Proposed form (finalized in implementation): `<entity:type:id.field>` or `<entity:type#id.field>`. Must not collide with existing prefixes.  
Entities hold secret REFERENCES only (e.g. `${protected:key}` or existing pickleball secret syntax). Never cleartext passwords.

## Git / CI compatibility

- DB never required to be committed.  
- Fresh clone + CI works with zero DB (falls back to today's file-only path when Dalton is off).  
- After hydrate-in, `git status` is clean.  
- Existing consumer projects keep working unchanged (zero-config default). Dalton is opt-in via `pkb_dalton=true` or explicit config presence.

## Migration from today's file-only flow

Default is today's path. When Dalton is enabled, the shared code path still loads features/configs but sources them from the hydrated DB instead of the filesystem. No existing Gherkin syntax or step behavior changes. Cucumber step annotations remain single string literals.

## Workbench and agent integration

**CLI-first:** every Dalton capability is reachable from the CLI.  
Workbench, MCP, and Gradle tasks only forward to the CLI (or share the exact same service layer the CLI uses). No parallel implementation.

## Logging

New Dalton code has toggleable, per-entity (or per-subsystem), date-stamped, size-capped logging. Existing diagnostic logging remains unchanged.

## Holes poked and resolved

- Lossless Gherkin round-trip is hard: mitigated by always storing raw original + careful formatter + conflict detection.  
- Concurrent parallel runs: WAL + busy_timeout + single logical writer queue where needed.  
- Scale (thousands of files): content-hash incremental hydration.  
- Secrets: references only.  
- Windows path/CI: SQLite path already proven.  
- Regression risk: opt-in + shared code path when off keeps existing tests green.

## CLI-first and logging checklist

- [ ] Every capability (hydrate, extract, status, entity CRUD, query, run-from-db) reachable from CLI.  
- [ ] Workbench surfaces only forward to CLI.  
- [ ] MCP tools only forward to CLI.  
- [ ] Gradle tasks only forward to CLI.  
- [ ] Toggleable logging for new code.  
- [ ] Per-entity or per-subsystem logging where applicable.  
- [ ] Date-stamped log files.  
- [ ] Size-capped (rotation or truncation) logging.  

See the phased roadmap for implementation order.
