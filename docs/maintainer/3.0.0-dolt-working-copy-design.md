**Dolt Design Summary (Pickleball 3.0.0)**

**Subsystem:** Dolt  
**Status:** the working copy is the Dolt store as of the Dolt-core store switch. SQLite details below are the previous contract. `dolt_schema=1` replaces schema 6. A schema-5 SQLite file is rehydrated, not upgraded in place.

---

### **Purpose**
Dolt establishes Git as the durable source of truth for feature files, configuration, resource maps, templates, and business entities. It provides humans, the Workbench, and AI agents with a fast, queryable, editable local working copy via an embedded database.

- Files are the source of truth; Git, PRs, and CI operate only on files.
- A local embedded database is hydrated from files during each run or command.
- Execution and editing occur against the database.
- Changes are extracted back to files for Git tracking.
- The database is disposable, rebuildable, and never committed.

---

### **Architecture**

- **Storage Engine:** Dolt 2.7.3 sql-server (`org.mariadb.jdbc:mariadb-java-client`, not shaded)
  - Location: `.pickleball/dolt/data` (gitignored), database `pickleball`, branch `main`
  - Schema `dolt_schema=1`; a fresh store is created, not upgraded in place from SQLite
  - One loopback server per project; branches isolate sandboxes
  - Disposable working copy, never committed
  - `sqlite-jdbc` remains only for migrate of the previous SQLite file and the diagnostic index

- **Schema (High-Level):**
  - `files`: path, content_hash (SHA-256), raw_content, mtime, last_hydrated_at, source_type, last_synced_hash, db_edited
  - `gherkin_ast` / scenarios / steps / tags / data_tables / docstrings: derived from parsed features; original raw retained
  - `entities`: entity_type, entity_id, version, payload_json/text, secret_references, source_file, content_hash
  - `runs`, `step_results`, `logs`: run history and logs
  - `provenance`: last_synced_hash, db_version, hydration_id for conflict detection

- **Hydration (In):**
  - Incremental by content hash
  - Triggers: CLI (`dolt hydrate`), Gradle task (forwards to CLI), auto on run if DB missing or stale (via AspectJ hooks)
  - Fresh clone works with no DB (falls back to files until first hydrate)

- **Extraction (Out):**
  - CLI: `dolt extract`
  - Lossless, deterministic round-trip: preserves comments, tags, docstrings, data tables, ordering, meaningful whitespace when no semantic edit
  - Byte-stable when no semantic edit
  - Conflict detection: if both file and DB changed since last sync, refuse overwrite without `--force`
  - After extract, `git status` is clean except for intentional changes

---

### **Decisions for Round 1**

- **Hybrid Model Chosen:**
  - Files = Git source of truth
  - DB = hydrated working copy, runtime store, entity store, run-history store
  - Content hashes enable provenance and conflict detection
  - Rejected: DB as pure cache (agents need edits to survive to Git); DB as primary (weakens Git SoT); event log (too complex for lossless Gherkin)

- **CLI-First Design:**
  - All capabilities (hydrate, extract, entity CRUD, status, query) exposed via CLI
  - Workbench, MCP, Gradle tasks only forward to CLI
  - Ensures consistency and testability

- **Zero-Config Default:**
  - Dolt is on unless it is turned off
  - Explicit `pkb_dolt` / `PKB_DOLT` wins; else `dolt.properties` `enabled=` or `pkb_dolt=` when present; else the default is on
  - `false|no|off|0` is the opt-out. An unknown value fails at first use
  - When disabled, existing file-loading paths are used and the database is not opened

- **Business Entities:**
  - Stored in DB, extracted to files (YAML/JSON)
  - Project chooses commit/gitignore per entity type
  - Additive syntax only: `<entity:Type#id.field>`
  - No cleartext secrets: only references (e.g., `<password:qaDb>`, `~MASK;`)

- **Git & CI Compatibility:**
  - DB folder gitignored
  - Fresh clones and CI work without DB
  - `git status` clean after hydrate
  - CI uses file-only path or auto-hydrates; DB never required

---

### **Limitations (Round 1)**

- **Lossless Gherkin Round-Trip:**
  - Most complex aspect
  - Solution: store original raw content; regenerate only on semantic edit; preserve comments/tags via AST attachment or separate storage

- **Concurrent Writers:**
  - Parallel Cucumber runs supported via WAL + `busy_timeout`
  - Short critical sections or last-write-wins with extract-time conflict detection

- **Scale:**
  - Thousands of files supported via content-hash incremental hydration

- **Windows Compatibility:**
  - Uses proven SQLite CI rules for paths and encoding

- **Non-Goals for 3.0.0 Round 1:**
  - No replacement of existing diagnostic reporting
  - No changes to Gherkin step annotations or phrases
  - DB not published or required for CI
  - No support for force-push, release, or cross-branch merge

## Round 2 Decisions (2026-11-11)

Round 2 adds a real edit path, GUI browse/edit (CLI-first), discovery configuration, packaging fixes for consumers, and a fast warm run path. All design choices delegated and locked here.

### A. Real DB edit path
- Shared core operation writes `raw_content` + `content_hash`, sets `db_edited=1`, leaves `last_synced_hash` untouched, re-projects parsed Gherkin tables in the same transaction, and validates Gherkin before commit.
- Exposed as CLI `dolt feature put <path> [--text=...] [--file=...]`. `dolt entity put` uses the same core.
- Structured edits (scenario/step row updates) are explicitly rejected. No regenerate-raw path (cannot guarantee byte-stability with comments/whitespace without risk of silent divergence).
- Unflagged / raw-SQL edits are detectable: hydrate sees `content_hash != last_synced_hash && db_edited=0` and reports "untracked DB edit" as a conflict (no silent clobber unless `--force`).
- A flagged edit (`db_edited=1`) whose file still matches `last_synced_hash` is kept on hydrate. The file is not copied back over the working copy.
- `dolt scenario put` and `dolt step put` fail with: Structured edits are not supported. Bad Gherkin fails with `Gherkin is not valid: <path>` and the transaction rolls back.

### B. Workbench GUI browse/edit
- Browse files, features, scenarios, steps, entities, run history/logs; view/edit feature text and entities; run hydrate/extract/status; show conflicts.
- CLI-first rule strictly enforced: GUI only shells out to Dolt CLI (new list/show/query/put commands with JSON). Never touches SQLite or Dolt classes directly.
- Read commands: `dolt files list|show`, `dolt features list|show`, `dolt scenarios list --feature=`, `dolt steps list --feature= --scenario=`, `dolt conflicts`. `--json` is one object with stable key order. Text mode is labels. A missing database stays missing.
- Human-viewable labels.
- Implemented: the Workbench Dolt tab calls `DoltCliForwarder` only. `DoltBrowser` turns `--json` into labels and feature text. Save writes a temp file and forwards `feature put --file` or `entity put --payload-file`. No SQLite and no `tools.dscode.dolt` types in that module.

### C. Discovery config
- `dolt.properties` / system properties: include/exclude globs, max-file-size (default 1 MiB), binary-policy=skip (default; log reason). Content sniff + extension list.
- Sensible default excludes. Existing users with no config keep current fixed-directory behavior plus new size/binary skips.
- Reported in `dolt status`. `--path` respects limits unless forced.
- Implemented: empty `include` keeps the fixed directories. User `exclude` is added to the defaults and cannot drop them. `ignored=` on the hydrate line is the discovery skip count (`skipped=` stays the unchanged-hash count). `--path --force` is the only limit bypass. `binary-policy=hash-only` stores a binary reference row (empty raw content, sha256 of the real bytes, `binary_ref=1`, `git_blob`, `byte_size`, `source_type=binary-ref`). Extract does not write that row back and reports `binary_ref_changed <path>` when the file on disk no longer matches. The default policy stays `skip`. Status prints `skipped` plus up to five `sample <path> <reason>` lines without creating a database, plus `binaryRefs` and Git provenance. UTF-8 bytes above 127 are not a binary sniff. The control-byte ratio applies only when the sample is at least 32 bytes, so a short non-UTF-8 config is still stored. Hydrate records `git_commit`, `git_branch`, `git_remote` (userinfo stripped), `github_repo`, and `git_dirty` on `provenance` (schema 5, old databases upgrade in place). Each file row stores `git_blob`. No git binary leaves those fields empty and warns once (`dolt git unavailable`). `pkb_dolt_log` accepts `git` and `binary`.

### D. Packaging
- `org.xerial:sqlite-jdbc:3.47.2.0` is a published runtime dependency (POM scope `runtime`) and is not shaded into the consumer shadow JAR.
- Enabling Dolt without the driver on the classpath fails loudly with an actionable message instead of silently falling back to files. The message says Dolt is on by default.
- Document clearly for Maven and Gradle consumers. Gradle dolt* tasks already supply the driver.
- Implemented: `DoltDatabase.MISSING_DRIVER` is that message, including `Dolt is on by default; add org.xerial:sqlite-jdbc or set pkb_dolt=false to run file-only.` `DoltRuntime.beforeFeatureLoad` throws it whenever Dolt is enabled and `org.sqlite.JDBC` is absent, including on later feature loads, so a caught failure cannot continue on the files. CLI hydrate, extract, and enabled status use the same sentence and do not create a database. `verifySqlitePackaging` checks the POM scope and that the shadow JAR has no `org/sqlite/` entry.

### E. Fast Dolt-first run path
- `dolt run` launches or reuses a warm worker (reuse Workbench worker model) holding a cached prebuilt classpath. Executes from DB. Recompiles Java glue only when fingerprint changes, then restarts worker.
- Timing comparison script/tool included.
- Maven wrapper added to consumer template if useful.
- Full Gradle/Maven remain CI and source-of-truth. Fast path runs the same engine and produces identical results.
- Goal: avoid full Gradle/Maven startup cost per edit-run cycle.
- Implemented: `dolt run` starts or reuses `DoltRunWorker` on loopback. That process is not the Workbench owner JVM. It calls `WorkbenchDirectRun`, so the engine id stays `pickleball-test-engine` and the run sets `pkb_dolt=true`. The worker prints `scenario PASSED|FAILED <name>` and `step PASSED|FAILED <text>` for each pickle step, then `dolt run exit=` with reuse, millis, and the plan. The glue fingerprint is SHA-256 of path, size, and mtime for `.java` under `src/main/java` and `src/test/java` and `.class` under the Maven and Gradle output trees. A change runs one `mvnw -q test-compile` or `gradlew testClasses --no-daemon`, then restarts the worker. The classpath is `pkb_dolt_run_classpath` or `.pickleball/dolt/sandboxes/<name>/worker/classpath.cache` (`main` uses `sandboxes/main/worker/`). DB-edited `.java` is compiled by `DoltGlueCompiler` into `sandboxes/<name>/classes/` and that directory is first on the classpath. `--dry-run` prints the plan and writes nothing. `scripts/time_dolt_run.py --self-check` documents the cold-versus-warm comparison; `--project` runs it, passes `--tags`, `--name`, `--glue`, and `--define KEY=VALUE` to both sides, and requires the same exit code, the same scenario and step lines, and `warm2Reused=true`. Measured 2026-11-11 on Linux x86_64 (Temurin 21.0.13) against a one-scenario fixture: coldMs=3962 coldExit=0, warm1Ms=4479 warm1Exit=0 warm1Reused=false, warm2Ms=1368 warm2Exit=0 warm2Reused=true. `mvnw` was already in `maven-consumer-project`. Gradle `doltRun`, the Workbench Run button, and MCP `dolt` forward to the CLI. `pkb_dolt_log=run` records the worker.

### F. Optional items decided
- File watcher (`dolt watch`) is not implemented. Windows watch flakiness, parallel-run locking, and the existing auto-hydrate plus manual hydrate are why. It can be added later as a CLI forwarder.
- Secrets: keep reference-only, no encryption at rest. Broaden detection with configurable `secret-fields=` list in `dolt.properties` (appends to name-based list). Optional heuristic warning. Document clearly.
- Implemented: `DoltSecrets` appends `secret-fields` (or `pkb_dolt_secret_fields`) to the built-in names. Cleartext on those names is still rejected in entity payloads and in history notes. A value of at least 32 characters with no spaces warns with `warn: high-entropy value on <field>` and is stored. The warning does not include the value. There is no encryption at rest.

**Long-term Dolt-first meaning:** DB is the primary store for interactive editing and fast execution. Files are the durable Git/CI export. Hydrate is bootstrap from clone. Warm `dolt run` is the normal iteration path.

---

**Conclusion:**
Dolt is the Git-backed working copy. Git files stay the source of truth. The database is `.pickleball/dolt/data` and is on unless explicitly turned off. Hydrate, extract, entity references, discovery (`skip` and `hash-only`), Git provenance, and `dolt run` are the current path. The native engine reads Dolt rows. `pkb_engine=cucumber` is the adapter.

The native engine reads Dolt rows without making Cucumber the only way to run a scenario. The default engine is native. `pkb_engine=cucumber` keeps the adapter.
