## Root Cause Analysis

**#1 Exit codes**: `exitProcess` / `keepExitCode` already does `System.exit` then `Runtime.halt` to defeat Maven exec:java rewrite. `consumer_sim.py` already has `exec-java-usage` and `exec-java-split-tags` stages that expect exit 2 and use `mvnw.cmd` on Windows. The consumer retest of `111dea5` still sees exit 1 through the documented `mvnw ... exec:java` on Windows. Possible true causes: the documented launch in the agent guide differs from the harness invocation; the Windows CI job does not exercise the assertion path the consumer uses; Apache `mvn.cmd` mapping is still hit on the consumer's path; or the halt is not reached on that exact PowerShell/wrapper path. All usage-error paths must hit the one policy and be proven by a test that runs the actual documented command on both Linux and the Windows CI job.

**#2 Value sources**: `workspace-show` currently marks a subset of keys via `WorkspaceSeed.computedKeys` (runner-set secrets and some hook keys when absent from property files). Other hook-computed values (a description that includes user, machine, locale, Java vendor, etc.) are unmarked. Users cannot tell which keys need a reseed. Replace the special-case marking with one source model: every value reports its source (`hook`, `properties`, `default`, `cli/override`). Hook-computed values are marked. One model, not a special case for secrets.

**#3 Timing stages**: Current notes are `command`, `index`, `maven-start`, `maven-done`. The gap between `index` and `maven-start` is invisible. Add notes for the stages in that gap (compile, seed fork, etc.) so the gap is visible in `launch-timing.txt`. Overlapping the feature index with compilation is deferred tech debt.

**#11-14**: Report4 phase 6 claimed these were proven by tests (`message`/`stackHead` non-null, idle status, events outcome, quote warning). Confirm the existing tests cover the reported cases; add any missing assertion. No new behavioral work if covered.
