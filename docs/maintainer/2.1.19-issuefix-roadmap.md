## Phase 2 — Warm-JVM fallback (Issue 2)
**Functionality:** Warm JVM sends STARTED after accepting a valid RUN and before WorkbenchDirectRun. Client uses short (~20s) handshake timeout until STARTED; after STARTED waits for EXIT with no socket timeout (or explicit --run-timeout as a failure, never a relaunch). Never call WarmProcess.release after acknowledgement. Never start a second execution of the same selection after acknowledgement. Fallback only if the warm JVM never started/acknowledged. Connection drop after STARTED is a failed warm run, not a fallback. PKB_WORKBENCH_SPEED=sequential still forces fresh JVM. Scan every tryDirect caller (discover, confirm, isolate).
**Docs:** Note the fix and the sequential workaround remaining valid in release notes.
**Tests:** Failing-first regression with a stub that delays EXIT past a shortened timeout (current code returns empty / notes fallback). After fix: stub that sends STARTED then delayed EXIT returns the exit code and does not note fallback. Stub that never sends STARTED may still fall back. Stub that sends STARTED then drops does not fall back. Keep WorkbenchWarmLifecycleTest and WorkbenchSpeedCacheTest green. Targeted: the new tests + WarmLifecycle + SpeedCache.
