## Framing Principles (carry forward from completed work)

- CLI-first: every future feature must be reachable from the CLI. Workbench GUI, MCP, and the control bridge stay thin forwarders of the same path.
- Human-viewable default vs lower-level opt-in per call, with mandatory labels. Extra DOM power must never be confused with a human-replicable path. Same discipline as find-interface.
- Existing Gherkin / step syntax and behavior do not change.
- Engine (dom-composite) remains a decoupled general-purpose engine with no pickleball knowledge. Any needed capabilities are asks for a future working branch + PR into main. Do not start engine implementation in this session.
- Predefined helper methods, not ad-hoc scripts. Agents request named actions (highlight, place-overlay, write-html) rather than arbitrary JavaScript.
- Logging: toggleable, per-entity, date-stamped, size-capped (existing `pkb_composite_log` style).
- Capability-gated with clean fallbacks. No invented geometry or results when the binary lacks the flag.

## Expansion of the Five Ideas

### 1. Live chat panel (AI agents and human users)

Workbench UI panel plus CLI/MCP commands (`chat-send`, `chat-history`, `chat-poll` or similar). Messages tagged by source (agent id, human, system). Persistence under `.pickleball` session or run directory so multiple agents and the human can share context.

Ties naturally to existing control-bridge semantic events and the agent-log / inbox patterns already present. Agents can post observations; humans reply with guidance. Low risk; pure controller surface. Multiple concurrent agents need clear ownership or per-run channels to avoid races.

### 2 & 3. Pop-ups / overlays over browser content + bidirectional input

Predefined helpers that place guidance on elements using the existing Geometry view for positioning (visual-viewport-relative for what a person sees). Examples: "click here", short explanations, temporary callouts.

Two implementation paths to consider:
- **In-page injection** (matches "writing HTML on the fly"): inject a temporary absolute-positioned overlay element (or shadow DOM) via predefined CDP `Runtime.evaluate` / `DOM.setOuterHTML` helper. Capture clicks / form inputs via injected event listeners that forward structured events back through the control channel or chat. Must be reversible (remove on demand or scenario end). Every injected surface carries a label ("agent-injected overlay; a person did not author this UI") both as a data attribute and in the return value.
- **Workbench-native overlays** (alternative framing): render the callout in the Workbench Swing UI (or a transparent overlay window) positioned by mapping Geometry coordinates to screen space. No page mutation. Safer for human-replicable path, but does not satisfy the explicit "writing HTML on the fly into pages" end goal as strongly.

Recommendation: support both, with in-page as the agent-privileged path that requires explicit opt-in and labels. Human-viewable queries continue to see the page as a person would; agent-injected nodes are labeled so they are not confused with original content. Input from the human on an overlay returns as a control event the agent can poll or receive via chat.

### 4. Dynamic CSS changes via predefined helpers

Helpers such as `highlight(handle, style=yellow)`, `setClass(handle, class=pkb-highlight)`, or `style.apply(handle, preset=outline-red)`. Implemented through CDP DOM attribute / style methods or a narrow Runtime helper, not free-form script. Predefined presets only (yellow highlight, red outline, etc.) for the first cut; arbitrary CSS strings later if needed and still labeled.

Reversible, logged, and carry the same agent-injected label. Uses existing ranked handles from find-interface. Low additional surface once the injection helper exists. CDP Overlay domain (`Overlay.highlightNode`) is an attractive non-mutating alternative for pure visual highlighting that does not alter the page DOM at all.

### 5. Predefined browser launch templates

Named templates for Chrome, Edge, and other Chromium browsers: headless and non-headless, with and without logs, selectable on the fly, as-is or with slight modifications. Examples: `chrome-headed-verbose`, `edge-headless-quiet`, `chrome-headed-logs`.

Builds directly on the existing local Chrome/Edge startup path (`pkb_browser`, Selenium Manager, fallback drivers). CLI/Workbench command such as `launch --template=... --arg=--window-size=1920,1080`. Multiple windows/tabs via existing window-handle management plus new launch instances. Templates live in config or as named presets; on-the-fly mods are additive overrides. Pure controller / launch surface; no engine change required.

## Writing HTML on the Fly: Risks, Mitigations, and Human vs Agent Distinction

Agents writing HTML into pages is the highest-power capability and the clearest departure from the human-replicable path.

**Risks:**
- Page pollution: injected content alters layout, query results, and subsequent human-viewable finds. A human later looking at the same page sees agent-created UI that was never part of the original application.
- State leakage and non-determinism: mutations persist across navigations or scenario steps unless explicitly cleaned.
- Security surface: even predefined helpers that accept HTML snippets can introduce XSS-like issues if the snippet is untrusted or if the helper is later loosened to arbitrary script.
- Confusion with human path: without labels, an agent (or a later human) can treat agent-authored DOM as if a person created or would see it the same way.
- Session isolation: multiple agents or concurrent scenarios sharing a browser profile can interfere.

**Mitigations (required for any implementation):**
- Explicit opt-in per call (same pattern as lower-level exposure). Default remains human-viewable / no-mutation.
- Mandatory labels on every injected node and on the action result: machine codes (`agent_injected`, `overlay`, `style_modified`) plus a short sentence. Data attributes on the DOM node itself so later queries can see them.
- Predefined helpers only. No free-form `Runtime.evaluate` of agent-supplied JavaScript. HTML snippets are limited (e.g., allowed tags, no script, or sandboxed in shadow DOM / iframe).
- Reversible by design: every inject has a matching remove; scenario end or explicit cleanup command removes agent surfaces.
- Logging of every inject/remove with the snippet hash or summary.
- Geometry-aware placement so overlays do not permanently reflow the original layout when possible.
- Human-viewable queries can optionally exclude or specially mark agent-injected nodes (capability or flag). Lower-level queries return them with labels.

**What a human user could vs could not do:**
- Humans using the Workbench GUI can open the chat panel, see overlays/highlights that agents placed, and interact with them (click a "click here" callout, fill an input). Those interactions are forwarded back to the agent. Humans cannot (by default) issue the lower-level inject commands themselves unless the GUI exposes them as explicit "agent mode" actions that still apply the labels.
- Agents can act on lower-level (hidden, off-viewport, occluded) targets and inject persistent or temporary HTML/CSS. Those actions always carry labels. The human-viewable path remains the default for "what a person would see or click."
- Full arbitrary HTML writing is agent-privileged with the labeling and cleanup rules above. It is not a human-replicable path.

## Adjacent Opportunities and Holes

- **Expose observe buffers:** New CLI/Workbench/MCP commands that surface the already-buffered `Network.*`, console, and log entries (filter by type, URL, time). Low risk, high value for agents deciding what HTML to write or what to assert. Ties directly to the existing investigation findings; do not re-investigate CDP buffering.
- **Capture-to-scenario:** Convert observed page traffic into regular pickleball service-call component scenarios. Requested earlier; not implemented. Natural complement to agent control loops.
- **Multi-window / multi-tab management:** First-class CLI commands to list, switch, and close windows/tabs, building on existing window handles. Templates make launching additional browsers straightforward.
- **Cleanup and session isolation:** Explicit commands and automatic hooks to remove agent-injected surfaces and to isolate browser profiles per run or per agent.
- Hole: concurrency model when multiple agents share a browser or when a human is actively interacting while an agent injects. Ownership / lock or per-agent overlay namespaces needed.
- Hole: how agent-injected content interacts with Geometry and find-interface ranking. Injected nodes should appear in lower-level results with labels; human mode may hide or flag them.

## Alternative Framings

- Prefer pure CDP Overlay domain for highlights and guidance whenever possible (no page mutation). Reserve in-page HTML injection for cases that truly need user input or persistent mock UI.
- Isolate all agent-written HTML inside a single managed shadow root or iframe so it cannot affect the main document query path.
- Treat chat + launch templates + observe exposure as the first coherent layer; overlays and HTML writing as a later privileged layer that requires explicit Dan agreement on the labeling and sandbox rules.
- Workbench-native (non-page) overlays for human guidance, with in-page injection only for agent-to-page mutation use cases (mocking, testing resilience).

## Proposed (Not Locked) Phased Outline for Future Agreement

This is a proposal only. Nothing is mandatory until Dan agrees on direction. Between any later implementation phases run only tests tied to modified functionality; full regression waits until implementation is done.

1. **Observe exposure + launch templates** (low risk, pure controller/CLI). Surface existing CDP buffers; add named browser templates with overrides. CLI-first.
2. **Chat panel** (controller surface). CLI/MCP commands + Workbench UI panel. Session persistence.
3. **CSS highlight helpers** (narrow injection). Predefined styles via CDP; reversible; labeled. Can use Overlay domain for non-mutating path.
4. **Overlays with input** (in-page or hybrid). Geometry-placed temporary surfaces; event forwarding; mandatory labels and cleanup.
5. **Full HTML write helpers** (highest power). Predefined write/replace with sandboxing, labels, and cleanup. Only after the above are solid and the human/lower-level distinction is proven in practice.
6. **Capture-to-scenario** (orthogonal but complementary). Convert observed traffic into service-call scenarios.

Engine asks (if any) go on a non-primary branch + PR into main. No pickleball knowledge in the engine.

## Risks Summary

Highest risk is agents writing HTML into pages: page pollution, non-determinism, security surface, and erosion of the human-replicable distinction. Mitigations are the same labeling discipline already used for lower-level exposure, plus reversibility, predefined helpers, and optional sandboxing. Lower-risk items (chat, templates, observe exposure, non-mutating highlights) can proceed with less concern.

## Strongest Recommended Direction

Start with the low-risk controller surfaces that directly enable agent awareness and browser lifecycle (observe buffer exposure + launch templates + chat), then add narrow, labeled, reversible CSS/overlay helpers that consume the existing Geometry and ranked-handle path. Full HTML writing is the last layer and must preserve the human vs lower-level distinction with mandatory labels. Do not implement until Dan agrees on the direction and the specific mitigations for in-page mutation.

No implementation in this session. No engine changes. No Gherkin changes. No new repository.
