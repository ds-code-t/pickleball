# Pickleball 2.1.19 Mapping Geometry Roadmap

**Goal (Dan, 2026-11-05, locked after investigation):** Surgical upgrade of the shared mapping so pickleball stops flattening composite hits to a single AABB. One Geometry view on ElementSnapshot exposes global document_css_px, visual-viewport-relative, layout-viewport-relative, nearest-scrollport-relative, and frame-document-relative. Scrollable elements expose scrollport client box AND scrollable content box corners. Expandable elements expose the control's own corners + expanded/collapsed state; when open also the revealed region's corners. Corner interactability on the boxes that are mapped. Closed-shadow page-JS hit-testing is a documented browser limit (CDP geometry is enough). Prefer exposing existing tables; modest optional schema columns only if a verified query cannot be answered from stored data.

**Baseline:** pickleball 2.1.19 at eb1af1a4. dom-composite main 2.10.0 at 9029e0c5. Composite is primary via ElementOperations / DomCompositeAdapter when binary present (`pkb_composite=auto`). ElementSnapshot.Bounds is currently only int x,y,width,height (AABB from query bounds) on the composite path; null on Selenium. Live query JSON consumed by CompositeWebElement contains only that AABB under "bounds". Full quads, 4x4 transforms, document quads, styles.overflow, hit_grid, frame transforms, and viewport live in the locked SCHEMA v1 tables of a .composite capture, not in the live query payload.

**HARD RULES:** never commit, push or merge to master; no force-push; no failing or weakened tests; docs updated with every change; simplicity and ONE shared code path (extend ElementSnapshot / Geometry view, ElementReads, DomCompositeAdapter — not per-call-site patches and not a second geometry system). Existing Gherkin/step syntax and behavior must not change unless a forced consumer-visible contract change is discovered (call it out). dom-composite may change (breaking OK, no other app uses it) but stays a decoupled general-purpose engine with no knowledge of pickleball. Coordinate engine API additions as general-purpose; update prompts/domc-asks.md. Pickleball gates on capabilities and keeps fallbacks when the binary does not list them. Between phases run ONLY targeted tests tied to the changed code. Final full regression (Gradle :test :pickleball-control-protocol:test :pickleball-control-api:test :pickleball-workbench:test --rerun-tasks, consumer_sim, verify_agent_contract.py, Windows CI) runs ONCE at the very end of all phases. After the last implementation push, Build must STOP and report the head commit, and run the final regression only when told to continue. CI runs the Windows job only. CLI-first and toggleable per-entity logging for any new engine capability.

**Architecture:** All changes go through the single shared path (ElementOperations → DomCompositeAdapter / ElementReads / Geometry). Selenium path keeps Bounds null and does not invent fake quads. Parity tests (Selenium vs composite, across launch modes) assert identical contracts where geometry is present. Measured checks for any new query. Consumer-shaped repros that fail before the fix and pass after.

**Every phase is mandatory and must be completed in full. Nothing is optional or deferred.**

## Phase 1: Geometry view on ElementSnapshot + capability-gated richer payload from engine
**Functionality:**
- Introduce an immutable Geometry view (record or nested record) on ElementSnapshot that holds: document_css_px (global, from document quad or bounds), visual-viewport-relative, layout-viewport-relative, nearest-scrollport-relative, frame-document-relative. Each space is a Quad (four corners) or a documented AABB when only that is available.
- Bounds remains the existing AABB (x,y,w,h) for backward compatibility; Geometry is additive.
- In DomCompositeAdapter / ElementReads: when capabilities list a new geometry flag (e.g. geometry or quads), request or consume the richer fields from query/describe. Fallback to current AABB-only when absent.
- Engine (dom-composite, general-purpose, no pickleball knowledge): expose optional richer geometry on query nodes or via a describe/geometry helper (capability-gated). Prefer deriving from existing SCHEMA tables / live box model rather than new required columns. Update prompts/domc-asks.md.
- Closed-shadow: document the page-JS retarget limit; use CDP-visible geometry.

**Docs:** Update this roadmap. Note in AGENTS.md or feature-map that Geometry is the shared richer view; Bounds stays for AABB. Update domc-asks.md with the general-purpose request.

**Tests:**
- Unit tests: Geometry present and consistent with Bounds on composite path; null/absent on Selenium. Capability-missing fallback keeps AABB.
- Parity: Selenium vs composite for the AABB contract (identical where both have it).
- Consumer-shaped repro that previously only saw AABB now reads Geometry spaces when capability present.
- Measured: one query returns the richer payload when listed.

**Logging checklist:** Trace-level geometry request; toggleable via pkb_composite_log. Info when capability used vs fallback.

**Regression risk:** Low. Bounds contract unchanged. Other callers of ElementSnapshot see additive Geometry. Launch modes covered by parity. Existing tests lock AABB.

## Phase 2: Scrollable elements — scrollport client box AND scrollable content box
**Functionality:**
- For elements that are scrollports (overflow auto/scroll/overlay per ARCHITECTURE scroll ownership), Geometry exposes both the scrollport client box corners and the scrollable content box corners (in the spaces from Phase 1).
- Nearest-scrollport-relative is relative to that client box / scroll offsets.
- Do not specially prioritize scrollbar-chrome corners unless they fall out cheaply from existing data.
- Engine: general-purpose way to return client vs content size/quads (optional schema column or derived from styles + box model if not already answerable). Update domc-asks.md.
- Through the same shared path.

**Docs:** Update this roadmap and any geometry notes.

**Tests:**
- Unit / parity: scrollable element yields both boxes on composite when capability present; Selenium has no geometry.
- Consumer repro for a scrollable region: corners of client and content are readable.
- Measured: no extra round trips beyond the geometry query.

**Logging checklist:** Geometry log names scrollport vs content when present.

**Regression risk:** Low-medium. Scroll ownership already defined in engine. Callers of snapshot see additive data. Existing scroll tests lock behavior.

## Phase 3: Expandable elements + corner interactability
**Functionality:**
- Always map the control's own corners and its expanded/collapsed state (from attributes / AX: aria-expanded, details open, etc.).
- When open, also map the revealed region's corners (the expanded content box or the relevant child region). Do not invent a predicted expanded box while collapsed.
- Corner interactability: for the boxes that are mapped, sample corners (or inset points) via hit_grid / hit_at / pointer-events / stacking to report whether the corner (or an inset) is the topmost clickable target of this node. Document closed-shadow and cross-origin limits.
- Engine helpers if needed (general-purpose hit sample or revealed-region query). Through shared path.

**Docs:** Update this roadmap. Note the no-predicted-box rule and the closed-shadow limit.

**Tests:**
- Parity and unit: collapsed control has its corners + state; open control has revealed corners. Interactability flag matches hit sample where available.
- Consumer repro: expandable that is open exposes revealed corners; collapsed does not invent them.
- Capability-missing keeps current behavior.

**Logging checklist:** Geometry log for expanded state and interactability samples.

**Regression risk:** Low. State already readable from attributes. Additive. Existing expandable conditions stay locked.
