# Release notes

## 3.0.0

Dalton is an opt-in hydrated working copy. Git files stay the source of truth. The database is `.pickleball/dalton/dalton.db`, gitignored, and never required for a fresh clone or CI. With Dalton off, feature loading, configuration, and execution are unchanged. A normal `mvn test` or `gradlew test` does not open that database.

- `dalton status` reports a missing database and does not create one.
- `dalton hydrate --dry-run` writes nothing. Gradle `daltonStatus` and the Workbench MCP tool `dalton` only forward to that CLI.
- `dalton hydrate` copies features, configs, calls, components, resource maps, and templates into that database and skips unchanged SHA-256 hashes. `--dry-run` still writes nothing when the database is missing. Gradle `daltonHydrate` only forwards to the CLI. A run hydrates only when `pkb_dalton=true` or `dalton.properties` sets `enabled=true`.
- A hydrated `.feature` file keeps its original bytes and also stores scenarios, steps, tags, docstrings, and data tables. With Dalton on, a consumer run hydrates on the first feature load and executes the database bytes. That is the JUnit feature parser and the CLI feature supplier. A database-only edit changes the scenario and step text that run. The file stays untouched. With Dalton off, loading does not open the database, creates none, and executes the file. `<entity:Type#id.field>` in a step resolves only when Dalton is on. With it off the reference text is unchanged. A secret field stays a reference such as `<password:qaDb>`.
- `dalton entity` stores business entities from `dalton-entities/<Type>/<id>.entity`. The reference `<entity:Type#id.field>` resolves only when Dalton is on. Secret fields must be references, not cleartext. `dalton entity export` writes database edits back and refuses when both sides changed.
- `dalton extract` (alias `hydrate-out`) writes stored file bytes back to disk and does not reformat them. An unedited row stays as the original file. Both sides changed prints `conflict: <path>` and exits 1 unless `--force` is set. Gradle `daltonExtract` only forwards to that CLI.
- `dalton history` stores run summaries beside diagnostic reports. It does not change `reports/diagnostic-runs` or `pkb_reportretention`. `retain` is date-stamped and size-capped. Gradle `daltonHistory`, Workbench, and MCP only forward to the CLI. Logging stays off unless `pkb_dalton_log` names the capability.

**Round 2 (in progress on branch 3.0.0):** Adds a real DB edit path (`dalton feature put` with Gherkin validation, re-projection, and `db_edited` flags), CLI query surface for GUI, discovery include/exclude/size/binary config, loud failure when sqlite-jdbc is missing for consumers, Workbench GUI browse/edit (CLI-only), and a warm `dalton run` fast path. File watcher is out of scope. See `docs/roadmaps/3.0.0-dalton-round2-roadmap.md` and the Round 2 section in `docs/maintainer/3.0.0-dalton-design.md`.

## 2.1.19

- dom-composite 2.4.0 is the element entry point when its binary is on the run. `DomCompositeAdapter` is the only path for find, click, type, hover, scroll, keys, wait, inspect, and desktop query. Existing Gherkin phrases, quote types, and context words (`in`, `from`, `for`, `after`, `before`) are unchanged. Dictionary XPath and CSS pass through. Other phrases become one composite pipeline.
- `pkb_composite=auto` (default) uses that path when the binary is found and otherwise stays on Selenium for the run, with one `error:` / `fix:` line. `pkb_composite=on` always prints that line when the binary is missing. `pkb_composite=off` does not look for the binary. `pkb_composite_bin` is checked before `COMPOSITE_BIN`. Logging is off unless `pkb_composite_log` names `location`, `adapter`, `session`, `element`, `fallback`, `batch`, `state`, `position`, or `all`. `batch` writes one `TRACE batch mode=<composite|selenium-batch|selenium-legacy> selector=<by> nodes=<count> durationMs=<n>` line per describe. There is no per-element line. `state` writes one `TRACE state snapshot miss fallback` line only when a state check has no snapshot. `position` writes one `TRACE position apply` line. Enabled, blank, required, expanded, collapsed, and on/off read that snapshot and do not search again.
- The Java binding is vendored (`dev.domcomposite.Client`). Native binaries are not published here. A classifier jar `dev.domcomposite:composite-native:2.4.0` (`linux-x64`, `linux-aarch64`, `windows-x64`, `macos-aarch64`, `macos-x64`) is extracted when it is present. Otherwise set `COMPOSITE_BIN`, `COMPOSITE_HOME`, or build the sibling `dom-composite` checkout.
- WebDriver remains for browser lifecycle only (navigation, window handles, CDP address, frame index). Submit, double-click, context-click, element drag, and named keys use the real verb when `capabilities.actions` lists `submit`, `dblclick`, `contextclick`, `drag`, or `key`. A binary that lists only click, type, and scroll keeps the old mapping: submit is click, double-click is two clicks, context-click is one click, and drag is click, scroll, click. An element drag with no offset is one `drag` (before: three calls). An offset drag stays click, scroll, click. A press of letters and digits uses composite type; a lone A-Z is lowercased. Chords the `key` verb can represent (`ENTER`, `CONTROL+A`, `SHIFT+TAB`, `ENTER` then `TAB`) use `key`. `A+B` and `CONTROL[A+B]` still focus with a composite click and then WebDriver Actions. When `capabilities.actions` lists `eval`, a composite snapshot is that one `eval` and no WebDriver script (before: one script that searched again). A binary that does not list `eval` keeps the script. An all-contexts scan (`Loading`, any `ALL_CONTEXTS` category) is one `query` with `all_frames` and `pierce=open` when the binary accepts that flag (before: a find, a script, and a frame switch per context). A binary that rejects `--pierce` keeps the Java walk. Foreign frames, closed shadows, depth 5, and the 20-frame cap are unchanged. `pkb_composite_log=adapter` writes `INFO adapter verb <name> real` or `fallback`, `INFO adapter snapshot eval` or `snapshot script`, and `INFO adapter scan all-contexts`. A visible or present wait on a composite hit is one `query` (`--wait-for visible` or `attached`, `--poll-ms 150`, `--stability-ms 0`) when the binary accepts `--poll-ms` (before: a displayed or connected check every 150 ms). A binary that rejects `--poll-ms` keeps that loop. An engine timeout is not waited a second time. `pkb_composite=off` does not query. Nested containment of two or more anchored composite hits is one extra xpath union (before: one ancestor query per hit). A hit with no id or name keeps the per-node walk. A refresh, when `capabilities.actions` lists `eval` and the node is still connected, is that liveness `eval` plus one snapshot `eval` and no `stableSelector` find (before: one find and one snapshot script). `pkb_composite_log=adapter` also writes `INFO adapter wait <rules> poll=150`, `wait fallback`, `nest batch`, `within <node id>`, `within fallback`, `nesting deepest` or `outermost`, `nesting fallback`, `eval nodes=<n>`, and `live <node id>`. A context find is `query --within` when `capabilities.query_flags` lists `within` (before: an id or name XPath, and an empty find when the context had neither). A parenthesized XPath stays inside that node. Nesting is `--nesting` on the same query, after `displayed`, when `query_flags` lists `nesting` (before: one extra anchor query, skipped when any hit had no id or name). Several snapshots are one `eval --node-ids` when `capabilities.eval_nodes` is set. A binary that lists neither flag keeps the old path. A primary binary that has not joined a browser finds on that WebDriver with Selenium, the same hits as `pkb_composite=off`. A process-only session is not a join. `pkb_composite_log=element` writes `INFO element find selenium unattached`. `--within` and `--nesting` are still sent only when `query_flags` lists them. `the 3rd`, `last`, and `every 2` are `--nth` and `--every` on that same query when `query_flags` lists `nth` and `every` and the phrase has no `matching` regex (before: the engine returned every hit and Java kept the position). A regex, a missing flag, or an all-contexts scan keeps `PositionSelection` in Java, because a regex runs after nesting and an all-contexts list can include a foreign-frame placeholder. `pkb_composite_log=adapter` writes `INFO adapter nth <n>`, `nth <n> every <step>`, `count <n>`, or `position java`. A count is one `query --count-only` when `query_flags` lists `count-only`. Desktop click and type fail with `error:` / `fix:` until composite reports those verbs in `capabilities.desktop`. Query, OCR, and template matching stay on the adapter. Native classifiers are `dev.domcomposite:composite-native:2.4.0` (`linux-x64`, `linux-aarch64`, `windows-x64`, `macos-aarch64`, `macos-x64`; binary `composite` or `composite.exe`).
- Live Workbench `inspect-page` and `find-element` count elements through `PageElementQuery` and `ElementOperations`. `workbench_element_inspect` uses `ElementControl` and the same lookup. A `query` string is the engine selector on that same call. Omitted exposure on that query is `human`. `lower` is per query and labels every node. `left-of`, `right-of`, `above`, `near`, and `below` are visual distance when the binary lists geometry. Otherwise no box is invented. `--explain` returns rank and score. `--promote-visual` binds an image match to a node, or leaves a labeled visual-only hit. `--limit` returns handles for one later act. Offline `--html` stays `source=offline-html` and does not run the engine query. Category+text does not send exposure. Gherkin `after` and `before` stay document order.
- The runtime binary decision takes the project directory, environment, class loader, and Maven home together. A test can pin those inputs. Production still discovers the binary from the working directory, the process environment, and the user home.
- A normal `mvn test` or `gradlew test` with no composite binary is unchanged.

## 2.1.18

- `copy-live` prefers one relative directory symlink, `live/classes` → `../base/classes`. Windows tries that symlink, then a junction, then the per-file hardlink pool, then a copy. The stage line is still `links=<n> copies=<n>`. A directory link reports every file as a link. Saving a file under that link copies the tree into a real directory first, so `base/classes` does not change. `base/classes` is still not a classpath entry. An unchanged second start still prints `classpath-cache hashed=false`. The preferred test-output root (including `live/classes`) finds its runner and step packages from class-file headers and loads only that runner. Jars still use the class loader. `PKB_WORKBENCH_LIVE_READY` is unset by the controller; when unset the worker does not wait. Linux JDK 21, 2 processors, 5259 files / 199252992 bytes: materialize wall 576 ms, `copy-live` 32 ms, `links=5259 copies=0`. Windows isolate was not rerun. That directory link replaces the projected ~6.6 s parallel `copy-live`, so wall is near 69 s until a Windows isolate records the post-digest stages. `validate --all` is unchanged and needs a controlled rerun. A normal `mvn test` uses the same header scan on `target/test-classes` and is otherwise unchanged.

- A fresh-cache materialize prints `links=<n> copies=<n>` on `copy-live`. Linking uses the same thread pool as the copy path. `Files.createLink` is still preferred. A provider that refuses links copies the rest of that tree. Any other link error copies that file and later files still try a link. `base/classes` stays the owned copy. `live/classes` stays the worker classpath root. Do not edit a linked file; `generated-classes` is the write directory. An unchanged second start still prints `classpath-cache hashed=false` and does not materialize. The controller writes `progress stage=worker-spawn` on the worker stderr log immediately after the consumer process starts. The worker writes `progress stage=jvm-main` as the first line of main, then `progress stage=classpath-scan` before classpath and glue initialization. The first successful CLI `GET /health` writes `progress stage=worker-ready` on the session log. `paused` still also records `worker-ready` on the worker log. Linux JDK 21, 2 processors, 5259 files / 199252992 bytes: materialize wall 521 ms, `copy-live` 85 ms, `links=5259 copies=0`. A 4000-file link bench was 91 ms serial and 51 ms on the pool (1.78x). Windows isolate was not rerun. Applying that ratio to the Windows serial `copy-live` of 11.8 s projects `copy-live` near 6.6 s, worker-ready near 57.8 s (was 63.0 s), and wall near 75.2 s (was 80.4 s). The post-digest gap is now those stages and was not otherwise shortened. `validate --all` is unchanged and needs a controlled rerun. A normal `mvn test` is unchanged.

- `validate` rejects a flag it does not use, including `--quiet`, with `error:` and `fix:`. `discover` and `confirm` still accept `--quiet`. A second `isolate` or `session-start` of the same `--run-id` moves the previous `session.log` and `startup-progress.json` to `.pickleball/runs/<id>/session/attempts/<n>/` before truncating them. `n` is the same next-attempt count discover uses. An `isolate` or `session-start` whose `--run-id` has no workspace prints `error: no workspace for run id <id>` and `fix: Run workspace-seed or discover for that run id.` and does not start the controller. A child that still exits early prints the last error line from the new session log the same way. Materialize prints `copy-base`, `copy-live`, and `digest` (`files=`, `bytes=`, `ms=`) between `materialize` and `hash`. `copy-live` hardlinks `base/classes` into `live/classes` when the filesystem allows, and copies otherwise. `base/classes` stays the owned snapshot. Do not edit a linked file; `generated-classes` is the write directory. The class fingerprint is relative path, size, and mtime and does not read class bytes. Jars are unchanged. An unchanged second start still prints `classpath-cache hashed=false` and does not materialize. A Linux unit materialize of 5259 class files (199252992 bytes) took 1333 ms (copy-base 994 ms, copy-live 166 ms, digest 81 ms). Windows consumer timing was not remeasured. A normal `mvn test` is unchanged.
- `validate` reads step definitions from compiled glue, the same classes the runner registers, including the resolved test classpath so a superclass or parameter type that lives only in a dependency jar still loads. Repeated step annotations and non-English `io.cucumber.java.<lang>` annotations register. When a source file is newer than its class file, validate prints `WARN: compiled glue is older than its source: <path>` and still matches the step. A commented-out `// @And` is not a definition. An ambiguous line names each conflicting class, method, and pattern. A literal prefix stops before `?`, `*`, or a `{n,m}` quantifier and drops that quantified character. An unescaped `|` or a Cucumber `/` alternation keeps no prefix past the alternated word. Optional text `(s)` and a leading `(?i)` contribute no prefix, so `validate --all` on a large suite stays inside a short budget and still prints `validate progress`. `--quiet` on discover and confirm drops `WARN:` and `WARNING:` seed lines and still prints `error:` and `fix:`. A normal `mvn test` is unchanged.
- A new `isolate` / `session-start` writes a fresh `startup-progress.json` and keeps every `progress stage=` line from this start, including `index-end` when later stages are already in the same read. A stage left in an older log, the newest log, or the previous progress file is not a stage of this start. When the classes and classpath are unchanged, the start prints `progress stage=classpath-cache hashed=false` and does not hash jars. A start that materializes keys each jar by path, size, mtime, and file identity (inode and ctime when the filesystem reports them). A jar first seen while its mtime is still within 2 seconds of now is recorded with a content hash, and that token does not change type later. A later start still inside that window, or an inode or ctime change under the same size and mtime, is hashed, and `hashed` is that count. Once that mtime is outside the window the same token is kept and its recorded time is refreshed. On Windows, fileKey() and ctime are not available, so the key is effectively path, size, and mtime plus the 2 s rule. It prints `progress stage=sync`, `progress stage=materialize`, `progress stage=copy-base files=<n> bytes=<n> ms=<n>`, `progress stage=copy-live files=<n> bytes=<n> ms=<n>`, `progress stage=digest files=<n> bytes=<n> ms=<n>`, `progress stage=hash jars=<n> reused=<n> hashed=<n> bytes=<n>`, and `progress stage=maven skipped=unchanged` when the pom hash still matches. A normal `mvn test` is unchanged.
- `java -jar` runs a launcher check (`sync`, and the missing `v/<current>/` warning) without Jackson on that classpath. Jackson loads on the first JSON read or write, not when `AgentCoordination` initializes. `stackHead` stays the first packaged frame outside Pickleball and Cucumber. A frame with no package, such as `Hidden.frame(Hidden.java:4)`, is not that head. Push and pull-request CI runs the Windows job only. Linux is verified locally on the maintainer box with JDK 21. macOS testing is tech debt. A normal `mvn test` is unchanged.
- The first `isolate` / `session-start` reuses the discover classpath cache (`resolved-classpath.v1`, a `target/` or `build/` output plus the lock-file hash) and does not compile again. `launch-timing.txt` records `stage=index start`, `stage=index end`, and `stage=overlap` (`index+compile`) when those stages start, before compile finishes. The controller prints `progress stage=index`, `progress stage=index-end`, and `progress stage=compile`, so the health wait is not one opaque stage. The cold-start default `pkb_workbench_worker_start_timeout` is 300 seconds. The worker's inner deadline stays 10 seconds under that (290 seconds). A normal `mvn test` is unchanged.
- Stock `mvnw.cmd` returns 1. `java -cp`, `java -jar`, and Linux `mvnw` exit 2. A Windows script that needs the exact code matches `error:` or uses `java -cp`. A missing `v/<current>/` prints `run export-guidance`. `gc-versions` records the removed version in `history.log`. The current version is never swept, and a missing `.last-used` counts as now. A normal `mvn test` is unchanged.
- `query` sets `scanCapped` from the lines that match `--run-id`, not from the whole `.pickleball/agent-log`. A scoped query reads worker logs only under `.pickleball/runs/<id>`. `stackHead` is the first packaged frame outside Pickleball and Cucumber; a frame with no package is not that head, and when every frame is framework code it stays `class: message`. `cause` is the top `Caused by:` line, not the stack dump. `query --verbose` adds `causeChain`. `failedScenarios` adds `path:line` and `example <line>` when the scenario identity has them. A normal `mvn test` is unchanged.
- `validate` uses the runner's Cucumber expressions, including Pickleball core steps, and expands Scenario Outline placeholders before matching. A long suite prints `validate progress` and stops at 2000 steps with `capped=true` and `fix: narrow validate with --tags or --name`. A normal `mvn test` is unchanged.
- `execute-step --text` with no double quotes warns and names `--text-b64` and `--text-file`, including `*, save E.`. A phrase that is missing a required value throws `syntax error: missing value` (or `missing element`) instead of a null failure. A normal `mvn test` is unchanged.
- The warm JVM exits when its state file disappears, including during a run. `stop` kills that pid from `warm-jvm.pid` even if `warm-jvm.v1` is already gone. `status` is `idle` until a `BEFORE_STEP` is open or a session command is in flight. A bare `RUNNING` mark is not a step. `/health` `running` is true only while a step is open or a session command is in flight.
