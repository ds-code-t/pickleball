# Release notes

## 3.0.0

Dalton is an opt-in hydrated working copy. Git files stay the source of truth. The database is `.pickleball/dalton/dalton.db`, gitignored, and never required for a fresh clone or CI. With Dalton off, feature loading, configuration, and execution are unchanged. A normal `mvn test` or `gradlew test` does not open that database.

- `dalton status` reports a missing database and does not create one.
- `dalton hydrate --dry-run` writes nothing. Gradle `daltonStatus` and the Workbench MCP tool `dalton` only forward to that CLI.
- `dalton hydrate` copies features, configs, calls, components, resource maps, and templates into that database and skips unchanged SHA-256 hashes. `--dry-run` still writes nothing when the database is missing. Gradle `daltonHydrate` only forwards to the CLI. A run hydrates only when `pkb_dalton=true` or `dalton.properties` sets `enabled=true`.
- A hydrated `.feature` file keeps its original bytes and also stores scenarios, steps, tags, docstrings, and data tables. With Dalton on, a consumer run hydrates on the first feature load and executes the database bytes. That is the JUnit feature parser and the CLI feature supplier. A database-only edit changes the scenario and step text that run. The file stays untouched. With Dalton off, loading does not open the database, creates none, and executes the file. `<entity:Type#id.field>` in a step resolves only when Dalton is on. With it off the reference text is unchanged. A secret field stays a reference such as `<password:qaDb>`.
- `dalton entity` stores business entities from `dalton-entities/<Type>/<id>.entity`. The reference `<entity:Type#id.field>` resolves only when Dalton is on. Secret fields must be references, not cleartext. `dalton entity export` writes database edits back and refuses when both sides changed.
- `dalton extract` (alias `hydrate-out`) writes stored file bytes back to disk and does not reformat them. An unedited row stays as the original file. Both sides changed prints `conflict: <path>` and exits 1 unless `--force` is set. Gradle `daltonExtract` only forwards to that CLI.
- `dalton history` stores run summaries beside diagnostic reports. It does not change `reports/diagnostic-runs` or `pkb_reportretention`. `retain` is date-stamped and size-capped. Gradle `daltonHistory`, Workbench, and MCP only forward to the CLI. Logging stays off unless `pkb_dalton_log` names the capability.

- `dalton files`, `dalton features`, `dalton scenarios list`, `dalton steps list`, and `dalton conflicts` read the database and do not create one. `--json` is one object. Text mode uses labels. `conflicts` exits 1 for an untracked edit or a row changed on both sides. Gradle `daltonQuery` only forwards to the CLI.

- Discovery reads `include`, `exclude`, `max-file-size` (default 1 MiB), and `binary-policy=skip` from `dalton.properties` or the `pkb_dalton_include`, `pkb_dalton_exclude`, `pkb_dalton_max_file_size`, and `pkb_dalton_binary_policy` system properties. An empty include keeps the fixed directories. Exclude adds to the defaults, including `.git`, `target`, `build`, `.pickleball`, and common binaries. A null byte or a high control-byte ratio is binary. UTF-8 is not. `dalton status` prints the skipped count and sample reasons and does not create a database. `--path` obeys the limits unless `--force` is also set. `pkb_dalton_log=discover` records each reason.
- When Dalton is enabled and `org.xerial:sqlite-jdbc` is not on the classpath, auto-hydrate and the CLI commands that open the database fail with `Dalton is enabled but org.xerial:sqlite-jdbc is not on the classpath. Add it as testRuntimeOnly / test scope or use the Gradle dalton* tasks.` They do not fall back to the files. The driver stays off the published POM and the consumer JAR. Gradle `dalton*` tasks supply it.
- The Workbench Dalton tab browses files, features, scenarios, steps, entities, and run history, and it edits feature text and entities. It only shells out through `DaltonCliForwarder`. It does not open the database.
- `dalton run` executes from the database on a warm JVM. It sets `pkb_dalton=true` and uses the same `pickleball-test-engine` as a normal run. It prints one line per scenario (`scenario PASSED|FAILED <name>`) and one line per pickle step (`step PASSED|FAILED <text>`). A Java glue change compiles once, then restarts the worker. `--dry-run` prints the plan and writes nothing. Gradle `daltonRun`, the Workbench Run button, and MCP `dalton` only forward to the CLI. Full Gradle or Maven stays the CI build.
- `secret-fields=` in `dalton.properties` adds names to the secret list. `pkb_dalton_secret_fields` wins over the file. A matching field must be a `<...>` reference or `~MASK;`. A long spaceless value on any other field warns and is stored. The database is not encrypted. The warning does not print the value.

- `dalton feature put <path>` (`--text` or `--file`) writes feature bytes into the database, sets `db_edited`, leaves `last_synced_hash`, and replaces stored scenarios, steps, tags, docstrings, and data tables in that transaction. Bad Gherkin is rejected and the previous rows stay. `dalton scenario put` and `dalton step put` are rejected. Hydrate prints `untracked DB edit on <path>` when the content hash moved and `db_edited` is still 0, and it does not overwrite that row unless `--force` is set. A flagged edit is kept when the file still matches the last sync. `dalton entity put` uses that same write. Gradle `daltonFeature`, Workbench, and MCP only forward to the CLI.

**Round 2:** Adds a real DB edit path (`dalton feature put` with Gherkin validation, re-projection, and `db_edited` flags), CLI query surface for GUI, discovery include/exclude/size/binary config, loud failure when sqlite-jdbc is missing for consumers, Workbench GUI browse/edit (CLI-only), a warm `dalton run` fast path, and `secret-fields=` for extra secret names. The database is not encrypted. File watcher is out of scope.

**Round 3 (in progress):** Pickleball gets its own execution engine so scenarios and steps can come from files, the Dalton database, in-memory text, or steps written at runtime. Cucumber becomes an optional adapter with identical results. Gherkin syntax and step annotations do not change.

- Phase 1 adds a Pickleball-owned model (`EngineFeature`, `EngineScenario`, `EngineStep`, `Table`, `DocText`, `Status`) and converters to Cucumber messages, pickles, data tables, and doc strings. Nothing in a Cucumber run changes.
- Phase 2 matches steps with a Pickleball registry that reads the existing step annotations and uses the same Cucumber expression and regex rules. Step text and annotations do not change. Matching does not run the step.
- Phase 3 adds an explicit execution context. Existing Cucumber runs keep the same scenario state. The context is used only when no Cucumber scenario is on the thread.
- Phase 4 uses Pickleball tables and doc text inside mappings and data operations. Cucumber data tables and doc strings stay at the converter edge. Existing steps that take a Cucumber data table still do.
- Phase 5 parses scenarios from a file, a Dalton row, in-memory text, or a list of steps. The Cucumber runner is not required to read them.
- Phase 6 finds scenarios by tags, name, feature name, example rows, and step text from files, memory, or Dalton. The Cucumber scan rules stay the same.
- Phase 7 runs a scenario or one step from text, a step list, a file, or a Dalton database row. Cucumber is not required. `engine run` and `engine step` are the CLI. Gradle `engineRun`, Workbench, MCP `engine`, and `dalton run --engine` only forward to that CLI. A normal Cucumber run is unchanged.
- Phase 8 runs `DynamicControl.executeStep` with no Cucumber scenario on the thread. A live or paused scenario still uses the existing detached step. The control bridge does this only when no scenario lane is active.
- Phase 9 keeps existing Cucumber and JUnit suites on the adapter. `pkb_engine=native` (else `PKB_ENGINE`, else `engine.properties` `mode=native`) selects the native engine. The default remains `cucumber`.
- Phase 10 runs steps written during a step. They are not feature files. The step result records `source=runtime`.
- Phase 11 compares a feature on the Cucumber adapter and the native engine. Plain glue matches. One `ASSERT` step matches. Browser and dynamic-step suites are not switched over. The default engine remains `cucumber`.

## 2.1.17

### Breaking changes

These three statuses apply only to Pickleball Workbench (`discover`, `confirm`, and the live session commands). A normal `mvn test` / `gradlew test`, Cucumber’s own exit code, and `DiagnosticReporter` are unchanged. Diagnostic mode still reports `NO_TESTS`. Nested `SCENARIO` / `COMPONENT` / `CALL` / `RUN` still fail when `CucumberScanUtil.listPickles` finds nothing.

- **EMPTY.** A Workbench `discover` or `confirm` that selects zero scenarios prints `status=EMPTY`, the effective tags, name, example, and browser, and exits non-zero. It does not print `status=PASSED`. The run record status is `EMPTY`. When the caller did not pass `--learned`, the record says `No scenarios matched …`.
- **FAILED when Maven exits 0.** `maven.test.failure.ignore` (and the Gradle equivalent) can make the wrapper exit 0 after a failed scenario. Discover and confirm read the current run's `run-index.json` (`outcome`, `counts.failed`, and `counts.errors`). A Surefire or index outcome of `ERROR` counts as a failure even when `counts.failed` is 0. The index is accepted at `.pickleball/runs/<run-id>/diagnostic/<run-id>/run-index.json`, at `diagnostic/run-index.json`, or under `reports/diagnostic-runs/<run-id>`, including a Windows path. That result sets the Workbench status, `record.json` (`failureCount`, `failedScenario`, `failureSummary`), the `summary status=` line, and the launcher exit. A worker that already wrote `PASSED` is upgraded when the index or a Surefire error says the run failed. `TIMEOUT` and `EMPTY` are not overwritten. A missing index falls back to a Surefire or Gradle XML report written during this run (failures and errors), then to the wrapper exit code. A normal `mvn test` exit code is unchanged.
- **Current run only.** A discover or confirm summary counts scenarios and steps only for that run. The count walks `.pickleball/runs/<run-id>/diagnostic` when that folder has a scenario directory (`events.jsonl`, or `scenarios/<id>/summary.json` after retention pruning removed the events), otherwise only `reports/diagnostic-runs/<run-id>`. It does not walk other runs. `steps=` adds every scenario in that run, for retention `all`, `failed`, and `none`. A scenario with a step list uses that size. A pruned scenario with an empty list uses the core summary `steps.executed`, then `steps.total`, then `passed` + `failed` + `skipped` + `other`. `run-index.json` `steps.executed` is used only when that sum is 0, so a smaller index does not replace it. A full scan that did not write those scenario directories uses `run-index.json` `counts.total` and `steps.executed`, then a console line such as `1 Scenarios` / `2 Steps`. The retained `pkb_run_profile` and `last-discover.json` come from that run's private `run-index.json` when the index has a `runProfile`. A project-wide `run-catalog.json` row is used only when this run did not write one. A later discover does not reprint an earlier run's tags or scenario count.
- **TIMEOUT.** `--run-timeout` on `discover` or `confirm` records `TIMEOUT` and exit non-zero when that budget is exceeded. Those commands reject `--step-timeout` (`use --run-timeout; per-step limits apply to execute-step`). `--step-timeout` on `execute-step` is measured from the call. `--run-timeout` on `execute-step` is measured from the run's `startedAt`. One transient HTTP failure does not record `TIMEOUT`. When the step budget expires, the step is still running; use `stop --force`. These budgets do not use `pkb_stepMaxTime`. When the budget interrupts a `discover` or `confirm` wrapper, Workbench kills that process and its descendants and waits up to 10 seconds for them to exit. A normal `mvn test` does not.
- **STOPPED.** `stop --force` kills the Workbench worker and its browser process tree and records `STOPPED`. A cooperative `stop` without `--force` is unchanged and still waits.

### Date, time, and expressions

Previously passing expressions, steps, and comparisons stay the same text and the same result.

- An invalid `<{...}>` in `TRACE:`, `DEBUG:`, `INFO:`, `WARN:`, `ERROR:`, or `FAIL:` log text stays the literal text. A valid `<{...}>` and a valid `<name>` still resolve. The same invalid expression outside a log step still fails the step. `ERROR:` and `FAIL:` still hard-fail because of the log token, not because the expression was invalid.
- Nested `<...>` references, including a saved value that itself contains `>`, resolve past two levels and do not leave a stray `>`. One- and two-level nesting stay byte-identical. Plain text such as `->`, `a > b`, and `>=` stays literal. The same `>` inside a nested reference, inside `<{...}>`, and inside `~[~...~]~` still resolves, and a whole-object reference stays a non-string.
- `equal to … within a margin of N minutes`, `within a margin of N minutes`, and `within N minutes` compare date-times only when the margin is a duration and both sides parse as date-times. Other strings stay a string compare, and the margin is ignored. Equal text that already compared as date-times still does. `within N second|minute|hour|day|week|month|year(s)` is rewritten to `margin-of N unit`, and `within a margin of` / `within the margin of` is rewritten to `margin-of`, only when that phrase, outside quotes and between commas or semicolons, already has a comparison word (`equal`, `equals`, `greater`, `less`, `before`, `after`, `at least`, or `at most`) and the within follows that word. A wait or click `within N`, a wait or click `within a margin of`, and a quoted `"within 5 minutes"`, stay unchanged. `margin of` is still normalised to `margin-of`.
- A calendar `DefaultOutputPattern` is also accepted as an input pattern, after the existing `DateTimeFormats`, so the calendar can parse its own rendered output. Patterns that already parsed still parse the same way.
- Pipe modifiers `next business day` and `business day on or after` roll to the calendar’s existing business dates. `next open`, `is business day`, and `+ N business days` are unchanged. An unknown modifier still throws `Unknown date/time pipe modifier`.
- Optional calendar setting `UnzonedInputZone: calendar` reads an unzoned input in the calendar zone. The default, and the values `UTC`, `GMT`, and `Z`, stay UTC. A zoned input is unchanged.

An interrupt still throws `IllegalStateException` and does not move the gate. `isBlank(Object)` is true for null and blank text, including a masked blank, and false for a number or any other object. A Cucumber `@Before` or `@After` can call the run-value methods, `throttle`, and `isBlank`. Scenario, step, and root-scenario reads, and `softFail`, still need a running step. `softFail` still fails the scenario at the end. The JUnit failure's cause message is that text, not null.
- A JDBC `SQLException` still does not fail the step. The message is `RESPONSE.error`, with empty `rows` and zero counts. A blank `sql` still fails before a connection is opened. `NULL` stays null, booleans stay booleans, and numbers, including decimals, stay numbers. Dates, timestamps, and strings come back as text. A `BLOB` comes back as `String.valueOf` of the byte array. A `CLOB` comes back as `String.valueOf` of the driver object. [Experimental features](experimental-features.md) is now in the packaged guidance.
- `saveScenarioObject(String name, Object value)` and `getScenarioObject(String name)` keep a Java object for the current Cucumber scenario, including a `@Before` or `@After` hook. The step sees the same instance the hook stored. The next scenario on that thread does not. This is not the mapping store and it is not Gherkin. A nested `RUN SCENARIO` on the same thread shares that store.

- `does not contain` is a comparison word, the same kind of partial match as `contains`.

## 2.1.16

### Breaking change

Element text matching is a full match. `matching` used to succeed when the pattern was found anywhere in the element text (`Pattern.find`). It now uses `Matcher.matches`, the same full-match rule phrase `matches` already used, and it honors quote types. A single quote on either side is case-insensitive. A backtick on either side is raw text. There is no regex warning.

On a page with buttons Save, Save All, and Autosave:

- `click the Button matching "Save"` clicks only Save
- `click the Button matching "Save.*"` clicks Save or Save All
- `click the Button matching 'save all'` clicks Save All

`containing` is still a literal partial match. For a partial regular expression, wrap the pattern in `.*`, for example `".*Sa.e.*"`. For exact text that contains `(` `)` `.` or `$`, use `equals` or escape the pattern. Quote types change case and whitespace only. There is no new syntax.

### New features

- Java value API on `tools.dscode.Values`: `getValue` / `saveValue` and the run, scenario, root-scenario, step, default, override, and singleton pairs, plus Jackson `Class<T>` overloads. See [Java values](java-values.md).
- `softFail(String message)` records a soft failure. The step continues, the scenario fails at the end, and `RUN IF SCENARIO SOFT FAILED` runs.
- `throttle(String key, int seconds)` waits until `seconds` have passed since the last call with that key in the JVM. There is no Gherkin syntax.
- `~XML-ESCAPE;` escapes `& < > " '`. It works everywhere conversion directives work, and it is rejected on a `MAP "key" TEXT/OBJECT VALUE` destination key.
- Custom reference prefixes. `registerPrefix` adds `<password:testAccount>`. `secret(value)` prints `******`. `~MASK;` stores a masked value that stays masked in logs, reports, the terminal, and Workbench. `<pw~UNMASK;>` returns the plain value.
- Experimental JDBC service calls. A `REQUEST.endpoint` that starts with `jdbc:` runs a JDBC call. HTTP calls are unchanged. Drivers for PostgreSQL, Microsoft SQL Server, Oracle, MariaDB, and H2 are published with Pickleball. See [Experimental features](experimental-features.md).

### Other

- XML readers reject `DOCTYPE` and `ENTITY` declarations. Normal XML is unchanged. `~XML;` uses Jackson's `XmlMapper` conversion, documented with captured output in [Mapping and templating](mapping-and-templating.md).
- A `file:/...` or unprefixed `/...` path that is not on the classpath fails with a hint to use `wd-file:/...` for a filesystem path.
- Literal key escapes and registered-object cleanup are documented. The existing `cleanup` property runs at scenario end after a pass, a soft failure, or a hard-failed step.
- A hard-failed scenario and a deferred `softFail` both fail the Cucumber scenario after cleanup. The workbook status and the JUnit result stay failed together. `CurrentScenarioState.absorbRecordedScenarioFailure` and `discardDeferredSoftFailure` are not a consumer API.
- A static import of `Values` includes the documented methods and `Values.Context`. Framework helpers are not part of that import.
- Sample `pkb_callpath` and `pkb_componentpath` values use the resources-folder names `calls` and `component`. When those properties are unset, the defaults remain `src/test/resources/calls` and `src/test/resources/component`.
