## Studio collaboration contract after Phase 4

The desktop UI and MCP server now share one Spring context and therefore one set of managed build/process/runtime services. `StudioCollaborationService` provides a bounded Studio-session activity journal, explicit visible agent sessions/notes, and desktop editor-presence metadata without storing unsaved contents or private model reasoning.

Existing-file collaborative edits use `WorkspaceConcurrencyService`: `workspace_read_versioned` returns a SHA-256 token, and `workspace_write_file_checked` refuses the write when a human editor has unsaved changes or the file no longer matches the expected token. Desktop saves use the same token and present overwrite/reload/cancel when the disk changed. The original `workspace_write_file` remains compatible for intentional create/replace operations.

Phase 4 adds ten MCP tools, bringing the surface from 42 to 52. `process_wait` and `runtime_wait_paused` are bounded deterministic conveniences over the existing `ManagedProcessService` and `RuntimeBridgeService`, not new execution engines. The focused consumer compatibility tag is `@phase4`.

## Runtime-control contract after Phase 3H

The private Studio-to-consumer bridge remains protocol version `1` and loopback/authenticated. Existing Phase 3A-3G capabilities remain compatible. Phase 3H adds the additive capabilities `element_inspect`, `service_call`, and `breakpoints` and six Studio MCP tools.

Element inspection is defined by Pickleball vocabulary, not Studio selectors: `ElementControl` resolves the active consumer `ExecutionDictionary`, including registered project categories, then inspects matches through the already-owned scenario WebDriver. Service-call control invokes the existing `ServiceCallSteps.inlineCall(...)` / `CALL:` machinery on the selected scenario thread inside a scoped outer-scenario state isolation; it does not create another HTTP client DSL. Semantic breakpoints match stable `ControlHook` events, use the same scenario lane/pause loop as explicit runtime pause, require at least one filter, and always use finite leases.

The focused consumer tag for this cross-cutting runtime-control surface is `@phase3h`. Because `ControlBridgeCoordinator` owns the scenario-thread command queue used by prior Phase 3 capabilities, the same scenario also revalidates events, mappings/snapshots, page/screenshot evidence, detached retry behavior, scenario targeting, and pause/resume.

## Reusable RUN authoring and result contract

The canonical reusable-invocation form is a bare `RUN` with one DataTable row per invocation. Rows may mix `SCENARIO`, `SCENARIOS`, `COMPONENT SCENARIO`, `COMPONENT SCENARIOS`, `SERVICE CALL`, and `SERVICE CALLS`. Multiplicity is part of each resolved `RunType`, so singular/plural validation is per row. A nonblank table `RunType` overrides an inline type for that row.

Inline `RUN ...` type, quoted `RunKey`, and inline selector text are shorthand for values common to all rows or for invocations that need no DataTable. Repository examples and AI-authored scenarios should prefer the table-driven form when composing related invocations and lift common values into the step text only when doing so reduces repetition.

Keyed deferred `RUN` results are finalized after the selected `ScenarioStep` subtree completes. `RETURN` is saved when present; otherwise the completed default scenario root is saved. Storage uses ordinary RunMap/NodeMap collection semantics rather than pre-execution `putReference()` registration. `StepBase.finalizerSteps`, `StepExtension.createFinalizerStep(...)`, and `CurrentScenarioState` own the generic after-subtree execution mechanism.

## Profile and controlled-run contract

Normal project configuration resolves before profile selection. Public normal source precedence remains JVM system properties, `globalTestProperties()`, `pickleball_local.properties`, `pickleball.properties`, then `globalTestDefaults()`. Named profiles compose left-to-right; later profiles win. `pkb_runvars` is the controlled-run input and `pkb_run_profile` is deterministic derived output only. Named/controlled runs inherit only missing project execution-context RunVars documented in `docs/ai-run-configuration.md`; explicit blank values suppress inheritance. Diagnostic lineage remains metadata separate from execution RunVars.
